# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Loom is a terminal UI (TUI) for managing multiple AI coding agents (Claude Code, Aider, Codex, Amp) in parallel. Each agent runs in an isolated git worktree with its own tmux session. Built with Go using the Charmbracelet Bubble Tea framework.

Loom was forked from [smtg-ai/claude-squad](https://github.com/smtg-ai/claude-squad) at v1.0.17 (April 2026) and has diverged substantially since — see [NOTICE.md](NOTICE.md).

## Build & Development Commands

```bash
# Build
CGO_ENABLED=0 go build -o loom

# Build & run via Nix (no dev shell needed)
nix run .

# Run tests
go test -v ./...

# Run a single package's tests
go test -v ./config
go test -v ./session/git

# Race detector — the default CGO_ENABLED=0 build disables it, so enable CGO
# (needs a C compiler; use CC=clang if gcc is absent). CI runs this as a job.
CGO_ENABLED=1 go test -race ./...

# Format code (CI enforces this). Never plain `gofmt -w .`: it rewrites vendor/
gofmt -w $(git ls-files '*.go' | grep -v '^vendor/')

# Lint (CI uses golangci-lint v1.60.1)
golangci-lint run --timeout=3m --fast

# Cleanup scripts (refuse to run inside a loom-managed tmux session)
./clean.sh        # Kill tmux server, remove worktrees and ~/.loom/
./clean_hard.sh   # Same as clean.sh + git worktree prune

# Dev sandbox — run a dev build safely from inside loom (.claude/skills/loom-dev)
go run ./tools/loomdev up                 # create + build (named after the branch leaf)
go run ./tools/loomdev run                # interactive, in this terminal (the sandbox's daemon keeps running after)
go run ./tools/loomdev start              # headless, then: wait --text toy / keys … / shot
go run ./tools/loomdev stop               # quit the headless TUI and stop the sandbox's daemon (--keep-daemon keeps it)
go run ./tools/loomdev down               # stop the sandbox's daemon, delete the sandbox and its tmux server
go run ./tools/loomdev down --force       # same, SIGKILLing a lock holder that won't stop if it runs a build from the sandbox's bin dir
go test -tags e2e ./e2e/...               # end-to-end smoke suite, the daemon's lifecycle included (needs tmux)

# Install (adds ~/.local/bin to PATH)
./install.sh
```

CGO is disabled for builds (`CGO_ENABLED=0`). Go version is 1.25.8 (the `go` directive in `go.mod`; there is no separate `toolchain` line).

A Nix flake (`flake.nix`) provides a dev shell with Go, golangci-lint, tmux, git, and gh.

## CLI Usage

```bash
# Run with default settings (a client of the loom daemon, which it starts when none runs)
loom

# Specify the agent program this TUI's new instances default to
loom --program "aider --model ollama_chat/gemma3:1b"

# The daemon (one per global dir; it owns every session and outlives every TUI)
loom serve          # Run it in the foreground (loom spawns one detached when none runs); logs to <globalDir>/logs/serve.log
loom serve stop     # Stop it: it finishes lifecycle jobs in flight and saves; sessions keep running, every open TUI quits. Never from a loom pane

# Subcommands
loom reset --force  # Delete a workspace's instances, kill its tmux sessions (only those started in its repo/worktrees dir), remove its worktrees and branches; refused while the daemon runs
loom debug    # Print config paths, the daemon (pid, socket, build, tmux server) and its log, the tmux server
loom version  # Print version

# Workspace management
loom workspace add [path]    # Register a git repo as a workspace
loom workspace list          # List registered workspaces
loom workspace remove <name> # Unregister a workspace
loom workspace use <name>    # Set default workspace
loom workspace rename <old> <new>  # Rename a workspace
loom workspace status [name] # Show instance counts
loom workspace migrate       # Migrate instances to workspaces (refused while the daemon runs)

# Select workspace explicitly
loom --workspace <name>

# Claude accounts (spread sessions across several subscriptions)
loom account add <name> [--no-login]   # create <globalDir>/accounts/<name>, link your Claude setup, claude auth login
loom account login <name>              # "default" is your main login
loom account list                      # email, plan, 5h/7d usage per account
loom account use <name>                # account new sessions preselect
loom account sync                      # share entries added to your main config since
loom account remove <name> [-y] [--force]  # refused while a session uses it or holds unshared files; -y skips the confirmation, --force overrides both
```

## Environment Variables

- `LOOM_HOME` — Override config directory (default: `~/.loom`). Must be absolute path; supports `~` expansion. Used as a backward-compatible fallback; internal code uses explicit `WorkspaceContext` threading.
- `LOOM_LOG_FORMAT` — Set to `json` to emit structured log records from `log.InfoKV/WarnKV/ErrorKV` as JSON lines; otherwise plain text. The legacy `InfoLog`/`WarningLog`/`ErrorLog` writers always stay plain text.
- `LOOM_LOG_LEVEL` — `debug|info|warn|error` (default `info`). Gates both the Structured logger and the legacy `InfoLog`/`WarningLog`/`ErrorLog` writers (legacy records below the gate are dropped at the writer layer). The `--log-level` CLI flag (persistent on all subcommands) takes precedence over the env var.
- `LOOM_PANE_RENDERER` — Set to `snapshot` to disable the embedded VT emulator and fall back to the legacy `tmux capture-pane` snapshot path for pane rendering (also the implicit path on Windows). Unset (default) renders panes from the emulator, enabling mouse forwarding, event-driven updates (no render/status polling), the native hardware cursor, and title/bell/focus pass-through. Scroll-back is emulator-owned on this path: windows render in-process from x/vt scrollback (`vt.Emulator.RenderWindow`), seeded once per attach from `tmux capture-pane -S - -E -1`; `tmux capture-pane` windowing survives only on the snapshot path. Each process reads its own: a TUI's picks its panes' renderer and its half of the tick, the daemon's (the environment it was spawned with) the model's tick interval (`core/tick.go:tickInterval`).
- `LOOM_TMUX_SOCKET` — Private tmux socket name: every tmux invocation gets `-L <name>` (via `tmux.Command`), overriding `$TMUX`. Used by the dev sandbox, whose safety comes from its own global dir (`LOOM_GLOBAL_DIR`), not this: from a loom pane it gets nothing past the nesting guard or `replaceGuard`. A daemon starting resolves its tmux server from it (`tmux.ResolveServer`), unless the last daemon's server still runs, and pins that server (`tmux.UseServer`); a TUI uses the server the daemon's hello names, whatever its own environment says (see the one-daemon gotcha).
- `LOOM_GLOBAL_DIR` — Relocates `GetGlobalConfigDir()` (workspace registry + global context), which ignores `LOOM_HOME` by design. Absolute; supports `~`. Also disables the legacy-home migration. It selects the daemon: one per global dir, so a loomdev sandbox has its own.
- `LOOM_ALLOW_NESTED` — Set to `1` to bypass the nesting guard of `loom serve` and `loom reset` (see Gotchas). It never lets a loom inside loom replace the daemon (`replaceGuard`).

The daemon's environment is frozen when it is spawned, by whichever `loom` first needed it: it decides what the model reads from its own environment (the credential override and `$CLAUDE_CONFIG_DIR` behind its warnings, `LOOM_PANE_RENDERER`, Claude's temp root) and an agent's `update-environment` variables, whatever the environment of a TUI attached later. The rest of an agent's environment, `ANTHROPIC_*` and the default account's `CLAUDE_CONFIG_DIR` included, comes from the tmux server's global environment, which is the daemon's only when the daemon started that server (see the credential gotcha).

Legacy fallbacks (`CLAUDE_SQUAD_HOME`, `CLAUDE_SQUAD_LOG_FORMAT`, `CLAUDE_SQUAD_LOG_LEVEL`) are still honored with a one-time deprecation warning to stderr; remove them from your shell init once you've migrated.

## Migration from claude-squad

On first launch, Loom renames `~/.claude-squad/` → `~/.loom/` atomically so in-flight instances, worktrees, and user scripts continue to work. Live tmux sessions with the legacy `claudesquad_` prefix are renamed to `loom_` before reconcile runs, so running agents keep their panes. The orphan sweep in `session/reconcile.go` recognizes both prefixes to clean up stragglers.

Auto-commit tags flipped from `[claudesquad]` → `[loom]` at the v0.1.0 cutover. Historic worktree commits retain the old tag — that is expected and not rewritten.

## Debugging

- Log files: the TUI writes `{configDir}/logs/loom.log` (rotated once to `.log.1` at startup when >5 MB); the daemon writes `<globalDir>/logs/serve.log` (`log.Initialize(dir, true)`: never rotated at startup, since a `loom serve` that loses the lock race would rotate the live daemon's, but rotated as it grows; its records carry `component=daemon` and its legacy lines a `[DAEMON]` prefix), and a runtime crash it can't log (a fatal error, an unrecovered goroutine panic) goes to `serve-crash.log` beside it (`debug.SetCrashOutput`). Each process logs to its own file: what the daemon logs (`subsystem=serve`, `core`, `account`, `github`, the server's `rpc` lines, and the `session` and `tmux` lines of the lifecycle it runs) is in `serve.log`; the TUI's (`subsystem=app`, the client's `rpc` lines, its pane clients' `tmux` lines) in `loom.log`. A TUI whose daemon fails to start quotes the lines the daemon added to both files, or names `serve.log` (`daemon.Connect`). Run `loom debug` to print both paths, the daemon (pid, socket, build and the tmux server its TUIs use; or "not running", or "starting"), the tmux server a daemon started now would pin (`daemon.TmuxServer`), the nesting guard's answer on it, and the effective log level and format. Its Claude temp root is computed from its own environment, not the daemon's.
- To enable verbose output, set `LOOM_LOG_LEVEL=debug` or pass `--log-level=debug`. Debug logs are routed exclusively through the Structured logger (`log.Debugf` / `log.DebugKV`); they never appear via the legacy `*log.Logger` vars.
- New code should prefer `log.For("subsystem", ...)` to get a pre-tagged `*slog.Logger`, or call `log.InfoKV/WarnKV/ErrorKV/DebugKV` directly. The resulting records carry `subsystem=...` so a single `grep subsystem=tmux loom.log` scopes output to one component.
- The session model (package `core`) logs under `subsystem=core` (`log.For("core")`), keeping the event names its code had in `app` (`tick.tmux_gone_marking_paused`, `workspace_terminal.restart_circuit_tripped`, …); only the two `log.DebugKV` records took the new prefix (`core.roster.query_failed`, `core.hook_scan.failed`). The account registry and the GitHub poller keep `subsystem=account` and `subsystem=github`, and the TUI logs under `subsystem=app`. A job result the model does not recognize is logged as `deliver.unknown_result` and dropped.

## Architecture

### Core Flow

`main.go` (Cobra CLI, joining the daemon: `daemon_client.go`) → `app/app.go` (Bubble Tea Model, the view) → `core/rpc` (`rpc.Client`, the TUI's `core.Core`, over a unix socket) → `loom serve`, the daemon (`serve.go`, `internal/daemon`: an `rpc.Server` serving the loop) → `core/` (`core.Model` on its `core.Loop`, the session model) → `session/instance.go` instances

The app follows Bubble Tea's Model-View-Update pattern. `app/app.go` owns the `home` model and its `Update`/`View`. Keyboard input is routed in two stages: `handleKeyPress` (`app.go`) dispatches by `m.state` to a per-state handler in `app/state_*.go`; within the default state, keys flow through the Lua engine via `app/app_scripts.go:dispatchScript`, which consults `script.Engine.HasAction` and returns a `tea.Cmd` that drains the resulting `scriptDoneMsg`. The canonical keymap lives in `script/defaults.lua` (embedded at build time); user scripts in `~/.loom/scripts/*.lua` can rebind or add keys. On startup, the app shows the workspace `main.go` resolved (a directory argument or `--workspace`, else the global one), restores the tabs the last run left open, or prompts the user to select one via the workspace picker overlay.

The model runs on a goroutine of its own (daemon stage 1E), behind a wire (stage 2), serves every registered workspace to any number of clients (stage 3A), and since stage 3B runs in a process of its own: the daemon, `loom serve`, one per global config dir, which outlives every TUI (see the `internal/daemon/` bullet and the one-daemon gotcha). The daemon (`serve.go`, `daemon.Serve`) takes the global dir's lock, builds the `core.Model` (`core.New`) and boots it (`Model.Boot`, `core/load.go`, which is not in `Core`: it loads the account registry, detects the default account's remote-control auth when the global config enables remote control or an extra account exists, and runs `boot`, which loads the global workspace and every registered one and then one orphan sweep). Boot returns its notices, which the server keeps for the first client (`Server.Keep`), since none is connected yet. Then the model runs on a `core.Loop` (`core/loop.go`), which the daemon begins (`Loop.Begin`: the first accounts refresh and usage probe, and the arming of the model's health tick), served by an `rpc.Server` on a unix socket the daemon listens on only once booted. A TUI joins it from `main.go`, after resolving the startup workspace (`joinDaemon`, `daemon_client.go`): `daemon.Connect` dials the socket the lock records, spawning `loom serve` detached when no daemon runs; `rpc.Dial` exchanges hellos and returns once the client's replica holds the snapshot; the newer build wins (`daemonLink.join`, `rpc.CompareBuilds`); and the TUI pins the daemon's tmux server (`tmux.UseServer`) before anything of its own touches tmux. `app.Run` takes the client, and `startHome` (`app/app_init.go`) builds the TUI over it: it rereads the registry (`ReloadRegistry`, so a workspace registered since the daemon booted is served), records a named startup workspace as last used (`SetLastUsed`), shows the startup workspace (`home.startupName`, from the `wsCtx` `main.go` resolved; "" is the global one) in its classic slot, and opens it (`Core.Open`) unless it restores the registry's saved tabs instead (`restoreSavedWorkspaces`). No production code runs the model in the TUI's process any more: `rpc.InProcess` (`core/rpc/inprocess.go`) runs the same stack over a `net.Pipe` for tests. Which workspaces the TUI shows (its tabs, its classic workspace, the saved tabs it failed to open, `home.failedOpen`) and the agent program its drafts default to (`home.program`, from `-p`, else the startup workspace's config) are its own state, not the model's (see the focused-slot gotcha). The TUI holds the client as its `core.Core` (`core/iface.go`), with the client's wakes (`home.wakes`, from `Client.Wakes`) and the function that closes it (`home.stopCore`, deferred in `Run`; the daemon serves on). It sees instances only as `core.InstanceView` values, acting on one by a request that names its `core.InstanceID` (see the `core/` bullet). The client keeps a full replica of the model's published state, sent whole when it connects and every change after. So every query (`rpc:local` in `iface.go`) is answered locally, and only actions cross the wire. A request waits for its reply, and the server sends a request's events ahead of its reply, so a read right after a request sees its effect. A cast (`SetSelected`, the pane triggers, the requests for a poll or probe sooner) goes one way, with no reply (see the `core/rpc/` bullet and the no-model-mutation gotcha). Blocking work is a `core.Job` (`func() any`) the model queues; the loop runs it on a goroutine of its own and delivers its result on the loop (`core.Model.Deliver`). After anything it did unprompted (a job's result, its tick) the loop signals `Loop.Wakes`, and the server publishes. The client signals its own `Wakes` when events arrive, coalesced to one pending wake, which `Run`'s `forwardWakes` goroutine turns into a `coreWakeMsg`. It never blocks the client's reader or the loop: `p.Send` waits for Update, and the model's goroutine must never wait on the TUI. The model reports what the view must do as `core.Event`s (`core/events.go`, all listed in `core.EventTypes()`), queued in an outbox. The state events carry the published state: `WorkspacesChanged`, `ModelChanged`, `AccountsChanged`, `GitHubChanged` and `ViewsChanged`. The others are `Reply`, `Notice`, `InstancesChanged`, `ClientsStale`, `SessionLaunched`, `Reactivated`, `Started`, `Recovered`, `StatusesChanged`, `Alive` and `HealthChecked`. `home.Update` is a thin wrapper: it runs the message switch (`update`), then `drainCore` (`app/core_glue.go`), which empties the client with `core.Core.Sync`, then `publishSelection`, which tells the model the selected row (`SetSelected`) when it moved (the server merges every connection's into the model's selection set: see the `core/rpc/` bullet). `Sync` is `rpc:client`: it never leaves the client. It returns the state events for what changed since the last `Sync`, coalesced to the newest state and in the model's publish order (the workspaces, the model, account and GitHub views, then each changed workspace's `ViewsChanged`), so the appliers of the events after them read the new views. Then come the other events, in the order they arrived; `applyCoreEvent` applies each. `startHome` drains after each model call and hands the resulting Cmds to `Init` (`home.initCmd`). A panic on the loop's goroutine or in a job is a `core.LoopPanic`. The server turns it into a `panic` reply and a `Fatal` frame to every connection and closes `Server.Fatal()`, and the daemon exits without saving, since the model's state is unknown. The daemon's client (`rpc.Dial`) never panics: it records the model's loss, as it does a connection lost without `Close` (the daemon stopped, crashed or was replaced), in `Client.Err`, answers local reads from its last replica, fails requests with the loss, drops casts, and wakes the TUI. `home.Update` checks the loss first (`home.coreLost`) and quits, and `Run` returns `app.ErrDaemonGone`, which `main.go` reports once the terminal is restored: "loom: the daemon stopped (see <serve.log>); your sessions keep running. Run loom again." The next `loom` starts a daemon; live reconnect is a later stage. An in-process client (`rpc.InProcess`, tests) still re-raises the loss in the caller of that call or the next one, local reads included, so Bubble Tea's recovery (which covers only `Update` and its own Cmd goroutines) restores the terminal.

The default state renders in one of two **view modes** (`m.viewMode`), toggled with `tab`: **focus** (session rail + agent/terminal split — the classic layout) and **overview** (`ui/overview.go`, a fleet-triage card grid). `enter`/`esc` return to focus; `n`/`N` drop to focus first, then run the create flow; `z` collapses a group; mouse input is dropped in overview (v1). The mode persists per workspace in state.json's `ui` block — switching workspaces applies the target workspace's persisted mode.

**Cross-workspace overview.** The overview spans the **open (tab-bar) workspaces only** — each open workspace renders as its own card group (focused first, then alphabetical; per-group states loaded/empty). Workspaces registered but not open as tabs do not appear, though the model serves them all; open more via the picker (`W`). The overview carries a **global domain cursor** `home.overviewCursor {slot,inst}` (translated to render coords `ui.OverviewCursor {Group,Item}` in `overviewData`); `j/k` walk `fleetOrder` across all groups. Cursor-committing keys route through **`focusCursorSlot()`** (`loadSlot` → select), so `enter`/`D`/`r`/`n` reuse the existing focus-mode intents on the right workspace. Focus-mode `]`/`[` (`jumpWaiting`) also crosses open workspaces, switching the focused slot as needed.

### Key Packages

- **`app/`** — Bubble Tea application model: the view and key routing; lifecycle goes through `core`, by request. It keeps everything that renders or reads a pane client, `m.state`, overlays, key dispatch, the Lua engine and script host, the workbench and review, the overview cursor, tab bar, menu and error bar, the split-ratio throttle, full-screen attach, the issue picker (its fetches are `core.Model.FetchIssue` requests), and the views of accounts and GitHub state. It holds none of the model's objects: no `*session.Instance`, workspace, registry, storage or state (`TestTUIHoldsNoModelObject`; see the no-model-mutation gotcha). A workspace the TUI shows (a tab, or its classic workspace while no tab is open) is a slot (`workspaceSlot`, `app/workspaces.go`), a view of a workspace the model serves, named by `core.WorkspaceID` (see the focused-slot gotcha). Which workspaces it shows is the TUI's own state (stage 3A): startup and the saved-tab restore (`startHome`, `restoreSavedWorkspaces`), opening a tab (`openTab`, `activateWorkspace`; `servedID` finds a served workspace by name in `Core.Workspaces`, after a `ReloadRegistry` for one registered since, and refuses a name whose directory the model serves under another (`servedFor`, comparing directories as the model does, `sameDir`): a twin, the other name still registered ("X is the same directory as Y, which loom serves: open Y"), or a rename made while the daemon runs ("stop the daemon (`loom serve stop`), then start loom, to open it as X"), since the TUI keys its tabs, the picker and the open list on names; startup and the restore open the served twin in a twin's place instead, with a one-time info note shown with the recovery summary: `twinOf`, `twinNote`, `addNote`, `showStartupInfo`. A workspace registered at `$HOME` shares the global config dir, so the model serves it as the global workspace and it is the global workspace's twin: startup on it shows global ("home shares its config dir with the global workspace; showing global"), a saved tab of it opens nothing, since the global workspace is no tab, with a note, the picker refuses it ("… which loom serves: pick Global"), and registering it (`loom ~`) opens no tab but shows global with the same note), closing one (`deactivateWorkspace`), global mode (`enterGlobalMode`, `stayInGlobalMode`), the picker's commit (`applyWorkspaceToggle`), registration (`registerWorkspaceMsg`: `Register`, then `openTab`, or global mode when the registered directory is the global workspace's), quit (`handleQuit`: it flushes the split ratios and persists the open list, and saves no session, which is the daemon's) and the open list it persists (`openList`: its tabs in order, then `failedOpen`; `persistOpenList`). Each shows a workspace through `Core.Open`, and none loads, saves or drops a workspace in the model. It caches the workspace's `core.WorkspaceView` (`slot.info`: name and paths, a `config.Settings` copy, UI prefs, help screens, storage flags, load error, recovery summary), replaced by each `WorkspacesChanged` and reread by `syncWorkspaces` after the TUI's own write; UI prefs (`mutateUIPrefs`) and help screens are `SetUIPrefs`/`SetHelpScreensSeen` requests, and the settings overlay edits a `config.Config` of the TUI's own (`m.settingsEdit`, built by `config.FromSettings`), each change sent back whole as `SaveSettings` (a saved default program becomes `home.program`, which the model no longer holds for the TUI). A theme or default program another TUI saved for the focused workspace applies when its `WorkspacesChanged` arrives (`applySettingsChange`, `app/state_settings.go`: the theme painted, `home.program` replaced), and only when it changed: this TUI's own save rereads the view first (`syncWorkspaces`). Each slot also keeps that workspace's `core.InstanceView`s as its view store (`workspaceSlot.views`, `app/views.go`): seeded from `core.Core.Views` (the client's replica) when the slot is built (`seedViews`), replaced wholesale by each `ViewsChanged`, and reread by `syncViews` where an Update reads back a change its own request just made: the replica holds it by the time the request returns, since the server sends a request's events ahead of its reply (see the stale-copies gotcha). Every reader sees the store through `rowsOf` (the rail's `ui.InstanceSource` is `slotRows`), which copies each row, lays the TUI's own overlays over it (`overlay()`: the bells of `home.bells`, set by a pane's bell and cleared by focus, and the pane ladder's scraped status in `home.ladder`, see the event-driven panes gotcha) and appends the creation flow's draft row. `findRow`/`viewByID`/`viewBySession` look a row up across every open slot, `activeViews` lists the active ones, `refreshSelection` repoints the split pane's and menu's copies at the selected row, and the `ViewsChanged` applier runs `pruneBells`/`pruneLadder`. Creation flows edit a `draft` (`app/drafts.go`, `m.draft`): it shows as a row with ID 0 at the end of its own slot's rail until `confirmDraft` sends `core.Model.Create`, and every cancel path calls `discardDraft`, with nothing to kill. `app/requests.go` is the request book: `newReq` records what a request with a `core.ReqID` waits on (`pendingCreate`, `pendingSend`, `pendingOp`, `pendingScript`, `pendingIssue`) and `handleReply` routes its `Reply`. Every lifecycle request the user starts carries one (`opReq`, a `pendingOp`) so that a refusal reaches the user: `refusal()` shows the Reply's error through `handleError` only when it matches `core.ErrRefused`, since a failed job is the model's to show, as a notice. A prompt send holds input to its instance until its Reply (`sendPrompt`, `holdInput`, `m.sending`): meanwhile `sendingTo` refuses inline attach and another send to it with an info line (the prompt overlay keeps its text), so keys typed after a send can't land between its paste and its Enter; Lua's `send_prompt` holds too. The TUI reaches tmux by session name, never through an instance, on the daemon's tmux server (pinned by `main.go` before `Run`): the full-screen attach builds `tmux.NewSessionNamed(name, program)`, and the liveness guards call `m.sessionAlive(name)` (a has-session probe; tests set its `aliveProbe` seam). The TUI's own environment still decides what it starts itself: the terminal pane's shells (their `update-environment` variables), and a relative or `~` `ctx:new_instance{path=…}`, which it makes absolute (`scriptPath`) before the `Create`. When the client loses the model (the daemon stopped or failed), `Update` quits at once (`home.coreLost`, `home.exitErr`) and `Run` returns `ErrDaemonGone` (`app/daemon_client_test.go`). `app/core_glue.go` is the seam: `coreWakeMsg`/`forwardWakes` carry the client's wakes, `drainCore`/`applyCoreEvent` apply events, `publishSelection` tells the model the selection, `newSlotView` builds a slot over a workspace's view, and `slotFor` finds the slot showing a `WorkspaceID`. `app/completions.go` keeps only the view's half of the completions (`applyStarted`, `applyRecovered`): every client attaches the session's pane, but only the one whose request it was (`Started.Req`/`Recovered.Req` non-zero, see the `core/rpc/` bullet) selects the row, attaches inline or shows a notice.
- **`core/`** — The session model (daemon stages 1B to 1E; since stage 2 it publishes all of its state, for a client's replica; since stage 3A it serves every workspace to every client; since stage 3B it runs in the daemon, `loom serve`): everything that acts on sessions without a terminal. `core.Model` (`model.go`) serves every workspace (`Model.workspaces`), each loaded once and never dropped; each is a `core.Workspace` (`workspace.go`) with its context, storage, config, app state, ordered instances (edited only by the model, through the unexported `add`/`remove`/`replace`, by identity; tests reach them through `AddForTest`/`RemoveForTest`/`InstancesForTest`), recovery summary, load error (`loadErr`) and `opened` flag, and `Loaded`/`IsLoaded` (`workspaces.go`) query them. **Boot** (`load.go`): `Model.Boot`, which the daemon runs once it holds the lock (`daemon.Serve`), before the loop starts, and which is not in `Core`, runs `InitAccounts`, the default account's remote-control detection (following the global config's setting, not the startup workspace's) and `boot`, which loads the global workspace (`globalWS`) and every registered one (`ensureLoaded`), one per config dir (`wsByConfigDir`, which compares canonical paths, `canonicalDir` through `session.CanonicalPath`: a renamed registry entry, the startup context, or a second registry entry reaching the same directory through a symlink is the same workspace, served once under the name it was first served by, since serving one directory twice would let a stale copy's save overwrite the other's), then runs one orphan sweep over them all (`sweepOrphans`). A workspace registered later is served from its `Register`, or from the `ReloadRegistry` that finds it (every TUI's `startHome` runs one); one unregistered stays served until the daemon restarts. `loadWS` (formerly `loadWorkspace`) is the one load path: `applySessionConfig`, `LoadAndReconcile`, the crash-restart of every session the reconcile found dead with its worktree intact (`crashRestart`), except the workspace terminal's, which waits for the workspace's first open, then `reconcileOrphans`. Loading every workspace relies on two ownership checks (`session/reconcile.go`), since tmux names are per server, not per workspace. Both take the record's `session.SessionHome{Dir, Exact}` (`Instance.SessionHome`): an agent's session starts in its worktree, so one started there or below is its own; a workspace terminal's starts in its repository itself (loom launches it with `-c <repo>`), so only an exact match is, because an agent titled after the workspace starts its session in `<repo>/.loom/worktrees` under the terminal's tmux name. Reconcile's `startedElsewhere` counts only positive evidence: a non-Paused record whose name is alive on a session started anywhere else goes straight to `ActionMarkPaused`, workspace terminals included, so reconcile neither restores it onto that session, crash-restarts it under a name known to be taken, nor kills the other session (an unreadable listing or start directory keeps the old behaviour). `session.HeldElsewhere`, which a caller about to kill or replace whatever runs under a name asks first, fails closed with three outcomes: held (a live session not provably the record's own, one with no start directory included), free (no session of that name, or no server), or an error (a listing tmux left unanswered, a timeout under load: no answer, so change nothing and ask again). `Instance.Kill` (and so a discard, which kills a `Recoverable` entry) and `Instance.Resume` ask it of the session under the record's name (`Instance.sessionHeldElsewhere`, through `tmux.Session.StartDir`): a kill leaves a held name's sessions running, the agent's and the terminal-pane `loom_term_` shell, and cleans up only what is the record's own; a resume refuses on a held name, before `decideResume`, rather than reattach to another workspace's session or relaunch under its name; and both refuse, changing nothing, when tmux can't say whose the session is (`core/held_name_test.go`). **Opened**: a client showing a workspace, as a tab or as the workspace it shows while none is open, calls `Open(id)` (`open`). The first open since the model started sets `opened`, which gates the workspace's terminal and its GitHub polling: `ensureTerminal` creates the terminal (killing a leftover session under its title only when the sweep's ownership test proves it this workspace's, `KillOwnedTmuxSession`). For one that died while nobody had the workspace open (`CrashRecovered`) or is Paused (its restart breaker stopped it, Paused for good before 3A, or reconcile found its name held), it asks `HeldElsewhere` and hands the answer to `settleTerminal`: held, the other session is left running and the terminal stays, or is marked, Paused; free, it relaunches the terminal (`crashRestart`, or `ResetRestartFailures` then `Restart`); unanswered, nothing changes or is saved, the workspace is marked `terminalUnsettled`, and the health tick asks again off the model's goroutine (`maybeSettleTerminals`, a background job per workspace, one check in flight, asked again after every unanswered one, delivered as `terminalChecked`; an answer about a terminal killed meanwhile settles nothing: the `TestSettleTerminals_…` tests) until tmux answers, since Paused for good would strand the terminal until the next first open after the daemon restarts. `ensureTerminal` saves the workspace after it creates, relaunches or pauses the terminal (`saveTerminal`), so a crash before the next save can't leave a live terminal with no record, which the next first open would kill and recreate, losing its conversation. Until then the terminal is dormant: `activeInstances` leaves it out, so the tick neither probes, relaunches nor pauses it. Which workspaces a client shows is the client's own state: an open publishes nothing tab-like, and nothing in the model closes a tab. **A failed load is kept, latched**: `loadWS` leaves the workspace empty with its storage's write latch engaged and records `loadErr` (published as `WorkspaceView.LoadErr`; the boot only logs it, `workspace.load_failed`, and the TUI reads `failedOpen`, not `LoadErr`, so a failed workspace not in the open list shows nowhere until something opens it); `sweepOrphans` leaves its roots out of the owned set, its titles being unknown, and still sweeps every other workspace (one broken workspace used to skip the whole sweep); and every `Open` retries it (`retryLoad`, which rebuilds its state, config and storage from disk, since a storage keeps the payload it was built over), returning the error while it still fails. **Session flags per config dir**: the loom-context and subagent-tracking launch toggles live in `session` keyed by config dir (`dirFlags`; `syncSessionFlags` sets a workspace's at its load and on `SaveSettings`), and a launch reads its own instance's, since with every workspace loaded one process-wide value would follow whichever loaded last. **The request is ambient** (`Model.cause`): while the model applies a request's job result (a `caused` result, which `Deliver` unwraps through `causedBy`, or a tracked one), the `Started`, `Recovered` and `Notice` events it emits carry the request in `Req` (`emit` stamps them), and the jobs it spawns meanwhile serve the request too (`spawn` wraps their results as `caused`), so a chain's last event (`Create`, then the start, then the initial prompt's send, then `Started`) still names it. The model's own jobs (the tick's probe, gated jobs, dead checks) go through `spawnBackground` and never inherit it. The loop takes the two kinds apart (`takeJobsSplit`) and counts the others (a request's jobs and their follow-ons, and whatever `spawn` queues) as foreground jobs until they land: `Loop.Quiesce`, the daemon's stop, fires no more ticks, waits for those (the daemon allows 30s, `Options.QuiesceTimeout`) and leaves the background ones to be dropped at `Stop`, so a pause or kill is never cut off mid-step. **The selection is a set** (`Model.selected`): `SetSelection` names every client's selected row at once (`SetSelected` names one), and the tick's probe refreshes the full diff of each (`selectedInstances`). Clients see an instance only as a `core.InstanceView` (`view.go`): a value holding everything the TUI renders or gates a key on (`Active()` is the active-instance rule, for a view; `WorktreeRepoPath` is what Lua's worktree handle is built on) and nothing that acts. It names its instance by a `core.InstanceID`, which the model assigns the first time it reports the instance (`idOf`) and never reuses within the process, so a request can't reach a same-titled instance in another workspace or an instance that took a removed one's place; 0 is never assigned (the TUI's draft row uses it). `Views(id)`/`View(id)` (`views.go`) build views of served workspaces only. Workspaces cross the boundary the same way: a `core.WorkspaceID` (`wsIDOf`, kept while the model serves the workspace, which is until it stops, so a tab closed and reopened shows the same one; never reused) and a `core.WorkspaceView` (`workspace_view.go`; its `LoadErr` is the text of a failed load, "" once it loaded, for a client to show a failed workspace by; the TUI so far goes by its own failed opens, `failedOpen`), answered by `Workspaces()` (every served workspace, in serve order) and `Workspace(id)` and published by `Sync` as one `WorkspacesChanged` carrying every served workspace's view whenever any changed (`publishWorkspaces`, `workspace_views.go`), ahead even of the `ViewsChanged`s. The workspace requests take and return IDs and views (`workspace_requests.go`: `Workspaces`, `Open`, `Views`, `Create`, `IsLoaded`, `Registry`, `ReloadRegistry`), and `Started`/`Recovered` name their owner by ID with its label (the owner is always served, so neither carries a closed-owner note any more). `SaveSettings` (`settings.go`) replaces a workspace's settings, writes its `config.json` and applies the change at once (that workspace's launch toggles in the session package, which only the model sets, and, for the global workspace only, the program the accounts' Claude commands run with, which in a daemon is the global config's; the program a client's drafts default to is the client's own, `home.program`); `SetUIPrefs` and `SetHelpScreensSeen` write its `state.json`. `Registry()` is a `RegistryView` copy (the registered workspaces, the open list, `LastUsed`) and `ReloadRegistry` rereads the registry from disk and serves any workspace registered since; the registry's writes are `Register` (which returns the new workspace's view, for the client to `Open`), `SetLastUsed` and `PersistOpenList` (the open list a client hands it, its tabs then the ones it failed to open: the model only writes it, and never acts on it); `AccountNames()` is all the TUI sees of the account registry; and every query hands out copies (`GitHubSnapshot`, `AccountUsage`, `AccountSync`, the views). `Sync` (`syncEvents`) publishes them by diffing, in a fixed order and ahead of every other event: the `WorkspacesChanged`, then `publishState`'s events (`state_publish.go`), then a `ViewsChanged` for each served workspace whose views changed since the last publish, carrying deep copies (`cloneViews`). It also forgets the IDs of instances no served workspace holds. `publishState` emits three events, each carrying one of the state views of `state_views.go` (the fourth, `WorkspacesView`, is the workspace views): `ModelChanged` (`ModelView`: the default account's remote-control auth and the registry), `AccountsChanged` (`AccountsView`: the names, the loaded and extra flags, the Claude program, the accounts, their auth, link reports and usage, and the probes' errors) and `GitHubChanged` (`GitHubView`: the snapshots, the poll errors and gh's availability). The model and account views are diffed whole (`reflect.DeepEqual`). The views' `Clone` methods deep-copy their slices and keep every other field (`ModelView.Clone` once rebuilt the `RegistryView` and lost `LastUsed`, so every replica's restore focused the first tab). The account view is also republished after every usage probe round (`usageGen`, bumped in `deliverUsage`): the TUI renders a usage sample's age when it refreshes, and a probe failing the same way again changes nothing the view holds. The GitHub view, whose snapshots can be large, is republished whenever a poll lands (`ghGen`, bumped in `deliverGH`, the one place its state changes). Nothing emits `AccountsChanged` or `GitHubChanged` by hand any more; the diffs fire on every change, the default auth included. `Model.Snapshot` is the whole published state as events, in `Sync`'s order, and leaves the diff baseline alone. `Loop.SyncAndSnapshot` serves the server and is not in `Core`: it runs a `Sync` and a `Snapshot` in one loop call, so a client that connects starts from exactly the state the next `Sync` diffs against. The state views' methods replicate the logic of the model's own queries, which stay as they are, since several run on every tick and building a view for each would be waste. So parity is tested twice. `TestStateViews_AnswerAsTheModel` and `TestWorkspacesView_AnswersAsTheModel` (`core/state_views_test.go`) compare view and model directly, and `core/rpc`'s `TestReplica_AnswersAsTheModel` compares the client with the loop over the wire, misses included. A query added to `Core` needs a view method and a case in both. Every lifecycle action is a request, by ID where it names an instance, with an optional `ReqID` (`requests.go`: `Kill`, `Pause`, `Resume`, `ResumeWith` (the `R` flow: the new launch options applied, then a resume), `Recover`, `Merge`, `Push`, `SendPrompt`, `Create(ws, NewInstance, req)`, which builds and adds an instance and, with `Start`, configures and starts it, and `FetchIssue`). A non-zero `ReqID` is answered by a `Reply` (`Req`, `ID`, `Err`, `Notice`, `Issue`): at once for a refusal or a `Create`, otherwise when the request's job lands (`track`, `deliverTracked`). Each request first runs `admit`: a served workspace must hold the ID (else `ErrNoSession`) and the instance must pass `precondition`, which mirrors the keys' gates in `app/intents.go` (no kill, pause or push of a workspace terminal or a busy session, no resume of one not Paused, …), so the model refuses exactly what no key can do. A refusal's error matches the `core.ErrRefused` sentinel (`ErrNoSession` does too); with `ReqID` 0 it is only logged (`request.refused`). A failed job is not a refusal: the model has already shown it as a `Notice`, and the Reply's `Err` carries it too. On the wire an error is a `core.WireError{Code, Message}` (`wire_error.go`), which keeps the three sentinels clients test with `errors.Is`. Its codes are `not_found` (`ErrNoSession`, which `Is` also `ErrRefused`), `refused` (`ErrRefused`), `storage` (`session.ErrStorageLoadFailed`), `error` (anything else: only its message survives), `panic`, `protocol`, `mismatch` and `unsupported` (`CodeUnsupported`: a method the server does not know, an ordinary error rather than a fatal one, so a newer client can probe an older server). `ToWire` encodes an error: a `WireError` passes unchanged, an error wrapping one keeps the inner code with the whole wrapped message, and any other takes the code of the first sentinel it matches. `FromWire(nil)` is a nil interface, never a typed nil. `Notice`, `Reply` (`events_json.go`) and `git.DiffStats` (`session/git/diff.go`) encode their error fields this way; `DiffStatsData`, the persisted form, is unchanged. The TUI shows other errors only as text. The TUI's pane triggers name instances by ID as well (`SetSelected`, `PaneOutput`, `PaneQuiet`, `VerifyDead`; `MarkOutput` takes the session name). Booting, loading and saving (`load.go`: `Boot`, `boot`, `loadWS`, `ensureLoaded`, `globalWS`, `retryLoad`, `open`, `ensureTerminal`, `sweepOrphans`, `reconcileOrphans`, `claimTitles`; `persist.go`: process (`loop.go`, with every forwarder in `loop_core.go`, each of which `TestLoopForwardsEachMethodToItsNamesake` checks runs its namesake on the model and nothing else). `*rpc.Client` implements it over a connection (to the daemon, in production), and that is what `home.core` holds (see the `core/rpc/` bullet). `iface.go` is also the wire's source: `core/rpc`'s wire code is generated from it, and its parameter names are the wire's field names (the terse ones were renamed for it: `auth`, `settings`, `prefs`, `program`, `number`, `workspace`). A method's line comment says how a client serves it: `// rpc:local` (23 queries) is answered from the client's replica; `// rpc:cast` (9 notifications) is sent one way, with no reply, and the server publishes nothing after one, so a cast must change no published state (it marks, names or starts what publishes on its own when it lands); `// rpc:client` (`Sync`) never leaves the client; and every other method (23) is a request, whose reply follows the events it produced. Stage 3A took the tab and startup methods out of `Core` (`LoadClassic`, `RestoreSaved`, `StayGlobal`, `KeepRestoreFailed`, `OpenNames`, `RestoreFailed`, `Classic`, `Tabs`, `EnterGlobal`, `CloseTab`, `OpenTab`, `Program`, `SetProgram` and `Save` are gone; `InitAccounts` and `SetRCAuth` remain on `Model` for `Boot`, and `Begin` on `Model` and `Loop` for whatever serves the loop) and added `Open`, `Workspaces` and `PersistOpenList` (which now takes the names; `Register` returns the new workspace's view). It is value-typed: `TestCoreIsValueTyped` (`core/value_boundary_test.go`) walks every method and every `Event` (`EventTypes()`, the production list the wire names and decodes events by, kept complete by `TestAllEventsListsEveryEvent`) by reflection and fails on anything but plain data (no func or chan, no interface but `error` and `Event`, no `sync` type, none of the model's own objects), with no exemption since stage 1E. `Model` is single-goroutine, and its `Loop` runs it: the loop serves each call as a round trip, starts the jobs the model queued (`takeJobs`, after every step) on goroutines of their own and delivers their results on the loop, fires the health tick from its own timer (`tickInterval`: 3s, 500ms on the snapshot path; armed by `Loop.Begin`, which whatever serves the loop calls once (`daemon.Serve`, or `rpc.InProcess` in tests; it is not in `Core`), and re-armed only when the probe's `HealthResult` lands, so probes never overlap), and signals `Wakes`. - **`core/rpc/`** — The wire (daemon stage 2; several clients since stage 3A; between processes, over the daemon's unix socket, since stage 3B): `core.Core` carried over a connection as newline-delimited JSON. **Frames** (`rpc.go`, `Frame`): each side's first frame is a hello (`Hello`: `protocol`, which is `rpc.Protocol`, now 2 (stage 3A removed event fields and `Core` methods; 3B added only optional ones) and bumped on any incompatible change; `build`, from `debug.ReadBuildInfo` (`rpc.Build`); and, optional since 3B, `version` (main's release, `rpc.SetVersion`), `time` (`vcs.time`, else the commit time stamped at link time into `rpc.commitUnix`, which `flake.nix` sets from `self.lastModified`, since a Nix build has no VCS information), `modified` (`vcs.modified`), `exe` (the SHA-256 of the running executable, read through `/proc/self/exe` where there is one, so a rebuild in place doesn't change a running process's answer), `exe_time` (that file's mtime) and, from a server only, `tmux`, the tmux server its sessions run on (`Server.SetTmux`); `rpc.Self()` is this binary's hello). The server sends its hello first, even to a peer of another protocol, then answers that peer `mismatch`, so `Dial`'s `*MismatchError` carries the server's hello and a newer client can still replace an older daemon. **Builds** (`build.go`): `CompareBuilds` says which of two hellos is newer: the same `exe` is the same build; otherwise the higher `version` (as semver), then the later `time`, then a modified tree over a clean one, then the higher `protocol` (a peer that sent none, 0, is older), then, only when both name their commit time, the newer `exe_time` (a dev build rebuilt at one commit replaces its sandbox's daemon). A field either side lacks decides nothing, and neither does an `exe_time` at or before 1970-01-01T00:00:01Z (`knownExeTime`: a Nix store dates every file there), and a full tie is the same build, so two installs of one release keep whichever daemon runs rather than replace each other's on every launch, a Nix build and a release binary of one commit keep each other's, and two Nix builds are ordered by their stamped commit times. A build that names no commit (a plain `go build` from a tarball) at the release of the daemon running keeps it; `loom serve stop` switches. The policy that acts on it is the TUI's join (`daemon_client.go`, see the `internal/daemon/` bullet). After the hello come requests (`id`, `method`, `params`), replies (`id`, `result`, `error` as a `core.WireError`), casts (a request with no `id`, which gets no reply), events (`event`, the event's Go type name, and `data`) and `fatal` (the model panicked, or the server could not encode an event). The full reference is `docs/specs/protocol.md`, request-ID routing included (its "Request IDs" section). **Generated code**: `methods_gen.go` is generated from `core/iface.go` by `internal/gen` (`go generate ./core/rpc`, the `//go:generate` line in `rpc.go`); never edit it by hand. It holds each method's `…Params` (one field per parameter, named after it) and `…Result` (`{"value":…,"ok":…}`; an error travels in the reply's `error`), the `methods` table with each method's kind, the server's `dispatch` (which takes a `tag func(*core.ReqID) error` and calls it on every `core.ReqID` parameter before the call: `TestGenerate_TagsEveryRequestID`), and the client's methods. A method's wire name is its Go name. The generator refuses an `rpc:` directive in a doc comment and an unknown line comment, and a parameter carrying a `ReqID` anywhere but as its own type (in a slice, map or pointer, or a field of a core struct, at any depth: `nestedReqID`, over core's type declarations, which `gen.CoreSources` reads beside `iface.go`; `TestGenerate_RefusesARequestIDTheServerCannotTag`), since dispatch tags only a parameter of type `ReqID` and a nested one would reach the model as its client numbered it. `TestGenerated_IsFresh` fails when `methods_gen.go` is stale, and `TestMethods_CoverCore` when the table misses a `Core` method. Adding a method, an event or an optional field is compatible and needs no bump (a peer answers a method it lacks with `unsupported`, ignores a field it does not know and drops an event it does not know); removing or renaming a method, event or field, or changing what a field means or a frame's shape, needs a `Protocol` bump (`rpc.Protocol`'s comment states the rule). **Server** (`server.go`, `server_conn.go`): it serves a `Backend` (`core.Core` plus `SyncAndSnapshot`, `SetSelection` and `Wakes`, all of which `*core.Loop` has) to any number of connections, which it numbers (`serverConn.n`). It publishes (the backend's `Sync`, to every connection) after every request and on every loop wake, and queues a request's reply only after that publish, so a request's events reach the client ahead of its reply. `rpc.Ping` is a request that only publishes and replies: the client's barrier. A cast publishes nothing (pane events cast up to ~60 times a second per session; see the `rpc:cast` rule in the `core/` bullet), and its failure is only logged (`server.cast_failed`). The server answers `rpc:local` methods as requests too, for a client without a replica. A peer that sends no hello within `helloTimeout` (10s) is dropped. A connection is sent its hello, then its snapshot, then the notices no connection was there for. The snapshot comes from one loop call, `Loop.SyncAndSnapshot`: its `Sync`'s events go to the connections already there and its `Snapshot` to the new one, so a late joiner's replica starts from the state the next `Sync` diffs against (`TestServe_ALateJoinerStartsFromThePublishedBaseline`). **The notice backlog** (stage 3B): a `Notice` published while no client is connected, and those a daemon hands over with `Keep` (its boot's, raised before any client could be), wait for the next connection; a request's `Notice` whose client has gone goes to the connections still there, and is kept only when there are none. The backlog keeps the newest `maxBacklog` (50) and logs each notice it keeps (`server.notice_kept`), so even one no client reads is on record (`server_backlog_test.go`). Each connection's outbound side is a queue its own writer goroutine drains (`serverConn`), so a slow client never blocks the server. A state event replaces a queued one of the same kind in place (`coalesceKey`: workspaces, model, accounts, github, and each workspace's views), so the queue holds at most one of each. Replies and other events are never dropped or reordered, because a resync could not rebuild a lost `Reply` and a script would hang on it; this coalescing replaces the spec's drop-and-resync. The non-state queue is unbounded (replies are bounded by the requests in flight). The server recovers a panic in a call, a `Sync` or the snapshot: the request's reply carries code `panic`, a `Fatal` frame goes to every connection, a later one included, and `Server.Fatal()` closes (`FatalError` says why), on which the daemon exits. An event that will not encode is fatal too (`CodeProtocol`, naming the event, `server.encode_event_failed`), because dropping it could strand a `Reply`'s requester. The server tracks every connection from `Serve` on, so `Close` ends even one that has not said hello, and `Serve` after `Close` closes its connection at once. A connection's close waits at most `closeFlushTimeout` (5s) for a peer that never reads. **Routing** (`route.go`, stage 3A): each client numbers its requests itself, from 1 and below 2^32, so request IDs collide across clients. The server keeps them apart without a table: dispatch's tag (`tagReq`) ORs the connection's number into the high 32 bits of every request ID it hands the model (0, no Reply wanted, stays 0; an ID at or above 2^32 is a `protocol` error), and at publish each connection is sent each event as `forConn` says, with the number masked out again (`local`): a `Reply`, and a request's `Notice`, go to the client that made it alone, with its own ID; `Started` and `Recovered` go to every client, since each attaches the session's pane, naming the request (`Req`) only to the one that made it (`reqFor`; 0 for every other). A table would leak: a `Create`'s `Reply` comes at once and its `Started` much later, so it would never know when to forget an entry. The events reach the right request because the model stamps them (`Model.cause`, see the `core/` bullet). `routed` lists the events that name a request, and `TestForConn_CoversEveryEventNamingARequest` keeps `forConn` complete. **Selection per connection**: the server calls a connection's methods through `connBackend`, whose `SetSelected` records that connection's selected row (`setSelected`; 0 forgets it) and hands the model every connection's, in connection order without repeats, through `Backend.SetSelection` (`Loop.SetSelection`, not in `Core`); a closed connection's is dropped (`dropSelection`). **Client** (`client.go`, `replica.go`): `Dial` sends its hello, checks the server's (`Peer`), starts the reader, and returns after a ping (`handshake`), by which time the replica holds the snapshot. A fatal frame met during that ping is `Dial`'s error rather than a panic; one landing after the ping checked is the client's loss as usual. The reader handles every frame in the order the server wrote them. It applies each state event to the `replica`, marking what changed. It queues the other events, records a fatal, and hands each reply to the call waiting for it. An unknown event name (a newer peer's) is logged and dropped (`client.unknown_event`). A known event that fails to decode is fatal (`CodeProtocol`), since it may be a `Reply` someone waits for or state the replica would hold stale. The replica answers every `rpc:local` query through the state views' methods and hands out copies. It ignores a `ViewsChanged` for a workspace it does not hold: the server's queue coalesces a `WorkspacesChanged` in place, so one that drops a workspace (a test's, or a future unregister; the model drops none today) can arrive ahead of a `ViewsChanged` queued for it, which would otherwise bring the dropped workspace's views back for good. `Sync` hands out the newest state once per kind, in the model's publish order, then the other events in arrival order. `Wakes` signals arrivals; wakes coalesce, and `Close` closes the channel once the reader has stopped. A request returns the method's error (`core.FromWire`). A request for a method with no error to return logs its failure (`requestNoErr`, `client.request_failed`) rather than drop it. A reply with code `panic` or `protocol` is fatal; an `unsupported` one (a method the server does not know) is the method's ordinary error, so a newer client can probe an older server. A connection lost without `Close` is fatal the same way (`client.connection_lost`): the TUI must not run on against a model it can't reach. What fatal means depends on the client. A daemon's client (`Dial`) panics nowhere: it records the loss (`Err`) and signals `Wakes`; local reads answer from the last replica, requests return the loss and casts are dropped, so the TUI can quit cleanly (`TestPanic_ADaemonsClientReportsIt`, `TestConnectionLost_IsFatal`). An in-process client (`InProcess`, which sets `raise`) panics with the `WireError` in the caller, and so does every later call, local reads included (`TestInProcess_RaisesTheModelsPanic`). `Close` marks the client closing first, so its own close is not a loss, and a call after it returns `errClosed`. `request` and `cast` copy the fatal and closed state under `c.mu` and panic only after unlocking: a panic holding the lock blocked the reader and hung `Close`. **In process** (`inprocess.go`): `InProcess(model)` takes a model booted already (`core.Model.Boot`) and runs `core.Start(model)`, `NewServer`, `net.Pipe` and a raising client, then `Loop.Begin` once the client has dialled, so nothing the first jobs publish (a `Notice`) goes to no connection (`TestInProcess_BeginsTheLoop`), and returns the client and a stop function that closes the client, the server and the loop. No production code calls it since stage 3B (the TUI's client is the daemon's); tests use it for the production stack in one process (`app`'s `TestRealLoop_…`, `core/rpc`'s client tests). `InProcessForTest` (`seams.go`) is the same over a `core.StartForTest` loop, which holds its jobs and is returned for its seams, with a synchronous client (see Testing Patterns); `FlushForTest` is the ping. **Protocol reference**: `docs/specs/protocol.md` is written from the method table and `core.EventTypes()` by `go test ./core/rpc -run TestProtocolReference -update`, and the test fails when it is stale. After any wire change, rewrite it and bump `Protocol` if the change is incompatible. **Tests** run production (non-synchronous) clients. `TestReplica_AnswersAsTheModel` compares every local query through the client with the loop's raw answer (times as UTC instants, errors as text), so a field the codec drops shows. `TestWire_EveryFieldSurvives` fills every field of every event and state view by reflection and round-trips it. `TestCoalesceKeys_MatchTheReplicasStateEvents` keeps the server's coalescing keys in step with the events the replica keeps. A scripted server end (`scripted_test.go`) sends frames a real `Server` never does: an unknown event, one that won't decode, a `protocol` reply. Others cover events before replies, casts, coalescing, wakes, panics, a lost connection against `Close`, encode failures, the hello and the late joiner (`Loop.SyncAndSnapshot` has its own, in `core/loop_test.go`), and `route_test.go` covers routing: two clients' colliding IDs each getting their own replies, a request's `Notice` and `Started` naming it only to its client, and every client's selection reaching the model. `build_test.go` covers `CompareBuilds` and `Self`, and `server_backlog_test.go` the notice backlog, `Fatal` and the hello deadline. Everything logs under `subsystem=rpc`.
- **`internal/daemon/`** (with the root's `serve.go` and `daemon_client.go`) — The daemon (stage 3B): `loom serve`, the process that owns a global config dir's sessions whether or not a TUI is open, and how a TUI finds it. **The lock** (`lock.go`): one daemon per global dir, holding a gofrs flock on `<globalDir>/loom.lock` for its whole life (the OS releases it on exit, crash included). It lives in the global dir, not beside the socket, so two processes whose environments would put the socket in different places still exclude each other, and since a loom from before the daemon took its takeover lock on the same file, the two exclude each other too. The holder's `Record` (`pid`, `tty`, `started`, `socket` once it listens, `build`, `host`, `tmux`) is written into the lock file itself on Unix, where flock is advisory, and into `loom.lock.json` beside it on Windows, whose lock (`LockFileEx`) is mandatory (`recordPath`, `proc_unix.go`/`proc_windows.go`). It is rewritten in place, never renamed, since the lock is on the inode, so `ReadRecord` rereads a record it meets half-written; never remove `loom.lock`. A record reads three ways: `IsDaemon` (a socket is set: dial it), booting (a build but no socket yet), and `IsPreDaemon` (a pid but neither: a 0.13 TUI, refused only while its pid lives). `acquire`, the daemon's take, stands down at once (`ErrRunning`, which `loom serve` prints before exiting 0) when a live loom process holds the lock (`liveHolder`: alive, and pre-daemon or `servesLoom`, whose `/proc/<pid>/cmdline` says `serve`), and waits (`Options.LockWait`, 5s) only while no live process does (a client's `ReadRecord` probing it, a daemon that took it and has not yet written its record), so a daemon started while another runs or stops never takes over once that one has gone. **The socket** (`paths.go`, `SocketPath`): `$XDG_RUNTIME_DIR/loom/<hash>.sock`, else `<globalDir>/run/serve.sock` when that fits a socket address (`maxSocketPath`, 100 bytes), else `loom-<uid>/<hash>.sock` in `os.TempDir()`, each in a 0700 directory this user owns that is not a symlink (`privateDir`); the socket itself is 0600, and `<hash>` is 16 hex digits of the SHA-256 of the resolved global dir. Only the daemon computes it: it records it, and clients dial what the record says, since their environment may differ from the daemon's. **`Serve`** (`serve.go`): it takes the lock, finds the socket's place before the boot (a host with none fails having swept and relaunched nothing), builds the model (`Options.NewModel`: the root's loads the registry, serving the global workspace alone with a kept notice when it won't load, and the global config's program) and boots it, keeps the boot's notices for the first client (`Server.Keep`), starts the loop and `Begin`s it, then listens, so a socket that answers is a daemon that is ready, and writes the socket into the record (a record it can't write stops it, since no client could find or stop it). Every 2s (`Options.WatchInterval`) it checks that the socket file is still its own (`os.SameFile`) and, when it is gone or replaced (a runtime dir removed at logout, a tmp cleaner), listens again wherever `SocketPath` finds room now and rewrites the record; a failed `Accept` (EMFILE) is waited out. When `Options.Stop` closes (the root's signal handler closes it on the first SIGTERM, SIGINT or SIGHUP) it closes the listener and the server, waits for foreground jobs and saves (`stopModel`: `Loop.Quiesce`, then `SaveForQuit`), stops the loop and removes the socket. A Ctrl-C meanwhile exits at once (`forcesExit`), while another SIGTERM or SIGHUP is only logged: two looms replacing the daemon together each send one, and the second must not cost it its save. When the model fails (`Server.Fatal()`) it exits without saving (`serve.model_gone`), and the next `loom` spawns a fresh daemon. **`Stop`** (`loom serve stop`, and a newer TUI replacing the daemon) signals the pid the record names rather than asking over the socket, so it stops a daemon of any protocol: it refuses another host's record (`Host`), signals only a pid whose arguments say `serve` (`servesLoom`), sends SIGTERM (`terminate`) and waits until that process has gone, whoever holds the lock by then. `StopPID`, a TUI replacing a daemon, stops only the daemon it dialed and compared (the record's pid when it dialed): when the lock is free by then, another process holds it, or the pid has died (its record outlives it while a probe or the next daemon holds the lock), it signals nothing and answers `ErrNotRunning`, since two new TUIs starting together both dial the old daemon, and the second must not stop the daemon the first just started. Windows has no graceful stop, and `Stop` says so. **`Connect`** (`connect.go`), the TUI's side: it makes the global dir (a first launch with a new `LOOM_GLOBAL_DIR`, or `LOOM_HOME` and no `~/.loom`, has none, and the spawn starts the daemon in it), reads the record and dials, or spawns `os.Executable() serve` detached (`spawn`: `Setsid` on Unix, `DETACHED_PROCESS` on Windows; stdio to `/dev/null`; the global dir as its working directory, never the client's, which it would keep for its whole life; the client's environment), backing off until a daemon answers. It waits past its timeout (`connectTimeout`, 20s, in the root) up to `bootTimeout` (3 minutes) for a live daemon still booting (a boot relaunches every dead agent before it listens), starts another (up to `maxSpawns`, 3) when the one it started stood down for a daemon that has gone since, and quotes what a daemon that exited early added to `serve.log` and `serve-crash.log` (`LogPath`, `CrashLogPath`). The spawner takes no lock: two clients starting a daemon each is harmless, since the second daemon stands down and both clients dial the first. **The tmux server** (`TmuxServer`): the last daemon's (`Record.Tmux`) while it still runs (`tmux.ServerRunning`), else `tmux.ResolveServer()` (`LOOM_TMUX_SOCKET`'s socket in `$TMUX_TMPDIR/tmux-<uid>`, `/tmp` by default, else `$TMUX`'s server, else that dir's `default`), so a daemon started from another environment (an ssh login, inside another tmux server, a newer loom replacing an older daemon) finds the agents where they run rather than find every session dead and relaunch each on its own server, two to a worktree. The daemon pins it (`tmux.UseServer`: `-S <path>` on every `tmux.Command`) before the boot and names it in its hello and record. **Joining** (root `daemon_client.go`): `joinDaemon` builds a `daemonLink` (with seams for tests), whose `join` dials (`dialDaemon`: `daemon.Connect`, then `handshake`, `rpc.Dial` under the connect's deadline, so a daemon that accepts and never answers can't hang loom; after 750ms of silence it prints "loom: waiting for the loom daemon (it loads every workspace as it starts)…") and compares builds (`rpc.CompareBuilds`). The same build is used, with its tmux server pinned (`tmux.UseServer(peer.Tmux)`). A newer daemon is refused ("the loom daemon is X, newer than this loom (Y): upgrade loom, or run `loom serve stop`"). An older one is replaced once, announced on stderr ("loom: replacing the loom daemon (…) with this build…"): `daemon.StopPID` of the daemon dialed (`dialDaemon` returns the pid from `Connect`'s record), then a connect that spawns this build. Unless `replaceGuard` refuses: from a `loom_*` or `claudesquad_*` tmux session on the daemon's own tmux server (compared cleaned, then through symlinks, `tmux.SameServer`), or on any server when the daemon named none, unless `LOOM_GLOBAL_DIR` is set; a session it can't name there counts as loom's. `LOOM_TMUX_SOCKET` and `LOOM_ALLOW_NESTED` don't bypass it: a loom built in a worktree and run in an agent's pane would otherwise stop the user's daemon. A loomdev sandbox still replaces its own daemon, whose server is the sandbox's. `refuseWhileServed` refuses `reset` and, through `cmd.StateWriteGuard` (which `main.go` sets, since `cmd` cannot import the daemon's packages), `workspace migrate` while any process holds the lock: both write `state.json` themselves, which the daemon would overwrite. **The root's `serve.go`** finds the tmux server (`TmuxServer`), runs the nesting guard on it (`nestingCheck(server)`) and logs its refusal to `serve.log` (a spawned daemon has no stderr; `Connect` quotes the log), pins the server, sends runtime crashes to `serve-crash.log` (`debug.SetCrashOutput`), turns signals into `Options.Stop`, and `loom serve stop` (`serveStopCmd`) waits up to 60s (`serveStopTimeout`). Tests: `internal/daemon` serves in process through the `spawn` seam (`spawnInProcess`), in `serve_test.go`, `connect_test.go` and `lifecycle_test.go` (`TestServe_StandsDownAtOnceForALiveDaemon`, `TestStop_ReturnsOnceItsProcessHasGone`, `TestTmuxServer_KeepsTheLastDaemonsServerWhileItRuns`, …); the root's `daemon_client_test.go` covers the join (`TestJoin_TheNewerSideWins`, `TestJoin_PinsTheDaemonsTmuxServer`, `TestReplaceGuard`, `TestHandshake_IsBounded`) and `main_test.go` the guard and pin of `serve` and `reset` (`TestServeCmd_GuardsTheServerItPins`, `TestResetCmd_SweepsTheServerADaemonWouldPin`); `e2e/daemon_test.go` runs real daemons (see Testing Patterns). Everything logs under `subsystem=serve`.
- **`session/`** — Core domain. `Instance` represents a running agent session with status lifecycle (Ready → Loading → Running → Paused). Its own API is lifecycle and state. Its tmux session is a lifecycle-only `tmux.Session` that never attaches a client (see the pane-client gotcha). Whatever lifecycle does to the agent's pane without a client lives on the `AgentPane` value returned by `Instance.Pane()` (`agent_pane.go`): liveness probes, the session name and the program the session was launched with (`SessionProgram`), typing text and prompts (`SendKeys`, `SendPrompt`: `load-buffer` + `paste-buffer`, see `session/tmux/`), pressing Enter (`TapEnter`: `send-keys`), and a capture-pane `Preview`. For example, `inst.Pane().SendPrompt(…)`. Rendering the pane and forwarding input through a PTY go through the TUI's client (`ui.Pane`, from `ui.PaneClients`). Its launch fields are set through `SetLaunchOptions`/`SetProgram`/`SetPrompt`/`SetCrashRecovered` and read through `Program()`/`HeadroomProxy()`/`CacheTTL1h()`/`Prompt()`/`CrashRecovered()`, never assigned directly — the accessors lock `i.mu`, so `session` code that already holds it reads the private fields instead (the lock is not reentrant). `storage.go` handles JSON serialization of the `instances` array in `state.json` and retains raw `InstanceData` for records that fail `ReconcileAndRestore` (the unrecovered cache) so a transient failure does not silently drop the entry on the next save. Records that fail to *decode* (corrupt, or a `schema_version` newer than this binary after a downgrade) are skipped by `MigrateAll`, held as raw bytes (`UndecodableCount`), and appended verbatim to every write — `SaveInstances`, `DeleteInstance`, `UpdateInstance` all go through `writeLocked`, which also loads first on a never-loaded `Storage`. A payload that is not a JSON array at all fails the load and latches every write shut (`ErrStorageLoadFailed`, state untouched) until a later load succeeds; `DeleteAllInstances` (`loom reset`) is the one write allowed through, and clears the latch. Both kinds of preserved record are claimed by worktree path (`PreservedWorktreePaths`) so orphan discovery doesn't offer them as `Recoverable`, and by title (`PreservedTitles`, folded in by `core`'s `claimTitles` at every sweep site) so the orphan tmux sweep and the hooks sweep spare their sessions, workspace-terminal auto-create doesn't kill and duplicate a preserved terminal, and a new session can't take a preserved title (`preservedTitleErr`); both are counted in the recovery summary. Unclaimed is not enough for the orphan tmux sweep (`CleanupOrphanedSessions`, `reconcile.go`) to kill a session: the tmux server is shared, so it also has to prove ownership. It reads each session's start directory (`#{session_path}`, the `-c` dir loom passes to `new-session`; unlike `pane_current_path` it ignores a later `cd` and survives the dir's deletion) and kills only when that directory, compared after `filepath.EvalSymlinks` and component-wise (`/a/repo` does not hold `/a/repo2`), lies inside an **owned** root of its `SweepScope` — each served workspace's repo root and `<configDir>/worktrees`, except a workspace whose load failed (`WorkspaceSweepRoots`; `NewSweepScope` builds it from the same workspaces `claimTitles` covers, in core's `sweepOrphans` at boot and in `loom reset`) — with no **foreign** root (every other registered workspace's, a failed one's included, and the global worktrees dir) nested deeper. It fails closed: an empty, relative or unplaceable directory is left alone (`orphan_tmux.skip_unowned`, debug). Kills are exact-name (`-t=`). `orphan.go` discovers worktree directories on disk not referenced in state.json and classifies them (`Disposition`): stale leftovers (dead tmux + clean) are auto-cleaned, ones with unsaved work or a live agent surface inline as `Recoverable` session entries. `reconcileOrphans` (`core/load.go`, run on every workspace load) drives this — there is no blocking recovery modal. Reconcile itself proves a live session is the record's before restoring onto it or killing it (`startedElsewhere`, by the record's `SessionHome`, `session/reconcile.go`): tmux names are per server, so a record whose name another workspace's session holds is marked Paused, and `HeldElsewhere` is the fail-closed check for a caller about to replace a session (see the `core/` bullet).

- **`session/tmux/`** — Tmux session management. `Session` (`session.go`) is a session as lifecycle sees it: `Start` launches without attaching and `Close` kills. It also covers liveness probes, capture-pane, `DismissTrustPrompt`, and input with no client: `TypeText`/`SendPrompt` send text through `load-buffer` + `paste-buffer -d -r` (raw bytes in one paste, with no length limit), never `send-keys -l`, which tmux refuses past about 16 KiB ("command too long") and which treats a trailing `;` as a command separator even after `--`; `PressKeys` sends key names through `send-keys`. `TestTypeTextMatchesPTYWrite_RealTmux` pins both against a write to an attach client's PTY, byte for byte, including the trailing-`;` and over-16-KiB cases. `TmuxSession` embeds a `Session` and is an attach client: `Close` detaches it and then kills the session, while `PausePreview` only detaches it, which is how the TUI releases a client. `NewAttachClient` (`attach.go`) builds an unattached client for a session it did not start, by name, which `Restore` then attaches. `NewTmuxSession` plus `Start` both launch and attach, and only the terminal pane's shells use that path. A started program's environment is the session's own (`-e`), plus the variables tmux's `update-environment` option lists (`SSH_AUTH_SOCK`, `DISPLAY`, …) as the starting process has them, plus the tmux server's global environment, which is that of whatever started the server (`Session.Start`): an agent's `update-environment` variables are the daemon's, the terminal pane's shells' the TUI's, and everything else (the credential overrides, the default account's `CLAUDE_CONFIG_DIR`, `PATH`) the server's. Prompt detection (`TmuxSession.DetectStatus`, `attach.go`) surfaces a `Prompting` status so the user knows an instance needs attention, and answers a trust prompt through `send-keys`. Also pumps `ptmx` output into an embedded VT emulator (`emulator_unix.go`/`emulator_windows.go`, gated by `LOOM_PANE_RENDERER`) so panes render from the emulator with a capture-pane fallback, and `ForwardMouse`/bracketed paste back interact mode. The pump writes through `vt.NewAltScreenFilter` before it reaches the emulator: tmux clients enter the alternate screen at attach and never leave it, and x/vt only accumulates scrollback on the primary screen, so the filter strips alt-screen mode switches (1047/1049/47) from the client stream to keep it on the primary screen where scrollback can accrue. `Restore` seeds pre-attach history once per attach (`capture-pane -S - -E -1`, stored as `SeedHistory`); `ui.ScrollModel` (one shared state machine used by both panes) windows seed + emulator scrollback + screen via `RenderWindow`/`ScrollbackLen`. `TmuxSession.stateMu` guards the `ptmx`/`monitor`/emulator fields against the race between the status scans off the Update goroutine (`statusDetectCmd`, `snapshotScan`; formerly the metadata fan-out) and the attach lifecycle. Prefix is `loom_`; `LegacyTmuxPrefix` (`claudesquad_`) is still recognized by the orphan sweep and the startup rename pass. The output pump also drives the event-based UI: a per-session coalescer (`notify.go`) emits dirty (≤ ~60/s), quiet (500ms settled), bell, and dead notifications through the package-level `tmux.SetNotifier` hook, which `app.Run` wires to `tea.Program.Send`. Status detection (`statusContent`) reads the emulator in-process; capture-pane remains only as the snapshot-path fallback.

Deferred `cs.actions.*` intents yield on their own, so a bare call already waits for the intent; `cs.await(cs.actions.X())` also works because the resumed action returns nil and `cs.await(nil)` returns at once. Exposed API: `cs.bind`/`cs.unbind`/`cs.register_action`, `cs.actions.*` (sync primitives + deferred intent factories), `cs.await`, `cs.log`, `cs.notify`, `cs.now`, `cs.sprintf`, plus userdata wrappers for `core.InstanceView` (the dispatch-time view: the host serves views, never the draft row), `git.GitWorktree` (built from the view), and a per-dispatch `ctx`. Lua changes instances only through the model: `inst:kill()`, `inst:pause()`, `inst:resume()`, `inst:send_prompt()` and `ctx:new_instance{}` enqueue an intent (`InstanceOpIntent`, `CreateInstanceIntent`) and yield until the request's `Reply` resumes them (`script.ResumeValue`, `Engine.ResumeWithHost`). On failure they raise (`scriptError`) a refusal's own message, which names the request (`"kill x: not allowed on a workspace terminal"`), or `"<op>: <err>"` for a failed job, a gone session and `ctx:new_instance`. On success the instance a lifecycle call acted on takes the session's view as the call left it (`Engine.luaValue`), so `inst:status()` after `inst:pause()` reads `Paused`; a killed one keeps its last view, marked `Deleting`. Because they yield, they refuse to run inside `pcall`/`xpcall`, a callback, a precondition or a coroutine the script made (`yieldable`), so a script can't catch their errors. `preview`, `send_keys` and `tap_enter` act on tmux by the view's session name (`tmux.NewSessionNamed`). The full API, errors included, is in `docs/specs/scripting.md`.

### Session Lifecycle

Statuses: `Ready` (initial), `Loading` (setup in progress), `Running` (agent active), `Paused` (worktree removed, branch preserved), `Recoverable` (an orphaned worktree found on disk, surfaced inline for recover/discard; never persisted).

1. **New**: User presses `n`/`N` → overlay collects title and optional prompt into the TUI's draft row (no instance exists yet) → confirming Launch Options sends `Create`, which builds the instance (status: Ready) and starts it at once (a script's `ctx:new_instance` leaves it unstarted)
2. **Start**: Creates git worktree + tmux session, records base commit → status: Loading → Running
3. **Running**: Agent works in isolated worktree; UI shows live terminal output + diff stats
4. **Pause**: Stashes uncommitted changes (`StashRef`), kills tmux session, removes worktree (branch preserved) → status: Paused
5. **Resume**: Rebuilds the worktree from the branch **only when it is absent or gutted** (no `.git`; leftovers moved aside), restores the stash, starts a new tmux session. An **intact** worktree is never rebuilt — the agent is relaunched in place with its recovery flag — and a live session is reattached (`session/resume_decision.go:decideResume`) → status: Running
6. **Kill**: Cleans up worktree, tmux session, and branch; instance removed from storage

The TUI starts each of these by a request to the model naming the instance's `InstanceID` (`core/requests.go`: `Create` with `Start` for steps 1–2, `Pause`, `Resume` or `ResumeWith`, `Kill`, `Recover`); the model starts the job doing the blocking work (`core/ops.go`) and applies its result (`core/completions.go`).

**Workspace Terminals**: A special instance type (`IsWorkspaceTerminal: true`) that runs directly in the root repo without a worktree. Cannot be paused/resumed. Diff tracking shows uncommitted changes in the root repo. It starts on a client's first open of its workspace (`Core.Open`, `ensureTerminal`), not when the model loads the workspace: until then it is dormant (not probed; a crash-restart deferred), and from then on it is relaunched on death under its restart breaker; a live one is always kept. A terminal its breaker stopped relaunches at the workspace's next first open, after the daemon restarts. A dead or Paused terminal whose tmux name another session holds (`session.HeldElsewhere`) is never relaunched over it: the other session keeps running and the terminal stays Paused; a check tmux leaves unanswered is retried by the health tick (`maybeSettleTerminals`).

### Gotchas

- **Instance data schema changes.** `session.InstanceData` has a `SchemaVersion` field and `session.CurrentSchemaVersion` constant. When adding/removing/renaming fields: bump `CurrentSchemaVersion`, add an upgrade step to the switch in `session/storage_migrate.go:Migrate`, and update the JSON fixture in `cmd/workspace_migrate_shape_test.go` (drift guard for the `workspace migrate` CLI's typed mirror struct). A record `Migrate` rejects is never fatal to the load and never dropped: `Storage` skips it and writes it back unchanged, so a downgraded loom leaves a newer binary's records intact for when it returns. Only a top-level payload that isn't an array fails the load. Then the model keeps the workspace served, empty and latched (`loadWS` records `Workspace.loadErr`, published as `WorkspaceView.LoadErr`, and `Storage` refuses writes with `ErrStorageLoadFailed`); the boot's orphan tmux sweep leaves its roots out of the owned set, its titles being unknown, so its sessions are spared whether or not any client keeps it open, while every other workspace is still swept; and every `Core.Open` of it rereads it from disk (`retryLoad`) and returns the error while it still fails. The TUI shows nothing of a workspace it could not open. Classic startup on one (`startHome`'s `Open`) exits with the error. A saved tab that fails to open at startup (`restoreSavedWorkspaces`) stays in the open list this TUI persists (`home.failedOpen`, appended by `openList`) and shows checked in the picker, labelled "(failed to load)", so later launches retry it, until it opens (`openTab`) or the user deselects it (`applyWorkspaceToggle`; the picker's footer says closing one drops it from the open list, so loom stops retrying it at start); global mode (`enterGlobalMode`, or `stayInGlobalMode` for a Global commit made from global mode, which rebuilds nothing) closes them all. When *every* restored tab fails, the classic slot shows the startup workspace instead, opening it with `Open`; if that fails too, the error is shown instead of exiting, the latch refuses every save (the daemon's stop skips the latched workspace: `core.Model.SaveForQuit`, `quitSkipsSave`), and `handleQuit` keeps the failed tabs in the open list for the next launch. Those skips are lossless because new sessions are refused while the focused storage `WritesRefused()` (`latchedStorageErr`), so a latched list stays empty. Don't add a write path that bypasses `Storage.writeLocked`; one already does — `loom workspace migrate` (`cmd/workspace_migrate.go`) decodes records into its own typed mirror and writes via `config.SaveStateTo`, so a newer-schema record passing through it loses every field this binary doesn't know.
- **`FromInstanceData` is decoupled from PTY attach.** It's a pure constructor — it does not spawn a tmux session. `inst.EnsureRunning()` only marks a restored instance whose session runs as started. Nothing in `session` attaches a PTY (see the pane-client gotcha).
- **Pane updates are event-driven, not polled.** With the emulator enabled there is NO preview tick: panes re-render on `paneDirtyMsg` from the output pump, status transitions ride `paneQuietMsg`, and the 3s health tick does liveness, pane-client prune and repair, diff stats and the background jobs, but scans no pane. The tick splits along the pane boundary, and since stage 1E along the loop too. The model's half (`core.Model.Tick`, `core/tick.go`) fires from the loop's own timer, favouring every client's selected row (each client's `SetSelected`, which the server merges into the model's selection set, `SetSelection`; the probe refreshes each one's full diff), and queues one probe job over every active instance of every served workspace, an unopened workspace's dormant terminal excepted (tmux liveness, parity, diff stats: `probeJob`), whose `HealthResult` `deliverHealth` applies (`applyLiveness` pauses the dead and relaunches a dead workspace terminal under its circuit breaker, `maxWorkspaceTerminalRestartFailures`; Claude's reported status is adopted; an instance a kill, pause or resume moved to Deleting or Loading while the probe ran fails `statusEligible` and is skipped entirely, liveness included), dispatches the gated jobs that are due (roster, hook scan, GitHub poll, usage probe, the Claude temp-dir sweeps workspace loads queued), and stats `accounts.json` for a change (`maybeReloadAccounts`). The TUI's half (the `tickUpdateMetadataMessage` case in `app/app.go`, on its own `tickUpdateMetadataCmd` at the same cadence, re-arming itself) expires toasts, prunes pane clients, runs the inline-attach backstop, runs the snapshot path's status scan (`snapshotScan` → `snapshotStatusMsg`) and the workbench scan; clients are repaired on `core.Alive`. The loop re-arms the model's tick when the probe's result lands, so ticks never overlap a probe still running; `core.HealthChecked`, emitted then, re-arms nothing in the TUI (it refreshes the workbench's diff tab). Pane events report to the model, by the ID of the row their session name resolves to (`viewBySession`): `paneDirtyMsg` calls `MarkOutput` (by session name: the dirty set the next probe takes to gate diff refreshes, `takeDirty`) and `PaneOutput`, `paneQuietMsg` calls `PaneQuiet` (both feed hook scans and the Prompting roster query), and `ptyDeadMsg` runs `VerifyDead`'s probe. The legacy 100ms preview tick and the 500ms health tick with its capture-pane status scan only survive under `LOOM_PANE_RENDERER=snapshot` (and Windows). When adding per-instance periodic work, put it on the health tick: the model's half when it needs no pane client, the TUI's when it does. When reacting to output, handle the pane event messages (defined in `app/events.go`, handled in `update`) — and never `Send` from the Update goroutine's own handlers (the pump/timer goroutines own that). Status derivation on this path must carry its own re-evaluation guarantee: quiet fires once per burst and the health tick runs no status ladder for emulator instances, so an inconclusive detection (`updated=true`, or a quiet dropped while `Loading`) re-arms via `maybeRedetect`/`redetectMsg` until a sample sees unchanged content — a rule that assumes "the next poll will correct it" silently latches (the old `updated→Running` latch; regression tests in `app/status_redetect_test.go`). The ladder (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path, and `paneDirtyMsg`'s Ready→Running promotion) is a **display overlay**: it never writes the model, only `m.ladder[id]` (`setLadder`: a status and since when), which `overlay()` shows in place of the model's status for an active row whose view has no reported status (`!StatusReported`), and `pruneLadder` drops once its row is gone, inactive or reported. Its gates read the row as shown, overlay included. So the model's status of a non-Claude session is its lifecycle status (Running once started), which is also the status `state.json` saves; Ready and Prompting from the ladder live only in the TUI. For Claude sessions this ladder is the **fallback** — see the Claude roster and Claude status gotchas below.
- **Session lifecycle never attaches a tmux client; the TUI's pane clients do.** `session.Instance` holds a `tmux.Session` (launch, probe, type text and keys, kill) and never a PTY. The TUI holds one attach client per live agent session in `ui.PaneClients` (`home.panes`), keyed by tmux session name, so two open workspaces sharing a title share one client. Every pane render, scroll, cursor, mouse event, paste and inline-attach key, and the status scrape too, goes through `m.panes.For(v)` (`ui.Pane`, for a view `v`); a Cmd takes the panes it reads resolved on Update (`statusDetectCmd`'s argument, `snapshotScan`'s targets). The TUI holds no instance, so it never calls a display method on anything an instance holds. A client is keyed by the view's `TmuxSession`, and its adapter (its trust-prompt and pending-prompt patterns) comes from the view's `SessionProgram` (`inst.Pane().SessionProgram()`), never `Program`: a resume that reattaches a live session (`R` with a new program) keeps the old `tmux.Session`, while `Program` already names the new program. Only an active row (`InstanceView.Active()`: started, not paused, not Loading, Deleting or Recoverable) gets a client. The attach points (`app/panes.go`) all run on Update: `ensureSlotPanes` at every workspace load; `replacePane` when a start, resume or recover lands in a loaded slot (the model's `core.Started`, `core.SessionLaunched` and `core.Recovered` events, a Lua `inst:resume()` included, since it is a model request too), and after a workspace terminal's auto-restart (`core.SessionLaunched`, from core's `applyLiveness`), because the old client was watching the session that was replaced; `ensurePane` for the repair after the health tick's probe and the Dead event's (`VerifyDead`), both on `core.Alive` (live session, client not attached, not during a full-screen attach: `attachingID`), a returning full-screen attach, and a reverted kill or pause (`core.Reactivated`, emitted when an `OpFailed` is delivered), whose client a tick may have pruned while it was Deleting or Loading. A client is usable only while `TmuxSession.Attached` holds (its PTY is open and the pump draining it has not hit EOF on its own; each pump owns its exit flag, set after its Dead notification returns, so a late old pump can't mark a newer attach dead), never by `PtmxAlive`, which stays true after that EOF and only says there is a handle to close: `Ensure`, `Alive` and `ui.Pane.Attached` go by it, so a client left on a session that died and was relaunched under its name (a workspace terminal another slot's client watched, say) is re-attached instead of showing "[exited]" forever. Every exit is a Dead event whose repair attaches again, so `Ensure` leaves a client whose pump exited on its own within `quickExitHoldoff` (1s) of attaching it to the health tick, warning once per burst (`pane.client_exited_after_attach`): an attach that exits at once while its session lives (tmux under a TERM it can't use) otherwise looped hundreds of times a second. Every loom session sets `detach-on-destroy on`: agent and terminal-pane sessions, through `Session.Start` and through `Restore` for a session an older loom launched. So under a global `off` an agent that exits during a full-screen attach drops the user back to loom, and a user's own terminal attached to a loom session detaches when that session dies. The setting exists for loom's own clients: under a global `off`, tmux switches a destroyed session's clients to another session instead of ending them, so a client keyed by the dead session's name would show, and take inline-attach keys for, another agent's pane, and never read EOF. A status scan of a pane with no client is no opinion: `statusDetectCmd` has no Cmd for it. Releases go through `prunePanes`, which `Retain`s the active rows' session names and hands every other client to `releaseClientsCmd`, and per open slot also detaches the terminal pane's clients of titles the slot has no live row for (`keepsTerminal`: started, not Paused, not Recoverable; `TerminalPane.DetachExcept`, never `Close`, which would kill the shell). The terminal pane starts a shell only for an active row (`ensureSessionLocked`, `ui/terminal.go`, gated on `InstanceView.Active()`), while `keepsTerminal` keeps a live shell on show for a Deleting or Loading row. A kill or pause ends the row's shell in its job while the row still reads Deleting or Loading, and a shell started in that window outlived the row, since the prune after it only detaches. Stage 2's extra hop (loop wake, server publish, client, TUI wake and drain) widened that window until a fast `D`, `y` hit it every time. A resumed, recovered or reverted row gets its shell with the refresh its completion triggers (`InstancesChanged`, `Recovered`). It runs on the health tick, on `core.ClientsStale` (emitted when a kill or pause completes, `KillResult`/`PauseResult`, and when an operation fails, `OpFailed`) and at every slot drop. Kill and pause do not close the client themselves, and have no TUI step: `Instance.Kill` and `Pause` end the agent's session and the terminal pane's shell (`CloseRelatedSession`, by name), which gives each pump EOF, and the prune the completion asks for (`ClientsStale`) releases both clients. The invariant: **a client is closed only after `Retain` or `Replace` has removed it from the registry.** That is why nothing re-attaches or double-closes a client while it closes (`Ensure` builds a new one): closing a still-registered client from a kill or pause job (the old TUI hook did) raced an `Ensure` or prune on the same name (a twin under a shared title, say), since `waitPumpExit` reads and writes `pumpDone` with no lock. A completion whose owner no open slot shows attaches nothing, since nothing displays it. A release runs `PausePreview` (detach, session left running) off Update, because it waits for the output pump, which blocks in `tea.Program.Send` until Update returns. On creack/pty the attach fd is blocking, so the read deadline `signalPumpStop` sets can't cut the pump's read short: closing a client of a still-live session waits the full 2s `pumpWaitTimeout`, while a dead session's client closes at once. `releaseClientsCmd` closes its clients in parallel, so N live clients cost about 2s, not N×2s. Full-screen attach (`startFullScreenAttachMsg`) still runs `PausePreview` on Update and pays the 2s there, a known stall that predates the split. Making the PTY pollable, so a release takes milliseconds, is a follow-up. This split is daemon stage 1A: a `loom serve` that attached its own clients would fight the TUI's over the window size.
- **Claude's roster outranks the pane scraper.** `session/claude_roster.go` shells out to `claude agents --json` (`rosterQueryJob`, `core/claude_status.go`, ~100ms on 2.1.280, a job off the model's goroutine) on its **own 3s cadence** — `maybeRosterQuery` throttles by `rosterInterval` and guards against overlap through its `pollGate` (`gateRoster`), because the health tick it rides fires every 500ms on the snapshot path and an unthrottled subprocess there would keep a `claude` process alive much of the time (and stack concurrent ones if the CLI hung). Every throttled background job (roster query, hook scan, GitHub poll, usage probe, accounts refresh, Claude temp-dir sweep) is gated this way (`core/gate.go`; intervals live in `gateIntervals`, keyed by kind, so even a zero-value `core.Model` is throttled): `dispatchGated` arms the gate only when its builder returns a `core.Job` (no job means no result to disarm it), and wraps the result in a `gatedResult` that `Deliver` disarms (`deliverGated`) **before** routing the inner result to its usual handler — so every delivery, errors included, re-arms the job and no handler touches in-flight state (a missed disarm would latch the job off for the session). A `request()` made while a dispatch is in flight dispatches the job once more after that flight lands (`redispatch`). A job returns one value, so nothing can hide a second result from the disarm: the old rule against a gated `tea.Batch`/`tea.Sequence` is gone. The split-ratio flush tick is not a gated job: the TUI dedupes it with a plain flag (`ratioTickArmed`). The query returns every live Claude session keyed by **cwd** — the roster covers ordinary interactive sessions, not just `claude --bg` ones, so Loom's own tmux-hosted agents appear in it. The model's `roster` field holds the result; `rosterStatusFor` joins on `Instance.GetWorktreePath()` and maps `busy`→`Running`, `waiting`→`Prompting`, `idle`→`Ready`. Only **interactive** entries are joined: background (`claude --bg`) sessions publish `state` where interactive ones publish `status`, and a `--bg` session started inside a worktree would otherwise collide with Loom's own tmux session and blind the join for an instance whose identity is not in doubt. An entry with no `kind` counts as interactive (older CLI builds omit the field). A roster answer is offered to each active Claude instance as it lands (`observeRoster`), stamped with the query's start time, and merges with hook observations under the newest-wins rule (next gotcha). Only the model writes a reported status: its health tick (`deliverHealth`) and `applyClaudeStatus` (hook scans, roster answers) both go through **`adoptClaudeStatus`** (`core/claude_status.go`), the single choke point that applies the status *and* records `Instance.WaitReason`; never re-implement that pairing at a call site. The TUI's status paths (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path) write no status at all: they read the row's `StatusReported` (the view's copy of whether the merged observation has an opinion) **before** the content ladder, and on a reported row leave the status to the model, so the ladder overlay never covers it. An authoritative answer also **suppresses `maybeRedetect`** — the ladder re-samples only because one content hash cannot separate "still working" from "just finished", and the roster says which it is. It **fails closed** in the same sense as `DetectClaudeRemoteControlAuth` — on any uncertainty it expresses *no opinion* rather than guessing, and the scraper ladder decides: non-Claude agents, an empty/failed query, no entry for the worktree, an ambiguous cwd (two *interactive* Claude sessions in one directory — deliberately dropped in `QueryClaudeRoster`, with a `session.roster.ambiguous_cwd` debug line), a cwd holding only background sessions, and unrecognized status strings all return `false` from `rosterStatusFor`. The Claude CLI is therefore never a hard dependency; a machine without it behaves exactly as before. A failed query **clears** the roster rather than retaining it — stale statuses are worse than none — and turns every roster-sourced observation into no opinion (`claudeState.rosterSilent`); a hook-sourced one stands. `RosterEntry.WaitingFor` (Claude's own reason for blocking: `"sandbox request"`, `"dialog open"`, `"input needed"`, `"goal proposal"`, …) rides through `adoptClaudeStatus` onto the transient `Instance.waitReason` and replaces the generic "awaiting input" phrase in `CardData.statusLabel`. It is treated as an **opaque string** — displayed verbatim and truncated, never mapped to a Loom enum — so a reason string this build has never seen renders fine instead of degrading to Unknown. It lives exactly as long as the roster-driven wait: any non-Prompting or non-authoritative outcome clears it, so a dismissed dialog cannot leave a label behind. Never serialized (absent from `InstanceData`, so it needs no `SchemaVersion` bump). - **Claude status: hooks and roster, newest observation wins.** Each Claude instance holds one merged observation (`session/claude_state.go`, `claudeState`, guarded by `Instance.mu`): hook events (`SessionStart`, `UserPromptSubmit`, `PermissionRequest`, `Notification`, `Stop`, `SessionEnd`) and roster answers are both offered to it, each stamped with when it was *observed* — a hook event's `At` from its file name (`hooks.eventTime`), a roster answer's `rosterResult.at` (`core/claude_status.go`) taken before the subprocess starts — and the newer one wins whichever source it came from. There is deliberately **no grace window**: a live probe (spec `docs/superpowers/specs/2026-09-23-claude-hook-events-design.md`, payloads in `session/hooks/testdata/probe-2.1.280/`) showed the roster moving 0–90ms *before* the hook's timestamp, so an answer stamped after an event already reflects it; stamping with the query's *start* is conservative, since an answer can reflect only a later moment, never an earlier one. The opt-in `TestRealClaude_HookStatusContract` asserts that ordering. Rules that are easy to break: only parent events (no `agent_id`) count, except `PermissionRequest`, whose prompt shows in the parent; `Stop` ends a *turn*, not the work — a `Stop` listing a running `subagent` task is Running, and teammate and `shell` tasks never count (idle teammates stay listed as running); only `SessionStart` sets the session ID (a failed `--resume` sends a `SessionEnd` carrying the unknown ID); a roster answer with no opinion voids a roster-sourced status but never a hook-sourced one; a same-status roster answer keeps the hook's more specific reason (`permission: Bash`). Delivery: `maybeHookScan` (`core/hook_scan.go`, `gateHookScan`, 250ms) runs on the health tick, on pane output (`core.Model.PaneOutput`) and, through `pollGate.request()` (which dispatches once more after an in-flight job lands), on pane quiet (`PaneQuiet`), when `Stop` and `PermissionRequest` arrive; a scan that changes a status applies it at once (`applyClaudeStatus`) and `request()`s a roster query to confirm it, which is what corrects a lead that resumes after a teammate reply with no event. Answering a prompt fires no hook, so output on a Prompting session queries the roster (`maybeRosterQuerySoon`, at most every `promptingRosterSpacing`). A reported status also exempts the session from `paneDirtyMsg`'s Ready→Running promotion. Without a working roster two gaps remain: an answered prompt stays Prompting until the next hook, and a lead resuming after a teammate reply shows Ready. A relaunch resumes the recorded conversation (`BuildResumeCommand`: `--resume <id>` when the ID is a UUID and its transcript exists, else `--continue`; Claude writes the transcript with the first message, so a session that never got one falls back), and a stopped session's card shows the end of Claude's last message (`ui.MessageTailLines`), valid from its `Stop` until the next prompt or permission request. App and core test instances start on a mock tmux session, so `Start` never prepares their hooks folder: like a restored instance they have no launch ID and adopt a scan's. - **Subagent rows come from hooks, not transcripts.** Transcripts can't tell you whether an agent is running (each content block is its own record, and `stop_reason` is missing from ~60% of responses), so Claude is launched with `--settings {ConfigDir}/hooks/<folder>/settings.json`, where `<folder>` is the path-escaped tmux session name (`hooksFolderName`: `url.PathEscape(tmux.ToLoomTmuxName(title))`, always a single path segment, so a `/` in a title can't nest one instance's folder inside another's, where launching, killing or sweeping the outer one would delete it), registering `SubagentStart`/`SubagentStop`/`TeammateIdle`/`Stop`/`SessionEnd` (plus the status events of the previous gotcha). Each hook writes a file to `events/`; `core.Model`'s `maybeHookScan` (`core/hook_scan.go`, via `gateHookScan`) collects them into `Instance`'s `subagent.Tracker` and `claudeState`. Rules that are easy to break: hooks are prepared **only on real launches** (`launchProgram(…, true)`: `Start(true)`, `startFreshWithRecovery`, `CrashRestart`, `Restart`), never on `Restore`, because a reattached Claude is still writing to its folder. `Restart()` (the workspace-terminal auto-restart) is a real launch too: it closes the dead session and rebuilds it as `Session.WithProgramEnv(launchProgram(program, true), env)` with a freshly resolved env — reusing the old object would relaunch its stale command (for a restored instance, the bare program: no hooks, no loom context) while the tracker kept the dead process's rows. Every real launch resets the previous launch's state first, even when hooks end up being skipped: `resetHookLaunch` (`session/subagent_hooks.go`) clears the tracker, warm flag, Claude status and last message (keeping the conversation ID the relaunch resumes), sets the launch ID to the `noHooksLaunchID` sentinel so no scan result matches, and removes the old hooks folder; a successful `Prepare` then sets the real launch ID. The folder lives outside `worktrees/` because `DiscoverOrphans` would walk it. Only the **parent's `Stop`** reconciles against `background_tasks` (a `SubagentStop` list can omit a parallel foreground agent), and a missing or malformed list must never be read as empty. Teammates can't be matched by ID in that list, so shutdown is inferred by count. Read events are kept as compact `.ev` files so a restarted loom replays them (`Request.Cold`); a restored instance adopts the folder's `launch-id`, and results for another launch ID are dropped. A scan returning `ErrNoHooks` for a launch with a real ID means its folder vanished mid-run, and `ForgetSubagentsWithoutHooks` drops its rows. Everything fails closed: an agent without its metadata sidecar is hidden. Windows, non-Claude programs, a user-supplied `--settings`, or a `'` in the config dir path launch without hooks (the folder name itself escapes `'`). `claude_subagent_tracking` only decides whether `Instance.Subagents` returns rows (stored inverted as `subagentRowsHidden`, so the zero value is enabled): every Claude launch that can take hooks gets them, because they also carry status, the conversation ID and the last message. - **The GitHub poller is roster-shaped and fails closed.** `maybeGHQuery` (`core/github.go`) rides the model's health tick on its own `ghInterval` (60s) cadence through the same `pollGate` as the roster (`gateGH`); the `ghAvailable` backoff below is a pre-check ahead of `dispatchGated`, and no opened repo means no dispatch, so nothing is armed. It polls only the repositories of **opened** workspaces (`openedRepos`: every workspace a client has opened since the model started, stage 3A; the model serves every registered one, and polling them all would spend `gh` calls on repos nobody looks at), each with its own workspace's base branch; an opened workspace with no repository (the global one) stands for the repositories its sessions run in (`Instance.Path`), against its own base branch, and with no session it polls nothing: it no longer stands for the directory loom started in, since the model runs in the daemon, whose working directory is the global dir. Last come the repositories a client asked for (`Core.WatchGitHub`, a cast: the issue picker asks for its repository on every open and again on every `GitHubChanged` while it stays open, which in global mode is the directory that TUI started in, and an `N` prompt's `#n` expansion for its draft's), against the global workspace's base branch, each polled for `ghWatchTTL` (15 minutes) after the last ask (`ghWatched` keeps each one's time; an expired one is dropped at the next ask), so a picker in use stays polled and a repository nobody asks about stops costing `gh` calls. An ask the poll has answered already (a snapshot or an error) renews the watch without polling at once. The workspaces with a repository of their own come first and the global workspace's after, deduplicated canonically (`canonicalDir`), so a global session in a registered repository is polled against that workspace's base branch, not the global config's. The poll job (`ghPollJob`) groups the paths it is asked for by their checkout's top level (`git.RepoRoot`, `git rev-parse --show-toplevel`, canonical; a path git can't place stands for itself), so a repository reached through a symlink or from a subdirectory is polled once, under its top level, against the first path's base branch, for the issues every path links. Its results (`ghState`, `ghErrs`, `ghBases`) are keyed by that canonical top level, and each path inside another's top level is recorded as an alias of it (`ghAliases`, published as `GitHubView.Aliases`); every lookup goes through `ghRepoKey` (the instance join, parity's base, `GitHubSnapshot`/`GitHubErr` on the model and the replica), so a session or a client reaching a repository by any spelling finds its state. Each poll resolves + fetches the base ref per opened repo (`git.FetchRef`, even without `gh`) and, when `gh` is available, runs `github.Query`; `ghState` is replaced wholesale, so an errored repo is dropped rather than kept — its cards render `Known=false` (nothing) rather than a stale badge, and `Known=true, HasPR=false` is a real "no PR", not "not yet checked". Results join onto `Instance.SetGitHubState` (transient; `viewOf` copies it into `InstanceView.GitHub` through `GitHubState()`, and `ui.BuildCardData` reads the view's); ahead/behind (`Instance.UpdateParity`, one local `rev-list`) rides the health tick's probe job (`probeJob`, `core/tick.go`) keyed on the model's `ghBases`. Call `core.Model.ExpediteGitHub()` to force the next tick to poll immediately (an in-flight poll still lands first) — a successful push (`core.Model.Push`, whose result `deliverPush` applies), an issue-born session (`handleIssuePicked`; `handleIssueExpanded` asks `WatchGitHub` for the draft's repository, which expedites too), the issue picker opening on a repo with no snapshot or error yet (through `WatchGitHub`), and a workspace's first open (`open`, behind `Core.Open`, expedites itself so the new repo is polled at the next tick; a later open does not) all do this. The TUI reads the poll through `GitHubSnapshot`/`GitHubErr`/`GitHubUnavailable` (answered from the client's replica of the `GitHubView`, which the model republishes whenever a poll lands), and `core.GitHubChanged` refreshes an open issue picker. GitHub state never sets `NeedsAttention`. `ghAvailable.ok` is a **one-way latch to true**: `maybeGHQuery`'s `req.check` is `!checked || !ok`, so once `CheckCLI` succeeds it is never re-run for the rest of the session — gh breaking mid-session (revoked token, network loss) surfaces only as per-repo query errors, never as an availability flip. An *unavailable* result is not latched the same way: it is re-probed every `ghRecheckInterval` (5 min) rather than forever, so a user who runs `gh auth login` after the daemon started recovers without restarting it. `ghPollRequest.configured` is a `map[string]string` keyed by repo path, built by `baseBranchByRepo()` from each opened workspace's own config, because every workspace has its own `config.json` (and the TUI's settings, `m.settings()`, are whichever slot is *focused*), not a shared primary — one string applied across the batch would resolve every non-focused repo against the wrong workspace's `BaseBranch`. `ghPollBudget` (45s) bounds the **entire** poll, not each repo: `github.Query` budgets each `gh` subprocess separately (2 list calls plus one `issue view` per linked closed issue), so without an overall ceiling one repo with many linked closed issues could stall every other workspace's refresh; it is deliberately kept under `ghInterval` so a poll can't outlive its own cadence. `UpdateParity` is called in `probeJob` **before** the `wantFull`/`ShouldRefreshDiff` early return — that gate exists to skip a git subprocess for an idle session with no tmux output, but the base branch moves with zero session activity, and "you are now N behind main" is exactly the case where `tmuxUpdated` is false. Both issue fetches are `core.Model.FetchIssue` requests (a `github.View` job) whose `Reply` carries the issue: the picker's pick and the `N` prompt's `#n` expansion record a `pendingIssue` holding an `issuePickedMsg` or `issueExpandedMsg`, which `handleReply` fills from the Reply and hands to `handleIssuePicked`/`handleIssueExpanded` (`app/state_issue_picker.go`). They can land up to ~20s after the user acted, into whatever is on screen by then; both handlers drop the result — with an explanation, not silently — when `msg.repo != m.repoPath()` (a different workspace is now focused) or `m.state != stateDefault` (another flow already owns the overlay and pending launch-options closure), because applying anyway would let `openLaunchOptionsForNew` silently replace it, stranding the other flow's draft. `handleIssueExpanded` also drops a result whose draft is no longer `m.draft` (a newer flow replaced it), and discards the draft whenever a guard fires (`issueExpandDropped`). `handleIssuePicked` returns on a fetch error before either guard; `handleIssueExpanded` degrades and continues on error (falls back to the literal, unlinked prompt), which is why its guards run **before** the `err != nil` branch instead of after.
- **x/vt callbacks run under the xvt wrapper's write lock.** `session/vt/xvt.go` registers `Callbacks` that fire inside `emu.Write`; they may only assign wrapper fields — re-locking `e.mu` deadlocks (RWMutex is not reentrant) and calling app code from them violates the no-model-mutation rule. New emulator-sourced state follows the same pattern: callback writes the field, a read-locked accessor exposes it. Events that must *notify* (not just store) follow the bell pattern: the callback sets a pending flag, and `Write`/`Resize` invoke the handler after releasing the lock — invoking under the lock deadlocked the whole UI once (bellFunc → `tea.Program.Send` blocks on the Update goroutine, which was blocked on `e.mu`; `TestBell_FiresOutsideWriteLock` pins this). One known vendored-library bug: the OSC-title parser truncates titles containing non-ASCII bytes (terminates on the lead byte of a multi-byte UTF-8 sequence) — `TmuxSession.PaneTitle` guards this by rejecting invalid UTF-8 rather than forwarding mangled bytes to the host terminal.
- **Paused does not mean the worktree is gone.** When an agent exits on its own (`/exit`, a crash), the model's health tick (`applyLiveness`, `core/tick.go`) only calls `TransitionTo(Paused)` (`tick.tmux_gone_marking_paused`): no stash, no removal, so the worktree still holds the only copy of any uncommitted work. The same state arrives via a failed `CrashRestart` and via adopting a dead-tmux `Recoverable` orphan (adoption sets `crashRecovered` but nothing restarts it, so the tick pauses it). Resume therefore classifies the path with `GitWorktree.InspectTree` and feeds it to the pure `decideResume`: dead + intact → relaunch in place (recording a missing base commit, `EnsureBaseCommit`), dead + gutted → rebuild (move-aside), `TreeUnverified` or an unanswered probe → refuse. Intact means `.git` present **and** `git rev-parse` (stdout only; paths compared with `os.SameFile`) reports the path as its own top level and as a *linked worktree of this repository* (`--git-common-dir` matches the repo's, `--git-dir` differs from it), not still locked `initializing` by an unfinished `worktree add`. The `.git` check is load-bearing: git in a gutted dir under `<repo>/.loom/worktrees` answers for the enclosing repo. The unverified refusal (`unverifiedTreeError`) tells a `git.IsTimeout` (retry) from a rejection (move the directory aside, with a shell-quoted `mv`; the next resume rebuilds), and `sameFile` reports a path it cannot stat as that error, never as the tree "belonging to" another repository. The move-aside advice works for a tree still locked `initializing` too: a `worktree add` killed mid-checkout leaves its registry entry locked, which makes `remove -f` refuse it, prune skip it and `worktree add` refuse the path ("a missing but locked worktree"), so `clearWorktreePath` first runs `git worktree unlock` — only when nothing live is provably left at the path (`nothingLiveAt`: absent, not a directory, or no `.git`; one that cannot be stat'ed counts as live), since a tree with its `.git` may hold work and its lock is what stops the single `-f` from deleting it. `worktree add` itself runs under its own long deadline (`gitWorktreeAddTimeout`, via `addWorktree`), not the 8s tick budget whose kill left that lock. `finishResume` closes the dead session object before starting its replacement and refuses when the probe gets no answer. Anything that reaches `gw.Setup()` runs `git worktree remove -f`, which silently deletes an intact dirty tree — never route an intact tree there. `CrashRestart` refuses a non-intact tree for the same reason, `startFreshWithRecovery` never cleans up on a failed start (its old `gw.Cleanup()` deleted the tree and the branch), and `Start(true)`'s failed-start cleanup (`failedStartCleanup` → `CleanupFailedStart`) deletes the branch only if `Setup` created it: a reused title checks out the branch an earlier session left behind. That cleanup runs only when nothing can be running in the tree: a name `tmux.Start` refused before launching (`tmux.ErrSessionExists`), or a session `SessionLiveness` confirms Dead, as Pause requires — any other failure may come after the agent launched (the existence poll reads unanswered probes as "not yet", and the cleanup `Close` can fail), so the tree and branch stay and the error says the agent may still be running. A pending `StashRef` in place (`restoreStashInPlace`): no longer in `git stash list` → forget it, never re-apply it, whatever the tree holds; clean tree → apply; tree already equals the stash (`StashOnDisk`, an interrupted pause) → forget it and drop the duplicate; dirty and different → refuse (naming the full SHA) until the user drops the entry. The rebuild path asks `StashListed` too, *before* `Setup`, and fails closed (nothing rebuilt) when the list can't be read — it used to apply a stash the user had dropped, by SHA, since the commit survives until gc. When Pause aborts because the session survived `Close`, it drops its own stash and saves the cleared reference: the tree still holds everything the stash captured. `refs/stash` is shared by every worktree of the repo, and `git stash drop` only takes a stash@{N} position, which shifts under concurrent sessions: `DropStash` checks the SHA git reports dropping, stores a wrong entry back (retrying a failed store once; after that its error names the commit and the `git stash store` that restores it), and retries, and `StashListed` fails, never answering "not listed", when the list can't be read. **None of this may end in the daemon's log** (`serve.log`): a forgotten stash may be the only copy of work, and a failed drop's error may be the only record of another session's entry. `ApplyStash` returns `git.ErrStashNotDropped` when the apply worked but the drop didn't (callers clear the reference and pass it on); a Resume or Kill that succeeded with something to report returns a `session.Notice` (`OnlyNotice` = the op succeeded; `NoticeIn` finds one inside a failure), naming the SHA plus `git stash apply <sha>` / `git fsck --unreachable | grep commit` for a forgotten stash. The model reports them as `core.Notice` events, which the TUI shows through `handleError` (`resumeOutcome` → `ResumeResult.Notice`, `KillResult.Notice`); a Lua `inst:resume()`/`inst:kill()` is a model request like the keys', so the model shows the notice the same way and the call returns without raising (its `Reply` carries the `Notice` too); Pause's abort includes a failed drop in its error. Tests: `session/resume_inplace_test.go`, `session/resume_decision_test.go`, `session/start_cleanup_test.go`, `session/stash_notice_test.go`, `session/git/worktree_inspect_test.go`, `session/git/worktree_hardening_test.go`, `session/git/stash_hardening_test.go`.
- **Only the deleting paths unlock a worktree.** `git worktree remove -f` refuses any locked tree, and an `add` killed mid-checkout leaves its tree locked `initializing` forever. `git.RefuseLocked` is called by orphan auto-clean (`RemoveOrphanWorktree`) and by `GitWorktree.Cleanup`/`Remove` (Kill, Pause). It removes that lock only once it is older than `gitWorktreeAddTimeout` plus a minute (loom kills its own add at that deadline). Any other lock, a user's or a young `initializing` one, gets a `*git.LockedError` (`errors.Is(err, git.ErrWorktreeLocked)`) naming `git worktree unlock`, returned before cleanup touches anything, branch and title sidecar included. Pause and Kill both check locks first (before Pause stashes, and before Kill closes the agent's tmux session or drops a stash), so a respected lock refuses either without killing the agent or leaving a pending stash, and a Kill a lock refuses keeps its row (`core.Kill` returns `OpFailed`) and shows the remedy, so D can be pressed again after the unlock. `reconcileOrphans` logs a locked orphan at debug and does not count it cleaned. `clearWorktreePath` (Setup, rebuild) deliberately keeps its own `nothingLiveAt` rule: an intact tree must never reach `remove -f`, and if one does, its lock is what stops it.
- **Claude's temp dirs are archived, not deleted, and found by physical path.** Claude keeps each session's scratchpad and task output under `<root>/<encoded cwd>/` (tmpfs on most Linux machines). Before loom archived it, that dir outlived every removed worktree. Pause archives it after the worktree is removed but before it marks the instance Paused (the status gate (`core.Model.Resume` only takes a Paused instance, plus the TUI's busy guards) keeps `r` off it, and `Resume` itself refuses while a Pause of the same worktree is in flight, which covers Lua `inst:resume()` and another client's request; the reverse holds too, and two of the same refuse each other, keyed by the canonical worktree path in `opsInFlight`). Kill archives it when nothing failed; a tmux session tmux confirms is already gone counts as closed (as in Pause), so killing an exited agent archives at once (a kill that fails leaves the dir for the sweep to take once the worktree is gone and the quiet period has passed). Both are best-effort. Resume restores `<name>.zip` before the agent launches, on the rebuild and relaunch-in-place paths only (a reattach launches nothing); a failed restore is a `Notice`, never a failed resume, and `Restore` creates a missing root (a reboot empties tmpfs). Lua `inst:pause()`/`inst:resume()` are model requests like the keys', so they archive and restore in the same jobs (the script waits for the Reply, not the engine's lock). Archives live in `<configDir>/archive/claude-tmp/` (dir 0700, files 0600) and are never pruned, unless the global `config.json`'s `claude_tmp_archive_dir` relocates them: `session.ClaudeTmpArchiveDir(configDir)` is the one place every archive, restore and sweep asks, re-reading the setting each time, and a resume also looks in the default folder so a zip parked before the setting changed is still restored. `<name>.zip` is the only file a resume restores; a Pause, Kill or sweep that finds one already there demotes it to `<name>.<UTC stamp>.zip`. Claude names the dir after its **physical** cwd, so `claudetmp.Names` encodes both the resolved path and the stored one, and `Locate` fails closed on zero or several matches and never matches a truncated name. `SweepClaudeTemp` is queued by `core`'s `reconcileOrphans` (`requestClaudeTmpSweep`, `core/claude_tmp.go`) on every workspace load (claim set snapshotted then; a workspace whose storage fails to load queues no sweep, since its claims are unknown) and dispatched by the model's health tick (`Model.Tick`) on `gateClaudeTmp`, one in flight; a dir that fails to archive is skipped until the daemon restarts, and the sweep reaps `.loom-trash-*` tombstones and `.loom-restore-*` restore staging dirs older than an hour and archive `*.partial` files (each archive writes its own, so a crash leaves one) older than a day. It takes a dir only when all of these hold: its name carries this config dir's encoded worktrees prefix and no other known config dir's (the encoding is lossy: `foo_bar` and `foo-bar` collide); it ends in a worktree timestamp and is not truncated; no record claims it; nothing in its top three levels changed in the last 24 hours (`sweepQuietPeriod`); and, rechecked just before archiving, no directory under the config dir's `worktrees*` dirs encodes to it. A live session's worktree exists before its Claude creates the dir, so a live session's dir fails that last check whenever its worktree is where the walk looks, and the walk fails closed at its depth limit; for the rest (a colliding workspace this loom doesn't know, an agent that outlived its Kill), the 24-hour quiet period is the backstop. - **Lua LState is not goroutine-safe.** All `script.Engine` dispatch runs under `engine.mu`; the Bubble Tea main loop invokes scripts via a `tea.Cmd` goroutine and awaits `scriptDoneMsg`. A script's lifecycle calls and `ctx:new_instance` are intents the `scriptHost` adapter queues; `handleScriptDone` turns them into model requests on the main goroutine (`handleScriptIntent` → `scriptInstanceOp`, `scriptCreate`), and each call's coroutine resumes when its `Reply` lands (`scriptReplied`, a `scriptResumeMsg`) — the host holds no `*home` and the userdata holds views, so nothing running inside the engine can reach `m.list` or an instance.
- **No model mutation from `tea.Cmd` goroutines.** Bubble Tea runs every returned `tea.Cmd` in its own goroutine, concurrent with `Update`/`View` — so a Cmd body must not mutate shared state, nor read unlocked model state (`m.list`, `m.splitPane`, `m.core`, …; the slot's fields resolve through the embedded focused slot, which `loadSlot` swaps). The TUI holds none of the model's objects to reach: `TestTUIHoldsNoModelObject` (`internal/testenv/instance_enforce_test.go`, grown from 1C's `TestTUIHoldsNoInstance`) fails on any production use in `app/`, `ui/` or `script/` of `session.Instance`, its constructors or its options, `session.Storage`, the launch toggles' setters, `core.Workspace`, `core.Model`, `core.New`, `core.Loop`, `core.Start` or `core.Job` (since stage 3B the TUI builds and runs no model: it holds a client of the daemon), `config.WorkspaceRegistry`/`LoadWorkspaceRegistry`, `config.AppState`/`State`/`LoadStateFrom` or `config.SaveConfigTo`, or `account.Registry` (under whatever name the file imports the package, with no exemption), and on the deleted bridges (`InstanceOf`, `IDFor`, `AdoptForScript`, `instOf`) anywhere; they read copies (`core.InstanceView`, `core.WorkspaceView`, …) and change the model only by request. `session.Storage`, `config.State`, and `tmux.TmuxSession` (its `ptmx`/`monitor`, via `stateMu` — snapshot under the lock, never hold it across PTY/subprocess I/O) each carry a mutex; `config.WorkspaceRegistry` does not, so its writes (`Add`, `UpdateLastUsed`, `SetOpenWorkspaces`) go through the model only (`core.Model.Register`, `SetLastUsed`, `PersistOpenList`), on Update — the startup registration prompt's Cmd returns `registerWorkspaceMsg` and Update calls `Register`. A `core.Job` follows the same rule as a Cmd body: it reads no model state. What it needs is captured on the model's goroutine when the job is built, as `saveSnapshot` (the instance list Pause and Resume save, `core/ops.go`) and `recoverInst` (the placeholder's record and config dir) do; the job only runs I/O and returns its result for `Deliver`. The model runs on a goroutine of its own (`core.Loop`) in the daemon's process, and `m.core` is a client that locks its own replica, so a call to `m.core` from a Cmd body would race neither. It would still read state no drain has applied, though, so the rule stands. Nothing on the loop's goroutine may wait on the TUI or call the loop (a call from inside a call deadlocks). The wire (stage 2) adds four rules. **Reads are local.** An `rpc:local` query reads the client's replica, never the model. The client's reader updates the replica as events arrive, so a job's result can land between two reads the TUI makes in one Update, as it could between two of 1E's serialized calls. So the TUI decides from its own cached stores (`slot.views`, `slot.info`, which change only at a drain), treats live queries (accounts, GitHub, the registry) as display data, and leaves the rest to the request, which re-validates (`admit`). Nothing may combine two live queries into one decision (the audit is in the 1E plan, B6). **Read-after-write holds because a request's events arrive before its reply.** The server publishes after the call and before it queues the reply. So the sites 1E kept (`syncViews`, `syncWorkspaces`, the drains right after a transition, the nested drain in `newLaunchOptionsOverlay`) see the request's effect with no extra round trip. A cast gives no such guarantee. **A cast must change no published state.** The server publishes nothing after one, so a change a cast made would reach the client only with some later publish. A method that changes published state is a request; `iface.go` states the rule. **A `time.Time` loses its monotonic reading on the wire.** It keeps its instant, but `reflect.DeepEqual` and `assert.Equal` compare the monotonic reading too, so a fixture compared with what came back through the client uses `time.Now().Round(0)` (`app/usage_test.go`). The model also keeps ticking and applying results while the TUI's event loop is blocked (a full-screen attach, `$EDITOR`, `claude auth login`); its events wait there, coalesced into one wake. The outbox has its own ordering rule: the model's events apply at the end of `Update` (`drainCore`), so a caller whose next steps depend on an event's effect drains right after the model call — the workspace transitions do (`openTab`, `enterGlobalMode`, `restoreSavedWorkspaces`, and `startHome`'s startup open), so an `Open`'s notices land before the recovery summary shown next, as they did when the load set them itself. `scriptHost` holds no `*home`: script nav/scroll/diff/workspace primitives record a `func(*home)` via `deferModelMutation`, drained into `scriptDoneMsg` and applied on the main goroutine in `handleScriptDone` (the ones that move the selection or the focused slot go through `deferFocusMutation` and apply only in `stateDefault`: the message can land after an awaited intent opened a flow), and reads (`ctx:selected()`, `ctx:instances()`, `ctx:config_dir()`, …) come from a snapshot `newScriptHost` takes on the Update goroutine when the dispatch or resume begins. The snapshot (views, minus the draft row) pins the focused slot, and `scriptDoneMsg.slot` carries it back: `handleScriptDone` sends a `ctx:new_instance` as a `Create` in that slot's workspace (`scriptCreate`) only if that slot is still focused, decided before the script's deferred actions run (one of them may be its own workspace switch); otherwise the call raises "new_instance: workspace changed while a script ran; not creating <title> here" (its deferred UI actions still apply to the new slot). Verify concurrent code with `go test -race` (see Build & Development Commands).

- **The focused workspace slot is embedded, not copied; a slot shows a workspace by `WorkspaceID`.** A slot (`workspaceSlot`, `app/workspaces.go`) is `{id, info, views, list, splitPane, workbench}`: the workspace's ID and its published view, plus the view state over it. The workspace's context, storage, config and app state belong to the model's `core.Workspace`; the slot reads the copies in its `core.WorkspaceView` (`info`, through `name()`, `label()`, `settings()`, `uiPrefs()`, `recovery()`, `m.repoPath()`, `m.configDir()`) and changes them only by request (`SaveSettings`, `SetUIPrefs`, `SetHelpScreensSeen`). Invariant (`checkSlotInvariant`, asserted in tests): every slot shows a workspace the model serves (`IsLoaded(slot.id)`); no slot appears in `m.slots` twice, and no two tabs show the same workspace (an open list naming one twice, or a name and its twin, restores one tab, and `failedOpen` holds a name once); with tabs open, `m.workspaceSlot == m.slots[m.focusedSlot]`; with none (classic/global mode) it is the classic slot, which is not in `m.slots` and shows the startup workspace, or the global workspace once `enterGlobalMode` has run (both global workspaces are the model's one `config.GlobalWorkspaceContext()` workspace, the nameless, repo-less context that resolves `LOOM_GLOBAL_DIR`, never `LOOM_HOME` — only a bare test home shows no workspace, `m.id == 0`); never nil. The transitions that leave the focused slot by another route (the first tab leaving classic mode, `openTab`; entering global mode, `enterGlobalMode`) run `leaveFocusedSlot` first, while the departing slot is still the one `m.*` writes its UI prefs through; `loadSlot`'s own teardown then finds nothing left (pinned by the `…FlushesPendingRatios…` tests in `app/workspace_slot_test.go`). - **Destructive actions target instances by `InstanceID`; async completions act on the workspace stamped at dispatch.** A kill, start, resume or recover runs for seconds with the UI live, and meanwhile the user can move the selection, switch workspace, close the owning tab or open another flow, and another client can act on the same instance. So two rules, with no exceptions: (a) **By identity, never by selection or list position.** The TUI names the instance a request acts on by its `InstanceID`, read from the row when the key's gate passed (a confirmation's task captures it then) and never re-resolved from the selection; the model never reuses an ID, so a stale one is refused (`ErrNoSession`) rather than landing on whatever took its place. A creation flow's session-to-be is the TUI's `draft` until `Create`, so cancelling one (`discardDraft`, from every cancel path, `discardPendingLaunchOptionsCancel` included) has nothing to kill. Inside the model, completions act on the `*session.Instance` they carry (`core/completions.go`): a failed start (a `StartResult` with an error) removes its instance from its owner's workspace and kills that instance (`killUnstarted`), a `KillResult` removes its instance from every served workspace through `removeEverywhere`, and an `OpFailed` reverts the instance it carries. Never reach for "the selected instance" or "the last row" in a completion, reply or cancel path. (b) **Stamped with the owning workspace, never "whatever is focused".** Each async completion carries the workspace it belongs to, stamped at dispatch (on the Update goroutine for the TUI's, on the model's goroutine for the model's): `scriptDoneMsg.slot` (the slot the script host snapshotted), the model's `core.StartResult.Owner` and `ResumeResult.Owner` (from `startOwner`, the served workspace holding the instance, not the focused one; the workspace the TUI passes is only the fallback) and `RecoverResult.Owner` (the workspace holding the placeholder, found by the `Recover` request's lookup). `KillResult` and `OpFailed` carry the instance and act on it wherever it is served (a pause saved inside its job, so `PauseResult` only asks for a prune). `handleScriptDone` creates a script's `ctx:new_instance` only in that slot, refusing it (the call raises) if focus has moved since. The model's completions (`deliverStart`, `deliverResume`, `deliverRecover`, …) resolve the owner (`owningWorkspace`), act on its instances and storage (`saveWS`; the owner is always served, since the model never drops a workspace), and report through events (`Started`, `Recovered`, `SessionLaunched`, …), stamped with the request that caused them (`Model.cause`), which the server routes (see the `core/rpc/` bullet). The model has no focus, so the focus rules live in the TUI's appliers (`app/completions.go`: `applyStarted`, `applyRecovered`), which act on the focus UI only for this client's own request (`Req` non-zero: another client's start or recovery only gets its pane attached). For its own, an owner that is the focused slot gets the row selected and inline attach (or, with another flow on screen, just "X started"), while a background owner gets the row selected in that slot's rail and "X started in Y", the focused slot's selection left alone (`applyStarted`). `applyRecovered` selects the row the same way, unless another flow is on screen in the focused slot, attaches nothing inline, and always confirms the recovery, naming a background owner. An N flow's initial prompt is sent by a job after the start lands (`sendInitialPrompt`), and `Started` is emitted only once that send returns (`deliverPromptSent`), so inline attach, which forwards keys to the agent, begins only after the prompt is in and no typed key can join it. The user can confirm a kill or pause during the send, so `applyStarted` enters inline attach only on a row still active (`InstanceView.Active()`, the test `replacePane` attaches a client by). A start or resume whose owner no open slot shows (its tab was closed meanwhile) attaches no pane client, since nothing displays it; its workspace stays served, so the instance is where it was when the tab reopens, with no copy of its record to reconcile against (the reopened-twin adoption is gone). And no completion moves the focused slot's selection unless `m.state == stateDefault`: creation flows, inline attach and the prompt overlay act on the selection, so moving it would retarget them (script primitives that move the selection or the focused slot apply through `deferFocusMutation` for the same reason). A job that needs the owner's storage captures it when the model builds it, from the workspace its request's lookup found (`killInst`, `pauseInst`, `saveSnapshot`); a kill or pause has no TUI step (see the pane-client gotcha). Reading `m.*` inside the goroutine races `loadSlot` and reaches the wrong workspace after a switch.

Titles differing only in those characters share a session name; the second `Start` fails with "already exists". A name that still holds one (made by an older loom, or another tool) cannot be targeted exactly at all (`-t=loom_feat:0` kills `loom_feat`), so the orphan sweep skips it (`tmux.ExactlyTargetable`, `orphan_tmux.skip_untargetable`). `TestNoRawTmuxExec` fails the build on any raw tmux exec outside `session/tmux/command.go` (whose `EnclosingSessionName` is the one deliberate exception).
- **Every git/gh exec goes through `internalexec.GitCommand`/`internalexec.GhCommand`** (`internal/exec/command.go`). `GitCommand(ctx, dir, args…)` adds `-C dir` (none for `""`) and forces **only git's message language** to C, because callers classify failures by matching git's **English** stderr (`isBranchAbsentErr`, `isWorktreeAbsentErr`, the `worktree unlock` answers in `unlockWorktree`) and parse its English output (`parseShortStat`'s "insertion"/"deletion"); a user's non-English locale would silently misclassify both. The env comes from `gitEnv`: it drops `LC_ALL` and `LANGUAGE`, re-pins every other `LC_*` category to the user's `LC_ALL` value when one was set (so their effective locale is unchanged), and appends `LC_MESSAGES=C` last — gettext and `strerror` translate from `LC_MESSAGES`, and gettext ignores `LANGUAGE` once it resolves to C. Not `LC_ALL=C`: `post-checkout` runs on every session create/resume under loom's git, and hooks such as Ruby's overcommit break under an ASCII `LC_CTYPE`. So git error text shown in the TUI is always English, while child processes git spawns (hooks, filters, textconv, credential helpers, gpg) keep the user's character set and collation; only their message language is forced to C. A caller needing extra env appends to `c.Env` (see `runGitCommandEnvTimeout`), never rebuilds it from `os.Environ()`. `GhCommand` sets `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`. Both only build the `*exec.Cmd` — run it through the injected `internalexec.Executor` wherever one is in scope. `TestNoRawGitGhExec` (`internal/exec/command_enforce_test.go`) fails the build on any raw `exec.Command`/`exec.CommandContext` of literal `"git"`/`"gh"` in production code outside `command.go`, resolving aliased and dot imports of `os/exec`; `_test.go` files are exempt.
- **The orphan sweep kills only sessions it can prove it owns; the nesting guard backs it up.** `CleanupOrphanedSessions` sees every session on the server it talks to, and "not in my lists" is no proof of an orphan: on 2026-09-23 a second loom's startup sweep killed all 20 loom sessions on a shared server, including the first loom's live agents in workspaces the second never loaded. So it kills an unclaimed `loom_*`/`claudesquad_*` session only when its start directory lies under a root this process owns (the ownership rule in the `session/` bullet); anything else is left running. One model per global dir serves every registered workspace (stage 3A; in the daemon since 3B), so it owns every registered workspace's roots and the global worktrees dir: the model sweeps once, at boot (`sweepOrphans`), with every served workspace's titles claimed, each workspace terminal's title included (a live terminal with no record waits for its workspace's first open, which replaces it). A workspace whose load failed is spared: its titles are unknown, so its roots are left out of the owned set (and, being registered, count as foreign), while every other workspace is still swept; before 3A one failed workspace skipped the whole sweep. Two global dirs that register the same repository both own its roots, so each one's boot could sweep the other's sessions there (rare; no guard yet). Reconcile has its own guard against the same hazard (`startedElsewhere`, see the `core/` bullet). `loom reset` uses the same rule with nothing claimed: it kills the reset workspace's sessions (default: global's), not every loom session on the server, since it deletes only that workspace's records and worktrees (`tmux.CleanupSessions`, the old kill-everything helper, is gone). The sweep returns a `SweepResult` (killed / unowned / untargetable / failed, logged every time as `orphan_tmux.sweep_done` at info) and an error for any listing failure other than "no server running" (`isNoTmuxServer`) and for every failed kill: some of the workspace's agents may still be running then, so `reset` stops before deleting worktrees and branches under them (`TestResetCmd_StopsBeforeWorktreesWhenSweepFails`); the boot's sweep only logs it. `ensureTerminal`'s relaunch of a dead or Paused terminal asks `session.HeldElsewhere` first and leaves a session it can't prove the terminal's own running (see the `core/` bullet), and its pre-start kill of a leftover session under the workspace terminal's title, at the workspace's first open, goes through the sweep's own test (`session.KillOwnedTmuxSession`): the title is just the workspace's name, which another loom's workspace elsewhere can share, so a session not started in this workspace's roots — or any listing that fails — is left running, and the terminal's `Start` then fails on the name instead. The rule does not stop a nested dev daemon that serves the *same* workspaces as its host (with one global dir, every registered one) from sweeping the host's sessions. The process that sweeps is the daemon, so the nesting guard (`nestingCheck`, `tmux.CheckNestingFromEnv`) runs in `loom serve` (root `serve.go`) and in `reset`, each decided on the tmux server it is about to pin (`daemon.TmuxServer`: the last daemon's while that server runs, else this environment's): it refuses inside a `loom_*`/`claudesquad_*` session on that server (`$TMUX`'s first field, compared with `tmux.SameServer`), unless `LOOM_ALLOW_NESTED=1`; a session it can't name on that server (tmux timing out under load) counts as loom's, as in `replaceGuard`. `LOOM_TMUX_SOCKET` gets no one past it: the pin ignores it while the last daemon's server runs, so a dev loom in a loom pane with a private socket set, while the user's daemon is down, used to start the user's daemon on the user's server. A loomdev sandbox passes because its global dir is its own, and with it its server. `reset` pins that server before its sweep too, so run after a `loom serve stop` from another environment it sweeps the daemon's server rather than find nothing there and delete the worktrees under live agents. A daemon spawned on demand has no stderr, so it logs the refusal to `serve.log` and `daemon.Connect` quotes it to the TUI that spawned it. The TUI itself runs no nesting guard: in a loom pane it is a client of its global dir's daemon, so a dev build run there joins the user's own daemon (or is refused by a newer one), and replacing an older one is `replaceGuard`'s to refuse (see the `internal/daemon/` bullet), which neither `LOOM_TMUX_SOCKET` nor `LOOM_ALLOW_NESTED` gets past. Never run a bare `loom serve stop` in a loom pane either: it stops the host's daemon, and every TUI on it quits. Run dev builds through `tools/loomdev` (its own global dir, daemon and tmux server), never directly in a pane. The guards only recognize loom-managed enclosing sessions (`loom_*`/`claudesquad_*`); a dev loom started from a non-loom tmux session (e.g. a plain shell pane) on a server that also hosts loom sessions is not refused, so use `loomdev` there too.
- **One daemon per global dir; every TUI is its client.** Two processes writing one workspace's sessions overwrite each other: `Storage.SaveInstances` rewrites a workspace's whole list from the writer's own memory, so each one's saves drop the records only the other knows, and the dropped ones come back as `Recoverable` orphans that have lost their launch flags, conversation ID and (when dead) account. So one process, the daemon (`loom serve`, since stage 3B), owns the model and writes `state.json`, holding the flock on `<globalDir>/loom.lock` for its whole life (see the `internal/daemon/` bullet), and any number of TUIs connect to it at once over its socket. Each TUI attaches its own pane clients to the sessions it shows, and tmux sizes a window to its most recently active client. The open list, the last-used workspace and the UI prefs are shared registry and state values: the last TUI to write one wins. **Lifetime**: the first `loom` that finds no daemon spawns one, detached, and it outlives every TUI until SIGTERM, SIGINT, SIGHUP or `loom serve stop`. The first signal stops it gracefully (it stops accepting, waits for foreground jobs, `Loop.Quiesce`, so a pause mid-stash finishes, then saves every workspace); a Ctrl-C meanwhile exits at once, without saving, and a second SIGTERM is only logged. Sessions are tmux's and keep running through any stop, and the next daemon reattaches them at its boot. A model failure (`Server.Fatal()`) makes it exit without saving, and the next `loom` spawns a fresh one. **Saves are the daemon's**: on requests, after the changes it makes on its own (`saveUnprompted`), and at its stop. A TUI's quit saves no session (`handleQuit` writes only its own state: the split ratios and the open list), so no workspace that won't save can hold a quit. **When the daemon goes** (a crash, `loom serve stop`, a newer loom replacing it), every TUI restores the terminal and exits with "loom: the daemon stopped (see <serve.log>); your sessions keep running. Run loom again." (`app.ErrDaemonGone`, see Core Flow); live reconnect is a later stage. **The newer build wins** at every join (`daemonLink.join`, `rpc.CompareBuilds`): a newer daemon refuses an older TUI ("upgrade loom, or run `loom serve stop`"), and a newer TUI stops an older daemon and starts its own build, so a TUI still open on the replaced daemon exits as above; a loom inside loom never replaces it (`replaceGuard`). **The environment is frozen at spawn**: the daemon keeps the environment of the `loom` that spawned it, so a TUI started later from another terminal or SSH session changes nothing the model reads from it (see Environment Variables): the tmux server (pinned, and kept from the last daemon while that server runs), the credential override and `$CLAUDE_CONFIG_DIR` its warnings read (see the credential gotcha), Claude's temp root, `LOOM_PANE_RENDERER` for the model's tick, and the `update-environment` variables every agent gets at `new-session` (`SSH_AUTH_SOCK`, `DISPLAY`, …). The rest of an agent's environment (`ANTHROPIC_*`, the default account's `CLAUDE_CONFIG_DIR`, `PATH`) is the tmux server's global environment, the daemon's only when the daemon started that server. What a TUI starts itself keeps the TUI's environment: the terminal pane's shells (their `update-environment` variables), a relative or `~` `ctx:new_instance` path, and a login from the Accounts screen. To pick up a new environment, `loom serve stop`, then start loom from it (and, on a tmux server the daemon did not start, change that server's environment too). **What else meets the lock**: a loom from before the daemon (0.13) took the same file for its takeover lock, so the two exclude each other: `Connect` and `Serve` refuse while such a TUI's pid lives ("quit it first"), and ignore a record one left behind. `reset` and `workspace migrate` refuse while any process holds the lock (`refuseWhileServed`), since they write `state.json` themselves. The other CLI subcommands take no lock: `loom account` and `loom workspace add` write registries the daemon rereads (`accounts.json` when its stat changes, the workspace registry on `ReloadRegistry`). Never remove `loom.lock`: a contender waiting on the old inode and a new holder on a recreated one would both "hold" it. loomdev sandboxes have their own global dir, so their own daemon. The takeover lock (`internal/takeover`, its `Take over? [y/N]` prompt and `loom.sock`) is gone.
- **Claude accounts are config dirs, linked, and resolved at launch.** An extra account's dir symlinks every top-level entry of the main config dir except a deny-list (`.credentials.json*`, `.claude.json*`, `sessions`, `daemon`, `daemon.log`, `session-env`, `ide`, `debug`, `cache`, `backups`, `shell-snapshots`, `statsig`, `jobs`, `stats-cache.json`, `.last-cleanup`, and each session's own `security_warnings_state_<uuid>.json`), so `projects/` (transcripts, auto-memory) is shared and `--resume` works across accounts. `Create` also seeds the main dir's own `projects/` (only when the main dir already exists) before linking, since Claude only creates it lazily on a config dir's first session — without this, the very first account made on a fresh install would never get it linked, and cross-account `--resume` would have nothing to share. `Sync` never replaces a real file: a link turned into a file (an atomic rewrite through it) is reported as diverged, since it may hold the only copy of a change. `Remove` and `Unshared` act only on `OwnedDir`'s return value — `filepath.Join(AccountsDir, name)`, recomputed from the account's name — never on the registry's raw stored `Dir`: a stored value like `<AccountsDir>/lnk/../name` can clean lexically to the canonical path while a symlinked `lnk` makes the kernel resolve it somewhere else entirely first, and acting on the raw string there deleted real content outside the account's own dir before `OwnedDir` was fixed to return the canonical path itself. A dir the account doesn't own that way is unregistered but left on disk. Without `force` `Remove` refuses (`*UnsharedError`) while the account dir holds real, non-symlink entries `Unshared` finds that aren't shared with the main dir, since those may be the only copy of a change; `os.RemoveAll` on an owned dir deletes the links themselves without following them. `LoadRegistry` goes further and refuses to *load* any account whose stored `Dir` is not in `filepath.Clean` form or does not resolve (`resolvedOrClean`: `EvalSymlinks` on the raw path first, so a `lnk/..` can't be cancelled lexically) to `<AccountsDir>/<name>`, then canonicalizes every loaded `Dir` in memory to `filepath.Join(AccountsDir, name)` (`canonicalizeDirs`), so a respelled global dir still loads but the stored spelling never reaches a launch, Sync or `Remove` — a hand-edited "bring your own directory" entry is out of scope entirely, since that same stored `Dir` is what gets launched as `CLAUDE_CONFIG_DIR` on every launch, so catching it only at removal time was never enough. The model reloads the registry (`ReloadAccounts`) before every user action that reads it and on its own cadence otherwise (see the reload-then-diff gotcha below), and `LoadRegistry` validates every loaded entry — an invalid or duplicate name, a non-absolute dir, or a dir that isn't `<AccountsDir>/<name>`, zeroes the loaded list and latches every write shut (`ErrRegistryLoadFailed`), the same as a file that fails to parse. Instances store the account *name* (`InstanceData.Account`, schema v8, "" = default); every real launch resolves it through the map the model publishes with `session.SetAccountDirs` (`publishAccounts`, `core/accounts.go`) and fails closed rather than falling back to default, which would bill the wrong subscription: `*MissingAccountError` for a name the registry no longer has, `*AccountDirMissingError` when the account is still registered but its dir has vanished from disk (the CLI would otherwise silently start a fresh, logged-out identity there instead), and `*RegistryLoadError` when the registry itself won't load — `SetAccountDirs` carries that error alongside the dirs map so it is never reported as "account removed". Both of the first two name their own fix in their message text rather than leaving the user to guess: `MissingAccountError` points at R on the existing session (pick another account there), `AccountDirMissingError` at `loom account remove` then adding the name again. Every account-scoped `claude` subprocess that captures output — `AuthStatus`, `ProbeUsage`, the roster query (`session.QueryClaudeRosterEnv`) — goes through `account.Command`, which refuses a missing `CLAUDE_CONFIG_DIR` up front (`ErrAccountDirMissing`) rather than let the CLI recreate it empty and logged out. `LoginCmd` does *not*: it hands back a bare interactive `*exec.Cmd` for `tea.ExecProcess`/the CLI's own foreground `Run()`, not a captured `Output()` call `Command`'s dir check could gate — so both callers (`cmd/account.go`'s and `app/accounts.go`'s `accountLoginCmd`) `os.Stat` the account's dir themselves first and refuse with the same advice (remove, then add again) rather than let `claude auth login` bootstrap a bare, unlinked identity there. `claude auth login` stores the credentials and `oauthAccount` but leaves `.claude.json`'s `hasCompletedOnboarding` unset, and the interactive CLI runs its onboarding (login screen included) whenever that flag is missing, so the first session on an account logged in from the CLI asked to log in again: every launch on an account (`launchEnv(true)`) therefore calls `account.EnsureOnboarded`, which sets the flag only for a logged-in account (`oauthAccount` or `.credentials.json`), keeps every other key, and never rewrites a file it can't parse; a failure is logged, not fatal. The Account row, and `CLAUDE_CONFIG_DIR` with it, is Claude-only — only Claude programs get it (`LaunchEnv`/`ClaudeConfigDirEnv`), so a wrapper program's sessions always run on the default account, and so does the terminal pane's shell regardless of the agent's account. The roster is per config dir (`claude agents --json` under an empty dir returns `[]`), so `rosterQueryJob` runs one query per account in use and `rosterStatusFor` joins `rosterByAccount[inst.Account()]` (the default account's stays in the model's `roster`); one account's failed query clears only its own entries. Remote-control auth is per account too (`core.Model.RCAuthFor`; an extra account not read yet is Unknown: no flag). Usage comes from `account.ProbeUsage`, a headless `claude -p` stream-json run answering the SDK's **experimental** `get_usage` control request (`skip_behaviors`, `--setting-sources ""`, `--strict-mcp-config`, no model call, ~1.4s observed), polled every 2 min on `gateUsage` and expedited when a picker opens; `TestRealClaude_UsageProbe` (opt-in, free) pins its shape. Usage is display-only: a failed probe keeps the last sample, dimmed with its age — the opposite of the roster's "stale is worse than none", because nothing acts on it. All account UI (strip, Launch Options row, badges) and polling stay off until an extra account exists; the strip's row goes through `topChromeHeight`, never `tabBar.Height()` directly. Three account-selection gaps stay open by design: `R` on a Paused session whose tmux session is still alive reattaches to it (`decideResume` → `resumeReattach`) on its old account even after picking another — reattaching launches nothing, so `Instance.Resume` skips the account resolution that would otherwise fail closed; an orphan recovered from disk (`r` on a `Recoverable` entry) whose tmux session is dead comes back on the default account, since nothing on disk records which one it ran on (a *live* one keeps its account: discovery reads the session's `CLAUDE_CONFIG_DIR` back with `tmux show-environment` and maps it through the registry, `liveSessionAccount`); and `remove --force` on an account a live session still uses can lose the race with that session's own Claude process, which can recreate a bare, unlinked dir there right after the delete — a later `add` of the same name then fails ("already exists") until the leftover dir is cleared by hand.
- **A credential in the daemon's environment silently overrides every account, and loom can end up running as one itself.** `account.CredentialOverrides` lists `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` — the same env vars the Claude CLI checks *before* ever reading a config dir's own stored credentials — and `ActiveCredentialOverride` returns the first one set in its own process's environment. The process that counts is the daemon, whose environment was frozen when it was spawned (see the one-daemon gotcha): the model reads it (`Core.CredentialOverride`, a local query answered from `AccountsView.CredentialOverride`), its usage probes and auth reads inherit it, and every client warns by it, never by its own environment. With one set, every account session runs and bills as that credential regardless of which `CLAUDE_CONFIG_DIR` loom launches it with, so switching accounts is a no-op the UI can't hide: the strip leads with "`⚠ $VAR set: all accounts use it`" (`ui.AccountStrip.SetWarning`/`credentialOverrideWarning`), the Accounts screen shows the same text as a screen-wide notice above its rows while an extra account exists (`SettingsOverlay.SetAccountNotice` → `AccountsManager.SetNotice`; hidden with only `default`, since there is no choice for it to void), and `loom account add`/`login`/`list` each print the same warning, from their own environment (`use`/`sync` don't, since neither runs a session). Agents don't take these variables from the daemon, though: they inherit `ANTHROPIC_*`, and the default account's `CLAUDE_CONFIG_DIR`, from the tmux server's global environment, which is the daemon's only when the daemon started that server. A daemon reusing the user's own tmux server, or the previous daemon's (`daemon.TmuxServer`), gives its agents that server's environment, while the warning reflects the daemon's. `extraAccountAuth` leaves an override-caused remote-control block's reason untouched — no login would fix it — rather than composing the "run `loom account login <name>`, or Settings → Accounts → l" hint it otherwise attaches to every other blocked reason. Separately, `noteRunningAsAccount` checks at boot whether the model's own `$CLAUDE_CONFIG_DIR` (the daemon's: a daemon spawned from an account's agent pane, say) already resolves inside its own accounts dir, and if so records a warning that "default" is actually that account's login, usage and sessions, not the main login's. It holds for the model's whole life, so it is published state (`Core.RunningAsAccount`, `AccountsView.RunningAsAccount`) that every client shows, not a notice only the first client to connect would see.
- **`loom account`'s CLI guards against unsafe or stale state before it touches anything.** `remove`'s `--yes`/`-y` skips only the confirmation prompt; `--force` is the one flag that overrides the in-use and unshared-files refusals, and reports what it overrode — `--force` alone still asks to confirm, so it can't be one accidental keystroke away from deleting a session's only account. The unshared-files check runs (and, if it refuses, reports) *before* the confirmation prompt, so the user is never asked to confirm a removal that then turns out to be refused; the prompt itself reads "delete `<dir>`" only when `Registry.OwnedDir` says loom owns that config dir, else that the dir isn't loom's and will be left in place. `account.ValidateMainDir` (absolute, symlink-resolved, neither inside nor containing the accounts dir) gates `add`, `sync` and `Registry.Create` before any linking starts — the TUI's account-add path runs through `Create` and so is covered too; its background refresh (`accountsRefreshJob`, `core/accounts.go`) applies the same guard through `syncMainDir` before re-syncing an existing account, skipping the Sync (and logging the refusal once, not on every tick) rather than linking from an unsafe dir. `login` (both the CLI and the Settings screen) refuses a registered account whose config dir has gone missing from disk, rather than let the CLI recreate it there bare and logged out, and says to `remove` then `add` it again instead. The CLI's own login (`runWithChildSignals`) catches SIGINT with `signal.Notify`/`signal.Stop` around the child rather than `signal.Ignore`: an ignored disposition is `SIG_IGN` at the OS level and survives `exec` into the login child, so Ctrl-C during `claude auth login` would reach neither loom nor claude (verified against a real child's `/proc/self/status` `SigIgn` mask); `signal.Notify` resets to the default disposition across `exec` instead, so the child gets an ordinary, interruptible SIGINT. `list` probes every account in parallel (one goroutine per row) and, when no main config dir can be found, skips the default account's usage probe with a "no main config dir found" note rather than run it in whatever directory `list` happens to be invoked from (`ProbeUsage`'s cwd becomes a project entry in Claude's own config). Run from a shell whose own `CLAUDE_CONFIG_DIR` already resolves inside `<AccountsDir>/<name>` — an account's own agent pane, say — `add`, `list`, `sync` and a bare `login` (or `login default`) all refuse (`guardAgainstAccountEnv`/`accountFromEnv`): treating that inherited env as "the default account" would silently log the wrong identity in as default, or list/sync it as the main login. `use`, `remove` and a named `login <account>` are unaffected, since they already read that account's own `CLAUDE_CONFIG_DIR` override rather than the inherited one. `cmd` deliberately does not import `session` — `session/tmux` imports back into `cmd`'s own tests, which would cycle — so `isClaudeProgram` asks `session/agent`'s adapter registry directly instead of `session.IsClaudeProgram`. `cmd`'s `claudeProgram()` reads the Claude binary from `config.GetGlobalConfigDir()`'s `config.json`, matching the TUI's global context (`config.GlobalWorkspaceContext()`) rather than `LOOM_HOME`'s, since `loom account` manages one registry shared across every workspace. `add`, `login` and `list` each print a warning (`warnCredentialOverride`) when a credential env var already overrides every account (see the account-selection gotcha above); `use` and `sync` don't, since neither runs a session.
- **Account state is reload-then-diff, not polled.** The registry, auth, sync, usage and the reload logic live in the model (`core/accounts.go`, `core/usage.go`); the views (strip, Accounts screen, Launch Options row) stay in `app/accounts.go`, and `core.AccountsChanged` refreshes them (`refreshAccountViews`). The model publishes it whenever its `AccountsView` changes and after every usage probe round, so a sample's age re-renders, and the TUI's account queries answer from the client's replica of that view. `accounts.json` isn't reread on a fixed schedule: `maybeReloadAccounts` rides the model's health tick and only stats the file, reloading (`core.Model.ReloadAccounts`) when its size or mtime moved; every user-paced action that reads the registry — opening Launch Options, opening Settings, an Accounts-screen request — calls `ReloadAccounts` first regardless of the stat. `accountsChanged` then compares a signature (the default, every `name=dir`, and the load error) against what was last seen (`noteAccountsState`, also called after this process's own writes so they don't read back as a change): a no-op reload touches no view, and a load error is reported once, when it first appears, not on every later tick that is still failing. Auth is re-read (`RequestAccountsRefresh`/`gateAccountsRefresh`, `accountsRefreshJob`) in three cases: a reload finds an account with no auth entry yet (added by another `loom account` or loom process), the default account's identity is still unknown while an extra account exists, or a usage probe finds an account that had plan access losing it (`lostAccess`) — the last is how "logged out" reaches the strip and Accounts screen between reloads, since an expired login probes the same as API-key auth (`Usage.Available=false`) until `claude auth status` actually re-runs. Launch Options shows a notice (`SetAccountNotice`) before the user confirms whenever the account it preselected no longer exists (a resumed session whose account was removed) or a live refresh removes the account currently selected in the row, both naming the account the session will actually run on. The Accounts screen's own remove refusal for unshared content points at `loom account remove --force <name>` as the way out (the screen has no force of its own); its in-use count (the model's `accountUsers`) counts each loaded workspace's live instances directly and falls back to reading `state.json` only for config dirs no loaded workspace covers, so a session visible in the list is never counted twice.
- **`handleMenuHighlighting`'s deferred-replay flag needs every full-screen modal state on its exclusion list.** It defers a keypress matching a registered global binding (`a`, `t`, `d`, `n`, …) to a later Update cycle via an async replay `tea.Cmd`, tracked by a single `m.keySent` flag that assumes the very next `KeyPressMsg` to arrive is always that replay. A modal state missing from the exclusion list lets fast typing (or a paste) into one of its own text fields collide with that mechanism and reorder a character — "toy" typed quickly rendered "oyt" — because the next keystroke steals the flag and the delayed one replays later, wherever the cursor has since moved to. `stateSettings` was missing from it until 2026-09-25 (typing into Default Program, Base Branch, a Profile name or an Account name could scramble); every new full-screen modal state must be added alongside `statePrompt`/`stateNew`/`stateLaunchOptions`/etc. in that same check, or it inherits this bug silently. Regression test: `app/menu_highlighting_settings_test.go`.
- **Every full-screen modal state that draws through `m.activeOverlay` must also be in `View()`'s overlay placement list.** `View` (`app/app.go`) places the active overlay over the screen only for the states its `switch m.state` names (`statePrompt`, `stateHelp`, `stateConfirm`, `stateWorkspace`, `stateSettings`, `stateMergePicker`, `stateLaunchOptions`, `stateIssuePicker`). A state missing from it still takes its keys, but nothing draws it: `stateIssuePicker` was left out when the picker came in, so `I` opened an invisible picker until 2026-10-08. A new modal state goes in this list and in `handleMenuHighlighting`'s exclusion list (previous gotcha). Regression test: `TestView_DrawsTheIssuePicker` (`app/state_issue_picker_test.go`).

### Persistent State

All stored in `~/.loom/`:
- `config.json` — user configuration, written only by the model (`core.Model.SaveSettings`; the settings overlay edits a copy): `DefaultProgram`, `BranchPrefix` (default: `{username}/`; overridable per session via the Session Launch Options modal — see `launch.Options.BranchPrefix` → `Instance.SetBranchPrefix` → `git.WorktreeSpec.BranchPrefix`, an ephemeral override that is never persisted), `BaseBranch` (default empty, read via `Config.GetBaseBranch()` — the branch new worktrees are cut from; empty auto-detects via `git.ResolveBaseCommit`: `origin/HEAD` → `main` → `master` → current `HEAD`), `Profiles` (named program presets), `Theme` (`"afterglow"` default, `"legacy"`; empty means default, read via `Config.GetTheme()`; cycled live from the settings overlay's Theme row), `ClaudeTmpArchiveDir` (`claude_tmp_archive_dir`, read from the global `config.json` only; empty keeps each workspace's Claude temp-dir archives in its own config folder; set, every workspace's go under it in a subfolder per config dir, see `session.ClaudeTmpArchiveDir`; read via `Config.ClaudeTmpArchiveRoot()`, which expands `~` and rejects a relative path), `ClaudeRemoteControl` (`*bool`, default on — launches Claude sessions with `--remote-control <title>`; nil is treated as enabled, read via `Config.RemoteControlEnabled()`), `ClaudePermissionMode` (`*string`, default `"default"` — launches Claude sessions with `--permission-mode <mode>`; nil is treated as `"default"` (no flag injected), read via `Config.PermissionMode()`; valid values enumerated in `config.ClaudePermissionModes` and cycled from the Claude Preferences overlay), `Claude1MContext` (`*bool`, default off — appends Claude's `[1m]` long-context suffix to the launched `--model` alias, e.g. `sonnet[1m]`; a no-op for `default`, `haiku`, and any alias whose `config.ClaudeModel.Supports1M` is false, read via `Config.Context1MEnabled()`; the composed value is single-quoted because tmux runs the program string through a shell and `[`/`]` are zsh glob metacharacters), `ClaudeSubagentTracking` (`*bool`, default on — shows the subagents and teammates loom's hooks track; every Claude launch gets the hooks regardless; nil is treated as enabled, read via `Config.SubagentTrackingEnabled()`, toggled from the Claude Preferences overlay's Track Subagents row)
- `state.json` — app state (e.g. help screens seen) plus the `ui` prefs block (`config.UIPrefs`: `view_mode`, `rail_hidden`, `terminal_hidden`, and `split_ratios` — a per-session-title map of agent/terminal split ratios, written throttled on `ctrl+up`/`ctrl+down` resizes)
- `instances` (an array inside `state.json`, not a separate file — `config.InstancesFileName` is unused) — serialized session data (`issue`, since schema v6, links a session to the GitHub issue number it was created from; `claude_session_id`/`claude_transcript_path`, since v7, name the conversation a crash relaunch resumes with `--resume`; `account`, since v8, names the Claude account the session runs on, empty = default)
- `workspaces.json` — registered workspaces with name, path, and last-used tracking, plus the open list (`open_workspaces`: the tabs the last TUI left open, then the ones it failed to open; the model writes it only when a client hands it one, `PersistOpenList`)
- `loom.lock` (global dir) — the daemon's lock, held for its whole life, and on Unix its record too (JSON: `pid`, `tty`, `started`, `socket`, `build`, `host`, `tmux`), which clients read to find the socket; on Windows the record is `loom.lock.json` beside it. Never removed (see the one-daemon gotcha)
- the daemon's socket — `$XDG_RUNTIME_DIR/loom/<hash>.sock`, else `run/serve.sock` (global dir) when that path fits, else `loom-<uid>/<hash>.sock` in the temp dir; named in the lock record (`daemon.SocketPath`)
- `logs/serve.log`, `logs/serve-crash.log` (global dir) — the daemon's log and its runtime-crash output; the TUI keeps `logs/loom.log` (in `LOOM_HOME`'s dir)
- `accounts.json` (global dir) — extra Claude accounts (`name`, `dir`) and the `default` new sessions preselect
- `accounts/<name>/` (global dir) — each extra account's `CLAUDE_CONFIG_DIR`: its own `.credentials.json`/`.claude.json`/runtime dirs, everything else symlinked to the main config dir
- `worktrees/` — git worktree directories
- `hooks/` — per-instance Claude hook folders for status, resume and subagent tracking (see `session/hooks`), one per path-escaped tmux session name; emptied at each launch, removed when an instance is killed, swept when unclaimed and its tmux session is gone
- `archive/claude-tmp/` (or `<claude_tmp_archive_dir>/<encoded config dir>/` when the global `config.json` sets one) — zips of Claude's per-session temp dirs (scratchpad, task output, minus `CACHEDIR.TAG` caches): one `<name>.zip` per paused session (restored and deleted on resume), plus permanent archives from kills, sweeps and demoted parks; never pruned by loom
- `scripts/` — user-supplied `*.lua` files loaded at startup (global, shared across workspaces)

## Testing Patterns

- Tests use `testify/assert` for assertions
- Dependency injection via interfaces: `cmd.Executor`, `tmux.PtyFactory`
- Constructor variants for testing: `NewSessionWithDeps()`, `NewAttachClientWithDeps()` and `NewTmuxSessionWithDeps()` accept mock dependencies
- `app` tests attach agent-pane clients through the registry, as production does: `app/testpanes_test.go`'s `attachTestClient` registers one per fixture instance and `wirePanes` points a test `home` at it. Fake attach PTYs (here and in `ui`) are `internal/testpty` pairs, open until the test ends or closes the peer: a `/dev/null` PTY reads EOF at once, which a client takes for a dead session (`Attached` false)
- Test setup pattern: `TestMain` initializes logging, runs tests, calls `os.Exit`
- Tests use temp directories for file I/O isolation
- `app` tests never touch the developer's default tmux server: `TestMain` (`app/app_test.go`) points `LOOM_TMUX_SOCKET` at a private server and kills it afterwards; `isolateTmux` gives a test its own fresh server, and `core.Model.SetExecForTest` swaps the workspace load paths' executor for a recorder. `core`'s `TestMain` (`core/testmain_test.go`) isolates tmux and `~/.loom` the same way, and a `core` test that starts real tmux sessions also calls its own `isolateTmux(t)` (`core/testhelpers_test.go`, a fresh private server per test, killed when it ends): on the package's shared server the previous test's cleanup can kill the last session, a tmux server exits when it has none, and a `new-session` that reaches it while it exits fails with "server exited unexpectedly". `startForeignSession` (`core/boot_test.go`) starts a session holding a title from another directory, standing in for another workspace's or another loom's, for the ownership-check tests
- `app` fixtures build workspaces with `testWS` (a `core.Workspace` from its handles plus instances, added through `AddForTest`) and slot views over them with `slotOver`, and install the model with `wireCore` (`app/testcore_test.go`), served over the pipe by `testLoop` (next bullet): it serves every slot's workspace in a model (`SetWorkspacesForTest`: the tabs in order, then the focused slot's, each opened) that has not booted, gives the home a tmux liveness probe (`aliveProbe` = `fixtureAlive`, the has-session answer of the fixture instance's mock session) unless the test set one, names each slot after the workspace it shows (`id`, `info`) and fills every slot's view store (`syncViews`), so a hand-built `home` with slots needs `wireCore` after its slots are assembled and before it is exercised. A test that needs the global and registered workspaces served too boots the wired model in place (`bootFixture`: `Model.Boot`, safe while the loop is idle; a later `wireCore` drops what it booted), after `registerWorkspaces` has registered them under the test's own `LOOM_GLOBAL_DIR` and installed the registry. A test of startup builds the TUI as `Run` does, over a booted model, with `startupHome` (or `tryStartupHome`, which returns `startHome`'s error): a `core.NewForTest` model with the test's executor and registry, booted as the daemon boots it, served by `startTestCore`, then `startHome` with the boot's notices, a startup workspace name ("" for the global one) and an optional pending directory. A slot holds only the workspace's ID and view, so `slotOver` (or `slotWith`, for a slot built by hand) records which workspace a fixture slot shows (`fixtureWS`), and tests reach the model's workspace and its handles through test-only slot accessors (`ws()`, `wsCtx()`, `storage()`, `appConfig()`, `appState()`, `testcore_test.go`; a slot production code built during the test resolves through the wired model by ID); a test that changes a handle (a pref, a setting, the context) and then reads through the TUI calls `m.syncWorkspaces()` first, and a settings test opens its overlay over a TUI-owned config (`settingsOverlayForTest`). Tests build instances in core and read them through the TUI: one that changes the model's instances outside an Update (`ws.AddForTest`, a status set on the instance) calls `m.syncViews()` before reading them, and reaches the instances again through `ws.InstancesForTest()`, the IDs through `testModel(m).IDOfForTest(inst)` (`testModel` is the loop's `*core.Model`, for its seams, safe to reach because the loop is idle between calls; `loopOf(m)` is the loop itself, found through `testStacks`) and an ID's instance through `InstanceForTest`; `ui` and `script` tests build `core.InstanceView` literals (`core.ViewForTest` copies a fixture instance into one). `reworkspace` rebuilds a slot's workspace with edited handles (a `core.Workspace`'s handles are fixed for its life), and `editRCAuth` edits the model's default-account remote-control auth (the loop's `SetRCAuthForTest`). The loop holds every job (`JobsForTest`), so no job's result rides a Cmd: tests deliver a result as the runtime would with `deliver(t, m, result)` (`DeliverForTest`, which wakes no client, then a `coreWakeMsg` through `Update`, whose drain's `Sync` pings first, so the server publishes what the delivery produced), and `pumpCore` runs a Cmd's tree and every held job until both settle, delivering each result, so a job that follows another (a start's initial-prompt send) lands too. `requestJob` returns the one job a request made outside an Update queued (calling it returns the result, undelivered), `requestResults` runs them all, and `tickModel` runs the model's tick as its timer would (`TickForTest`). Results whose types core keeps unexported come from `core/seams.go`'s `…ForTest` constructors (`FetchedIssueForTest`, …; `UntrackedForTest` strips a request's tracking from a result). A test that hands the model an operation's result directly wraps it with `core.CausedForTest(req, result)` when the TUI must treat it as its own request's: the `Started`, `Recovered` and `Notice` it produces then name `req`, while an unwrapped one is another client's, so `applyStarted`/`applyRecovered` only attach its pane
- `app` tests talk to their model over the wire, as production does, but in process, over a pipe, with no daemon. `startTestCore` (`app/testcore_test.go`) serves a test's model: `rpc.InProcessForTest` runs the model on a `core.StartForTest` loop, which holds every job and never ticks on its own, behind a server, with a **synchronous** client. That client pings before every local read (`Sync` included), so a read sees whatever the model published by then, a change the test made to the model directly included. It also pings after every cast, so a cast has reached the model when it returns. So tests meet the model as they did in 1E; the race detector found three tests reading the model right after a cast before casts pinged. `testLoop` serves a test's model this way, so a test that installs its own model wraps it in `testLoop`, and `startupHome` serves its model the same way. `startTestCore` records each client's stack in `testStacks`, through which `loopOf(m)` finds the loop for its seams and `stackOf(m).stop` stops the stack. `TestRealLoop_…` (`app/core_wake_test.go`) swaps in the production loop and a raising client (`rpc.InProcess`), to show a job's result reaches the TUI by wakes alone; run it under `-race`. `TestDaemonGone_QuitsCleanly` (`app/daemon_client_test.go`) dials a server with `rpc.Dial`, as the TUI dials the daemon, and closes the server under a running TUI. `core/rpc`'s own tests use production (non-synchronous) clients. A fixture time compared with what came back through the client is `time.Now().Round(0)` (see the no-model-mutation gotcha)
- `core` tests build a model with `NewForTest` (no workspace, no side effects), install workspaces with `SetWorkspacesForTest(wss...)` (variadic: each served and opened, in serve order; the model has not booted, and a `Boot` loads the global and registered workspaces beside them), build a model over registered workspaces laid out on disk with `core/boot_test.go`'s `workspaceDef` and `bootModel` (its own global dir, a tmux executor on which every session is dead), which the test then boots, and open one with `openDef`, deliver a result as a request's job would with `CausedForTest`, and take fixtures from `core/testhelpers_test.go` (`storedWorkspace`, a workspace over a fresh config dir and storage; `newInst`, `newTerminal`, `pausedInst`, `startedInst`, `gitRepo`, `pausedWorktreeInst`). A test of a function that lives in `core` lives in `core`; a test of the TUI's response to a model result goes through `home.Update` and stays in `app`. `TestCoreImportsNoUI` and `TestNoProductionCallsOfTestSeams` guard the seam (see the `core/` bullet)
- The daemon is tested at three levels. `internal/daemon`'s tests run `Serve` in their own process, on a goroutine, and swap `Connect`'s `spawn` for one that does the same (`spawnInProcess`, `connect_test.go`), each daemon stopped when its test ends. The root package's `daemon_client_test.go` drives `daemonLink.join` through its seams (`dial`, `stop`, `mayReplace`, `stderr`), and `main_test.go` covers `loom debug`'s daemon lines and `reset`/`workspace migrate` refusing while the lock is held. `e2e/daemon_test.go` (`go test -tags e2e ./e2e/...`, needs tmux) runs real `loom` builds in a loomdev sandbox (`internal/devsandbox`: its own tmux server and global dir, so its own daemon): spawn on demand (the daemon's working directory included), a stale socket, the daemon killed under an open TUI, two TUIs on one daemon, two TUIs starting at once, a newer build replacing the daemon under an open older TUI, an older build refusing, `loom serve stop` with live sessions (they come back on the same agent process, not paused), the daemon outliving its TUI's tmux session, a same-version rebuild replacing the sandbox daemon, and a stop during a start race. The suite's cleanup fails a test whose daemon outlives its sandbox (`e2e/e2e_test.go`)
- No test touches the developer's real `~/.loom`. Every package whose tests can reach `config` (directly or through another loom package) has a `TestMain` calling `internal/testenv.IsolateLoomDirs`/`MustIsolateLoomDirs`, which points `LOOM_HOME` and `LOOM_GLOBAL_DIR` at a throwaway dir for the whole binary (it also points `CLAUDE_CODE_TMPDIR` at a throwaway dir it creates empty, so Claude's root reads as absent); a test needing its own dirs still `t.Setenv`s over them. `TestEveryConfigReachingPackageIsolatesLoomDirs` (`internal/testenv`) walks the module's import graph and fails on a config-reaching package without one — a new package's first test needs a `TestMain` (copy any `testmain_test.go`). `config` is the one exception: its tests exercise default resolution, so its `TestMain` leaves those vars unset and points `HOME` at a throwaway instead (assert "default is ~/.loom" by computing `os.UserHomeDir()`, never by touching it)

## Code Conventions

- Error wrapping: `fmt.Errorf("context: %w", err)`
- Module path is `github.com/aidan-bailey/loom`
- Platform-specific code in `_unix.go` / `_windows.go` suffixed files
- Private struct fields, public methods (PascalCase)
- Minimal goroutine usage; concurrency mainly in tmux monitoring

## CI/CD

GitHub Actions workflows in `.github/workflows/`:
- **build.yml** — Build and test on push/PR to main (triggered by Go file changes)
- **lint.yml** — golangci-lint on Go code changes
- **release.yml** — Auto-triggers on Build success on main (or `workflow_dispatch`). Reads `version` from `main.go`; skips if `v$VERSION` already exists on GitHub; otherwise tags, generates release notes from conventional commits via `git-cliff` (see `cliff.toml`), and runs GoReleaser to build/publish artifacts. To cut a release: bump the `version` string in `main.go`, regenerate `CHANGELOG.md` with `git cliff -o CHANGELOG.md --tag v$VERSION`, commit, and merge to main.
