# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Loom is a terminal UI (TUI) for managing multiple AI coding agents (Claude Code, Aider, Codex, Amp) in parallel. Each agent runs in an isolated git worktree with its own tmux session. Built with Go using the Charmbracelet Bubble Tea framework.

Loom was forked from [smtg-ai/claude-squad](https://github.com/smtg-ai/claude-squad) at v1.0.17 (April 2026) and has diverged substantially since — see [NOTICE.md](NOTICE.md).

## Build & Development Commands

```bash
# Build
CGO_ENABLED=0 go build -o loom

# Build & run via Nix (no dev shell needed)
nix run .

# Run tests
go test -v ./...

# Run a single package's tests
go test -v ./config
go test -v ./session/git

# Race detector — the default CGO_ENABLED=0 build disables it, so enable CGO
# (needs a C compiler; use CC=clang if gcc is absent). CI runs this as a job.
CGO_ENABLED=1 go test -race ./...

# Format code (CI enforces this). Never plain `gofmt -w .`: it rewrites vendor/
gofmt -w $(git ls-files '*.go' | grep -v '^vendor/')

# Lint (CI uses golangci-lint v1.60.1)
golangci-lint run --timeout=3m --fast

# Cleanup scripts (refuse to run inside a loom-managed tmux session)
./clean.sh        # Kill tmux server, remove worktrees and ~/.loom/
./clean_hard.sh   # Same as clean.sh + git worktree prune

# Dev sandbox — run a dev build safely from inside loom (.claude/skills/loom-dev)
go run ./tools/loomdev up                 # create + build (named after the branch leaf)
go run ./tools/loomdev run                # interactive, in this terminal
go run ./tools/loomdev start              # headless, then: wait --text toy / keys … / shot
go run ./tools/loomdev down               # delete the sandbox and its tmux server
go test -tags e2e ./e2e/...               # end-to-end smoke suite (needs tmux)

# Install (adds ~/.local/bin to PATH)
./install.sh
```

CGO is disabled for builds (`CGO_ENABLED=0`). Go version is 1.25.8 (the `go` directive in `go.mod`; there is no separate `toolchain` line).

A Nix flake (`flake.nix`) provides a dev shell with Go, golangci-lint, tmux, git, and gh.

## CLI Usage

```bash
# Run with default settings
loom

# Specify agent program
loom --program "aider --model ollama_chat/gemma3:1b"

# Subcommands
loom reset --force  # Delete a workspace's instances, kill its tmux sessions (only those started in its repo/worktrees dir), remove its worktrees and branches
loom debug    # Print config paths and debug info
loom version  # Print version

# Workspace management
loom workspace add [path]    # Register a git repo as a workspace
loom workspace list          # List registered workspaces
loom workspace remove <name> # Unregister a workspace
loom workspace use <name>    # Set default workspace
loom workspace rename <old> <new>  # Rename a workspace
loom workspace status [name] # Show instance counts
loom workspace migrate       # Migrate instances to workspaces

# Select workspace explicitly
loom --workspace <name>

# Claude accounts (spread sessions across several subscriptions)
loom account add <name> [--no-login]   # create <globalDir>/accounts/<name>, link your Claude setup, claude auth login
loom account login <name>              # "default" is your main login
loom account list                      # email, plan, 5h/7d usage per account
loom account use <name>                # account new sessions preselect
loom account sync                      # share entries added to your main config since
loom account remove <name> [-y] [--force]  # refused while a session uses it or holds unshared files; -y skips the confirmation, --force overrides both
```

## Environment Variables

- `LOOM_HOME` — Override config directory (default: `~/.loom`). Must be absolute path; supports `~` expansion. Used as a backward-compatible fallback; internal code uses explicit `WorkspaceContext` threading.
- `LOOM_LOG_FORMAT` — Set to `json` to emit structured log records from `log.InfoKV/WarnKV/ErrorKV` as JSON lines; otherwise plain text. The legacy `InfoLog`/`WarningLog`/`ErrorLog` writers always stay plain text.
- `LOOM_LOG_LEVEL` — `debug|info|warn|error` (default `info`). Gates both the Structured logger and the legacy `InfoLog`/`WarningLog`/`ErrorLog` writers (legacy records below the gate are dropped at the writer layer). The `--log-level` CLI flag (persistent on all subcommands) takes precedence over the env var.
- `LOOM_PANE_RENDERER` — Set to `snapshot` to disable the embedded VT emulator and fall back to the legacy `tmux capture-pane` snapshot path for pane rendering (also the implicit path on Windows). Unset (default) renders panes from the emulator, enabling mouse forwarding, event-driven updates (no render/status polling), the native hardware cursor, and title/bell/focus pass-through. Scroll-back is emulator-owned on this path: windows render in-process from x/vt scrollback (`vt.Emulator.RenderWindow`), seeded once per attach from `tmux capture-pane -S - -E -1`; `tmux capture-pane` windowing survives only on the snapshot path.
- `LOOM_TMUX_SOCKET` — Private tmux socket name: every tmux invocation gets `-L <name>` (via `tmux.Command`), overriding `$TMUX`. Used by the dev sandbox.
- `LOOM_GLOBAL_DIR` — Relocates `GetGlobalConfigDir()` (workspace registry + global context), which ignores `LOOM_HOME` by design. Absolute; supports `~`. Also disables the legacy-home migration.
- `LOOM_ALLOW_NESTED` — Set to `1` to bypass the nesting guard (see Gotchas).

Legacy fallbacks (`CLAUDE_SQUAD_HOME`, `CLAUDE_SQUAD_LOG_FORMAT`, `CLAUDE_SQUAD_LOG_LEVEL`) are still honored with a one-time deprecation warning to stderr; remove them from your shell init once you've migrated.

## Migration from claude-squad

On first launch, Loom renames `~/.claude-squad/` → `~/.loom/` atomically so in-flight instances, worktrees, and user scripts continue to work. Live tmux sessions with the legacy `claudesquad_` prefix are renamed to `loom_` before reconcile runs, so running agents keep their panes. The orphan sweep in `session/reconcile.go` recognizes both prefixes to clean up stragglers.

Auto-commit tags flipped from `[claudesquad]` → `[loom]` at the v0.1.0 cutover. Historic worktree commits retain the old tag — that is expected and not rewritten.

## Debugging

- Log file: `{configDir}/logs/loom.log` (rotated once to `.log.1` at startup when >5 MB). Run `loom debug` to print the exact path plus the effective log level and format.
- To enable verbose output, set `LOOM_LOG_LEVEL=debug` or pass `--log-level=debug`. Debug logs are routed exclusively through the Structured logger (`log.Debugf` / `log.DebugKV`); they never appear via the legacy `*log.Logger` vars.
- New code should prefer `log.For("subsystem", ...)` to get a pre-tagged `*slog.Logger`, or call `log.InfoKV/WarnKV/ErrorKV/DebugKV` directly. The resulting records carry `subsystem=...` so a single `grep subsystem=tmux loom.log` scopes output to one component.
- The session model (package `core`) logs under `subsystem=core` (`log.For("core")`), keeping the event names its code had in `app` (`tick.tmux_gone_marking_paused`, `workspace_terminal.restart_circuit_tripped`, …); only the two `log.DebugKV` records took the new prefix (`core.roster.query_failed`, `core.hook_scan.failed`). The account registry and the GitHub poller keep `subsystem=account` and `subsystem=github`, and the TUI logs under `subsystem=app`. A job result the model does not recognize is logged as `deliver.unknown_result` and dropped.

## Architecture

### Core Flow

`main.go` (Cobra CLI) → `app/app.go` (Bubble Tea Model, the view) → `core/` (`core.Model` behind the `core.Core` interface, the session model) → `session/instance.go` instances

The app follows Bubble Tea's Model-View-Update pattern. `app/app.go` owns the `home` model and its `Update`/`View`. Keyboard input is routed in two stages: `handleKeyPress` (`app.go`) dispatches by `m.state` to a per-state handler in `app/state_*.go`; within the default state, keys flow through the Lua engine via `app/app_scripts.go:dispatchScript`, which consults `script.Engine.HasAction` and returns a `tea.Cmd` that drains the resulting `scriptDoneMsg`. The canonical keymap lives in `script/defaults.lua` (embedded at build time); user scripts in `~/.loom/scripts/*.lua` can rebind or add keys. On startup, the app detects the current workspace or prompts the user to select one via the workspace picker overlay.

The TUI drives the model synchronously on its Update goroutine (daemon stages 1B and 1C; the model gets its own goroutine in 1D). It holds the model as a `core.Core` (`core/iface.go`) and sees instances only as `core.InstanceView` values, acting on one by a request that names its `core.InstanceID` (see the `core/` bullet). Blocking work is a `core.Job` (`func() any`), which the TUI runs as a Cmd (`coreCmd`) and whose result comes back as a `coreResultMsg` that `update` hands to `core.Model.Deliver`. The model reports what the view must do as `core.Event`s (`core/events.go`: `ViewsChanged`, `Reply`, `Notice`, `InstancesChanged`, `ClientsStale`, `SessionLaunched`, `Reactivated`, `Started`, `Recovered`, `StatusesChanged`, `Alive`, `HealthChecked`, `GitHubChanged`, `AccountsChanged`), queued in an outbox along with the jobs it starts itself. `home.Update` is a thin wrapper: it runs the message switch (`update`), then `drainCore` (`app/core_glue.go`), which empties the model with `core.Model.Sync` (a `ViewsChanged` for each workspace whose views changed comes first, so the appliers of the events after it read the new views), applies each event in order (`applyCoreEvent`) and wraps each job as a Cmd. `newHome` drains after each model call and hands the resulting Cmds to `Init`, which also calls `core.Model.Begin` (the first accounts refresh and usage probe).

The default state renders in one of two **view modes** (`m.viewMode`), toggled with `tab`: **focus** (session rail + agent/terminal split — the classic layout) and **overview** (`ui/overview.go`, a fleet-triage card grid). `enter`/`esc` return to focus; `n`/`N` drop to focus first, then run the create flow; `z` collapses a group; mouse input is dropped in overview (v1). The mode persists per workspace in state.json's `ui` block — switching workspaces applies the target workspace's persisted mode.

**Cross-workspace overview.** The overview spans the **open (tab-bar) workspaces only** — each open workspace renders as its own card group (focused first, then alphabetical; per-group states loaded/empty). Workspaces registered but not open do not appear; open more via the picker (`W`). The overview carries a **global domain cursor** `home.overviewCursor {slot,inst}` (translated to render coords `ui.OverviewCursor {Group,Item}` in `overviewData`); `j/k` walk `fleetOrder` across all groups. Cursor-committing keys route through **`focusCursorSlot()`** (`loadSlot` → select), so `enter`/`D`/`r`/`n` reuse the existing focus-mode intents on the right workspace. Focus-mode `]`/`[` (`jumpWaiting`) also crosses open workspaces, switching the focused slot as needed.

### Key Packages

- **`app/`** — Bubble Tea application model: the view and key routing; lifecycle goes through `core`, by request. It keeps everything that renders or reads a pane client, `m.state`, overlays, key dispatch, the Lua engine and script host, the workbench and review, the overview cursor, tab bar, menu and error bar, the split-ratio throttle, full-screen attach, the issue picker (its fetches are `core.Model.FetchIssue` requests), and the views of accounts and GitHub state. It holds no `*session.Instance` (`TestTUIHoldsNoInstance`; see the no-model-mutation gotcha). A loaded workspace is a slot (`workspaceSlot`, `app/workspaces.go`), a view over a `core.Workspace` (see the focused-slot gotcha), and each slot keeps that workspace's `core.InstanceView`s as its view store (`workspaceSlot.views`, `app/views.go`): seeded from `core.Model.Views` when the slot is built (`seedViews`), replaced wholesale by each `ViewsChanged`, and reread from the model by `syncViews` where an Update reads back a change its own request just made (see the stale-copies gotcha). Every reader sees the store through `rowsOf` (the rail's `ui.InstanceSource` is `slotRows`), which copies each row, lays the TUI's own overlays over it (`overlay()`: the bells of `home.bells`, set by a pane's bell and cleared by focus, and the pane ladder's scraped status in `home.ladder`, see the event-driven panes gotcha) and appends the creation flow's draft row. `findRow`/`viewByID`/`viewBySession` look a row up across every open slot, `activeViews` lists the active ones, `refreshSelection` repoints the split pane's and menu's copies at the selected row, and the `ViewsChanged` applier runs `pruneBells`/`pruneLadder`. Creation flows edit a `draft` (`app/drafts.go`, `m.draft`): it shows as a row with ID 0 at the end of its own slot's rail until `confirmDraft` sends `core.Model.Create`, and every cancel path calls `discardDraft`, with nothing to kill. `app/requests.go` is the request book: `newReq` records what a request with a `core.ReqID` waits on (`pendingCreate`, `pendingSend`, `pendingOp`, `pendingScript`, `pendingIssue`) and `handleReply` routes its `Reply`. Every lifecycle request the user starts carries one (`opReq`, a `pendingOp`) so that a refusal reaches the user: `refusal()` shows the Reply's error through `handleError` only when it matches `core.ErrRefused`, since a failed job is the model's to show, as a notice. A prompt send holds input to its instance until its Reply (`sendPrompt`, `holdInput`, `m.sending`): meanwhile `sendingTo` refuses inline attach and another send to it with an info line (the prompt overlay keeps its text), so keys typed after a send can't land between its paste and its Enter; Lua's `send_prompt` holds too. The TUI reaches tmux by session name, never through an instance: the full-screen attach builds `tmux.NewSessionNamed(name, program)`, and the liveness guards call `m.sessionAlive(name)` (a has-session probe; tests set its `aliveProbe` seam). `app/core_glue.go` is the seam: `coreCmd`/`coreResultMsg` run jobs, `drainCore`/`applyCoreEvent` apply events, `newSlotView` builds a slot over a workspace, and `slotFor` finds the slot showing a workspace. `app/completions.go` keeps only the view's half of the completions (`applyStarted`, `applyRecovered`).
- **`core/`** — The session model (daemon stages 1B and 1C): everything that acts on sessions without a terminal. `core.Model` (`model.go`) holds the classic workspace (no tab open: `Classic()`) or the open tabs (`Tabs()`); each is a `core.Workspace` (`workspace.go`) with its context, storage, config, app state, ordered instances (edited only by the model, through the unexported `add`/`remove`/`replace`, by identity; tests reach them through `AddForTest`/`RemoveForTest`/`InstancesForTest`) and recovery summary, and `Loaded`/`IsLoaded` (`workspaces.go`) query them. Clients see an instance only as a `core.InstanceView` (`view.go`): a value holding everything the TUI renders or gates a key on (`Active()` is the active-instance rule, for a view; `WorktreeRepoPath` is what Lua's worktree handle is built on) and nothing that acts. It names its instance by a `core.InstanceID`, which the model assigns the first time it reports the instance (`idOf`) and never reuses within the process, so a request can't reach a same-titled instance in another workspace or a reopened workspace's fresh copy of a record; 0 is never assigned (the TUI's draft row uses it). `Views(ws)`/`View(id)` (`views.go`) build views for loaded workspaces only. `Sync` publishes them by diffing: it builds every loaded workspace's views, emits a `ViewsChanged` carrying deep copies (`cloneViews`) for each workspace whose views changed since the last publish, ahead of every other event, and forgets the IDs of instances no loaded workspace holds. Every lifecycle action is a request, by ID where it names an instance, with an optional `ReqID` (`requests.go`: `Kill`, `Pause`, `Resume`, `ResumeWith` (the `R` flow: the new launch options applied, then a resume), `Recover`, `Merge`, `Push`, `SendPrompt`, `Create(ws, NewInstance, req)`, which builds and adds an instance and, with `Start`, configures and starts it, and `FetchIssue`). A non-zero `ReqID` is answered by a `Reply` (`Req`, `ID`, `Err`, `Notice`, `Issue`): at once for a refusal or a `Create`, otherwise when the request's job lands (`track`, `deliverTracked`). Each request first runs `admit`: a loaded workspace must hold the ID (else `ErrNoSession`) and the instance must pass `precondition`, which mirrors the keys' gates in `app/intents.go` (no kill, pause or push of a workspace terminal or a busy session, no resume of one not Paused, …), so the model refuses exactly what no key can do. A refusal's error matches the `core.ErrRefused` sentinel (`ErrNoSession` does too); with `ReqID` 0 it is only logged (`request.refused`). A failed job is not a refusal: the model has already shown it as a `Notice`, and the Reply's `Err` carries it too. The TUI's pane triggers name instances by ID as well (`Tick(selected)`, `PaneOutput`, `PaneQuiet`, `VerifyDead`; `MarkOutput` takes the session name). Loading and saving (`load.go`: `LoadClassic`, `loadWorkspace`, `reconcileOrphans`, `claimTitles`; `persist.go`: `Persistable`, `Save`, `SaveForQuit`), the workspace transitions and every registry write (`workspaces.go`: `OpenTab`, `CloseTab`, `EnterGlobal`, `StayGlobal`, `RestoreSaved`, `Register`, `SetLastUsed`, `PersistOpenList`; the workspaces that failed to restore, `RestoreFailed`), the lifecycle operations behind the requests (`ops.go`: `killInst`, `pauseInst`, `startInst`, … — the instance-pointer API, `activeInstances`, `holding`, `statusEligible`, `adoptClaudeStatus` included, is unexported) and their completions (`completions.go`), the health tick's model half (`tick.go`), every gated background job (`gate.go`, `claude_status.go`, `hook_scan.go`, `github.go`, `accounts.go`, `usage.go`), the default account's remote-control auth (`RCAuth`/`SetRCAuth`) and the agent program (`Program`/`SetProgram`) all live here. `core.Core` (`core/iface.go`) lists every method the TUI calls, and `home.core` has that type; `*Model` is its only implementation. Its instance half is final (IDs, views, `Reply`); its workspace and account half still passes the model's own objects (`*Workspace`, `*config.WorkspaceRegistry`, `*account.Registry`) until 1D converts it to values. Every method runs on one goroutine, in 1B and 1C the TUI's Update goroutine. Blocking work is a `Job` that reads no model state; `Deliver` routes its result by type. A request starts its own job, and every job (the tick's probe, gated jobs, the kill after a failed start, an N flow's initial prompt included) goes to the outbox with the `Event`s, which the TUI empties with `Sync` (core's own tests may call `Drain`, which publishes no views). Focus is the TUI's: the model never knows which tab is focused, so where an operation needs a workspace the user chose (`Create`'s, also the start's fallback owner; `EnterGlobal`'s config rollback) the caller passes it, an ID request finds its workspace by lookup, and whatever depends on focus or `m.state` (the selection, inline attach, the "started in X" wording, the `stateDefault` guard) stays in the TUI's event appliers. `core` imports nothing of the TUI: `TestCoreImportsNoUI` (`core/boundary_test.go`) walks the import graph and fails on `app`, `ui/...`, `script`, `keys` or a `charm.land` package reached from `core`, directly or through another loom package. `core/seams.go` holds the test-only exports (`…ForTest`), and `TestNoProductionCallsOfTestSeams` (`internal/testenv/seams_enforce_test.go`) fails on any production use of one: a call, or a reference taken as a value.
- **`session/`** — Core domain. `Instance` represents a running agent session with status lifecycle (Ready → Loading → Running → Paused). Its own API is lifecycle and state. Its tmux session is a lifecycle-only `tmux.Session` that never attaches a client (see the pane-client gotcha). Whatever lifecycle does to the agent's pane without a client lives on the `AgentPane` value returned by `Instance.Pane()` (`agent_pane.go`): liveness probes, the session name and the program the session was launched with (`SessionProgram`), typing text and prompts (`SendKeys`, `SendPrompt`: `load-buffer` + `paste-buffer`, see `session/tmux/`), pressing Enter (`TapEnter`: `send-keys`), and a capture-pane `Preview`. For example, `inst.Pane().SendPrompt(…)`. Rendering the pane and forwarding input through a PTY go through the TUI's client (`ui.Pane`, from `ui.PaneClients`). Its launch fields are set through `SetLaunchOptions`/`SetProgram`/`SetPrompt`/`SetCrashRecovered` and read through `Program()`/`HeadroomProxy()`/`CacheTTL1h()`/`Prompt()`/`CrashRecovered()`, never assigned directly — the accessors lock `i.mu`, so `session` code that already holds it reads the private fields instead (the lock is not reentrant). `storage.go` handles JSON serialization of the `instances` array in `state.json` and retains raw `InstanceData` for records that fail `ReconcileAndRestore` (the unrecovered cache) so a transient failure does not silently drop the entry on the next save. Records that fail to *decode* (corrupt, or a `schema_version` newer than this binary after a downgrade) are skipped by `MigrateAll`, held as raw bytes (`UndecodableCount`), and appended verbatim to every write — `SaveInstances`, `DeleteInstance`, `UpdateInstance` all go through `writeLocked`, which also loads first on a never-loaded `Storage`. A payload that is not a JSON array at all fails the load and latches every write shut (`ErrStorageLoadFailed`, state untouched) until a later load succeeds; `DeleteAllInstances` (`loom reset`) is the one write allowed through, and clears the latch. Both kinds of preserved record are claimed by worktree path (`PreservedWorktreePaths`) so orphan discovery doesn't offer them as `Recoverable`, and by title (`PreservedTitles`, folded in by `core`'s `claimTitles` at every sweep site) so the orphan tmux sweep and the hooks sweep spare their sessions, workspace-terminal auto-create doesn't kill and duplicate a preserved terminal, and a new session can't take a preserved title (`preservedTitleErr`); both are counted in the recovery summary. Unclaimed is not enough for the orphan tmux sweep (`CleanupOrphanedSessions`, `reconcile.go`) to kill a session: the tmux server is shared, so it also has to prove ownership. It reads each session's start directory (`#{session_path}`, the `-c` dir loom passes to `new-session`; unlike `pane_current_path` it ignores a later `cd` and survives the dir's deletion) and kills only when that directory, compared after `filepath.EvalSymlinks` and component-wise (`/a/repo` does not hold `/a/repo2`), lies inside an **owned** root of its `SweepScope` — each loaded workspace's repo root and `<configDir>/worktrees` (`WorkspaceSweepRoots`; `NewSweepScope` builds it at each sweep site from the same workspaces `claimTitles` covers) — with no **foreign** root (every other registered workspace's, and the global worktrees dir) nested deeper. It fails closed: an empty, relative or unplaceable directory is left alone (`orphan_tmux.skip_unowned`, debug). Kills are exact-name (`-t=`). `orphan.go` discovers worktree directories on disk not referenced in state.json and classifies them (`Disposition`): stale leftovers (dead tmux + clean) are auto-cleaned, ones with unsaved work or a live agent surface inline as `Recoverable` session entries. `reconcileOrphans` (`core/load.go`, run on every workspace load) drives this — there is no blocking recovery modal.
- **`session/agent/`** — `Adapter` interface and per-program implementations (claude, aider, gemini, default fallback). Centralizes trust-prompt keys, recovery flags, and `Matches(program)` checks (resolved through `Registry.Lookup`). Look here when adding a new agent program rather than touching `tmux.go` or `agent_restart.go` directly.
- **`session/hooks/`** — Loom's side of the Claude Code hooks it registers on every Claude launch. `hooks.go` writes the per-launch hooks folder (`settings.json`, `launch-id`, `events/`); `scan.go` turns new event files into compact `.ev` files, replays them when needed, and stamps each event's `At` from its file name; `event.go` parses payloads, keeping only the fields loom reads from each event. `testdata/probe-2.1.280/` holds the payloads of a live probe (see its README). No tmux, UI or app dependency.

Lua changes instances only through the model: `inst:kill()`, `inst:pause()`, `inst:resume()`, `inst:send_prompt()` and `ctx:new_instance{}` enqueue an intent (`InstanceOpIntent`, `CreateInstanceIntent`) and yield until the request's `Reply` resumes them (`script.ResumeValue`, `Engine.ResumeWithHost`). On failure they raise (`scriptError`) a refusal's own message, which names the request (`"kill x: not allowed on a workspace terminal"`), or `"<op>: <err>"` for a failed job, a gone session and `ctx:new_instance`. On success the instance a lifecycle call acted on takes the session's view as the call left it (`Engine.luaValue`), so `inst:status()` after `inst:pause()` reads `Paused`; a killed one keeps its last view, marked `Deleting`. Because they yield, they refuse to run inside `pcall`/`xpcall`, a callback, a precondition or a coroutine the script made (`yieldable`), so a script can't catch their errors. `preview`, `send_keys` and `tap_enter` act on tmux by the view's session name (`tmux.NewSessionNamed`). The full API, errors included, is in `docs/specs/scripting.md`.

### Session Lifecycle

Statuses: `Ready` (initial), `Loading` (setup in progress), `Running` (agent active), `Paused` (worktree removed, branch preserved), `Recoverable` (an orphaned worktree found on disk, surfaced inline for recover/discard; never persisted).

1. **New**: User presses `n`/`N` → overlay collects title and optional prompt into the TUI's draft row (no instance exists yet) → confirming Launch Options sends `Create`, which builds the instance (status: Ready) and starts it at once (a script's `ctx:new_instance` leaves it unstarted)
2. **Start**: Creates git worktree + tmux session, records base commit → status: Loading → Running
3. **Running**: Agent works in isolated worktree; UI shows live terminal output + diff stats
4. **Pause**: Stashes uncommitted changes (`StashRef`), kills tmux session, removes worktree (branch preserved) → status: Paused
5. **Resume**: Rebuilds the worktree from the branch **only when it is absent or gutted** (no `.git`; leftovers moved aside), restores the stash, starts a new tmux session. An **intact** worktree is never rebuilt — the agent is relaunched in place with its recovery flag — and a live session is reattached (`session/resume_decision.go:decideResume`) → status: Running
6. **Kill**: Cleans up worktree, tmux session, and branch; instance removed from storage

The TUI starts each of these by a request to the model naming the instance's `InstanceID` (`core/requests.go`: `Create` with `Start` for steps 1–2, `Pause`, `Resume` or `ResumeWith`, `Kill`, `Recover`); the model starts the job doing the blocking work (`core/ops.go`) and applies its result (`core/completions.go`).

**Workspace Terminals**: A special instance type (`IsWorkspaceTerminal: true`) that runs directly in the root repo without a worktree. Cannot be paused/resumed. Diff tracking shows uncommitted changes in the root repo.

### Gotchas

- **Instance data schema changes.** `session.InstanceData` has a `SchemaVersion` field and `session.CurrentSchemaVersion` constant. When adding/removing/renaming fields: bump `CurrentSchemaVersion`, add an upgrade step to the switch in `session/storage_migrate.go:Migrate`, and update the JSON fixture in `cmd/workspace_migrate_shape_test.go` (drift guard for the `workspace migrate` CLI's typed mirror struct). A record `Migrate` rejects is never fatal to the load and never dropped: `Storage` skips it and writes it back unchanged, so a downgraded loom leaves a newer binary's records intact for when it returns. Only a top-level payload that isn't an array fails the load. Then classic startup (`core.Model.LoadClassic`), `OpenTab` and `EnterGlobal` abort rather than continue with an empty list, `RestoreSaved` skips the orphan tmux sweep (the failed workspace's titles are unknown) and keeps the workspace in the registry's open list (`core.Model.RestoreFailed`, merged in by `OpenNames`/`PersistOpenList` and shown checked in the picker, labelled "(failed to load)" with a warning that closing it lets the next launch's sweep end its live sessions) so later launches keep skipping it until the workspace opens or is deselected (from global mode, a Global commit deselects them without reloading the global slot (`StayGlobal`) — a reload of a latched storage would fail and strand them), and `Storage` refuses writes with `ErrStorageLoadFailed`. When *every* restored workspace fails, `RestoreSaved`'s fallback (`loadClassicFallback`) loads the startup context's storage with classic-startup semantics (shared `loadWorkspace`, minus the orphan sweep) so the global list shows its real sessions; if that load fails too, the error is shown instead of exiting, the latch refuses every save, `applyWorkspaceToggle` skips its pre-transition global save on `ErrStorageLoadFailed` so a workspace can still be opened, and `handleQuit` quits without saving (`core.Model.SaveForQuit`'s `quitSkipsSave`; keeping the failed workspaces in the registry's open list for the next launch). Those skips are lossless because new sessions are refused while the focused storage `WritesRefused()` (`latchedStorageErr`), so a latched list stays empty. Don't add a write path that bypasses `Storage.writeLocked`; one already does — `loom workspace migrate` (`cmd/workspace_migrate.go`) decodes records into its own typed mirror and writes via `config.SaveStateTo`, so a newer-schema record passing through it loses every field this binary doesn't know.
- **`FromInstanceData` is decoupled from PTY attach.** It's a pure constructor — it does not spawn a tmux session. `inst.EnsureRunning()` only marks a restored instance whose session runs as started. Nothing in `session` attaches a PTY (see the pane-client gotcha).
- **Pane updates are event-driven, not polled.** With the emulator enabled there is NO preview tick: panes re-render on `paneDirtyMsg` from the output pump, status transitions ride `paneQuietMsg`, and the 3s health tick does liveness, pane-client prune and repair, diff stats and the background jobs, but scans no pane. The tick splits along the pane boundary. The model's half (`core.Model.Tick`, given the selected row's ID; `core/tick.go`) queues one probe job over every active instance (tmux liveness, parity, diff stats: `probeJob`), whose `HealthResult` `deliverHealth` applies (`applyLiveness` pauses the dead and relaunches a dead workspace terminal under its circuit breaker, `maxWorkspaceTerminalRestartFailures`; Claude's reported status is adopted; an instance a kill, pause or resume moved to Deleting or Loading while the probe ran fails `statusEligible` and is skipped entirely, liveness included), dispatches the gated jobs that are due (roster, hook scan, GitHub poll, usage probe, the Claude temp-dir sweeps workspace loads queued), and stats `accounts.json` for a change (`maybeReloadAccounts`). The TUI's half (the `tickUpdateMetadataMessage` case in `app/app.go`) expires toasts, prunes pane clients, runs the inline-attach backstop, repairs clients on `core.Alive`, runs the snapshot path's status scan (`snapshotScan` → `snapshotStatusMsg`) and the workbench scan. `core.HealthChecked`, emitted once the probe's result is applied, re-arms the tick, so ticks never overlap a probe still running. Pane events report to the model, by the ID of the row their session name resolves to (`viewBySession`): `paneDirtyMsg` calls `MarkOutput` (by session name: the dirty set the next probe takes to gate diff refreshes, `takeDirty`) and `PaneOutput`, `paneQuietMsg` calls `PaneQuiet` (both feed hook scans and the Prompting roster query), and `ptyDeadMsg` runs `VerifyDead`'s probe. The legacy 100ms preview tick and the 500ms health tick with its capture-pane status scan only survive under `LOOM_PANE_RENDERER=snapshot` (and Windows). When adding per-instance periodic work, put it on the health tick: the model's half when it needs no pane client, the TUI's when it does. When reacting to output, handle the pane event messages (defined in `app/events.go`, handled in `update`) — and never `Send` from the Update goroutine's own handlers (the pump/timer goroutines own that). Status derivation on this path must carry its own re-evaluation guarantee: quiet fires once per burst and the health tick runs no status ladder for emulator instances, so an inconclusive detection (`updated=true`, or a quiet dropped while `Loading`) re-arms via `maybeRedetect`/`redetectMsg` until a sample sees unchanged content — a rule that assumes "the next poll will correct it" silently latches (the old `updated→Running` latch; regression tests in `app/status_redetect_test.go`). The ladder (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path, and `paneDirtyMsg`'s Ready→Running promotion) is a **display overlay**: it never writes the model, only `m.ladder[id]` (`setLadder`: a status and since when), which `overlay()` shows in place of the model's status for an active row whose view has no reported status (`!StatusReported`), and `pruneLadder` drops once its row is gone, inactive or reported. Its gates read the row as shown, overlay included. So the model's status of a non-Claude session is its lifecycle status (Running once started), which is also the status `state.json` saves; Ready and Prompting from the ladder live only in the TUI. For Claude sessions this ladder is the **fallback** — see the Claude roster and Claude status gotchas below.
- **Session lifecycle never attaches a tmux client; the TUI's pane clients do.** `session.Instance` holds a `tmux.Session` (launch, probe, type text and keys, kill) and never a PTY. The TUI holds one attach client per live agent session in `ui.PaneClients` (`home.panes`), keyed by tmux session name, so two open workspaces sharing a title share one client. Every pane render, scroll, cursor, mouse event, paste and inline-attach key, and the status scrape too, goes through `m.panes.For(v)` (`ui.Pane`, for a view `v`); a Cmd takes the panes it reads resolved on Update (`statusDetectCmd`'s argument, `snapshotScan`'s targets). The TUI holds no instance, so it never calls a display method on anything an instance holds. A client is keyed by the view's `TmuxSession`, and its adapter (its trust-prompt and pending-prompt patterns) comes from the view's `SessionProgram` (`inst.Pane().SessionProgram()`), never `Program`: a resume that reattaches a live session (`R` with a new program) keeps the old `tmux.Session`, while `Program` already names the new program. Only an active row (`InstanceView.Active()`: started, not paused, not Loading, Deleting or Recoverable) gets a client. The attach points (`app/panes.go`) all run on Update: `ensureSlotPanes` at every workspace load; `replacePane` when a start, resume or recover lands in a loaded slot (the model's `core.Started`, `core.SessionLaunched` and `core.Recovered` events, a Lua `inst:resume()` included, since it is a model request too), and after a workspace terminal's auto-restart (`core.SessionLaunched`, from core's `applyLiveness`), because the old client was watching the session that was replaced; `ensurePane` for the repair after the health tick's probe and the Dead event's (`VerifyDead`), both on `core.Alive` (live session, client not attached, not during a full-screen attach: `attachingID`), a returning full-screen attach, and a reverted kill or pause (`core.Reactivated`, emitted when an `OpFailed` is delivered), whose client a tick may have pruned while it was Deleting or Loading. A client is usable only while `TmuxSession.Attached` holds (its PTY is open and the pump draining it has not hit EOF on its own; each pump owns its exit flag, set after its Dead notification returns, so a late old pump can't mark a newer attach dead), never by `PtmxAlive`, which stays true after that EOF and only says there is a handle to close: `Ensure`, `Alive` and `ui.Pane.Attached` go by it, so a client left on a session that died and was relaunched under its name (a workspace terminal another slot's client watched, say) is re-attached instead of showing "[exited]" forever. Every exit is a Dead event whose repair attaches again, so `Ensure` leaves a client whose pump exited on its own within `quickExitHoldoff` (1s) of attaching it to the health tick, warning once per burst (`pane.client_exited_after_attach`): an attach that exits at once while its session lives (tmux under a TERM it can't use) otherwise looped hundreds of times a second. Every loom session sets `detach-on-destroy on`: agent and terminal-pane sessions, through `Session.Start` and through `Restore` for a session an older loom launched. So under a global `off` an agent that exits during a full-screen attach drops the user back to loom, and a user's own terminal attached to a loom session detaches when that session dies. The setting exists for loom's own clients: under a global `off`, tmux switches a destroyed session's clients to another session instead of ending them, so a client keyed by the dead session's name would show, and take inline-attach keys for, another agent's pane, and never read EOF. A status scan of a pane with no client is no opinion: `statusDetectCmd` has no Cmd for it. Releases go through `prunePanes`, which `Retain`s the active rows' session names and hands every other client to `releaseClientsCmd`, and per open slot also detaches the terminal pane's clients of titles the slot has no live row for (`keepsTerminal`: started, not Paused, not Recoverable; `TerminalPane.DetachExcept`, never `Close`, which would kill the shell). It runs on the health tick, on `core.ClientsStale` (emitted when a kill or pause completes, `KillResult`/`PauseResult`, and when an operation fails, `OpFailed`) and at every slot drop. Kill and pause do not close the client themselves, and have no TUI step: `Instance.Kill` and `Pause` end the agent's session and the terminal pane's shell (`CloseRelatedSession`, by name), which gives each pump EOF, and the prune the completion asks for (`ClientsStale`) releases both clients. The invariant: **a client is closed only after `Retain` or `Replace` has removed it from the registry.** That is why nothing re-attaches or double-closes a client while it closes (`Ensure` builds a new one): closing a still-registered client from a kill or pause job (the old TUI hook did) raced an `Ensure` or prune on the same name (a twin under a shared title, say), since `waitPumpExit` reads and writes `pumpDone` with no lock. A completion whose owner was closed attaches nothing, since nothing displays it. A release runs `PausePreview` (detach, session left running) off Update, because it waits for the output pump, which blocks in `tea.Program.Send` until Update returns. On creack/pty the attach fd is blocking, so the read deadline `signalPumpStop` sets can't cut the pump's read short: closing a client of a still-live session waits the full 2s `pumpWaitTimeout`, while a dead session's client closes at once. `releaseClientsCmd` closes its clients in parallel, so N live clients cost about 2s, not N×2s. Full-screen attach (`startFullScreenAttachMsg`) still runs `PausePreview` on Update and pays the 2s there, a known stall that predates the split. Making the PTY pollable, so a release takes milliseconds, is a follow-up. This split is daemon stage 1A: a `loom serve` that attached its own clients would fight the TUI's over the window size.
- **Claude's roster outranks the pane scraper.** `session/claude_roster.go` shells out to `claude agents --json` (`rosterQueryJob`, `core/claude_status.go`, ~100ms on 2.1.280, a job off the Update goroutine) on its **own 3s cadence** — `maybeRosterQuery` throttles by `rosterInterval` and guards against overlap through its `pollGate` (`gateRoster`), because the health tick it rides fires every 500ms on the snapshot path and an unthrottled subprocess there would keep a `claude` process alive much of the time (and stack concurrent ones if the CLI hung). Every throttled background job (roster query, hook scan, GitHub poll, usage probe, accounts refresh, Claude temp-dir sweep) is gated this way (`core/gate.go`; intervals live in `gateIntervals`, keyed by kind, so even a zero-value `core.Model` is throttled): `dispatchGated` arms the gate only when its builder returns a `core.Job` (no job means no result to disarm it), and wraps the result in a `gatedResult` that `Deliver` disarms (`deliverGated`) **before** routing the inner result to its usual handler — so every delivery, errors included, re-arms the job and no handler touches in-flight state (a missed disarm would latch the job off for the session). A `request()` made while a dispatch is in flight dispatches the job once more after that flight lands (`redispatch`). A job returns one value, so nothing can hide a second result from the disarm: the old rule against a gated `tea.Batch`/`tea.Sequence` is gone. The split-ratio flush tick is not a gated job: the TUI dedupes it with a plain flag (`ratioTickArmed`). The query returns every live Claude session keyed by **cwd** — the roster covers ordinary interactive sessions, not just `claude --bg` ones, so Loom's own tmux-hosted agents appear in it. The model's `roster` field holds the result; `rosterStatusFor` joins on `Instance.GetWorktreePath()` and maps `busy`→`Running`, `waiting`→`Prompting`, `idle`→`Ready`. Only **interactive** entries are joined: background (`claude --bg`) sessions publish `state` where interactive ones publish `status`, and a `--bg` session started inside a worktree would otherwise collide with Loom's own tmux session and blind the join for an instance whose identity is not in doubt. An entry with no `kind` counts as interactive (older CLI builds omit the field). A roster answer is offered to each active Claude instance as it lands (`observeRoster`), stamped with the query's start time, and merges with hook observations under the newest-wins rule (next gotcha). Only the model writes a reported status: its health tick (`deliverHealth`) and `applyClaudeStatus` (hook scans, roster answers) both go through **`adoptClaudeStatus`** (`core/claude_status.go`), the single choke point that applies the status *and* records `Instance.WaitReason`; never re-implement that pairing at a call site. The TUI's status paths (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path) write no status at all: they read the row's `StatusReported` (the view's copy of whether the merged observation has an opinion) **before** the content ladder, and on a reported row leave the status to the model, so the ladder overlay never covers it. An authoritative answer also **suppresses `maybeRedetect`** — the ladder re-samples only because one content hash cannot separate "still working" from "just finished", and the roster says which it is. It **fails closed** in the same sense as `DetectClaudeRemoteControlAuth` — on any uncertainty it expresses *no opinion* rather than guessing, and the scraper ladder decides: non-Claude agents, an empty/failed query, no entry for the worktree, an ambiguous cwd (two *interactive* Claude sessions in one directory — deliberately dropped in `QueryClaudeRoster`, with a `session.roster.ambiguous_cwd` debug line), a cwd holding only background sessions, and unrecognized status strings all return `false` from `rosterStatusFor`. The Claude CLI is therefore never a hard dependency; a machine without it behaves exactly as before. A failed query **clears** the roster rather than retaining it — stale statuses are worse than none — and turns every roster-sourced observation into no opinion (`claudeState.rosterSilent`); a hook-sourced one stands. `RosterEntry.WaitingFor` (Claude's own reason for blocking: `"sandbox request"`, `"dialog open"`, `"input needed"`, `"goal proposal"`, …) rides through `adoptClaudeStatus` onto the transient `Instance.waitReason` and replaces the generic "awaiting input" phrase in `CardData.statusLabel`. It is treated as an **opaque string** — displayed verbatim and truncated, never mapped to a Loom enum — so a reason string this build has never seen renders fine instead of degrading to Unknown. It lives exactly as long as the roster-driven wait: any non-Prompting or non-authoritative outcome clears it, so a dismissed dialog cannot leave a label behind. Never serialized (absent from `InstanceData`, so it needs no `SchemaVersion` bump). - **Claude status: hooks and roster, newest observation wins.** Each Claude instance holds one merged observation (`session/claude_state.go`, `claudeState`, guarded by `Instance.mu`): hook events (`SessionStart`, `UserPromptSubmit`, `PermissionRequest`, `Notification`, `Stop`, `SessionEnd`) and roster answers are both offered to it, each stamped with when it was *observed* — a hook event's `At` from its file name (`hooks.eventTime`), a roster answer's `rosterResult.at` (`core/claude_status.go`) taken before the subprocess starts — and the newer one wins whichever source it came from. There is deliberately **no grace window**: a live probe (spec `docs/superpowers/specs/2026-09-23-claude-hook-events-design.md`, payloads in `session/hooks/testdata/probe-2.1.280/`) showed the roster moving 0–90ms *before* the hook's timestamp, so an answer stamped after an event already reflects it; stamping with the query's *start* is conservative, since an answer can reflect only a later moment, never an earlier one. The opt-in `TestRealClaude_HookStatusContract` asserts that ordering. Rules that are easy to break: only parent events (no `agent_id`) count, except `PermissionRequest`, whose prompt shows in the parent; `Stop` ends a *turn*, not the work — a `Stop` listing a running `subagent` task is Running, and teammate and `shell` tasks never count (idle teammates stay listed as running); only `SessionStart` sets the session ID (a failed `--resume` sends a `SessionEnd` carrying the unknown ID); a roster answer with no opinion voids a roster-sourced status but never a hook-sourced one; a same-status roster answer keeps the hook's more specific reason (`permission: Bash`). Delivery: `maybeHookScan` (`core/hook_scan.go`, `gateHookScan`, 250ms) runs on the health tick, on pane output (`core.Model.PaneOutput`) and, through `pollGate.request()` (which dispatches once more after an in-flight job lands), on pane quiet (`PaneQuiet`), when `Stop` and `PermissionRequest` arrive; a scan that changes a status applies it at once (`applyClaudeStatus`) and `request()`s a roster query to confirm it, which is what corrects a lead that resumes after a teammate reply with no event. Answering a prompt fires no hook, so output on a Prompting session queries the roster (`maybeRosterQuerySoon`, at most every `promptingRosterSpacing`). A reported status also exempts the session from `paneDirtyMsg`'s Ready→Running promotion. Without a working roster two gaps remain: an answered prompt stays Prompting until the next hook, and a lead resuming after a teammate reply shows Ready. A relaunch resumes the recorded conversation (`BuildResumeCommand`: `--resume <id>` when the ID is a UUID and its transcript exists, else `--continue`; Claude writes the transcript with the first message, so a session that never got one falls back), and a stopped session's card shows the end of Claude's last message (`ui.MessageTailLines`), valid from its `Stop` until the next prompt or permission request. App and core test instances start on a mock tmux session, so `Start` never prepares their hooks folder: like a restored instance they have no launch ID and adopt a scan's. - **Subagent rows come from hooks, not transcripts.** Transcripts can't tell you whether an agent is running (each content block is its own record, and `stop_reason` is missing from ~60% of responses), so Claude is launched with `--settings {ConfigDir}/hooks/<folder>/settings.json`, where `<folder>` is the path-escaped tmux session name (`hooksFolderName`: `url.PathEscape(tmux.ToLoomTmuxName(title))`, always a single path segment, so a `/` in a title can't nest one instance's folder inside another's, where launching, killing or sweeping the outer one would delete it), registering `SubagentStart`/`SubagentStop`/`TeammateIdle`/`Stop`/`SessionEnd` (plus the status events of the previous gotcha). Each hook writes a file to `events/`; `core.Model`'s `maybeHookScan` (`core/hook_scan.go`, via `gateHookScan`) collects them into `Instance`'s `subagent.Tracker` and `claudeState`. Rules that are easy to break: hooks are prepared **only on real launches** (`launchProgram(…, true)`: `Start(true)`, `startFreshWithRecovery`, `CrashRestart`, `Restart`), never on `Restore`, because a reattached Claude is still writing to its folder. `Restart()` (the workspace-terminal auto-restart) is a real launch too: it closes the dead session and rebuilds it as `Session.WithProgramEnv(launchProgram(program, true), env)` with a freshly resolved env — reusing the old object would relaunch its stale command (for a restored instance, the bare program: no hooks, no loom context) while the tracker kept the dead process's rows. Every real launch resets the previous launch's state first, even when hooks end up being skipped: `resetHookLaunch` (`session/subagent_hooks.go`) clears the tracker, warm flag, Claude status and last message (keeping the conversation ID the relaunch resumes), sets the launch ID to the `noHooksLaunchID` sentinel so no scan result matches, and removes the old hooks folder; a successful `Prepare` then sets the real launch ID. The folder lives outside `worktrees/` because `DiscoverOrphans` would walk it. Only the **parent's `Stop`** reconciles against `background_tasks` (a `SubagentStop` list can omit a parallel foreground agent), and a missing or malformed list must never be read as empty. Teammates can't be matched by ID in that list, so shutdown is inferred by count. Read events are kept as compact `.ev` files so a restarted loom replays them (`Request.Cold`); a restored instance adopts the folder's `launch-id`, and results for another launch ID are dropped. A scan returning `ErrNoHooks` for a launch with a real ID means its folder vanished mid-run, and `ForgetSubagentsWithoutHooks` drops its rows. Everything fails closed: an agent without its metadata sidecar is hidden. Windows, non-Claude programs, a user-supplied `--settings`, or a `'` in the config dir path launch without hooks (the folder name itself escapes `'`). `claude_subagent_tracking` only decides whether `Instance.Subagents` returns rows (stored inverted as `subagentRowsHidden`, so the zero value is enabled): every Claude launch that can take hooks gets them, because they also carry status, the conversation ID and the last message. - **The GitHub poller is roster-shaped and fails closed.** `maybeGHQuery` (`core/github.go`) rides the model's health tick on its own `ghInterval` (60s) cadence through the same `pollGate` as the roster (`gateGH`); the `ghAvailable` backoff below is a pre-check ahead of `dispatchGated`, and no open repo means no dispatch, so nothing is armed. Each poll resolves + fetches the base ref per open repo (`git.FetchRef`, even without `gh`) and, when `gh` is available, runs `github.Query`; `ghState` is replaced wholesale, so an errored repo is dropped rather than kept — its cards render `Known=false` (nothing) rather than a stale badge, and `Known=true, HasPR=false` is a real "no PR", not "not yet checked". Results join onto `Instance.SetGitHubState` (transient; `viewOf` copies it into `InstanceView.GitHub` through `GitHubState()`, and `ui.BuildCardData` reads the view's); ahead/behind (`Instance.UpdateParity`, one local `rev-list`) rides the health tick's probe job (`probeJob`, `core/tick.go`) keyed on the model's `ghBases`. Call `core.Model.ExpediteGitHub()` to force the next tick to poll immediately (an in-flight poll still lands first) — a successful push (`core.Model.Push`, whose result `deliverPush` applies), an issue-born session (`handleIssuePicked`/`handleIssueExpanded`), the issue picker opening on a repo with no snapshot yet, and opening a tab (`OpenTab` expedites itself) all do this. The TUI reads the poll through `GitHubSnapshot`/`GitHubErr`/`GitHubUnavailable`, and `core.GitHubChanged` refreshes an open issue picker. GitHub state never sets `NeedsAttention`. `ghAvailable.ok` is a **one-way latch to true**: `maybeGHQuery`'s `req.check` is `!checked || !ok`, so once `CheckCLI` succeeds it is never re-run for the rest of the session — gh breaking mid-session (revoked token, network loss) surfaces only as per-repo query errors, never as an availability flip. An *unavailable* result is not latched the same way: it is re-probed every `ghRecheckInterval` (5 min) rather than forever, so a user who runs `gh auth login` after starting loom recovers without a restart. `ghPollRequest.configured` is a `map[string]string` keyed by repo path, built by `baseBranchByRepo()` from each open tab's own config, because the TUI's `m.appConfig()` is whichever slot is *focused*, not a shared primary — one string applied across the batch would resolve every non-focused repo against the wrong workspace's `BaseBranch`. `ghPollBudget` (45s) bounds the **entire** poll, not each repo: `github.Query` budgets each `gh` subprocess separately (2 list calls plus one `issue view` per linked closed issue), so without an overall ceiling one repo with many linked closed issues could stall every other workspace's refresh; it is deliberately kept under `ghInterval` so a poll can't outlive its own cadence. `UpdateParity` is called in `probeJob` **before** the `wantFull`/`ShouldRefreshDiff` early return — that gate exists to skip a git subprocess for an idle session with no tmux output, but the base branch moves with zero session activity, and "you are now N behind main" is exactly the case where `tmuxUpdated` is false. Both issue fetches are `core.Model.FetchIssue` requests (a `github.View` job) whose `Reply` carries the issue: the picker's pick and the `N` prompt's `#n` expansion record a `pendingIssue` holding an `issuePickedMsg` or `issueExpandedMsg`, which `handleReply` fills from the Reply and hands to `handleIssuePicked`/`handleIssueExpanded` (`app/state_issue_picker.go`). They can land up to ~20s after the user acted, into whatever is on screen by then; both handlers drop the result — with an explanation, not silently — when `msg.repo != m.repoPath()` (a different workspace is now focused) or `m.state != stateDefault` (another flow already owns the overlay and pending launch-options closure), because applying anyway would let `openLaunchOptionsForNew` silently replace it, stranding the other flow's draft. `handleIssueExpanded` also drops a result whose draft is no longer `m.draft` (a newer flow replaced it), and discards the draft whenever a guard fires (`issueExpandDropped`). `handleIssuePicked` returns on a fetch error before either guard; `handleIssueExpanded` degrades and continues on error (falls back to the literal, unlinked prompt), which is why its guards run **before** the `err != nil` branch instead of after.
- **x/vt callbacks run under the xvt wrapper's write lock.** `session/vt/xvt.go` registers `Callbacks` that fire inside `emu.Write`; they may only assign wrapper fields — re-locking `e.mu` deadlocks (RWMutex is not reentrant) and calling app code from them violates the no-model-mutation rule. New emulator-sourced state follows the same pattern: callback writes the field, a read-locked accessor exposes it. Events that must *notify* (not just store) follow the bell pattern: the callback sets a pending flag, and `Write`/`Resize` invoke the handler after releasing the lock — invoking under the lock deadlocked the whole UI once (bellFunc → `tea.Program.Send` blocks on the Update goroutine, which was blocked on `e.mu`; `TestBell_FiresOutsideWriteLock` pins this). - **Paused does not mean the worktree is gone.** When an agent exits on its own (`/exit`, a crash), the model's health tick (`applyLiveness`, `core/tick.go`) only calls `TransitionTo(Paused)` (`tick.tmux_gone_marking_paused`): no stash, no removal, so the worktree still holds the only copy of any uncommitted work. The same state arrives via a failed `CrashRestart` and via adopting a dead-tmux `Recoverable` orphan (adoption sets `crashRecovered` but nothing restarts it, so the tick pauses it). Resume therefore classifies the path with `GitWorktree.InspectTree` and feeds it to the pure `decideResume`: dead + intact → relaunch in place (recording a missing base commit, `EnsureBaseCommit`), dead + gutted → rebuild (move-aside), `TreeUnverified` or an unanswered probe → refuse. Intact means `.git` present **and** `git rev-parse` (stdout only; paths compared with `os.SameFile`) reports the path as its own top level and as a *linked worktree of this repository* (`--git-common-dir` matches the repo's, `--git-dir` differs from it), not still locked `initializing` by an unfinished `worktree add`. The `.git` check is load-bearing: git in a gutted dir under `<repo>/.loom/worktrees` answers for the enclosing repo. The unverified refusal (`unverifiedTreeError`) tells a `git.IsTimeout` (retry) from a rejection (move the directory aside, with a shell-quoted `mv`; the next resume rebuilds), and `sameFile` reports a path it cannot stat as that error, never as the tree "belonging to" another repository. The move-aside advice works for a tree still locked `initializing` too: a `worktree add` killed mid-checkout leaves its registry entry locked, which makes `remove -f` refuse it, prune skip it and `worktree add` refuse the path ("a missing but locked worktree"), so `clearWorktreePath` first runs `git worktree unlock` — only when nothing live is provably left at the path (`nothingLiveAt`: absent, not a directory, or no `.git`; one that cannot be stat'ed counts as live), since a tree with its `.git` may hold work and its lock is what stops the single `-f` from deleting it. `worktree add` itself runs under its own long deadline (`gitWorktreeAddTimeout`, via `addWorktree`), not the 8s tick budget whose kill left that lock. `finishResume` closes the dead session object before starting its replacement and refuses when the probe gets no answer. Anything that reaches `gw.Setup()` runs `git worktree remove -f`, which silently deletes an intact dirty tree — never route an intact tree there. `CrashRestart` refuses a non-intact tree for the same reason, `startFreshWithRecovery` never cleans up on a failed start (its old `gw.Cleanup()` deleted the tree and the branch), and `Start(true)`'s failed-start cleanup (`failedStartCleanup` → `CleanupFailedStart`) deletes the branch only if `Setup` created it: a reused title checks out the branch an earlier session left behind. That cleanup runs only when nothing can be running in the tree: a name `tmux.Start` refused before launching (`tmux.ErrSessionExists`), or a session `SessionLiveness` confirms Dead, as Pause requires — any other failure may come after the agent launched (the existence poll reads unanswered probes as "not yet", and the cleanup `Close` can fail), so the tree and branch stay and the error says the agent may still be running. A pending `StashRef` in place (`restoreStashInPlace`): no longer in `git stash list` → forget it, never re-apply it, whatever the tree holds; clean tree → apply; tree already equals the stash (`StashOnDisk`, an interrupted pause) → forget it and drop the duplicate; dirty and different → refuse (naming the full SHA) until the user drops the entry. The rebuild path asks `StashListed` too, *before* `Setup`, and fails closed (nothing rebuilt) when the list can't be read — it used to apply a stash the user had dropped, by SHA, since the commit survives until gc. When Pause aborts because the session survived `Close`, it drops its own stash and saves the cleared reference: the tree still holds everything the stash captured. `refs/stash` is shared by every worktree of the repo, and `git stash drop` only takes a stash@{N} position, which shifts under concurrent sessions: `DropStash` checks the SHA git reports dropping, stores a wrong entry back (retrying a failed store once; after that its error names the commit and the `git stash store` that restores it), and retries, and `StashListed` fails, never answering "not listed", when the list can't be read. **None of this may end at loom.log**: a forgotten stash may be the only copy of work, and a failed drop's error may be the only record of another session's entry. `ApplyStash` returns `git.ErrStashNotDropped` when the apply worked but the drop didn't (callers clear the reference and pass it on); a Resume or Kill that succeeded with something to report returns a `session.Notice` (`OnlyNotice` = the op succeeded; `NoticeIn` finds one inside a failure), naming the SHA plus `git stash apply <sha>` / `git fsck --unreachable | grep commit` for a forgotten stash. The model reports them as `core.Notice` events, which the TUI shows through `handleError` (`resumeOutcome` → `ResumeResult.Notice`, `KillResult.Notice`); a Lua `inst:resume()`/`inst:kill()` is a model request like the keys', so the model shows the notice the same way and the call returns without raising (its `Reply` carries the `Notice` too); Pause's abort includes a failed drop in its error. - **Only the deleting paths unlock a worktree.** `git worktree remove -f` refuses any locked tree, and an `add` killed mid-checkout leaves its tree locked `initializing` forever. `git.RefuseLocked` is called by orphan auto-clean (`RemoveOrphanWorktree`) and by `GitWorktree.Cleanup`/`Remove` (Kill, Pause). It removes that lock only once it is older than `gitWorktreeAddTimeout` plus a minute (loom kills its own add at that deadline). Any other lock, a user's or a young `initializing` one, gets a `*git.LockedError` (`errors.Is(err, git.ErrWorktreeLocked)`) naming `git worktree unlock`, returned before cleanup touches anything, branch and title sidecar included. Pause and Kill both check locks first (before Pause stashes, and before Kill closes the agent's tmux session or drops a stash), so a respected lock refuses either without killing the agent or leaving a pending stash, and a Kill a lock refuses keeps its row (`core.Kill` returns `OpFailed`) and shows the remedy, so D can be pressed again after the unlock. `reconcileOrphans` logs a locked orphan at debug and does not count it cleaned. `clearWorktreePath` (Setup, rebuild) deliberately keeps its own `nothingLiveAt` rule: an intact tree must never reach `remove -f`, and if one does, its lock is what stops it.
- **Claude's temp dirs are archived, not deleted, and found by physical path.** Claude keeps each session's scratchpad and task output under `<root>/<encoded cwd>/` (tmpfs on most Linux machines). Before loom archived it, that dir outlived every removed worktree. Pause archives it after the worktree is removed but before it marks the instance Paused (the status gate (`core.Model.Resume` only takes a Paused instance, plus the TUI's busy guards) keeps `r` off it, and `Resume` itself refuses while a Pause of the same worktree is in flight, which covers Lua `inst:resume()` and a reopened twin; the reverse holds too, and two of the same refuse each other, keyed by the canonical worktree path in `opsInFlight`). Kill archives it when nothing failed; a tmux session tmux confirms is already gone counts as closed (as in Pause), so killing an exited agent archives at once (a kill that fails leaves the dir for the sweep to take once the worktree is gone and the quiet period has passed). Both are best-effort. Resume restores `<name>.zip` before the agent launches, on the rebuild and relaunch-in-place paths only (a reattach launches nothing); a failed restore is a `Notice`, never a failed resume, and `Restore` creates a missing root (a reboot empties tmpfs). Lua `inst:pause()`/`inst:resume()` are model requests like the keys', so they archive and restore in the same jobs (the script waits for the Reply, not the engine's lock). Archives live in `<configDir>/archive/claude-tmp/` (dir 0700, files 0600) and are never pruned, unless the global `config.json`'s `claude_tmp_archive_dir` relocates them: `session.ClaudeTmpArchiveDir(configDir)` is the one place every archive, restore and sweep asks, re-reading the setting each time, and a resume also looks in the default folder so a zip parked before the setting changed is still restored. `<name>.zip` is the only file a resume restores; a Pause, Kill or sweep that finds one already there demotes it to `<name>.<UTC stamp>.zip`. Claude names the dir after its **physical** cwd, so `claudetmp.Names` encodes both the resolved path and the stored one, and `Locate` fails closed on zero or several matches and never matches a truncated name. `SweepClaudeTemp` is queued by `core`'s `reconcileOrphans` (`requestClaudeTmpSweep`, `core/claude_tmp.go`) on every workspace load (claim set snapshotted then; a workspace whose storage fails to load queues no sweep, since its claims are unknown) and dispatched by the model's health tick (`Model.Tick`) on `gateClaudeTmp`, one in flight; a dir that fails to archive is skipped until loom restarts, and the sweep reaps `.loom-trash-*` tombstones and `.loom-restore-*` restore staging dirs older than an hour and archive `*.partial` files (each archive writes its own, so a crash leaves one) older than a day. It takes a dir only when all of these hold: its name carries this config dir's encoded worktrees prefix and no other known config dir's (the encoding is lossy: `foo_bar` and `foo-bar` collide); it ends in a worktree timestamp and is not truncated; no record claims it; nothing in its top three levels changed in the last 24 hours (`sweepQuietPeriod`); and, rechecked just before archiving, no directory under the config dir's `worktrees*` dirs encodes to it. A live session's worktree exists before its Claude creates the dir, so a live session's dir fails that last check whenever its worktree is where the walk looks, and the walk fails closed at its depth limit; for the rest (a colliding workspace this loom doesn't know, an agent that outlived its Kill), the 24-hour quiet period is the backstop. Loom computes Claude's root from its own environment, so if the tmux server's `TMPDIR` or `CLAUDE_CODE_TMPDIR` differs, archiving finds nothing (safe); `loom debug` prints the root loom uses. `internal/testenv.IsolateLoomDirs` points `CLAUDE_CODE_TMPDIR` at a throwaway dir so no test reaches the real root. - **Inline orphan recovery (no modal).** `reconcileOrphans` (`core/load.go`, called from `OpenTab` and from `loadWorkspace`, the loader classic startup (`LoadClassic`), the restore fallback and `EnterGlobal` share — so it runs on every workspace-load path) auto-cleans stale worktrees and surfaces unsaved/live ones as `Recoverable` list entries. `Recoverable` is **ephemeral**: filtered out of `core.Persistable`, re-derived from disk each load, and inert (`EnsureRunning` no-ops on it). `r` recovers (`core.Model.Recover`: adopt via `ReconcileAndRestore`), `D` discards (worktree removed, branch kept via `IsExistingBranch`). When adding a per-instance loop, treat `Recoverable` like `Paused`/not-started so it never drives a PTY.
- **Lua LState is not goroutine-safe.** All `script.Engine` dispatch runs under `engine.mu`; the Bubble Tea main loop invokes scripts via a `tea.Cmd` goroutine and awaits `scriptDoneMsg`. A script's lifecycle calls and `ctx:new_instance` are intents the `scriptHost` adapter queues; `handleScriptDone` turns them into model requests on the main goroutine (`handleScriptIntent` → `scriptInstanceOp`, `scriptCreate`), and each call's coroutine resumes when its `Reply` lands (`scriptReplied`, a `scriptResumeMsg`) — the host holds no `*home` and the userdata holds views, so nothing running inside the engine can reach `m.list` or an instance.
- **No model mutation from `tea.Cmd` goroutines.** Bubble Tea runs every returned `tea.Cmd` in its own goroutine, concurrent with `Update`/`View` — so a Cmd body must not mutate shared state, nor read unlocked model state (`m.list`, `m.splitPane`, `m.core`, …; the slot's fields resolve through the embedded focused slot, which `loadSlot` swaps). The TUI holds no instance to reach: `TestTUIHoldsNoInstance` (`internal/testenv/instance_enforce_test.go`) fails on any production use in `app/`, `ui/` or `script/` of `session.Instance`, its constructors or its options (under whatever name the file imports `session`), and on the deleted bridges (`InstanceOf`, `IDFor`, `AdoptForScript`, `instOf`) anywhere; they read `core.InstanceView` copies and change instances only by request. `session.Storage`, `config.State`, and `tmux.TmuxSession` (its `ptmx`/`monitor`, via `stateMu` — snapshot under the lock, never hold it across PTY/subprocess I/O) each carry a mutex; `config.WorkspaceRegistry` does not, so its writes (`Add`, `UpdateLastUsed`, `SetOpenWorkspaces`) go through the model only (`core.Model.Register`, `SetLastUsed`, `PersistOpenList`), on Update — the startup registration prompt's Cmd returns `registerWorkspaceMsg` and Update calls `Register`. A `core.Job` follows the same rule as a Cmd body: it reads no model state. What it needs is captured on the model's goroutine when the job is built, as `saveSnapshot` (the instance list Pause and Resume save, `core/ops.go`) and `recoverInst` (the placeholder's record and config dir) do; the job only runs I/O and returns its result for `Deliver`. The outbox has its own ordering rule: the model's events apply at the end of `Update` (`drainCore`), so a caller whose next steps depend on an event's effect drains right after the model call — the workspace transitions do (`activateWorkspace`, `enterGlobalMode`, `restoreSavedWorkspaces`), so a load's notices land before the recovery summary shown next, as they did when the load set them itself. `scriptHost` holds no `*home`: script nav/scroll/diff/workspace primitives record a `func(*home)` via `deferModelMutation`, drained into `scriptDoneMsg` and applied on the main goroutine in `handleScriptDone` (the ones that move the selection or the focused slot go through `deferFocusMutation` and apply only in `stateDefault`: the message can land after an awaited intent opened a flow), and reads (`ctx:selected()`, `ctx:instances()`, `ctx:config_dir()`, …) come from a snapshot `newScriptHost` takes on the Update goroutine when the dispatch or resume begins. The snapshot (views, minus the draft row) pins the focused slot, and `scriptDoneMsg.slot` carries it back: `handleScriptDone` sends a `ctx:new_instance` as a `Create` in that slot's workspace (`scriptCreate`) only if that slot is still focused, decided before the script's deferred actions run (one of them may be its own workspace switch); otherwise the call raises "new_instance: workspace changed while a script ran; not creating <title> here" (its deferred UI actions still apply to the new slot). Verify concurrent code with `go test -race` (see Build & Development Commands).
- **Script key collisions.** `cs.bind` / `cs.register_action` overwrite each other — last-write-wins across all scripts and `defaults.lua`. `ctrl+c` is hard-reserved in the default state (app-level) so user scripts cannot steal the interrupt; `keys.KeyForString` is a reverse lookup of the built-in binding table used only for menu-bar highlighting, not for dispatch gating. Duplicate load-order: `defaults.lua` loads first, then `~/.loom/scripts/*.lua` in filename order, so user bindings for the same key win.

- **Overview and workbench are `viewMode`s, orthogonal to the state machine.** `m.viewMode` (focus/overview/workbench) is not an `m.state` value — overlays and per-state handlers work unchanged on top of it. In overview, `state_default.go` gates script dispatch through the `overviewKeyAllowed` whitelist (everything else no-ops rather than acting on an invisible pane), mouse events are dropped, and bell/attention badges clear only on entering focus so the attention-sorted grid stays stable while you look at it. - **The focused workspace slot is embedded, not copied; a slot is a view over a `core.Workspace`.** A slot (`workspaceSlot`, `app/workspaces.go`) is `{ws, views, list, splitPane, workbench}`: the model's workspace plus the view over it. The workspace's context, storage, config and app state belong to the `core.Workspace` and are read through accessors (`m.wsCtx()`, `m.storage()`, `m.appConfig()`, `m.appState()`), never copied. Its instances are the model's, edited only by the model; the slot keeps their published views (`views`, the store `ViewsChanged` replaces), which the rail reads through `slotRows`, and acts on them only by request, by `InstanceID`. `home` embeds `*workspaceSlot` — the focused slot — so `m.ws`, `m.list`, `m.splitPane`, `m.workbench` and the accessors resolve to that slot's own, and `m.slots` is `[]*workspaceSlot`: every open slot's state is always current, with no save step and no `i == m.focusedSlot` branch to pick "the live copy". Invariant (`checkSlotInvariant`, asserted in tests): `m.slots` mirrors `core.Model.Tabs()` in order (`m.slots[i].ws == Tabs()[i]`); with tabs open, `m.workspaceSlot == m.slots[m.focusedSlot]`; with none (classic/global mode) it is the classic slot, which is not in `m.slots` and shows `core.Model.Classic()` (its context is the startup context; the global workspace `EnterGlobal` builds carries `config.GlobalWorkspaceContext()`, the same nameless, repo-less context classic global startup gets, so both resolve `LOOM_GLOBAL_DIR`, never `LOOM_HOME` — `m.wsCtx()` is nil only in bare test homes); never nil. The model owns the transitions (`core/workspaces.go`: `OpenTab`, `CloseTab`, `EnterGlobal`, `StayGlobal`, `RestoreSaved`), and the TUI builds and drops the views around them (`activateWorkspace`, `deactivateWorkspace`, `enterGlobalMode`, `stayInGlobalMode`, `restoreSavedWorkspaces`; `newSlotView` builds a view); the ones that load (`activateWorkspace`, `enterGlobalMode`, `restoreSavedWorkspaces`) drain the model right after the call, so the load's notices land first. Change focus only with `loadSlot`, which runs `leaveFocusedSlot` (workbench cleanup + pending split-ratio flush) on the departing slot before the swap, so every focus change flushes. Every `m.slots` mutation restores the invariant before returning: `activateWorkspace` focuses the first tab opened from classic mode; `deactivateWorkspace` refocuses via `loadSlot` when it closes the focused tab, and `CloseTab` refuses to close the last one (and keeps a tab whose save fails open) — leaving workspace mode is `EnterGlobal`'s job, which saves every tab before it even reads the global state (the load crash-restarts agents and cleans orphans and hooks, which an abort could not undo) and aborts with nothing switched if a save or the load fails (a Global commit made from global mode itself rebuilds nothing: `StayGlobal` only closes the failed-to-restore workspaces); `applyWorkspaceToggle` keeps the open tabs when every desired workspace failed to activate. Never "switch" workspaces by editing the focused slot: the rule that used to forbid assigning its promoted handles is now enforced by there being none to assign, since a slot shows one `core.Workspace` for its life and a workspace's handles are fixed for its own. Every slot needs a non-nil `splitPane` and `workbench`. Dropping a slot (closing a tab, the classic slot giving way to the first tab, `enterGlobalMode` dropping the tabs or a classic workspace slot) must release the clients it no longer needs. Each drop site returns two Cmds: `prunePanes`, which closes the pane clients of sessions no loaded instance is active on, and `releaseSlotCmd`, which detaches the attach clients its terminal pane holds on `loom_term_*` shells (`TerminalPane.DetachAll`, never `Close`, which kills the shells; the pane `enterGlobalMode` carries into the global slot keeps only the clients of sessions the global list holds (`DetachExcept`)), and the caller also runs `instanceChanged` so the panes and menu (the global slot carries the old `splitPane` over) keep no copy of a dropped row. The release runs `PausePreview` in the Cmd, never on the Update goroutine — it waits for the output pump, which blocks in `Send` until Update returns. The model's `applyLiveness` drops probe results for instances no loaded workspace holds, so a stale tick can't re-attach a released one. Async completions follow the identity and owning-slot rules in the next gotcha. `openSlots()` yields the open tabs, or the classic slot alone, for fleet-wide walks.
- **Destructive actions target instances by `InstanceID`; async completions act on the workspace stamped at dispatch.** A kill, start, resume or recover runs for seconds with the UI live, and meanwhile the user can move the selection, switch workspace, close the owning tab or open another flow. So two rules, with no exceptions: (a) **By identity, never by selection or list position.** The TUI names the instance a request acts on by its `InstanceID`, read from the row when the key's gate passed (a confirmation's task captures it then) and never re-resolved from the selection; the model never reuses an ID, so a stale one is refused (`ErrNoSession`) rather than landing on whatever took its place. A creation flow's session-to-be is the TUI's `draft` until `Create`, so cancelling one (`discardDraft`, from every cancel path, `discardPendingLaunchOptionsCancel` included) has nothing to kill. Inside the model, completions act on the `*session.Instance` they carry (`core/completions.go`): a failed start (a `StartResult` with an error) removes its instance from its owner's workspace and kills that instance (`killUnstarted`), a `KillResult` removes its instance from every loaded workspace through `removeEverywhere`, and an `OpFailed` reverts the instance it carries. Never reach for "the selected instance" or "the last row" in a completion, reply or cancel path. (b) **Stamped with the owning workspace, never "whatever is focused".** Each async completion carries the workspace it belongs to, stamped on the Update goroutine at dispatch: `scriptDoneMsg.slot` (the slot the script host snapshotted), the model's `core.StartResult.Owner` and `ResumeResult.Owner` (from `startOwner`, the loaded workspace holding the instance, not the focused one; the workspace the TUI passes is only the fallback) and `RecoverResult.Owner` (the workspace holding the placeholder, found by the `Recover` request's lookup). `KillResult` and `OpFailed` carry the instance and act on it wherever it is loaded (a pause saved inside its job, so `PauseResult` only asks for a prune). `handleScriptDone` creates a script's `ctx:new_instance` only in that slot, refusing it (the call raises) if focus has moved since. The model's completions (`deliverStart`, `deliverResume`, `deliverRecover`, …) resolve the owner (`owningWorkspace`), act on its instances and storage (`core.Model.Save`, which skips a closed workspace's save once a loaded one has reopened it), and report through events (`Started`, `Recovered`, `SessionLaunched`, …). The model has no focus, so the focus rules live in the TUI's appliers (`app/completions.go`: `applyStarted`, `applyRecovered`), which touch the focus UI (select, inline attach) only when the owner is the focused slot. An N flow's initial prompt is sent by a job after the start lands (`sendInitialPrompt`), and `Started` is emitted only once that send returns (`deliverPromptSent`), so inline attach, which forwards keys to the agent, begins only after the prompt is in and no typed key can join it. The user can confirm a kill or pause during the send, so `applyStarted` enters inline attach only on a row still active (`InstanceView.Active()`, the test `replacePane` attaches a client by). A start or resume whose owner was closed meanwhile attaches no pane client, since nothing displays it, unless its workspace was reopened meanwhile: then it swaps itself in for the reopened workspace's copy of its record, matched by title and worktree path (`reopenedTwin`; reconcile turns the Loading record into a Paused, unattached instance), provided its tmux session survived the reopen (`adoptIntoReopened`: reconcile kills a session that was already up). And no completion moves the focused slot's selection unless `m.state == stateDefault`: creation flows, inline attach and the prompt overlay act on the selection, so moving it would retarget them (script primitives that move the selection or the focused slot apply through `deferFocusMutation` for the same reason). A job that needs the owner's storage captures it when the model builds it, from the workspace its request's lookup found (`killInst`, `pauseInst`, `saveSnapshot`); a kill or pause has no TUI step (see the pane-client gotcha). Reading `m.*` inside the goroutine races `loadSlot` and reaches the wrong workspace after a switch.
- **The TUI's copies of a view go stale; reread them.** Views are values, so whatever keeps one keeps a copy that follows nothing on its own: the split pane and the menu hold the selected row (`SetInstance`), a Cmd holds the row it was built from (`statusDetectCmd`'s argument), the script host its dispatch-time snapshot. The slots' stores catch up with the model only at the drain (`ViewsChanged`, from `Sync`), and `refreshSelection` repoints the split pane's and menu's copies at a fresh copy of the selected row on every store or overlay change (the `ViewsChanged` applier for the focused slot, `setLadder`, `newDraft`/`discardDraft`, `createReplied`). So a request whose pre-step changes the model at once (a kill's Deleting; a pause's, resume's or recover's Loading; a create's new row) shows in the same Update only after `syncViews`: `runTask` runs it after a confirmation's task, the unconfirmed kill, pause, resume and recover paths after their request, and `attachDoneMsg` after a full-screen attach, which held the event loop while jobs landed. Those call sites are mutation-pinned in `app/views_freshness_test.go`. Code that keeps a view beyond one Update must re-read it by ID when it acts (`viewByID`, `viewBySession`), or be a deliberate snapshot that a request re-validates: the merge picker's sources (`pendingMergeSourceItems`) are frozen when it opens, so a background change can't retarget the merge, and `Merge`'s `admit` refuses a side that is gone or busy by the time it commits.
- **Overview cursor and nav share one classic-vs-slots split.** `overviewData`'s cursor translation, `moveCursor`/`fleetOrder`, and `jumpWaiting` all key on the same `len(m.slots)==0` classic-vs-workspace-mode split — keep them in sync or nav and render diverge. In workspace mode they read every slot's list as `m.slots[i].list`, the focused one included (it is the same object as `m.list`). The overview only ever renders open workspace slots; there is no background/lazy fleet loading (removed 2026-07-21).

- **Every tmux exec goes through `tmux.Command`/`tmux.CommandOnSocket`.** They honor `LOOM_TMUX_SOCKET`; a raw `exec.Command("tmux", …)` would follow `$TMUX` to whatever server encloses the process. **Every target is exact, built by `tmux.SessionTarget`/`tmux.PaneTarget`** (`session/tmux/target.go`): a bare `-t name` falls back to a prefix match when no session has exactly that name, and loom's sessions die on their own all the time, so a command aimed at a dead `loom_api` lands on a live `loom_api-v2` — closing it killed the sibling (`TestKillIsExactMatch_RealTmux`), and `Restore`/`ResumePreview` attached the dead session's preview PTY to it, so its seed, emulator and every keystroke, paste and initial prompt went to the other agent (`TestDeadSessionNeverReachesPrefixSibling_RealTmux`; likewise `FullScreenAttachCmd`, the captures, and `RenameLegacySessions`, which renamed `claudesquad_api-v2`). Session-typed commands (`attach-session`, `has-session`, `kill-session`, `rename-session`, `switch-client`) take `"-t", SessionTarget(name)` (`=name`); pane- and window-typed ones (`capture-pane`, `display-message`, `send-keys`, `paste-buffer`, `set-option`, `resize-window`, `list-panes`) take `"-t", PaneTarget(name)` (`=name:`) — plain `=name` fails there ("can't find pane: =loom_x"; `set-option` says "no such session"), while `=name:` works and fails cleanly on a missing session (`display-message` then prints empty formats and exits 0). `TestTmuxTargetsAreExact` fails the build on any production `"-t"` not followed by one of the two helpers, and on any target spelled inline (`"-t="+name`, `fmt.Sprintf("-t=%s", …)`); its allow-list holds only `EnclosingSessionName`'s `$TMUX_PANE` pane id. Session names never hold `:` or `.`: `ToLoomTmuxName`/`ToLegacyTmuxName` drop whitespace and map both to `_`, because tmux creates `loom_fix:login` literally but every target parses `:` and `.` as its session:window.pane separators (`-t=loom_fix:login` asks for window `login` of `loom_fix`), so a title like "fix: login" used to probe Dead until `Start` timed out, `Close` could not kill it, and the failed-start cleanup removed the worktree under the running agent (`TestColonTitle_StartsProbesAliveAndCloses_RealTmux`). Titles differing only in those characters share a session name; the second `Start` fails with "already exists". A name that still holds one (made by an older loom, or another tool) cannot be targeted exactly at all (`-t=loom_feat:0` kills `loom_feat`), so the orphan sweep skips it (`tmux.ExactlyTargetable`, `orphan_tmux.skip_untargetable`). `TestNoRawTmuxExec` fails the build on any raw tmux exec outside `session/tmux/command.go` (whose `EnclosingSessionName` is the one deliberate exception).
- **Every git/gh exec goes through `internalexec.GitCommand`/`internalexec.GhCommand`** (`internal/exec/command.go`). `GitCommand(ctx, dir, args…)` adds `-C dir` (none for `""`) and forces **only git's message language** to C, because callers classify failures by matching git's **English** stderr (`isBranchAbsentErr`, `isWorktreeAbsentErr`, the `worktree unlock` answers in `unlockWorktree`) and parse its English output (`parseShortStat`'s "insertion"/"deletion"); a user's non-English locale would silently misclassify both. The env comes from `gitEnv`: it drops `LC_ALL` and `LANGUAGE`, re-pins every other `LC_*` category to the user's `LC_ALL` value when one was set (so their effective locale is unchanged), and appends `LC_MESSAGES=C` last — gettext and `strerror` translate from `LC_MESSAGES`, and gettext ignores `LANGUAGE` once it resolves to C. Not `LC_ALL=C`: `post-checkout` runs on every session create/resume under loom's git, and hooks such as Ruby's overcommit break under an ASCII `LC_CTYPE`. So git error text shown in the TUI is always English, while child processes git spawns (hooks, filters, textconv, credential helpers, gpg) keep the user's character set and collation; only their message language is forced to C. A caller needing extra env appends to `c.Env` (see `runGitCommandEnvTimeout`), never rebuilds it from `os.Environ()`. `GhCommand` sets `GH_PROMPT_DISABLED=1` and `GH_NO_UPDATE_NOTIFIER=1`. - **The orphan sweep kills only sessions it can prove it owns; the nesting guard backs it up.** `CleanupOrphanedSessions` sees every session on the server it talks to, and "not in my lists" is no proof of an orphan: on 2026-09-23 a second loom's startup sweep killed all 20 loom sessions on a shared server, including the first loom's live agents in workspaces the second never loaded. So it kills an unclaimed `loom_*`/`claudesquad_*` session only when its start directory lies under a root this process owns (the ownership rule in the `session/` bullet); anything else is left running. `loom reset` uses the same rule with nothing claimed: it kills the reset workspace's sessions (default: global's), not every loom session on the server, since it deletes only that workspace's records and worktrees (`tmux.CleanupSessions`, the old kill-everything helper, is gone). The sweep returns a `SweepResult` (killed / unowned / untargetable / failed, logged every time as `orphan_tmux.sweep_done` at info) and an error for any listing failure other than "no server running" (`isNoTmuxServer`) and for every failed kill: some of the workspace's agents may still be running then, so `reset` stops before deleting worktrees and branches under them (`TestResetCmd_StopsBeforeWorktreesWhenSweepFails`); the startup sweeps only log it. `OpenTab`'s pre-start kill of a leftover session under the workspace terminal's title goes through the same test (`session.KillOwnedTmuxSession`): the title is just the workspace's name, which another loom's workspace elsewhere can share, so a session not started in this workspace's roots — or any listing that fails — is left running, and the terminal's `Start` then fails on the name instead. The rule does not stop a nested dev loom that loads the *same* workspace as its host from sweeping the host's sessions, so `main.go`'s `nestingCheck` refuses the TUI and `reset` inside a `loom_*`/`claudesquad_*` session unless `LOOM_TMUX_SOCKET` names a server other than the enclosing one (or `LOOM_ALLOW_NESTED=1`) — a tmux server copies the environment of the client that started it, so every pane of a server started with `LOOM_TMUX_SOCKET` set inherits that same variable, and trusting it unconditionally would wave through a bare run inside its own sandbox server. Run dev builds through `tools/loomdev`, never directly in a pane. The guard only recognizes loom-managed enclosing sessions (`loom_*`/`claudesquad_*`); a dev loom started from a non-loom tmux session (e.g. a plain shell pane) on a server that also hosts loom sessions is not refused, so use `loomdev` (or `LOOM_TMUX_SOCKET`) there too.
- **One TUI per global dir; a second one takes over.** Two looms on the same workspaces overwrite each other's sessions: `Storage.SaveInstances` rewrites a workspace's whole list from the writer's own memory, so each loom's saves (create, kill, recover, quit) drop the records only the other knows. The dropped ones come back as `Recoverable` orphans that have lost their launch flags, conversation ID and (when dead) account. Both looms would also attach a client to every agent session and fight over its window size. So the TUI holds an flock on `<globalDir>/loom.lock` for its lifetime (`internal/takeover`; the OS releases it on exit, crash included) and serves takeover requests on `<globalDir>/loom.sock`. `main.go`'s `acquireUILock` takes it **before the registry or any state is read**. When it is held, it asks `Take over? [y/N]`, naming the holder's pid, tty and start time from the lock file. On yes it sends a request (`takeover.Request`), and the holder's listener ends a full-screen attach (`foregroundAttach`: the attach's context is cancelled, and `FullScreenAttachCmd` turns that into SIGTERM, a clean tmux client exit) because the event loop is blocked in it. The holder then sends `takeoverMsg`, which saves like `q` (`saveForQuit`) and quits, printing who took over. The newcomer waits for the lock (`takeoverWait`, 15s), so it loads what the holder saved last. A save that fails keeps the holder running and the newcomer times out naming `kill <pid>`. A holder in `$EDITOR` or `claude auth login` is never interrupted, which also ends in that timeout. Without a terminal the newcomer refuses, and a lock that can't be taken at all warns and starts unlocked. A loom from before the lock holds none, so the first takeover after upgrading can't see it. Never remove `loom.lock`: a contender waiting on the old inode and a new holder on a recreated one would both "hold" it. CLI subcommands don't take the lock, and loomdev sandboxes have their own global dir.
- **Claude accounts are config dirs, linked, and resolved at launch.** An extra account's dir symlinks every top-level entry of the main config dir except a deny-list (`.credentials.json*`, `.claude.json*`, `sessions`, `daemon`, `daemon.log`, `session-env`, `ide`, `debug`, `cache`, `backups`, `shell-snapshots`, `statsig`, `jobs`, `stats-cache.json`, `.last-cleanup`, and each session's own `security_warnings_state_<uuid>.json`), so `projects/` (transcripts, auto-memory) is shared and `--resume` works across accounts. `Create` also seeds the main dir's own `projects/` (only when the main dir already exists) before linking, since Claude only creates it lazily on a config dir's first session — without this, the very first account made on a fresh install would never get it linked, and cross-account `--resume` would have nothing to share. `Sync` never replaces a real file: a link turned into a file (an atomic rewrite through it) is reported as diverged, since it may hold the only copy of a change. `Remove` and `Unshared` act only on `OwnedDir`'s return value — `filepath.Join(AccountsDir, name)`, recomputed from the account's name — never on the registry's raw stored `Dir`: a stored value like `<AccountsDir>/lnk/../name` can clean lexically to the canonical path while a symlinked `lnk` makes the kernel resolve it somewhere else entirely first, and acting on the raw string there deleted real content outside the account's own dir before `OwnedDir` was fixed to return the canonical path itself. A dir the account doesn't own that way is unregistered but left on disk. Without `force` `Remove` refuses (`*UnsharedError`) while the account dir holds real, non-symlink entries `Unshared` finds that aren't shared with the main dir, since those may be the only copy of a change; `os.RemoveAll` on an owned dir deletes the links themselves without following them. `LoadRegistry` goes further and refuses to *load* any account whose stored `Dir` is not in `filepath.Clean` form or does not resolve (`resolvedOrClean`: `EvalSymlinks` on the raw path first, so a `lnk/..` can't be cancelled lexically) to `<AccountsDir>/<name>`, then canonicalizes every loaded `Dir` in memory to `filepath.Join(AccountsDir, name)` (`canonicalizeDirs`), so a respelled global dir still loads but the stored spelling never reaches a launch, Sync or `Remove` — a hand-edited "bring your own directory" entry is out of scope entirely, since that same stored `Dir` is what gets launched as `CLAUDE_CONFIG_DIR` on every launch, so catching it only at removal time was never enough. The model reloads the registry (`ReloadAccounts`) before every user action that reads it and on its own cadence otherwise (see the reload-then-diff gotcha below), and `LoadRegistry` validates every loaded entry — an invalid or duplicate name, a non-absolute dir, or a dir that isn't `<AccountsDir>/<name>`, zeroes the loaded list and latches every write shut (`ErrRegistryLoadFailed`), the same as a file that fails to parse. Instances store the account *name* (`InstanceData.Account`, schema v8, "" = default); every real launch resolves it through the map the model publishes with `session.SetAccountDirs` (`publishAccounts`, `core/accounts.go`) and fails closed rather than falling back to default, which would bill the wrong subscription: `*MissingAccountError` for a name the registry no longer has, `*AccountDirMissingError` when the account is still registered but its dir has vanished from disk (the CLI would otherwise silently start a fresh, logged-out identity there instead), and `*RegistryLoadError` when the registry itself won't load — `SetAccountDirs` carries that error alongside the dirs map so it is never reported as "account removed". Both of the first two name their own fix in their message text rather than leaving the user to guess: `MissingAccountError` points at R on the existing session (pick another account there), `AccountDirMissingError` at `loom account remove` then adding the name again. Every account-scoped `claude` subprocess that captures output — `AuthStatus`, `ProbeUsage`, the roster query (`session.QueryClaudeRosterEnv`) — goes through `account.Command`, which refuses a missing `CLAUDE_CONFIG_DIR` up front (`ErrAccountDirMissing`) rather than let the CLI recreate it empty and logged out. `LoginCmd` does *not*: it hands back a bare interactive `*exec.Cmd` for `tea.ExecProcess`/the CLI's own foreground `Run()`, not a captured `Output()` call `Command`'s dir check could gate — so both callers (`cmd/account.go`'s and `app/accounts.go`'s `accountLoginCmd`) `os.Stat` the account's dir themselves first and refuse with the same advice (remove, then add again) rather than let `claude auth login` bootstrap a bare, unlinked identity there. `claude auth login` stores the credentials and `oauthAccount` but leaves `.claude.json`'s `hasCompletedOnboarding` unset, and the interactive CLI runs its onboarding (login screen included) whenever that flag is missing, so the first session on an account logged in from the CLI asked to log in again: every launch on an account (`launchEnv(true)`) therefore calls `account.EnsureOnboarded`, which sets the flag only for a logged-in account (`oauthAccount` or `.credentials.json`), keeps every other key, and never rewrites a file it can't parse; a failure is logged, not fatal. The Account row, and `CLAUDE_CONFIG_DIR` with it, is Claude-only — only Claude programs get it (`LaunchEnv`/`ClaudeConfigDirEnv`), so a wrapper program's sessions always run on the default account, and so does the terminal pane's shell regardless of the agent's account. The roster is per config dir (`claude agents --json` under an empty dir returns `[]`), so `rosterQueryJob` runs one query per account in use and `rosterStatusFor` joins `rosterByAccount[inst.Account()]` (the default account's stays in the model's `roster`); one account's failed query clears only its own entries. Remote-control auth is per account too (`core.Model.RCAuthFor`; an extra account not read yet is Unknown: no flag). Usage comes from `account.ProbeUsage`, a headless `claude -p` stream-json run answering the SDK's **experimental** `get_usage` control request (`skip_behaviors`, `--setting-sources ""`, `--strict-mcp-config`, no model call, ~1.4s observed), polled every 2 min on `gateUsage` and expedited when a picker opens; `TestRealClaude_UsageProbe` (opt-in, free) pins its shape. Usage is display-only: a failed probe keeps the last sample, dimmed with its age — the opposite of the roster's "stale is worse than none", because nothing acts on it. All account UI (strip, Launch Options row, badges) and polling stay off until an extra account exists; the strip's row goes through `topChromeHeight`, never `tabBar.Height()` directly. Three account-selection gaps stay open by design: `R` on a Paused session whose tmux session is still alive reattaches to it (`decideResume` → `resumeReattach`) on its old account even after picking another — reattaching launches nothing, so `Instance.Resume` skips the account resolution that would otherwise fail closed; an orphan recovered from disk (`r` on a `Recoverable` entry) whose tmux session is dead comes back on the default account, since nothing on disk records which one it ran on (a *live* one keeps its account: discovery reads the session's `CLAUDE_CONFIG_DIR` back with `tmux show-environment` and maps it through the registry, `liveSessionAccount`); and `remove --force` on an account a live session still uses can lose the race with that session's own Claude process, which can recreate a bare, unlinked dir there right after the delete — a later `add` of the same name then fails ("already exists") until the leftover dir is cleared by hand.
- **A credential in loom's own environment silently overrides every account, and loom can end up running as one itself.** `account.CredentialOverrides` lists `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` — the same env vars the Claude CLI checks *before* ever reading a config dir's own stored credentials — and `ActiveCredentialOverride` returns the first one set in loom's own environment. With one set, every account session runs and bills as that credential regardless of which `CLAUDE_CONFIG_DIR` loom launches it with, so switching accounts is a no-op the UI can't hide: the strip leads with "`⚠ $VAR set: all accounts use it`" (`ui.AccountStrip.SetWarning`/`credentialOverrideWarning`), the Accounts screen shows the same text as a screen-wide notice above its rows while an extra account exists (`SettingsOverlay.SetAccountNotice` → `AccountsManager.SetNotice`; hidden with only `default`, since there is no choice for it to void), and `loom account add`/`login`/`list` each print the same warning (`use`/`sync` don't, since neither runs a session). `extraAccountAuth` leaves an override-caused remote-control block's reason untouched — no login would fix it — rather than composing the "run `loom account login <name>`, or Settings → Accounts → l" hint it otherwise attaches to every other blocked reason. Separately, `warnIfRunningAsAccount` checks once at startup whether loom's own `$CLAUDE_CONFIG_DIR` already resolves inside its own accounts dir (started from an account's agent pane, say) and warns that "default" is actually that account's login, usage and sessions, not the main login's.
- **`loom account`'s CLI guards against unsafe or stale state before it touches anything.** `remove`'s `--yes`/`-y` skips only the confirmation prompt; `--force` is the one flag that overrides the in-use and unshared-files refusals, and reports what it overrode — `--force` alone still asks to confirm, so it can't be one accidental keystroke away from deleting a session's only account. The unshared-files check runs (and, if it refuses, reports) *before* the confirmation prompt, so the user is never asked to confirm a removal that then turns out to be refused; the prompt itself reads "delete `<dir>`" only when `Registry.OwnedDir` says loom owns that config dir, else that the dir isn't loom's and will be left in place. `account.ValidateMainDir` (absolute, symlink-resolved, neither inside nor containing the accounts dir) gates `add`, `sync` and `Registry.Create` before any linking starts — the TUI's account-add path runs through `Create` and so is covered too; its background refresh (`accountsRefreshJob`, `core/accounts.go`) applies the same guard through `syncMainDir` before re-syncing an existing account, skipping the Sync (and logging the refusal once, not on every tick) rather than linking from an unsafe dir. `login` (both the CLI and the Settings screen) refuses a registered account whose config dir has gone missing from disk, rather than let the CLI recreate it there bare and logged out, and says to `remove` then `add` it again instead. The CLI's own login (`runWithChildSignals`) catches SIGINT with `signal.Notify`/`signal.Stop` around the child rather than `signal.Ignore`: an ignored disposition is `SIG_IGN` at the OS level and survives `exec` into the login child, so Ctrl-C during `claude auth login` would reach neither loom nor claude (verified against a real child's `/proc/self/status` `SigIgn` mask); `signal.Notify` resets to the default disposition across `exec` instead, so the child gets an ordinary, interruptible SIGINT. `list` probes every account in parallel (one goroutine per row) and, when no main config dir can be found, skips the default account's usage probe with a "no main config dir found" note rather than run it in whatever directory `list` happens to be invoked from (`ProbeUsage`'s cwd becomes a project entry in Claude's own config). Run from a shell whose own `CLAUDE_CONFIG_DIR` already resolves inside `<AccountsDir>/<name>` — an account's own agent pane, say — `add`, `list`, `sync` and a bare `login` (or `login default`) all refuse (`guardAgainstAccountEnv`/`accountFromEnv`): treating that inherited env as "the default account" would silently log the wrong identity in as default, or list/sync it as the main login. `use`, `remove` and a named `login <account>` are unaffected, since they already read that account's own `CLAUDE_CONFIG_DIR` override rather than the inherited one. `cmd` deliberately does not import `session` — `session/tmux` imports back into `cmd`'s own tests, which would cycle — so `isClaudeProgram` asks `session/agent`'s adapter registry directly instead of `session.IsClaudeProgram`. `cmd`'s `claudeProgram()` reads the Claude binary from `config.GetGlobalConfigDir()`'s `config.json`, matching the TUI's global context (`config.GlobalWorkspaceContext()`) rather than `LOOM_HOME`'s, since `loom account` manages one registry shared across every workspace. `add`, `login` and `list` each print a warning (`warnCredentialOverride`) when a credential env var already overrides every account (see the account-selection gotcha above); `use` and `sync` don't, since neither runs a session.
- **Account state is reload-then-diff, not polled.** The registry, auth, sync, usage and the reload logic live in the model (`core/accounts.go`, `core/usage.go`); the views (strip, Accounts screen, Launch Options row) stay in `app/accounts.go`, and `core.AccountsChanged` refreshes them (`refreshAccountViews`). `accounts.json` isn't reread on a fixed schedule: `maybeReloadAccounts` rides the model's health tick and only stats the file, reloading (`core.Model.ReloadAccounts`) when its size or mtime moved; every user-paced action that reads the registry — opening Launch Options, opening Settings, an Accounts-screen request — calls `ReloadAccounts` first regardless of the stat. `accountsChanged` then compares a signature (the default, every `name=dir`, and the load error) against what was last seen (`noteAccountsState`, also called after this process's own writes so they don't read back as a change): a no-op reload touches no view, and a load error is reported once, when it first appears, not on every later tick that is still failing. Auth is re-read (`RequestAccountsRefresh`/`gateAccountsRefresh`, `accountsRefreshJob`) in three cases: a reload finds an account with no auth entry yet (added by another `loom account` or loom process), the default account's identity is still unknown while an extra account exists, or a usage probe finds an account that had plan access losing it (`lostAccess`) — the last is how "logged out" reaches the strip and Accounts screen between reloads, since an expired login probes the same as API-key auth (`Usage.Available=false`) until `claude auth status` actually re-runs. Launch Options shows a notice (`SetAccountNotice`) before the user confirms whenever the account it preselected no longer exists (a resumed session whose account was removed) or a live refresh removes the account currently selected in the row, both naming the account the session will actually run on. The Accounts screen's own remove refusal for unshared content points at `loom account remove --force <name>` as the way out (the screen has no force of its own); its in-use count (the model's `accountUsers`) counts each loaded workspace's live instances directly and falls back to reading `state.json` only for config dirs no loaded workspace covers, so a session visible in the list is never counted twice.
- **`handleMenuHighlighting`'s deferred-replay flag needs every full-screen modal state on its exclusion list.** It defers a keypress matching a registered global binding (`a`, `t`, `d`, `n`, …) to a later Update cycle via an async replay `tea.Cmd`, tracked by a single `m.keySent` flag that assumes the very next `KeyPressMsg` to arrive is always that replay. A modal state missing from the exclusion list lets fast typing (or a paste) into one of its own text fields collide with that mechanism and reorder a character — "toy" typed quickly rendered "oyt" — because the next keystroke steals the flag and the delayed one replays later, wherever the cursor has since moved to. `stateSettings` was missing from it until 2026-09-25 (typing into Default Program, Base Branch, a Profile name or an Account name could scramble); every new full-screen modal state must be added alongside `statePrompt`/`stateNew`/`stateLaunchOptions`/etc. in that same check, or it inherits this bug silently. Regression test: `app/menu_highlighting_settings_test.go`.

### Persistent State

All stored in `~/.loom/`:
- `config.json` — user configuration: `DefaultProgram`, `BranchPrefix` (default: `{username}/`; overridable per session via the Session Launch Options modal — see `launch.Options.BranchPrefix` → `Instance.SetBranchPrefix` → `git.WorktreeSpec.BranchPrefix`, an ephemeral override that is never persisted), `BaseBranch` (default empty, read via `Config.GetBaseBranch()` — the branch new worktrees are cut from; empty auto-detects via `git.ResolveBaseCommit`: `origin/HEAD` → `main` → `master` → current `HEAD`), `Profiles` (named program presets), `Theme` (`"afterglow"` default, `"legacy"`; empty means default, read via `Config.GetTheme()`; cycled live from the settings overlay's Theme row), `ClaudeTmpArchiveDir` (`claude_tmp_archive_dir`, read from the global `config.json` only; empty keeps each workspace's Claude temp-dir archives in its own config folder; set, every workspace's go under it in a subfolder per config dir, see `session.ClaudeTmpArchiveDir`; read via `Config.ClaudeTmpArchiveRoot()`, which expands `~` and rejects a relative path), `ClaudeRemoteControl` (`*bool`, default on — launches Claude sessions with `--remote-control <title>`; nil is treated as enabled, read via `Config.RemoteControlEnabled()`), `ClaudePermissionMode` (`*string`, default `"default"` — launches Claude sessions with `--permission-mode <mode>`; nil is treated as `"default"` (no flag injected), read via `Config.PermissionMode()`; valid values enumerated in `config.ClaudePermissionModes` and cycled from the Claude Preferences overlay), `Claude1MContext` (`*bool`, default off — appends Claude's `[1m]` long-context suffix to the launched `--model` alias, e.g. `sonnet[1m]`; a no-op for `default`, `haiku`, and any alias whose `config.ClaudeModel.Supports1M` is false, read via `Config.Context1MEnabled()`; the composed value is single-quoted because tmux runs the program string through a shell and `[`/`]` are zsh glob metacharacters), `ClaudeSubagentTracking` (`*bool`, default on — shows the subagents and teammates loom's hooks track; every Claude launch gets the hooks regardless; nil is treated as enabled, read via `Config.SubagentTrackingEnabled()`, toggled from the Claude Preferences overlay's Track Subagents row)
- `state.json` — app state (e.g. help screens seen) plus the `ui` prefs block (`config.UIPrefs`: `view_mode`, `rail_hidden`, `terminal_hidden`, and `split_ratios` — a per-session-title map of agent/terminal split ratios, written throttled on `ctrl+up`/`ctrl+down` resizes)
- `instances` (an array inside `state.json`, not a separate file — `config.InstancesFileName` is unused) — serialized session data (`issue`, since schema v6, links a session to the GitHub issue number it was created from; `claude_session_id`/`claude_transcript_path`, since v7, name the conversation a crash relaunch resumes with `--resume`; `account`, since v8, names the Claude account the session runs on, empty = default)
- `workspaces.json` — registered workspaces with name, path, and last-used tracking
- `loom.lock` / `loom.sock` (global dir) — the running TUI's takeover lock (holder pid, tty, start time) and its request socket; see the one-TUI gotcha
- `accounts.json` (global dir) — extra Claude accounts (`name`, `dir`) and the `default` new sessions preselect
- `accounts/<name>/` (global dir) — each extra account's `CLAUDE_CONFIG_DIR`: its own `.credentials.json`/`.claude.json`/runtime dirs, everything else symlinked to the main config dir
- `worktrees/` — git worktree directories
- `hooks/` — per-instance Claude hook folders for status, resume and subagent tracking (see `session/hooks`), one per path-escaped tmux session name; emptied at each launch, removed when an instance is killed, swept when unclaimed and its tmux session is gone
- `archive/claude-tmp/` (or `<claude_tmp_archive_dir>/<encoded config dir>/` when the global `config.json` sets one) — zips of Claude's per-session temp dirs (scratchpad, task output, minus `CACHEDIR.TAG` caches): one `<name>.zip` per paused session (restored and deleted on resume), plus permanent archives from kills, sweeps and demoted parks; never pruned by loom
- `scripts/` — user-supplied `*.lua` files loaded at startup (global, shared across workspaces)

## Testing Patterns

- Tests use `testify/assert` for assertions
- Dependency injection via interfaces: `cmd.Executor`, `tmux.PtyFactory`
- Constructor variants for testing: `NewSessionWithDeps()`, `NewAttachClientWithDeps()` and `NewTmuxSessionWithDeps()` accept mock dependencies
- `app` tests attach agent-pane clients through the registry, as production does: `app/testpanes_test.go`'s `attachTestClient` registers one per fixture instance and `wirePanes` points a test `home` at it. Fake attach PTYs (here and in `ui`) are `internal/testpty` pairs, open until the test ends or closes the peer: a `/dev/null` PTY reads EOF at once, which a client takes for a dead session (`Attached` false)
- Test setup pattern: `TestMain` initializes logging, runs tests, calls `os.Exit`
- Tests use temp directories for file I/O isolation
- `app` tests never touch the developer's default tmux server: `TestMain` (`app/app_test.go`) points `LOOM_TMUX_SOCKET` at a private server and kills it afterwards; `isolateTmux` gives a test its own fresh server, and `core.Model.SetExecForTest` swaps the workspace load paths' executor for a recorder. `core`'s `TestMain` (`core/testmain_test.go`) isolates tmux and `~/.loom` the same way
- `app` fixtures build workspaces with `testWS` (a `core.Workspace` from its handles plus instances, added through `AddForTest`) and slot views over them with `slotOver`, and install the model with `wireCore` (`app/testcore_test.go`): it mirrors the slots into a model the way `newHome` does (the tabs in order, or the focused slot's workspace as the classic one), gives the home a tmux liveness probe (`aliveProbe` = `fixtureAlive`, the has-session answer of the fixture instance's mock session) unless the test set one, and fills every slot's view store (`syncViews`), so a hand-built `home` with slots needs `wireCore` after its slots are assembled and before it is exercised. Tests build instances in core and read them through the TUI: one that changes the model's instances outside an Update (`ws.AddForTest`, a status set on the instance) calls `m.syncViews()` before reading them, and reaches the instances again through `ws.InstancesForTest()`, the IDs through `testModel(m).IDOfForTest(inst)` (`testModel` is the home's `*core.Model`, for its seams) and an ID's instance through `InstanceForTest`; `ui` and `script` tests build `core.InstanceView` literals (`core.ViewForTest` copies a fixture instance into one). `reworkspace` rebuilds a slot's workspace with edited handles (a `core.Workspace`'s handles are fixed for its life), and `editRCAuth` edits the model's default-account remote-control auth. Tests deliver a job's result as the runtime would with `deliver(t, m, result)` (a `coreResultMsg` through `Update`, which drains the events), and `pumpCore` runs a Cmd and feeds every core result it yields back through `Update`, so a job that follows another (a start's initial-prompt send) lands too. `requestJob`/`requestResults` run the jobs a request made outside an Update queued. Results whose types core keeps unexported come from `core/seams.go`'s `…ForTest` constructors (`FetchedIssueForTest`, …; `UntrackedForTest` strips a request's tracking from a result)
- `core` tests build a model with `NewForTest` (no workspace, no side effects), install workspaces with `SetWorkspacesForTest`, and take fixtures from `core/testhelpers_test.go` (`storedWorkspace`, a workspace over a fresh config dir and storage; `newInst`, `newTerminal`, `pausedInst`, `startedInst`, `gitRepo`, `pausedWorktreeInst`). A test of a function that lives in `core` lives in `core`; a test of the TUI's response to a model result goes through `home.Update` and stays in `app`. `TestCoreImportsNoUI` and `TestNoProductionCallsOfTestSeams` guard the seam (see the `core/` bullet)
- No test touches the developer's real `~/.loom`. Every package whose tests can reach `config` (directly or through another loom package) has a `TestMain` calling `internal/testenv.IsolateLoomDirs`/`MustIsolateLoomDirs`, which points `LOOM_HOME` and `LOOM_GLOBAL_DIR` at a throwaway dir for the whole binary (it also points `CLAUDE_CODE_TMPDIR` at a throwaway dir it creates empty, so Claude's root reads as absent); a test needing its own dirs still `t.Setenv`s over them. `TestEveryConfigReachingPackageIsolatesLoomDirs` (`internal/testenv`) walks the module's import graph and fails on a config-reaching package without one — a new package's first test needs a `TestMain` (copy any `testmain_test.go`). `config` is the one exception: its tests exercise default resolution, so its `TestMain` leaves those vars unset and points `HOME` at a throwaway instead (assert "default is ~/.loom" by computing `os.UserHomeDir()`, never by touching it)

## Code Conventions

- Error wrapping: `fmt.Errorf("context: %w", err)`
- Module path is `github.com/aidan-bailey/loom`
- Platform-specific code in `_unix.go` / `_windows.go` suffixed files
- Private struct fields, public methods (PascalCase)
- Minimal goroutine usage; concurrency mainly in tmux monitoring

## CI/CD

GitHub Actions workflows in `.github/workflows/`:
- **build.yml** — Build and test on push/PR to main (triggered by Go file changes)
- **lint.yml** — golangci-lint on Go code changes
- **release.yml** — Auto-triggers on Build success on main (or `workflow_dispatch`). Reads `version` from `main.go`; skips if `v$VERSION` already exists on GitHub; otherwise tags, generates release notes from conventional commits via `git-cliff` (see `cliff.toml`), and runs GoReleaser to build/publish artifacts. To cut a release: bump the `version` string in `main.go`, regenerate `CHANGELOG.md` with `git cliff -o CHANGELOG.md --tag v$VERSION`, commit, and merge to main.
