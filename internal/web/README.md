# internal/web

The daemon's web layer: what `loom serve` starts so a phone can see the fleet and act on it. It is a client of the daemon's own `rpc.Server`, joined over `net.Pipe` as the `web` role, plus `core.WebHost` for the device records the model keeps in `web.json`. It serves two embedded apps (the classic one and the new one, which each device picks), a JSON API and a live stream on a loopback port that a Cloudflare tunnel reaches, and sends Web Push. It holds no session state, and logs under `subsystem=web`. Rules for changing it: [`CLAUDE.md`](CLAUDE.md).

## How it runs

`daemon.Serve` calls `web.Start` after the mod server listens and `Layer.Close` first when it stops, before the bye. `Start` joins the server as the `web` role, which the server does not count as a client, so a notice raised while only the layer is connected waits for the next TUI. It builds its parts (`startParts`) and then drains the client as the TUI does: on each wake it takes `Sync`'s events, hands them to each sink in turn, and applies the `WebView` a `ModelChanged` carries.

The layer listens only while `WebView.Listen` is set. It acts on `WebView.Rev`, which the model bumps on every `ConfigureWeb` and on nothing else: whenever `Rev` differs from the last one the layer acted on, it closes the listener, which ends every stream, and binds `Listen` unless it is empty (then it stays closed). Two `ConfigureWeb`s that one `Sync` coalesces still differ from that `Rev`, so a disable and an enable are never missed. What happened goes back to the model through `WebHost.WebServing`, which leaves `Rev` alone, so a report never binds. A listen that fails (the port is taken) leaves the web off with the reason in `WebView.Error` and a notice for the next TUI, and is tried again only by the next `ConfigureWeb`, the same values included: `loom web enable` again. The listener takes loopback IP literals only, whatever `web.json` says.

A panic in the drain or the listener stops the layer, tells the model (the same notice) and leaves the daemon running. Each goroutine the layer starts defers `recoverPanic` first, which calls `fail`; `fail` returns at once and stops the layer on a goroutine of its own, so a part can call it from the goroutine that panicked. `Close` runs the same stop, once between them: whichever comes first stops the layer, and the other waits until it is complete. `Close` still has to run at the daemon's stop.

## Every request

`guard` stands in front of every route:

1. The security headers go on the answer, errors included.
2. The `Host` must be the host of a member of the origin set (default port dropped, any case), else 421. The set is the configured origin and, when the listener is bound to `127.0.0.1` or `[::1]`, its local origin `http://loom.localhost:<port>` (`core.LocalOrigin`; browsers resolve `*.localhost` to loopback). Bare `localhost` and the IP literal are never members: a device cookie set on them would reach every server the browser reaches there, on any port, and a token is tied to no origin. A listener on another loopback address (`127.0.0.2`) has no local origin. The `loom.localhost` cookie is host-only, so no service at bare `localhost` or a loopback literal receives it, but cookies ignore the port: a hostile listener on another loopback port (another OS user's server, a forward to a compromised machine, a container's published port) that steers the browser to `loom.localhost:<its port>` receives it. That is accepted on a single-user machine. The local origin grants nothing the tunnel's does not: every route but pairing still needs the device cookie, and each origin holds its own.
3. A method other than GET or HEAD must carry exactly one `Origin` header equal to a member of the set, else 403.
4. The body is capped at `maxBody` (1 MiB).

With no listener bound there is no origin rule, and `guard` refuses everything.

## Pairing and the device cookie

`POST /api/v1/pair` takes `{"code": "K7QM-2XPA"}` and asks the host to redeem it. The model checks the code, consumes it and makes the device; the layer sets the token it returns as the cookie `__Host-loom` (Secure, HttpOnly, SameSite=Strict, Path=/) and answers `{"device": "<name>"}`. The refusals are `{"error": <text>}` with a status the app keys on: a wrong, used or expired code is 400 (never 401, which the app reads as "not paired"), too many wrong codes 429, a name already paired or 16 devices paired 409, and a web that is off 503; any other failure is a 500 with a fixed text.

`authed` wraps every route after pairing: it reads the cookie, decodes it as unpadded base64url, refuses (401, without asking the host) a value that is not exactly 32 bytes, and asks the host which device holds the SHA-256 of those 32 bytes. No device is a 401; otherwise the device is touched (last seen) and the handler runs with its name.

## Routes and the API

Every route under `/api/v1` except `POST /api/v1/pair` needs the device cookie. The app shell and its static files are public and hold no data.

The routes are one table in `internal/web/routes.go` (`Layer.routes()`), and the generated reference `docs/specs/web-api.md` lists every route and stream event with its types, success status and what it does and refuses (each entry's `doc`); `internal/web/ui/src/api/gen.ts` is the same contract as TypeScript, and `internal/web/api.fields` pins what has shipped; `GET /api/v1/stream` is the one route outside the table (see The stream), and the mockup route is a page entry whose handler is hand-served.

Responses are JSON. An error is `{"error": "<text>"}` with 400, 401, 403, 404, 405, 409, 421, 429, 500, 503 or 504; 403 and 421 are the guard's (another origin, another host), 405 a HEAD on the stream. A refusal by the model is 409 with its text; a stopping daemon is 503. A read (turns, diff, a job's log) answers its data; one the model does not answer within `replyWait` is 504, and its request is no longer tracked once answered, since its Reply carries the data and no notice follows it. An action answers `{"notices": [...]}`; a request still running after `replyWait` (30 s) answers 202 `{"pending": true}` and its outcome arrives on the stream. The notices a response carries are not sent on the stream again: they are kept among the recent notices the snapshot carries, so a response the phone never got loses none. A handler takes the layer's next request ID, makes the request and waits for the `Reply` the drain routes back. Create checks the workspace and the title as `loom session new` does and resolves the launch options as it does.

A session as JSON: `id`, `workspace`, `title`, `branch`, `worktree` and `tmux` (the worktree's path and the tmux session's name, which the Kill sheet names; each is left out while empty), `group`, `label`, `status`, `since`, `wait` (`reason`, `detail`), `last_message`, `diff` (`added`, `removed`), `ahead`, `behind`, `parity_known`, `pr` (`number`, `state`, `checks`, and `url` when `gh` gave an `https` one; or null), `account`, `agents` (each `id`, `name`, `description`, `idle`; `id` is the agent id `?agent=` takes), `remote_url` (`https://claude.ai/code/<RemoteSession>`, or empty), `claude` (the session runs Claude, so the app offers its conversation), `mockup` (`screen`, `changed`, `fresh`: the brainstorm companion's screen, fresh while it changed in the session's latest turn; or null), `jobs` (the work-queue jobs the session submitted: running, waiting, then at most 10 finished, newest first; each `id`, `state` (`running`, `queued`, `held`, `done`, `failed`, `cancelled`, `lost`), `description`, `command`, `agent` (the subagent that submitted it, or empty), `submitted`, `started`, `ended` (RFC 3339, empty while unset), `exit` (`code`, `signal`; null until it ends), `failure`, `cancel_reason`, `waiting` (why a waiting job has not started), `parked`, `paused`, `pause_reclaimed` (its memory went to swap), `forced` (started past the queue's fit), `control` (`pause` or `resume` in flight, empty for none) and `control_error` (the last failed one's error); no CPU or memory, which move with every sample), `jobs_label` (the TUI card's badge, `⚙ job 14 +1` or `⚙ queued`, empty for none) and `jobs_focus` (the job the label names, 0 for none), and `verdict` and `gist` (the stop classifier's verdict on the last turn, `needs_you`, `done`, `waiting` or `stopped`, and its one line; left out while empty). A `needs_you` verdict puts a Ready session in the `needs_you` group labelled "Asks you", `done` labels it "Done", and `waiting` puts it in `working` as "Waiting". IDs are JSON numbers. A workspace is `id`, `name`, `label` and `shown`.

Groups: Prompting is `needs_you`; a started Ready is `your_turn`; Running, Loading and Deleting are `working`; Paused, Recoverable and an unstarted Ready are `paused`, each with its own label. Workspace terminals are left out.

## The stream

`GET /api/v1/stream` is server-sent events. Every connect starts with a `snapshot` (the build, the host name, the workspaces in the order the app lists them, each flagged `shown` when it is open as a tab in loom or holds a session that isn't paused, or when no tab is open; the sessions by workspace; the device; `badge` (the sessions that need you across the served workspaces); the last `recentNotices` (20) notices; `usage`, each account's plan usage, with `usage_stale_after_s` (`core.UsageStaleAfter`), the age past which the app dims a sample; `quick_replies`, the list the app offers; and `terminal`, whether the web terminal is on), so nothing is replayed. After it: `sessions` (one workspace's whole list when it changes, at most four a second: `publishEvery`), `workspaces` (also when a `shown` flag or the order changes), `usage`, `quick_replies`, `terminal` (`{enabled}`, sent when the switch changes), `device`, `notice`, `ping` every `pingEvery` (20 s, since Cloudflare closes a stream idle for 125 s) and `bye` when the daemon stops. `sessions` and `workspaces` both carry `badge`, the same fleet-wide count as the snapshot's, sent even at 0 so the app clears its icon. The stream sets the device cookie again when it connects, so a device in use never expires, and a revoked device's streams end as soon as the device list is published. At most `maxStreamsPerDevice` (4) are open per device, a fifth closing that device's oldest, and `maxStreams` (32) in all, a 33rd being refused with 503. The stream has no write timeout over its whole life: each event's write is bounded at `streamWriteTimeout` (30 s), and the stream pings instead.

## The app

`index.html` loads `js/app.mjs`, which routes `#` (the fleet), `#s/<id>` (a Claude session's conversation, `js/turns.mjs`; a session that does not run Claude draws its info tab; `#s/<id>/turns` is its old address, replaced by `#s/<id>` in place), `#s/<id>/info` (its info tab, `js/session.mjs`), `#s/<id>/agent/<agentId>` (a subagent's turns, `js/agent.mjs`), `#s/<id>/job/<n>` (one of its work-queue jobs, `js/job.mjs`), `#s/<id>/diff` (its changes, `js/changes.mjs`), `#s/<id>/mockup` (its brainstorm mockup, `js/mockup.mjs`) and `#s/<id>/mockup/full` (the mockup alone), `#s/<id>/flow?plan=` (its flow board, `js/flow.mjs`), `#s/<id>/flow/<story>?plan=` (a row of it), `#s/<id>/flow/doc/<doc>?plan=&at=` (one of the flow's documents, `js/flowdoc.mjs`), `#flows` (the host's flows, `js/flows.mjs`), `#new`, `#settings` and `#pair` and renders each screen from `screens` (`internal/web/static/js/screens.mjs`). `js/api.mjs` makes the calls and reconnects the stream with a backoff from 1 s to 30 s, drops a stream silent for 45 s, and opens a fresh one whenever the page becomes visible again, since a page iOS resumes can sit on a stream that delivers nothing; `js/store.mjs` keeps the last snapshot in IndexedDB, drawn at once and marked stale with every action off until the stream is back, and cleared by a 401 or an unpairing. The service worker (`sw.js`) caches the shell only, never the API, and updates when a snapshot's `build` differs from the shell's. The app sets the Home Screen badge (`navigator.setAppBadge`, cleared at 0) from the `badge` of each snapshot, `sessions` and `workspaces` event, and the worker sets it from a push's. Opened in Safari rather than from the Home Screen, the app shows the Add to Home Screen steps instead of pairing. The classic app has no build step and no JavaScript test harness: its modules are checked with `node --check`, and its logic stays in Go. The Preact + htm file is pinned by a SHA-256 in a test, and its licence is in `NOTICE.md`.

The skin is loom's TUI on the phone (spec `docs/superpowers/specs/2026-10-23-pwa-skin-glance-design.md`): the afterglow colours as `app.css`'s tokens, dark only, `ui-monospace` type (SF Mono on the iPhone), glyph rows, and boxes whose label sits in their top border (`js/skin.mjs` holds the glyphs and icons). Every screen with a snapshot sits between the app's pinned header and footer, which `app.mjs` draws from `js/chrome.mjs`'s rows: the header holds the screen's context row (the `Head` `js/screens.mjs` names for it) and, for a session, its tabs, and the toasts hang from its bottom edge; the footer holds the status row (the link's pill, `loom@host`, and the counts of Needs you, Your turn and Working over the shown workspaces, each opening its group's next session: `fleetGroups` and `nextInGroup` in `js/fleet.mjs`), and hides while the reply box has focus. The fleet lists the `shown` workspaces, each Claude session's row showing its account's share beside its age, amber from 80% (`rowShare` in `js/usage.mjs`, which also formats a window); a session's Account tile shows that share, its reset, and the other window's share and reset; Claude's text in a turn is drawn from its tree with `js/markdown.mjs`, and a reply box fills from the quick-reply chips, edited in Settings (`GET …/message` stays, but no screen draws the last message now). The conversation screen reads its turns on open (a conversation left and returned to is restored from the turns and scroll position `js/turns.mjs` keeps per session, then refreshed) and refreshes the newest turn (`after`) when the stream changes the session's status or last message and every 5 s while it is Running; the changes screen refreshes when the session's counts or status change and every 10 s while it is Running. A session's views (conversation, changes, info, and mockup while its brainstorm companion runs) are tabs under its context row (`SessionTabs`), and each but the subagent screen ends in `js/reply.mjs`'s reply box, which keeps a draft per session across them; `useRun` is their shared runner. A Claude session's conversation pins a fact strip under the tabs (`js/strip.mjs`: status and age, changes, PR and the account's share, a link to the info tab; while the session has jobs yet to end, their badge `jobs_label` on its right, a link to the job `jobs_focus` names), draws Claude's thinking as folds, and draws an Agent step as a link to the subagent's screen (`#s/<id>/agent/<agentId>`: the same turn renderer over `GET …/turns?agent=`, the brief first, a strip by the page's `agent.state`, no reply box, refreshed while the agent runs; the info tab's Agents rows link there too). ## The new app and the switch

The new app lives in `internal/web/ui/` and builds into `internal/web/dist/` (committed, embedded as `nextFiles` beside the classic `staticFiles`). The device picks the app: `routeStatic` serves the four shell files (`/`, `/index.html`, `/sw.js`, `/manifest.webmanifest`) from the tree `treeOf` picks (a `ui` parameter on the URL, `next` or else classic, else the `__Host-loom-ui` cookie, `next` or else classic), with `Vary: Cookie`; any other path comes from the picked tree and else from the other. The cookie holds no data (`Secure; Path=/; SameSite=Strict`, a year, not HttpOnly) and the apps set it: the classic Settings' "Try the new app" and the new app's "Back to classic" (in its Settings, and under the splash it draws before it has a snapshot, on every route, so the switch works with the daemon down and nothing saved) set it and register the worker again at `/sw.js?ui=<app>`; a browser that arrives at the new app by `?ui=next` with no cookie, as `loom web open`'s link does, has `adoptNextApp` (`internal/web/ui/src/app/pairHold.ts`) set it before its worker registers; each app registers its worker by the cookie at every launch, each worker fetches its own shell with its `?ui=` and caches under its own prefix (`loom-shell-` and `loom-next-`), deleting the other's on activate, and the new app keeps its snapshot in IndexedDB `loom-next`, apart from the classic one's. Offline, the cookie is set and the switch finishes on the next launch. The new app draws every screen the classic one does: the fleet and the session views below, the part 3 screens in the section after them, and pairing; no route draws a placeholder. The stack and the build are listed in `internal/web/ui/CLAUDE.md`; the first load is held under `firstLoadBudget` (250,000 bytes gzipped) by `TestDist_FirstLoadIsWithinBudget`.

The terminal's document, `/terminal.html`, is the second HTML entry of the build (`internal/web/ui/terminal.html`, an input of `vite.config.ts`) and the one place xterm.js runs. Its script (`src/terminal/main.ts`) makes a terminal with the WebGL addon loaded before `open()` (the DOM renderer serves when WebGL is unavailable or its context is lost) and the fit addon, reads the session's id from the hash (`/terminal.html#<id>`), opens the WebSocket at `api.terminalURL(id)` on the page's own host (`wss:` on an `https:` page), sends its size as the first frame (`src/terminal/socket.ts`), writes the daemon's binary frames into the terminal, sends its keys back in binary frames of at most 64 KiB (a paste is split, since the daemon ends a longer frame with 4006), and, on a page that is not in a frame, shows its state in a status line. It sets `window.loomTerminal` on every page, and the panel drives it when the page is framed (`src/terminal/frame.ts`: `send`, `key`, `text`, `setTouch`, `setLink`, `reconnect`, `focus`, `close`, `onState` and `onChord`), the one interface a panel drives it through: input is sent only to a live connection and never queued, the terminal is reset by RIS written ahead of a new connection's first bytes, a terminal that cannot start reports a `closed` state, the new size is sent 100 ms after the last change, and a connection that ends with 1001, 4005 or no close frame reconnects on a backoff from 1 s to 30 s that returns to 1 s only once a connection has stayed live for 30 s (`src/terminal/reconnect.ts`), at once when the page becomes visible or is restored from the back-forward cache, never while the app's link is down, and in place of a live one when the link comes back up or the page was hidden for 30 s or longer; every other ending waits for `reconnect()`. Touch mode scrolls the terminal with a finger and never focuses it; ⌘K inside the frame is handed to the app, Ctrl+Shift+C copies the selection, Ctrl+Shift+V is left to the browser, and Ctrl+K and every other key go to the shell. xterm.js appends `<style>` elements at run time, which the app's policy drops, so `routeStatic` answers `/terminal.html`, and only it, with `terminalCSP` (`style-src` allows `'unsafe-inline'`, scripts stay `'self'`, and `frame-ancestors 'self'` lets the app frame it); the new app's worker passes a navigation to it through to the network, which it would answer with the cached shell otherwise; and the page carries no `loom-build` meta, since the build is filled only into `index.html` and `sw.js`. `TestDist_XtermLoadsOnlyInTheTerminalPage` keeps xterm.js out of the app's first load. A device still on the classic app has the classic worker, which answers a navigation to `/terminal.html` with the classic shell, so the page is opened from the new app.

## The new app's session views

## The terminal

`GET /api/v1/sessions/{id}/terminal` upgrades to a WebSocket onto the session's worktree shell (the tmux session `tmux.TerminalSessionName(title)`, which the TUI shares). It is off until the host turns it on (`loom web terminal on`, or the `Web Terminal` row in the TUI's settings; no route under `/api/v1` changes it), and it is a `page` entry in the table, so the generated client builds only its URL.

Before the upgrade the route answers JSON: 426 for a request that is not a WebSocket upgrade (a method but GET, below HTTP/1.1, or without the `Connection` and `Upgrade` headers) and 400 for a handshake without `Sec-WebSocket-Version: 13` or without exactly one `Sec-WebSocket-Key` that decodes to 16 bytes, both checked first, before the origin, the slot and the model; 403 unless there is exactly one `Origin` header that the origin set accepts (`guard` checks it only for a method but GET and HEAD) and 403 while the switch is off; 404 for an unknown session or a workspace terminal; 429 past 4 connections a device or 16 in all (`maxTerminalsPerDevice`, `maxTerminals`), counted from before the model is asked, so a slot is reserved (`terminals.reserve`) and released when the handler returns; 503 while the layer is stopping or the part has not read the device yet; and the model's refusal as 409 (`EnsureTerminal`: an instance that is unstarted, paused, loading, being deleted, recoverable, a workspace terminal or without a worktree; a tmux session of the shell's name held elsewhere, that is, not started in the instance's worktree; a tmux that cannot answer; a shell that ended while loom looked at it; and a session that was paused or killed while its shell was being opened), 504 when it did not answer in time and 500 when its reply named no shell. It never logs the bytes: only `web.terminal_open` and `web.terminal_close`, with the device, the session and the close's reason.

Frames: binary frames carry terminal bytes both ways. The app's first text frame `{"resize":{"cols":120,"rows":40}}` opens the attach at that size (2 to 500 columns, 1 to 200 rows); loom answers `{"state":"live"}` once attached, after the history above the visible screen. The attach's output passes through `vt.NewAltScreenFilterWithoutMouse`, which removes the alternate-screen modes and the mouse modes (1000, 1002, 1003, 1005, 1006, 1015) from every `CSI ? … h` and `CSI ? … l`, so the browser's xterm.js never reports the mouse: its wheel scrolls its own scrollback and a drag selects, and a full-screen program in the shell (vim, less, htop) gets no mouse and no wheel. tmux's `mouse` option is not changed, and the TUI's pump keeps `vt.NewAltScreenFilter`. A frame from the app is at most 64 KiB. Loom pings every 20 s and drops a connection whose ping goes unanswered for 10 s, and a browser that falls 1 MiB behind is ended rather than blocking tmux. An ending is a close frame with a code and a reason: 4001 the terminal is off on this host, 4002 this device is no longer paired, 4003 the session was paused or killed, 4004 the shell exited, 4005 the browser fell behind, 4006 a frame loom does not understand, 4007 loom could not attach to the shell, and 1001 loom is stopping (the daemon stopping or the listener rebinding). The switch turning off, a device revoked or paired again, a rebind and the layer's stop end the connections they touch through the terminals' part, since `http.Server.Close` does not track a hijacked connection. The route records the connection it hijacks (`recordHijack` wraps the writer given to `websocket.Accept`) and hands it to the connection, which closes it outright when its close handshake has not finished 5 s (`termCloseWait`) after loom's close frame: the library's close reads with no deadline whatever frame the browser is part-way through sending, and a stalled browser would otherwise hold its slot for good.

## Push

Turned on by a tap in the app: it subscribes with the VAPID public key and posts the subscription, and the button waits while the phone subscribes, which can take minutes. Once a launch the app checks its subscription against the device's, since Apple answers 201 to a subscription the phone has dropped: while the state is `ok` or none it posts its subscription again, and holding none, or no permission to notify, while the device has one, it has the model drop it (`DELETE /api/v1/device/push`, recorded as expired) and says so. Triggers come from the projection's transitions: *waiting* when a session enters Prompting or stays in it with a reason or tool summary that differs from the last non-empty one pushed in that stretch (a cleared one never pushes, nor does its return; leaving Prompting ends the stretch), *finished* when a started session goes from Running to Ready. While the stop classifier judges that turn the finished push is owed, and the turn's verdict decides it, once per turn: `needs_you` pushes *waiting* (body `asks: <gist>`), `done` pushes *done* (body `Done: <gist>`, under the device's finished toggle), `waiting` pushes nothing, and `stopped`, or no verdict at all, pays the owed *finished*; a reply first drops it. *escalated* is the issue watcher's (`loom watch`): when a workspace's published `Watch.Escalations` lists an escalation (an issue and the moment it was recorded) that the workspace's previous projection did not, one push goes out, titled `<workspace>: issue #<n> escalated` with the recorded reason as its body, under the device's waiting toggle, with `Urgency: high`, `url` `/` (it has no session) and a `Topic` per workspace and issue (the same 8 bytes as unpadded base64url with the top bit set, which no session's ID has). The first projection after the layer starts is a baseline and pushes nothing, for sessions, and a turn that ended before it never pushes; for escalations the baseline is a workspace's first projection with `Watch.Loaded` true, because the watcher's memory loads on its first poll and a projection before that lists nothing (a baseline taken there would push every old escalation once it loads). A device gets the kinds its settings allow, and nothing while paused or while the web is off (an empty `listen`). The subscriptions and the VAPID key stay while the web is off, so enabling it again resumes pushes without the phone subscribing again. The payload (`kind`, `session`, `title`, `body`, `badge`, `url`) is encrypted per RFC 8291; its `url` is `/#s/<id>/mockup` while the session's mockup is fresh and no ask is open (`opensMockup`), else `/#s/<id>`; waiting goes with `Urgency: high`, finished and done with `normal`, both with a one-hour TTL and a `Topic` per session: the session ID's 8 bytes as unpadded base64url, since Apple refuses a `Topic` whose length is 1 mod 4 (400 `BadWebPushTopic`). The sender is a goroutine of its own with a queue of at most 100: it posts with a 10 s timeout, at most 30 a minute per device, retries a 429, a 5xx or a transport error up to three times, honouring a `Retry-After` of at most 30 s (a longer one is given up on), drops a subscription answered 404 or 410 and records it as expired, records any other status as failing with it, and only logs a transport error that outlasts its retries. A result names the endpoint it was sent to, and changes nothing once the device holds another subscription. `loom web devices` shows the state.

## Limits

Bodies are capped at 1 MiB (`maxBody`). A conversation page holds at most 10 turns and, past its newest, 256 KiB of text (a prompt 16 KiB, a text item 64 KiB, a fold its newest 200 steps), from at most 16 MiB of the transcript; a diff keeps at most 1 MiB of lines, 5,000 lines a file and 2,000 bytes a line. A reply is 1 byte to 64 KiB after trimming, a new session's prompt at most 64 KiB, and its title as `core.CheckNewTitle` says. A launch override must be an account the registry holds, a model in `config.ClaudeModelAliases()`, a permission mode in `config.ClaudePermissionModes` and an effort in `config.ClaudeEfforts`. A push subscription is an `https` endpoint of at most 2 KiB on `web.push.apple.com`, `fcm.googleapis.com`, `updates.push.services.mozilla.com` or a host ending in `.notify.windows.com`, with no user and no port but 443. Ids in paths are decimal and served by the model: an unknown session is 404, an unknown workspace 400. Settings: `listen` is exactly `127.0.0.1:<port>` or `[::1]:<port>` with a port from 1 to 65535 (0 is refused), and `origin` is at most 255 bytes; disabling the web voids every pending pairing code.
