# Loom PWA Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Spec:** `docs/superpowers/specs/2026-10-21-loom-pwa-design.md`

**Goal:** An installable web app, served by the daemon through a Cloudflare tunnel, that shows loom's fleet on an iPhone, replies through the loom mod, runs the lifecycle actions, pushes a notification when a session starts waiting or finishes, and hands off to the session's Remote Control.

**Architecture:** A new package, `internal/web`, runs inside `loom serve` when `web.json` enables it. It is a `core.Core` client over `net.Pipe` to the daemon's own `rpc.Server` (hello role `web`), plus `core.WebHost` for device records, which the model owns in `web.json`. It serves an embedded no-build PWA, a JSON API and a server-sent event stream on a loopback port, and sends Web Push itself. `core`, `core/rpc`, `session` and `internal/cli` gain the small pieces it needs.

**Tech Stack:** Go 1.25 standard library (`net/http`, `embed`, `crypto/ecdh`, `crypto/ecdsa`, `crypto/hkdf`, `crypto/aes`, `crypto/cipher`), cobra, testify; ES modules (`.mjs`) with one vendored Preact + htm file; Web Push (RFC 8030, RFC 8291, RFC 8292).

## Execution

- **Where.** This worktree, on branch `aidanb/loom-pwa`, which loom manages: never switch branches. Every path is relative to the repo root. Commit by pathspec, `git add -- <files>` then `git commit -m "<message>" -- <files>`, with Conventional Commit types scoped by package (`core`, `rpc`, `session`, `cli`, `web`, `daemon`).
- **Before the run.** The owner runs the spike (spec, "Spike, as a gate") and records its outcome in the spec. If it changed the design, the plan is redrafted before `/flow-supervise`.
- **Order.** Stories 1 to 13, one at a time: the profile makes every Go build exclusive, and each story builds on the ones before it.
- **Gates.** The profile's story gates run after each story: gofmt, `go vet ./...`, `go test ./...`. Stories 6 and 8 change the daemon and name the e2e suite in their Verify lines; it needs tmux.
- **Generated files.** Story 2 describes the hello's new field in the prose `TestProtocolReference` writes (`core/rpc/wire_test.go`), then regenerates `docs/specs/protocol.md` (`CGO_ENABLED=0 go test ./core/rpc -run TestProtocolReference -update`). Story 3 regenerates `core/rpc/methods_gen.go` (`go generate ./core/rpc`) and `protocol.md` again. Never edit either by hand.
- **CLAUDE.md budgets.** `core/CLAUDE.md` has 93 bytes free (19907/20000), so Stories 3 and 4 add no rule to it: Story 13 writes the web layer's rules in `internal/web/CLAUDE.md` and a guide. Story 6 creates `internal/web/CLAUDE.md` with its own rules, since the coverage lint fails a Go package without one.
- **Tests.** No test touches the real `~/.loom`, `~/.claude` or the user's tmux server: `internal/web` gets a `TestMain` that calls `testenv.IsolateLoomDirs`, and real-tmux tests run on a private server. Fixtures go through the production path: a booted model, the real `rpc.Server`, a client over `net.Pipe`.
- **Running loom.** Never run loom itself (`./loom`, `go run .`) or `loom serve stop` in a loom pane. Manual checks use the `loom-dev` skill (`go run ./tools/loomdev`).
- **JavaScript.** The app's modules are `.mjs`, so the Verify lines can check their syntax with `node --check` (Node 22 is on PATH here; CI has no Node, so no Go test depends on it).

## Names contract

Every name one story defines and another uses. A story may add names of its own; a name another story needs and this section lacks goes back to the manager.

**session (Story 1)**

- `session.RosterEntry` gains `PID int` and `RemoteSession string`. `RemoteSession` is the `bridgeSessionId` of `<config dir>/sessions/<PID>.json`, empty unless that file's `sessionId` equals the entry's (spec, "Changes outside `internal/web`").
- `hooks.Event` gains `ToolSummary string`, set for `PermissionRequest` only, read from the payload's `tool_input` and kept in the compact form under the key `tool_summary`.
- `(*session.Instance).ClaudeWaitDetail() string`: the current observation's tool summary, empty unless it is Prompting.
- `(*session.Instance).WaitDetail() string` and `(*session.Instance).SetWaitDetail(detail string)`, beside `WaitReason`/`SetWaitReason`; `adoptClaudeStatus` sets and clears both together.
- `core.InstanceView` gains `RemoteSession string` and `WaitDetail string`.

**core/rpc (Story 2)**

- `rpc.RoleWeb = "web"`; `rpc.Hello` gains `Role string` (`json:"role,omitempty"`).
- `func rpc.DialAs(nc io.ReadWriteCloser, role string) (*rpc.Client, error)`; `rpc.Dial(nc)` is `DialAs(nc, "")`.
- The server counts a connection whose hello's role is `RoleWeb` as no client for the notice backlog: a notice is kept while no other connection exists, and a joining web connection never takes the backlog.

## After the run

The owner, on the iPhone, through the fresco tunnel, with a dev build from the `loom-dev` skill or a released build:

- [ ] `loom web enable --listen 127.0.0.1:7420 --origin https://<host>` reports serving.
- [ ] Safari shows the Add to Home Screen steps; the installed app shows pairing.
- [ ] `loom web pair --name iPhone`, then the code, pairs the phone.
- [ ] The fleet matches the TUI, groups included, and updates live.
- [ ] Turning on notifications works; a waiting and a finished push arrive with the app open and closed, and the badge counts what needs you.
- [ ] Open in Claude reaches the session, and a permission prompt can be answered there.
- [ ] A reply reaches Claude through the mod, and is refused with a reason for a session without one.
- [ ] New session, pause, resume, push and merge work; kill asks first.
- [ ] `loom web revoke iPhone` ends the app's stream and returns it to pairing.
