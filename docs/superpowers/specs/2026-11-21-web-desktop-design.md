# Loom web: the desktop

Date: 2026-11-21. Branch `aidanb/desktop-app`. Sub-project 3 of the web programme (`docs/superpowers/specs/2026-11-18-web-foundation-design.md`, The programme), taken before sub-project 2 (Phone) by the owner's choice. A desktop layout for the new app in `internal/web/ui/`, a keyboard and a ⌘K palette, a loopback origin beside the tunnel's, and `loom web open`; no Core request, no wire change, no `rpc.Protocol` bump, and no route under `/api/v1` added or changed.

## Problem

The owner wants loom web on a desktop: a multi-pane workspace driven from the keyboard, on the daemon's own machine and on others. Today the new app is a 40rem phone column centred on a wide screen (foundation §2), every action needs a tap, and the web layer accepts exactly one origin, the tunnel's, so a browser on the daemon's machine reaches it through Cloudflare and back. An older attempt, branch `aidanb/desktop-application` (June 2026, cut from v0.1.2), wrapped an in-process `session.Instance` in a Wails window; it predates the daemon, breaks "one owner of state", and is not this design's base. Its terminal latency work (`638ba1ea`) is a reference for Parity's terminal.

## Decisions by the owner (2026-11-21)

From the brainstorm, with mockups in `docs/superpowers/specs/2026-11-21-web-desktop/` (`layout.html`, `frame.html`):

- **Form:** the same app, responsive, opened in any desktop browser or installed as a browser app (Chrome or Edge's Install App). No native wrapper (Wails, Tauri, Electron) and no third tree; a wrapper can come later around the same app.
- **Reach:** on the daemon's machine, directly at `http://loom.localhost:<port>` (bare `localhost` until the skeleton review, §21); elsewhere, through the tunnel's URL, as the phone does.
- **Layout A**, three columns: the fleet sidebar, the route's panel in the middle, an inspector holding another view of the same session. Layout B (split panes, any panel of any session) is a later addition, so the layout's state is shaped to admit it (§6); layout C (a grid of session tiles) is not taken.
- **Keys:** the TUI's single keys wherever no text field has focus, and ⌘K everywhere.
- **Palette:** commands, sessions and places. Searching conversation text is out of scope (it needs a route that does not exist).
- **Pairing on localhost:** `loom web open`, which mints a code and opens the browser on it. Loopback is never trusted: every agent on the machine could then drive the fleet.
- **Approach:** a responsive shell in the same app with the desktop shell loaded lazily (§4), not a general pane tree from day one and not a separate desktop entry point.

## Decisions

### Scope

1. **In scope:** the desktop layout and its panes (§4–§13), the keymap and its view commands (§14–§17), the palette (§18–§20), the loopback origin (§21–§23), `loom web open` and the pairing link (§24–§26), webshot's desktop devices (Testing), and their rules and docs (§27).
2. **Out of scope:** layout B's split panes; searching conversation text; a native wrapper; a light theme; every Parity feature (the terminal and the TUI keys that only it gives meaning: `T`, `a`, `t`, `f`, `w`, `F`, `c`, `I`, `R`, `W` and the split keys); any change to the phone layout below 1024px; user-defined keys (they come with Lua in the daemon, Parity).
3. **Done when** every screen renders in webshot at the phone and both desktop sizes with no console error, CSP violation or unanswered route; the key, palette, origin and `loom web open` tests pass; the phone's first load is unchanged by the desktop code; and the desktop checklist (Testing) passes.

### The layout

4. **One app, two shells.** `useLayout()` (`app/viewport.ts`) is `phone` under 1024px, `desk2` from 1024 to 1279px and `desk3` from 1280px, read from `matchMedia` through `useSyncExternalStore`, so resizing the window swaps the layout live. `AppShell` becomes a switch: `PhoneShell` is today's frame, unchanged; `DesktopShell` is a `React.lazy` module of its own (`desktop/DesktopShell.tsx`), its stem added to `checkLazyViews`' list and its table test, so the phone's first load does not grow. Routes do not change: the hash names the middle's panel on both shells, and a push link opens the same view. A breakpoint crossed keeps the route, the drafts and each session's held scroll.
5. **The frame at `desk3`:** a top bar across the window, then the sidebar (fixed width, about 250px), the middle (the rest), and the inspector (about 330px, at most a third of the window). At `desk2` there is no inspector: the middle's session tabs reach every view. There is no footer on desktop; the top bar carries what the phone's footer does.
6. **The layout's state** is the sidebar's and the inspector's visibility and the inspector's tab, kept in localStorage `loom.desktop` as `{ "sidebar": true, "inspector": true, "slots": [{ "tab": "changes" }] }`: `slots` is a list so layout B can add panes without a new key, and this sub-project reads and writes only its first entry. A value that does not parse, or names a tab no panel has, is the default (both shown, the inspector's tab the first that applies).
7. **The top bar:** the link's pill and `loom@host` (with the last update's time while offline), the workspace filter, the palette's box ("Search sessions, commands, places" with its key; it comes with the palette, part 2), the needs-you, your-turn and working counts (each opens the group's next session, as the footer's do), and links to new session, the host's flows (while a shown session has flows) and settings. The pill and the counts are pulled out of `StatusRow` into `LinkPill` and `GroupCounts`, which the phone's footer and the top bar both draw. The workspace filter moves out of the fleet panel into `fleet/filter.ts` (`FILTER_KEY` and its hook, `loom.filter` unchanged), which the fleet panel and the top bar both use.
8. **The sidebar** is the fleet's groups over the shown workspaces in compact two-line rows: the group's dot, the title and its age on the first line; on the second, why it waits (an ask or a permission), else the flow's chip in its tone, else what it said last. The session on screen is highlighted; a row opens `sessionHref`; Paused folds as on the phone (a Collapsible, closed by default). It is chrome, like the footer, not a panel. On the fleet route (`#/`) the sidebar is hidden and the middle draws the fleet panel's Body in full, since the sidebar would repeat it; on desktop the fleet's Head is not drawn and its Body draws no workspace filter of its own, since the top bar carries both.
9. **The middle** is exactly the phone's frame for the route: the panel's Head, the session's tabs, its Strip and its Body, in a pane that scrolls on its own under a pinned head. Conversation text keeps a readable measure (the reply box and turns at most about 48rem). At any width, pairing and the splash drawn with no snapshot use the phone's centred column (`PhoneShell`), and the full mockup draws full-window with no chrome.
10. **The inspector** draws on session routes only (not on the fleet, the host's flows, new session, settings or pairing), at `desk3`, while shown. Its tab strip lists `sessionTabs(session)` minus the tab the middle lights (`tabOf`); its chosen tab is the slot's, and when that tab is the middle's or does not apply it shows the next applicable tab after it in tab order, wrapping, that is not the middle's (none: the inspector draws nothing). It draws the tab panel's `Body` through `PanelHost` with `{ sessionId, params: { id }, search: {} }`, in its own error boundary and scroll pane. A link inside it (an agent, a job, a story) navigates the middle.
11. **Shared parts by layout:** `askConfirm` keeps its API and draws a Drawer on the phone and a centred Base UI Dialog on desktop; the `Toaster` stays top-centre on the phone and sits bottom-right on desktop. `AppShell` mounts the one `ConfirmSheet` and the one `Toaster` above both shells, each told the layout, so a shell swap neither drops an open confirmation nor a toast. Phone-only rules (44px targets, 16px form text, safe-area insets) stay in the panels; the desktop chrome (top bar, sidebar, inspector tabs) is denser.

### Panels in panes

12. **Panels scroll through `ScrollPane`, never the window.** `app/scroll.tsx` gives a panel its scroller through context: the window on the phone, the pane's element on desktop, with its scroll position, its viewport height, its content height, `scrollTo`, a scroll subscription and the height of the pane's pinned head. Conversation, JobBody and FlowDocBody move onto it, with their behaviour unchanged on the phone (their tests pin it). FlowDocBody's jump reads the pane's head height instead of `[data-slot="header"]`'s.
13. **A body reads its session from its props, never from the route.** `NoSession` takes the session id as a prop instead of reading `useRoute()`. A Head or a Strip may read the route, since only the middle draws them.

### The keys

14. **One table, `app/keymap.ts`,** maps a key to a command id, as `script/defaults.lua` does for the TUI. Every key runs a registered command through `runCommand`; the palette and the help read the same table. The keys are bound only in `DesktopShell`, by one `keydown` listener on the document (`desktop/useKeys.ts`), which does nothing while a text field has focus, while a dialog or the palette is open, during IME composition (`isComposing`), or with ⌘, Ctrl or Alt held (Shift is part of the key), except ⌘K and Ctrl+K, which open the palette from anywhere, a text field included. `Esc` in the reply box blurs it.
15. **The keys:**

    | Key | Command | Does |
    |---|---|---|
    | `j`, `↓` / `k`, `↑` | `nav.nextSession` / `nav.prevSession` | the next or previous session the sidebar shows, in its order (a folded Paused group's skipped), stopping at the ends; it opens in the middle's tab when that tab applies to it, else at its default (conversation, or info for a session that is not Claude's) |
    | `g` / `G` | `nav.firstSession` / `nav.lastSession` | the first or last |
    | `J` / `K` | `nav.pageDown` / `nav.pageUp` | ten sessions on or back, stopping at the ends |
    | `]` / `[` | `nav.nextWaiting` / `nav.prevWaiting` | the next or previous session that needs you, wrapping (`nextInGroup` over `needs_you`) |
    | `}`, `;` / `{`, `l` | `nav.nextWorkspace` / `nav.prevWorkspace` | the workspace filter's next or previous choice, wrapping through "all" |
    | `i`, `Enter` | `nav.focusReply` | focus the reply box (`data-slot="reply"`), on a session whose conversation is in the middle |
    | `d` | `nav.toggleChanges` | the changes tab in the middle while it applies to the session, or back to the conversation |
    | `n`, `N` | `go.new` | new session |
    | `s`, `r`, `p`, `m`, `D` | `session.pause`, `.resume`, `.push`, `.merge`, `.kill` | the session's commands, with their dialogs |
    | `S` | `go.settings` | settings |
    | `\` | `view.toggleSidebar` | show or hide the sidebar |
    | `\|` | `view.toggleInspector` | show or hide the inspector |
    | `?` | `app.help` | the key help |
    | ⌘K, Ctrl+K | `app.palette` | the palette |

    The session commands' ids are the ones part 2 registered; the view commands (`nav.*`, `go.*`, `view.*`, `app.help`, `app.palette`) are new, in `commands/nav.ts`.
16. **View commands are `offline`:** they act on nothing in loom (they move the view, toggle chrome or open a dialog), so they run while the snapshot is stale. `internal/web/ui/CLAUDE.md`'s offline rule is amended to name them beside the switch and pairing. A session command keeps its `when` and stays off while stale.
17. **The help** (`desktop/KeyHelp.tsx`) is a Dialog listing the table: each key with its command's title, grouped as navigation, session, view and app, generated from `keymap.ts` so it never drifts.

### The palette

18. **A Base UI Dialog around a Base UI Autocomplete** (`desktop/Palette.tsx`), opened by ⌘K, Ctrl+K or the top bar's box. Its items come from `desktop/palette.ts` (pure): sessions (every session of every workspace, paused included, matched on title, branch and workspace name), commands (each registered command that takes no args, matched on its title, with its key from the table), and places (Settings, the host's flows, New session, the fleet, and the current session's tab panels and flow board, matched on their titles). Commands that need args picked in a view (a job's controls, an ask's answers) are not listed.
19. **Matching and order:** a hand-written fuzzy score (a subsequence match, consecutive and word-start characters scoring higher), no dependency. Results are grouped sessions, commands, places, each ordered by score, then by title compared by code point (never `localeCompare`). An empty query lists the sessions that need you, then the commands whose `when` holds for the current session, then the places.
20. **Enter** opens a session or a place, or runs a command through `runCommand`, so a confirmation, the in-flight key and the toasts behave as on a button. A command whose `when` fails, or that is not `offline` while the snapshot is stale, is drawn dimmed and does nothing.

### The loopback origin

21. **The origin rule becomes a set:** the configured origin plus the listener's local origin, `http://loom.localhost:<port>`, when it is bound to `127.0.0.1` or `::1` (Chrome, Edge and Firefox resolve every `*.localhost` name to loopback). Bare `localhost` and the IP literal are not in the set (the owner, 2026-11-21, from /flow:draft's skeleton review): cookies are not isolated by port, so a device cookie set on `localhost` or `127.0.0.1` would reach every server the browser reaches there on any port (an `ssh -L` or editor forward to another machine, a container's published port, another user's dev server), and `authed` ties a token to no origin. A listener on another loopback IP has no local origin. The existing guard test case "localhost is not 127.0.0.1" (origin `http://127.0.0.1:7420`, Host `localhost:7420`) stays refused on every listener; `loom.localhost:7420` is accepted on a `127.0.0.1:7420` listener and refused on a listener on another port. `guard` answers 421 to a `Host` outside the set and 403 to a write without exactly one `Origin` in it. A configured origin that is itself the local one is in the set once. No flag and no setting: the listener is loopback-only, so its local origin is known.
22. **The local origin grants nothing the tunnel's does not:** every route but `POST /api/v1/pair` still needs a paired device's cookie. DNS rebinding cannot present a `*.localhost` name as its `Host` (browsers resolve those to loopback themselves), and a page on another local port is another origin, refused. The device cookie is host-only to `loom.localhost`, so no service reached at bare `localhost` or a loopback literal ever receives it. Cookies ignore the port, though, so a hostile listener on another loopback port (another OS user's server, a forward to a compromised machine, a container's port) that steers the browser to `loom.localhost:<its port>` receives it; the owner accepts that as safe on a single-user machine (2026-11-21, from /flow:draft's plan review), and the docs say so. Browsers treat `http://*.localhost` as a secure context, so the `__Host-` cookies, the worker and Install App work there; each origin holds its own cookie, so the local browser and a tunnel browser are separate devices. Safari may not resolve `*.localhost`: a Safari desktop pairs through the tunnel.
23. **Push is unchanged:** the VAPID subject stays the configured origin, so a desktop subscribed on localhost gets notifications while the configured origin is https; an http configured origin still sends none (`noteHTTPOrigin`). `loom web status` prints the local origin beside the configured one.

### `loom web open` and the pairing link

24. **`loom web open [--name <device>]`**, the name `desktop` by default: refused while the web is off ("The web app is off; turn it on with loom web enable."); when no device has the name it mints a code with `PairDevice` and opens `<local>/?ui=next#/pair?code=<code>`; when the name is paired it opens `<local>/?ui=next` with no code and says so ("desktop is already paired. If this browser is not, pass --name or run loom web revoke desktop."). The URL is always printed. `<local>` is the bound address's local origin (`WebView.Addr`), `http://loom.localhost:<port>`; a listener on another loopback IP has none, and the command says so and mints nothing. The command is refused, minting nothing, unless the web is serving (`WebView.Serving`), quoting the layer's error when it has one, and the URL is built before a code is minted. `?ui=next` makes the daemon serve the new app's shell to a browser with no `__Host-loom-ui` cookie yet (`treeOf`); the code stays in the fragment, so no request or log sees it. The name is checked by `ValidateDeviceName`, as `loom web pair` checks it.
25. **The opener** is `xdg-open` (Linux and the BSDs), `open` (macOS) or `rundll32 url.dll,FileProtocolHandler` (Windows), in `_unix.go` and `_windows.go` files, behind a seam the tests replace. It is started and waited on for at most 5 seconds: an exit status other than 0 within them is a failure, and an opener still running after them counts as opened and is left running, never killed (some openers stay up while the browser starts, and killing one can take the browser with it). An opener missing or failing (no display, over SSH) prints that the browser could not be opened, leaves the URL printed, and exits 0; a code minted stays good for its ten minutes. The pairing link, code included, is the opener's argument, so another local OS user can read the code from the process list (`/proc/<pid>/cmdline`, `ps`) while the opener or a freshly started browser runs, and redeem it first; the owner accepts that as safe on a single-user machine (2026-11-21, from /flow:draft's plan review), and `USAGE.md` says so. `internal/cli/CLAUDE.md` is at its 20,000-byte budget, so the command gains no rule there.
26. **The app reads `#/pair?code=`:** `routeOf` reads `#/pair?code=…` as the fleet, so `main.tsx` takes the code before the router or the stream starts: a hash of `#/pair` or `#pair` with a `code` query is replaced in place by `#/pair` (`history.replaceState`), and the code, through `normalizeCode`, is held in memory when it has 8 characters (any other is dropped and the pairing screen shows as usual). The held code is used once, to run `device.pair`, and only once the daemon has answered 401 (the unpaired signal); a live snapshot first means this browser is paired, so the code is dropped (it expires unused) and the fleet opens, as a pairing screen receiving a snapshot does today. A refused code leaves the pairing screen with the daemon's words as a toast. Served by `?ui=next` with no `__Host-loom-ui` cookie, the app sets the cookie to `next` before it registers its worker, so later launches and the worker's own requests keep the new app. A worker takeover that reloads the page (another build's or the classic app's worker controlling the origin) drops the held code: the pairing screen shows, and the code in the printed URL can be typed. Remote desktops pair through the tunnel with `loom web pair`, as the phone does.

### Errors and edge cases

- **The desktop chunk fails to load:** the shell's error boundary shows what failed and a reload.
- **An inspector panel throws:** its boundary replaces the inspector only; the middle, the sidebar and the top bar keep working.
- **A key with no binding, or a binding while a text field has focus:** nothing happens, and the key reaches the field.
- **A stale snapshot:** view commands and the palette still work; session commands show dimmed and refuse, as buttons do.
- **`loom.desktop` unreadable** (private window, a bad value): the default layout.
- **The window crosses a breakpoint mid-dialog:** the open confirmation is drawn again in the new layout's form (§11) and the command still waits for its answer.
- **`loom web open` with the port taken, the web off, or no browser:** each said plainly; nothing guessed.
- **A pairing link opened in a browser that is already paired:** the code is dropped unused (§26).

## Delivery

An epic of 2 parts, each a plan merged to main before the next part is designed.

**Settled by the design session, from the spec and the code:**

4. **The palette mark.** `Command` gains `palette?: boolean`, set only on a command that takes no args; the palette lists exactly the registered commands that set it: `session.pause`, `session.resume`, `session.push`, `session.merge`, `session.kill`, `push.enable`, `device.unpair`, `app.backToClassic`, `view.toggleSidebar` and `view.toggleInspector` (§18's "takes no args", made explicit, since the registry cannot tell). `allCommands()` lists the registry in definition order. 5. **The phone's first load.** `commands/view.ts` is imported by `desktop/DesktopShell.tsx`, never by `commands/index.ts`, and the palette, its store and its listener are modules of the desktop chunk; the only part 2 code in the entry is `confirmOpen()` in `app/ConfirmSheet.tsx` and `hasShownFlows` in `fleet/groups.ts` (moved out of `FleetLinks`, which keeps calling it). `checkLazyViews` is unchanged.
6. **The chord.** Meta or Ctrl held, Alt and Shift not, not `isComposing`, and `event.key` `k` or `K`: the listener calls `preventDefault()`, then does nothing while a confirmation is open (`confirmOpen()`), and otherwise toggles the palette, so a second ⌘K closes it. Esc closes it (the Dialog's own).
7. **The score** (§19), `fuzzyScore(query, text)`: both lowercased (`toLowerCase()`) and walked by code point. An alignment matches every query code point, in order, to a text code point: it starts at a position holding the query's first code point and takes each later one at its next occurrence. Each matched code point scores 1, plus 2 when it directly follows the previous matched one in the text, plus 3 when it starts a word (the text's first code point, or one after a code point that is neither a letter nor a digit, `\p{L}` or `\p{N}`). The score is the best alignment's over every start, null when none matches, and 0 for an empty query. `fuzzyScore("pa", "Pause")` is 7, `fuzzyScore("pa", "update panel")` 7, `fuzzyScore("ps", "Pause")` 5, `fuzzyScore("sp", "session.push")` 8, and `fuzzyScore("xyz", "Pause")` null. The query is trimmed; no length bound is needed, since the work is quadratic only in a matched field's length and the fields are a fleet's titles, branches and workspace names.
8. **The items.** Sessions: `allSessions(snapshot)`, every workspace's, paused included, each matched on its title, its branch and its workspace's name (`label || name`), the best of the three; drawn with its title and a hint of the workspace's name and the branch (`·` between, an empty one left out); opened at `sessionHref(session)`. Commands: the palette set (decision 4), matched and drawn by title (a function title called with the context); no key is shown beside any but the box's own chord. Places, in this order: the current session's tab panels (`sessionTabs`, each by its tab label, its hint the session's title; the flow board is its `flow` tab, when it applies), then Fleet, New session, Flows (only while a shown workspace's session has flows, the top bar's rule, `hasShownFlows`) and Settings.
9. **The order** (§19). A non-empty query drops what doesn't match, then orders each group by score (higher first), then by title by code point (`compareCodePoints`, never `localeCompare`), then by the item's key by code point. An empty query lists the sessions that need you in their group's order (the longest wait first), then the palette commands whose `when` holds for the current context, by title by code point, then every place in list order. A group with no items is not drawn.
10. **Enter** (§20). A session or a place closes the palette and goes to its link (`window.location.assign`). A command closes the palette, then runs through `runCommand` with the route's context (`useCommandContext()`) and no args, so its confirmation shows alone and the in-flight key and the toasts behave as on a button. A command `commandEnabled` refuses (its `when` fails, or it is not `offline` while the snapshot is stale) is a `disabled` item: drawn dimmed, skipped by the highlight, and inert to Enter and the pointer. Each opening starts with an empty query.
11. **The box** (§7): a button in the top bar after `loom@host` and before the workspace filter, about 16rem wide (`loom@host` keeps the slack), reading "Search sessions, commands, places" and the chord: `⌘K` where `navigator.platform` names a Mac, iPhone or iPad, `Ctrl K` elsewhere. A click opens the palette.
