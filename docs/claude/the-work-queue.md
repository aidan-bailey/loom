# The work queue (the model's side of `loom job`)

**Read this when** you change `core/queue*.go`, `gateQueue`, `adoptJobs`, a job's notice or the subagent it goes to (`core/mod_calls.go`), or `sched`'s runtime (the shim, the lock probe, group signals, the usage sampler).

**What it is.** The daemon's model owns a per-host queue of jobs that sessions submit with `loom job`. It admits each against the caps in the global `config.json`'s `scheduler` block, starts it as a detached `loom job-shim` (a child in a session of its own, so it outlives the daemon), watches it through the shim's lock, and tells the owner's Claude when it ends. The pure half (types, caps, first-fit admission, the `jobs.json` store, the per-job file codecs) and the process half (the shim, the lock probe, group signals, the sampler) are the `sched` package; the queue's state and decisions are `core/queue.go` (state, load and save, boot adoption, retention), `core/queue_admit.go` (admission passes, starting), `core/queue_watch.go` (the gated job's lock tests, sampling, settling, a cancel's escalation), `core/queue_ops.go` (the operations the requests wrap), `core/queue_notice.go` (notices) and `core/queue_beliefs.go` (signatures, sizing, `beliefs.json`) and `core/queue_chain.go` (dependent jobs: the prerequisite check, release, the cascade and its messages, the boot's `resolveHeld`) and `core/queue_holds.go` (past-peak holds: `refreshHolds`, `breakHold`). The gate is `gateQueue` in `core/gate.go`, 3 s; [`adding-a-gated-job.md`](adding-a-gated-job.md) covers the gate's own traps.

## Rules

1. **Test the lock before you signal a group.** A job's process group is its shim's pid. Send a signal (`sched.SignalGroup`) only to a group whose `sched.Probe` shows `run.lock` held, which proves the pid is still the shim. The exceptions are a lost job (the shim is gone and left no `exit.json`) and the shim of a failed start (`queueState.silent`) once it is gone: the group gets SIGKILL only when the latest `ps` sample shows processes in the group and none with the shim's pid. A live process with that pid and no lock is a reused pid, and its group is never signalled. *Silent:* a signal to an unrelated process group (your shell, an editor, another job). Convention only; a test that proves a signal is withheld needs a reused-pid fixture.
2. **Settle before you admit, at boot.** `Model.Boot` loads `jobs.json` (`loadQueue`), whose last steps are `adoptJobs` and then the first `admitJobs`. `adoptJobs` runs one lock pass over every running job (and every job the record calls queued, since a start whose save failed leaves a running shim behind a queued record), before the loop starts. `Model.Begin` then calls `maybeQueue`, which hands the adopted running jobs to `gateQueue`'s watch. The caps count the jobs adopted, and nothing runs twice: a held lock means running, an `exit.json` means settle from it, neither means `lost`. A queued record whose lock test failed is held out of admission (`queueState.unprobed`) and tested again (`reprobeHeld`) before each pass. *Silent:* an admission pass before settling starts jobs on top of ones already running.
3. **The queue is touched only on the loop.** `queueState` is read and written by the model's goroutine; a job (the start, the sample) gets a snapshot (ids, paths, pids) and returns one result that `Deliver` applies. A result lands after the job it names may have been cancelled or removed: look the record up again before acting. *Silent:* a race that only `CC=clang CGO_ENABLED=1 go test -race` finds, and only when a test overlaps it.
4. **Remove a job's files only through `sched.RemoveJobDir`.** It removes `JobDir(dir, id)`, built from the ID; never a path read from `jobs.json`, `spec.json` or the wire. It has two callers: retention, which drops finished jobs beyond `keep_finished`, oldest end first, once `jobs.json` no longer lists them (`removeJobDirsJob`), and `submitJob`'s take-back of a directory it has just created, when a later write fails. `submitJob` creates the directory exclusively (`sched.CreateJobDir`): one that already exists refuses that submission and is left as it is, and `NextID` moves past it in memory (not saved at that point, so the next submit tries the next ID, not this one again; `sched.LoadStore` also raises `NextID` past every numeric `jobs/<id>` on load), so a job never takes over an old job's `output.log`, `exit.json` or lock. *Silent:* a recursive delete of whatever a corrupt file names, or a new job reading an old one's result.
5. **Leave a `jobs.json` that fails to load alone.** An unreadable, invalid or newer-version file (`sched.ErrNewerStore`) sets `queueState.loadErr`: submissions are refused with the reason, admission pauses, a notice is raised, and the running shims carry on. Never write over it, and never start from an empty queue. Write the store only through `sched.SaveStore`. The same goes for `config.json`: `refreshPolicy` reads only the `scheduler` block (`diskSchedulerBlock`), and a file it cannot read pauses admission with `config.json could not be read: <err>` and is left where it is, never loaded through `config.LoadConfigFrom`, which would rename it aside and fall back to the host's defaults. *Silent:* an overwritten file loses every queued job and the ID counter, and IDs are reused; a quarantined `config.json` swaps the owner's caps for the defaults.
6. **A write that fails is not a lost change.** A request that cannot write `spec.json` or `jobs.json` is refused with the error and changes nothing; `setSchedulerCaps` reads `config.json` through `readGlobalConfig` and refuses on any read or decode error (`config.json could not be read, so the caps were not saved: …`), leaving the file byte for byte as it was. A change the model made on its own (a start, a settle, a usage peak) stays in memory, raises a notice and is written with the next save.
7. **Never paste a notice.** A job's end goes to the owner's Claude through the loom mod's outbox (`OriginJob`). With no live mod, or an owner that is not running, the notice is recorded on the job as undelivered, with the reason. A paste into the pane could answer an open dialog. A pause, a kill or a reset someone requests cancels the session's jobs first (`cancelOwnerJobs`; `Reset` calls it for every session of the workspace) and sends no notice; a pause the daemon makes on its own for a session whose tmux session died (`pauseGone`) leaves its jobs running, since a dead pane is nobody's choice to drop the work.
8. **Fail closed.** A cwd that is gone at start fails the job ("its folder is gone"); a shim that writes no `started.json` within 5 s fails the job, and its group is sent SIGKILL only once its lock proves the shim alive: until then `queueState.silent` keeps the pending kill, which `gateQueue` sends when a later lock test finds the shim alive and drops when no process has its pid any more, or after 10 minutes; a process sample that fails or times out (`/proc` on Linux, `ps` elsewhere) is skipped and the lock tests go on without it. Nothing is guessed. A job's usage (`applyUsage`) sums its session (`sched.Snapshot.Session`: on Linux each process's CPU with its reaped children's, so short-lived compiles count, and a child under coreutils `timeout`, which changes group, stays counted); the lost-job proof (`orphanedGroup`) keeps its group, the one the signal reaches.
9. **Size from the belief, live, and learn only from what ran.** `submitJob` resolves the job's signature with `sched.FindRepo` (git's files only: it runs on the loop, so never add a git subprocess there), sizes its claim with `sched.Size` from its belief (`sizeRecord`), and marks the belief seen once the job is stored. Every admission pass re-sizes the queued jobs this build sized (`resizeQueued`, before `sched.Admit`): a claim stays live until the job starts, and a record queued by a build before sizing (no `Sources`) keeps its claim. `admitJobs` then asks `sched.Grant` for spare cores (job scaling spec §5.3), and `startJob` adds them to the record's claim, recording them in `Record.Spare`, before the start job writes the hint: the claim a job starts with is the total, and `RunOf` records the spare cores in `Run.Spare`. `settledJob` records the run (`recordRun`, through `sched.RunOf`); `adoptJobs` and `noteAlive` mark a job `Adopted`, so its partly sampled peak counts only as a floor. A `beliefs.json` that fails to load sets `beliefsErr`: learning is off, jobs take their flags and the default claim, nothing is recorded, and the file is never written (`saveBeliefsQuiet` checks). *Silent:* a git subprocess on the loop stalls every client; a floor taken as a full peak teaches a failing build's small peak to the next good run.
10. **Give a job a subagent only on one exact match, and choose a subagent notice's path as the inbox hands it over.** `submitJob` asks `attribution` (`core/mod_calls.go`) for the one `loom job` Bash call the mod reported in flight on the submitting launch whose command holds the whole argv and has a use left (one use per `claudemod.JobCallPattern` match, spent only after the save); none, or more than one, leaves `Record.Agent` empty and the job the session's. The pattern also matches `loom feedback add`, whose note reads its call's agent and model without spending a use ([`the-feedback-inbox.md`](the-feedback-inbox.md) rule 2). `ModInbox` gives a notice carrying an agent to a mod whose hello said `agents`, and the session's copy naming the subagent (`withSubmitter`, `oldModLine`) to any other, deciding at hand-out because the hello may come after the enqueue. A `failed` report on it queues the session's copy with the reason (`modFailed`, `unreachableLine`); a link's end settles it undelivered, like any notice the mod took. *Silent:* a guess by timing or position sends a build's result to the wrong agent; a choice made at enqueue hands a mod that can't send to subagents a message it submits to the main loop without saying whose it is. Enforced by `TestSubmit_TakesItsAgentFromTheOneCallThatMadeIt`, `TestSubmit_ACallAccountsForAsManySubmitsAsItRuns`, `TestModCall_ACommandThatSubmitsNothingIsNotKept`, `TestJobQueue_ASubagentsNoticeGoesToItWhenTheModCan` and `TestJobQueue_ASubagentThatCantTakeItsNoticeLeavesItToTheSession`.
11. **Release and cascade inside the settle, never in a pass.** `settledJob` ends with `settleChain`: a job that ended done releases the jobs held after it (`releaseDependents`: queued from now, at the lower of their order and its), and any other end cancels them down the chain (`cascade`), with one message per branch (`sendCascadeNotices`) and the others recorded `carried`. At boot, `resolveHeld` runs before `adoptJobs`, since `adoptJobs`' settles end in `afterSettle`, which runs an admission pass; it cancels the held jobs that carry a cancel request first, so a release cannot take one back. A held job counts as waiting (`State.Waiting`) everywhere a queued one does except `Admit` and `Grant`, which never see it: cancel at once, pause, kill and reset, the move to the front, live sizing, the advisor's asks and the view. `cancelOwnerJobs` marks every job before it ends any, so a cascade inside a pause keeps the pause's reason and sends nothing. *Silent:* a release made in a pass starts a dependent a pass late, or behind jobs submitted after its chain; a cascade that skips the branch rules sends a message per job, or a pause's cancellations send messages.
12. **Work out holds on the loop, from the trace alone, and persist nothing of them but `HoldBroke` and the profile** ([spec](../superpowers/specs/2026-11-05-past-peak-holds-design.md)). `applyUsage` adds a point to `queueState.traces` for a running job that was not adopted, and turns a usage above a released hold into `breakHold` (`Record.HoldBroke`, the claim to the end); `refreshHolds` runs `sched.Hold` for every running job after each sample (`deliverQueuePass`) and before each pass (`admitJobs`), keeping `queueState.holds` (where each hold stands) and `queueState.holding` (what `Admit`, `Grant`, `Forecast` and the view count). `settledJob` takes the trace for `recordRun`, which gives a done run that was not adopted its profile (`sched.BuildProfile`), and drops the job's entries from all three maps. A restarted daemon adopts its jobs at their claims. `setSchedulerCaps` keeps the file's `release_past_peaks`, as it keeps the `agent` block, since the caps form sends only its own fields (`TestJobQueue_ACapsEditKeepsTheReleaseSwitch`). *Silent:* a trace kept past its job's settle becomes part of another run's profile; a hold worked out off the loop races the sample; a hold that skipped `HoldBroke` keeps releasing a command that has already outgrown its profile.
13. **Make every D-Bus call from a spawned job, never on the loop, and drop the confiner after a call fails** ([spec](../superpowers/specs/2026-11-05-cgroup-greedy-scheduler-design.md)). The one exception is the boot's first probe (`probeConfinerAtBoot`, in `loadQueue` before the first admission pass), which runs in `Boot` before the loop serves anyone, bounded by 2 s, so the jobs a restart admits are contained. Later probes (`maybeProbeConfiner`, every minute while jobs wait and start uncontained; an idle queue makes none), the slice's ensure (`runJobStart`) and every other call run as background jobs with a 5 s bound; a failed one goes through `confinerFailed`, which logs once, closes the connection and leaves `containWhy` saying why until a probe reaches systemd again. Core's own tests set `newConfiner = nil` (no probe): a probe's job would join every count they make. The shim, not the daemon, joins the job's scope (`spec.json`'s `scope`), and reports the cgroup it landed in through `started.json`, which `runJobStart` and `noteAlive` copy to the record; a job's usage comes from that cgroup (`sched.ReadCgroup` in `runQueuePass`, the working set and `cpu.stat`) and falls back to its session. Tests reach no real bus: `testenv.IsolateLoomDirs` points `DBUS_SESSION_BUS_ADDRESS` at a dead socket, and a test installs a `fakeConfiner` with `SetConfinerForTest` and a cgroup root with `SetCgroupRootForTest`. *Silent:* a call on the loop freezes every client while the bus hangs; a confiner kept after a failure starts every job with a scope its shim can't join.
14. **Admit greedily only with a confiner, and from fresh numbers** ([spec](../superpowers/specs/2026-11-05-cgroup-greedy-scheduler-design.md) §7). `greedyInputs` answers false while `containWhy` has a reason, so fallback admission is today's `Admit`, holds included; it reads MemAvailable itself (a `/proc` file, `readMemAvailable`), since an idle queue has no pass to read it, and predicts each running job from its trace's progress (`predictRunning`), counting it flat at its hold or claim without 3 curves, when uncontained or adopted, and at its use plus 15% when that is above its prediction. `deliverQueuePass` runs an admission pass after every sample while jobs wait. Core's `TestMain` fixes `readMemAvailable` at 64 GB, so a test's admissions never follow the host's free memory. *Silent:* greedy admission without a confiner packs jobs with no ladder behind it; a budget from a stale pass admits into memory the agents took since.
15. **Change a job's rung only when its call returned, admit nothing while a job is laddered, and requeue only through `requeueJob`** ([spec](../superpowers/specs/2026-11-05-cgroup-greedy-scheduler-design.md) §8). `stepLadder` runs after every pass in greedy mode, one action in flight (`laddering`); `deliverLadderDone` sets `Rung` only for a call that returned, and a failed one leaves the rung, logs and shows `LadderErr`, and is tried again. `applyUsage` reconciles the rung from the cgroup each pass while no action is in flight (frozen is paused, a `memory.high` is squeezed), which also covers a restart. `ladderHoldoff` is greedy admission's hold-off. A requeue sets `Record.Requeue` and writes `cgroup.kill`; `settleGone` sees it (or a kernel OOM kill: the slice's `oom_kill` rose, `queueState.oomAt`, and the contained job ended by SIGKILL or with no result) and calls `requeueJob`, which records a floor run, archives the attempt (`sched.ArchiveAttempt`), keeps the submission's and sizing's fields and clears every run field, and sends `sendRequeueNotice` with no fate (the mod message names job 0, so the end notice still comes). A cancel of a laddered job restores it first, so it can act on its SIGTERM. *Silent:* a rung recorded for a call that failed leaves a running job shown paused; admissions during a squeeze feed the shortage they wait out; a requeued record that kept its `PID`, `Cgroup` or `Exit` settles the next attempt from the last one's files.
16. **Agent jobs (`Kind` `agent`, flow in loom part 3a) are not build jobs.** `submitJob` skips their signature, sizing, `CheckClaim` and the advisor, and records `AccountKey`; `Admit` starts them by `Policy.AgentJobs` per account and never counts them against the caps or makes one the head; `Grant` passes them over; the shim gives them `AgentHints` (only `LOOM_JOB` and `SCCACHE_CLIENT_SIDE`); `startJob` runs them uncontained (`agentUncontained`), so the ladder, which takes only jobs with a cgroup, never squeezes, freezes or requeues one. *Silent:* contained, an agent's scope gets `CPUWeight(0)`, the least weight there is, and a requeue reruns an agent over the tree it half edited. Enforced by `TestQueueContain_AnAgentJobRunsUncontained`. Their own direct commands still run outside admission, as an agent's did before ([spec](../superpowers/specs/2026-11-06-flow-in-loom-agent-runs-design.md)).

## The advisor

`core/queue_advisor.go` runs the scheduler's agent (`sched/advisor`). `submitJob` marks a job `asking` when `askForPrior` holds (the advisor is available, `sched.NeedsPrior`, and the signature's last prior didn't fail in the last 10 minutes) and queues a prior (`queueAdvice`; jobs of one signature share one call). `dispatchAdvisor` keeps one call in flight, priors first; it drops a call while the advisor is off (`advisorOff`: learning off, the block invalid or off, no Claude program, an unregistered account, the 30-minute pause after three failures) or its account's 5-hour window is at 90% (`advisorUsageHigh`), releasing the jobs that waited. `deliverAdvisor` stores a checked prior (`priorOf` copies a `like` belief's learned parts) or a note, and releases the jobs; `admitJobs` releases a job that has waited `wait_seconds` (`releaseOverdueAsks`), and `loadQueue` asks again for jobs a previous daemon left asking (`resumeAsks`). `recordRun` scores a prior (`sched.ScorePrior`) and queues a reconcile on a surprise (`sched.Surprise`), at most once per belief in six hours. Every call that ends, and every call dropped before it runs, goes to the call log (`logCall`: `advisor.jsonl`, the last 500, loaded at boot by `loadAdvisorCalls`, kept in memory only when it fails to load); `agentView` publishes the live state (calls waiting, the call in flight from `flightAt`, failures in a row, the pause, today's calls and cost) and `ReadAgent` pages the log. Tests run a fake `claude` script through `SetAdvisorForTest` (`core/seams.go`); with no Claude program (`NewForTest`'s default) the advisor is off, so no test reaches a real model.

`queueView` adds each job's usual duration, P90 and overdue mark from its belief (`sched.Usual`, `sched.OverdueAfter`, at the job's cores: a queued job's base claim, a running job's total), a queued job's `Ideal` (`sched.SpareWidth`) and each queued job's forecast start (`sched.Forecast`, with `hostUsual` for jobs with no estimate). `ReadBeliefs` answers from the registry with copies (`Belief.Clone`), and refuses while learning is off; `ForgetBelief` writes `beliefs.json` before it answers (a failed write keeps the belief) and gives queued jobs of the forgotten signature a new, empty belief.

## Testing with real shims

A test binary has no `job-shim` command, so a package whose tests start real shims (`sched`, `core`, `internal/cli`) re-executes its own test binary as the shim:

- Its `TestMain` calls `sched.MaybeRunTestShim()` as its first statement. When the environment variable `sched.ShimTestEnv` (`LOOM_SCHED_TEST_SHIM`) is `1`, the process runs `sched.RunShim` on its last argument and exits instead of running tests.
- The runner a test hands the model is `sched.TestRunner()` (the test binary, with that variable set), installed with `Model.SetJobRunnerForTest` in `core/seams.go`.
- Real jobs are short commands (`sh -c`, `sleep`), and every test leaves no process group behind: cancel or wait for each job it starts.
- A test that must see a job running gives it a command that outlasts the pump (`sleep 1`): one that exits at once (`sh -c 'exit 0'`) can already be settled when the `wqPump` after its submit returns.
- Build fixtures through the production path: a booted model, a real shim, a `jobs.json` written with `sched.SaveStore`. A fake runner skips the lock, the `Setsid` and the `exit.json`, which is where the bugs are.

## Traps

- **A `TestMain` without the hook.** The shim child is the test binary with the variable set; without `MaybeRunTestShim` it runs the whole suite, whose tests start more shims. Add the hook to a new package's `TestMain` before its first real-shim test.
- **Environment.** The job's environment comes only from `spec.json`; the shim process itself gets the daemon's environment plus `Runner.Env`. Do not build a git or tmux command from a job's environment.
- **The sample is a hint, not proof.** Usage and the lost-job rule read one `ps -A` snapshot; procps and BSD format `time` differently and `ParsePS` reads both. Skip a failed sample, never reuse a stale one for the kill rule.
- **`KillMode`.** Under systemd's default `control-group`, restarting the unit kills every shim in its cgroup. `USAGE.md`'s unit sets `KillMode=process`; a report of "jobs die with the daemon" on a unit without it is not a model bug.
- **Windows.** The runtime's stubs return `sched.ErrUnsupported` and `SubmitJob` refuses with it. After touching `sched`'s platform files, run `GOOS=windows CGO_ENABLED=0 go build ./...` and the same for `darwin`.
- **The queue's published view follows more than the records.** `QueueChanged` is also published when a job's owner resolves differently (a rename, an unregister, a kill), so `JobView`'s owner fields stay current; a change to the queue that never calls `q.moved()` is never published.
- **`loadQueue` ends with an admission pass.** A seeded queued job that fits starts at load, so a test that wants jobs left queued uses an over-cap claim or a paused policy block.
- **A cap edit never touches running jobs.** It changes only what starts next; an `--exclusive` claim is stored as a flag, so it follows the caps it is admitted under.
- **Host load the queue doesn't see.** When the host is busier than its running jobs, attribute each process by ancestry: a job's processes descend from `job-shim <global dir>/jobs/N`, and anything else is outside the queue. On 2026-11-05 the gap was agents' commands that never entered it (flow's agent-wait script detached them with `setsid` until flow d937675 wrapped them in `loom job run`) and the sccache server, a child of PID 1, compiling for those commands, which lack the `SCCACHE_CLIENT_SIDE` hint jobs get. Match a server-side `rustc` to its client by `--crate-name` and `--out-dir` before blaming a job, and count a reaped child's CPU (`cutime`) against its nearest live ancestor, or a job that ends mid-sample reads as the daemon's.
- **A job wider than its claim.** Claims bound admission only; a running job's width is whatever its tools make of `sched.Hints`, and a tool that reads none of them sizes itself to the host. Compare the claim with the cores peak in `beliefs.json`'s run profiles (`profile.cores.steps`, milli-cores), then read `/proc/<pid>/environ` of the job's processes (`ps -s <shim pid>`) to find the one that ignored its hint. On 2026-11-05 4-core jobs peaked at 10–14 cores because cargo-nextest reads `NEXTEST_TEST_THREADS`, never `RUST_TEST_THREADS`, and defaults to one test process per CPU; still unhinted are linkers, `tokio` runtimes (`TOKIO_WORKER_THREADS`), Go test binaries (`GOMAXPROCS`), rayon (`RAYON_NUM_THREADS`) and Node test runners.

## What the gates won't tell you

- Whether a new signal path tests the lock first (rule 1): no test fails when one forgets.
- Whether a new write of the queue's files goes through `sched.SaveStore` and the codecs.
- Whether a real-shim test leaves a process running after it ends.
