# The feedback inbox (the model's side of `loom feedback`)

**Read this when** you change `core/feedback*.go`, `gateFeedback`, `FeedbackChanged`, what a note records about its session, or how a fix session is started.

**What it is.** Loom's session agents file notes about loom itself with `loom feedback add` (the loom context asks them to, `session/loom_context_shared.md`). The daemon's model owns a per-host inbox under `<globalDir>/feedback/`, a headless Haiku groups each note into a thread, the owner reads the threads ranked by how many sessions hit each (`loom feedback list`, the TUI's `F` view), closes them, or starts a fix session from one. The pure half (types, the store, ranking, the grouper's request, schema, answer and prompt, the fix title and prompt, the call log) is the `feedback` package; the model's half is `core/feedback.go` (state, boot, the settings reread, the view and its publish, the save), `core/feedback_requests.go` (`FileFeedback`, `CloseThread`, `FixThread`) and `core/feedback_group.go` (the gated grouping call and its delivery). Design: [`../superpowers/specs/2026-11-05-session-feedback-design.md`](../superpowers/specs/2026-11-05-session-feedback-design.md).

## Rules

1. **The model alone writes `feedback.json`, through `saveFeedback`, and a file that failed to load is never written.** `bootFeedback` loads it with `feedback.Load`; an error sets `feedbackState.loadErr`, raises a Notice, and every request is refused while the file stays as it was. A request whose save fails rolls the inbox back and is refused (`FileFeedback`, `CloseThread`); a change the model made on its own (a grouping, a fix's mark) stays in memory with a Notice and is written by the next save. *Silent:* an overwrite with an empty inbox drops every note. Enforced by `TestFeedback_AnInboxThatFailedToLoadIsLeftAndRefuses` and `TestFileFeedback_AFailedSaveKeepsNothing`.
2. **Who filed a note comes from the model's own state, never from the request.** `FileFeedback` resolves `FeedbackNote.Launch` with `instByLaunch` (an unknown launch is refused), takes the title, workspace, branch and Claude session from the instance, the subagent and the session's model from the one `loom feedback add` call the mod reported in flight on that launch (`attribution` with `feedbackCall`; none, or two, record neither), the build from `Options.Build`, and keeps the CLI's effort (`$CLAUDE_EFFORT`) only when it is one of Claude's levels. `claudemod.JobCallPattern` matches `loom feedback add` for this, so a feedback call is also a candidate for a job submit's attribution, which needs the whole argv in the command and refuses two candidates. *Silent:* a note naming the wrong session, or a guessed model. Enforced by `TestFileFeedback_StampsTheSessionAndSaves`, `TestFileFeedback_TheSubagentAndModelComeFromTheReportedCall` and `TestFileFeedback_ABadEffortIsDropped`.
3. **No note is dropped or merged on a guess.** A failed call, an answer `feedback.ParseAnswer` refuses, or one `feedback.Apply` can't place leaves the note `ungrouped`, retried after `grouperRetryAfter`; `grouperPauseAfter` failures in a row pause the grouper with one Notice, until the daemon restarts or the `feedback.grouper` block changes (`refreshFeedbackSettings` compares it with `pausedWith`); a disabled grouper leaves notes `pending`. An answer naming a thread the request didn't offer, or one closed since, opens a new thread. Enforced by `TestGroup_FailureLeavesUngroupedAndRetries`, `TestGroup_ThreeFailuresPauseWithANotice`, `TestGroup_OffLeavesNotesPending` and `TestGroup_AClosedThreadAnswerOpensANewThread`.
4. **One grouping call in flight, through `gateFeedback`.** Its interval is 0 (it only dedupes); `FileFeedback`, the tick and each delivery call `maybeGroupFeedback`, whose builder returns nil when no note is due or the grouper is off (`grouperOff`). The call runs `advisor.Run` with the grouper's prompt and schema, keeping the advisor's lockdown, in the empty `grouper` folder under the inbox's dir. Enforced for the one result by `TestProductionGatedJobsYieldOneResult` and the disarm by `TestGatedDeliveryDisarmsFirst`.
5. **`FixThread` makes the `Create` a `loom session new` would.** It resolves the workspace (the request's, else `feedback.workspace`), runs the new-session checks (`CheckRoom`, `CheckWritable`, `CheckNewTitle`, a title the workspace holds), composes the launch (`launch.FromSettings`, `ChooseLaunchAccount` over the model itself, the remote-control check), and calls `createWS`, whose ID marks the thread `fixing`. A start that fails removes its instance, so a `fixing` thread whose session is gone can be fixed again; one whose session is still served is refused. Enforced by `TestFixThread_CreatesInTheWorkspaceAndMarksFixing`, `TestFixThread_Refusals` and `TestFixThread_AGoneFixSessionCanBeFixedAgain`.

## How it fits

- **Publishing:** `FeedbackChanged` is a state event, published by `publishFeedback` when `feedbackState.rev` or `grouperOff()` moved, after the queue's and before the views, coalesced by the server (`coalesceKey` `feedback`) and kept by the replica, which answers `Core.Feedback`. Bump `rev` on every change to the inbox or the grouper's settings.
- **Settings:** `refreshFeedbackSettings` rereads the global `config.json`'s `feedback` block (`diskConfigBlock`) when forced (boot, a note, a fix) and at most once a minute from the grouper's builder, so a hand edit applies.
- **Tests:** `fbModel` (`core/feedback_test.go`) boots an inbox under a fresh global dir with a session on launch L1; `fbGrouper` points the grouper at a fake `claude` through `SetFeedbackGrouperForTest` (`core/seams.go`), and `fbRunAll` runs the queued calls to the end.
