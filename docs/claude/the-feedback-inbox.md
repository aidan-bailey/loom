# The feedback inbox (the model's side of `loom feedback`)

**Read this when** you change `core/feedback*.go`, `gateFeedback`, `gateFeedbackIssues`, `FeedbackChanged`, what a note records about its session, or how a fix session is started.

**What it is.** Loom's session agents file notes about loom itself with `loom feedback add` (the loom context asks them to, `session/loom_context_shared.md`). The daemon's model owns a per-host inbox under `<globalDir>/feedback/`, a headless Haiku groups each note into a thread, the owner reads the threads ranked by how many sessions hit each (`loom feedback list`, the TUI's `F` view), closes them, or starts a fix session from one. The pure half (types, the store, ranking, the grouper's request, schema, answer and prompt, the fix title and prompt, the call log) is the `feedback` package; the model's half is `core/feedback.go` (state, boot, the settings reread, the view and its publish, the save), `core/feedback_requests.go` (`FileFeedback`, `CloseThread`, `FixThread`, `PublishThread`), `core/feedback_group.go` (the gated grouping call and its delivery) and `core/feedback_issues.go` (the gated issue poll and its delivery). The owner can publish a thread as a GitHub issue the issue watcher fixes: `PublishThread` links the thread (`Thread.Issue`, status `published`), the repo skill `/feedback-triage` (`.claude/skills/feedback-triage/SKILL.md`) reviews each thread with the owner and does every GitHub write, and the issue poll closes the thread when its issue closes. Design: [`../superpowers/specs/2026-11-05-session-feedback-design.md`](../superpowers/specs/2026-11-05-session-feedback-design.md) and, for publishing, [`../superpowers/specs/2026-11-20-feedback-issue-triage-design.md`](../superpowers/specs/2026-11-20-feedback-issue-triage-design.md).

## Rules

1. **The model alone writes `feedback.json`, through `saveFeedback`, and a file that failed to load is never written.** `bootFeedback` loads it with `feedback.Load`; an error sets `feedbackState.loadErr`, raises a Notice, and every request is refused while the file stays as it was. A request whose save fails rolls the inbox back and is refused (`FileFeedback`, `CloseThread`); a change the model made on its own (a grouping, a fix's mark) stays in memory with a Notice and is written by the next save. *Silent:* an overwrite with an empty inbox drops every note. Enforced by `TestFeedback_AnInboxThatFailedToLoadIsLeftAndRefuses` and `TestFileFeedback_AFailedSaveKeepsNothing`.
2. **Who filed a note comes from the model's own state, never from the request.** `FileFeedback` resolves `FeedbackNote.Launch` with `instByLaunch` (an unknown launch is refused), takes the title, workspace, branch and Claude session from the instance, the subagent and the session's model from the one `loom feedback add` call the mod reported in flight on that launch (`attribution` with `feedbackCall`; none, or two, record neither), the build from `Options.Build`, and keeps the CLI's effort (`$CLAUDE_EFFORT`) only when it is one of Claude's levels. `claudemod.JobCallPattern` matches `loom feedback add` for this, so a feedback call is also a candidate for a job submit's attribution, which needs the whole argv in the command and refuses two candidates. *Silent:* a note naming the wrong session, or a guessed model. Enforced by `TestFileFeedback_StampsTheSessionAndSaves`, `TestFileFeedback_TheSubagentAndModelComeFromTheReportedCall` and `TestFileFeedback_ABadEffortIsDropped`.
3. **No note is dropped or merged on a guess.** A failed call, an answer `feedback.ParseAnswer` refuses, or one `feedback.Apply` can't place leaves the note `ungrouped`, retried after `grouperRetryAfter`; `grouperPauseAfter` failures in a row pause the grouper with one Notice, until the daemon restarts or the `feedback.grouper` block changes (`refreshFeedbackSettings` compares it with `pausedWith`); a disabled grouper leaves notes `pending`. An answer naming a thread the request didn't offer, or one closed since, opens a new thread. Enforced by `TestGroup_FailureLeavesUngroupedAndRetries`, `TestGroup_ThreeFailuresPauseWithANotice`, `TestGroup_OffLeavesNotesPending` and `TestGroup_AClosedThreadAnswerOpensANewThread`.
4. **One grouping call in flight, through `gateFeedback`.** Its interval is 0 (it only dedupes); `FileFeedback`, the tick and each delivery call `maybeGroupFeedback`, whose builder returns nil when no note is due or the grouper is off (`grouperOff`). The call runs `advisor.Run` with the grouper's prompt and schema, keeping the advisor's lockdown, in the empty `grouper` folder under the inbox's dir. Enforced for the one result by `TestProductionGatedJobsYieldOneResult` and the disarm by `TestGatedDeliveryDisarmsFirst`.
5. **`FixThread` makes the `Create` a `loom session new` would.** It resolves the workspace (the request's, else `feedback.workspace`), runs the new-session checks (`CheckRoom`, `CheckWritable`, `CheckNewTitle`, a title the workspace holds), composes the launch (`launch.FromSettings`, `ChooseLaunchAccount` over the model itself, then the request's model and effort when set, refused by `checkLaunchChoice` unless the launch modal offers them, the remote-control check), and calls `createWS`, whose ID marks the thread `fixing`. A start that fails removes its instance, so a `fixing` thread whose session is gone can be fixed again; one whose session is still served is refused. Enforced by `TestFixThread_CreatesInTheWorkspaceAndMarksFixing`, `TestFixThread_Refusals` and `TestFixThread_AGoneFixSessionCanBeFixedAgain`.
6. **A thread is linked to an issue only through `PublishThread`, which never relinks and never moves `Issue.Posted` back.** It reads the reference with `feedback.ParseIssueRef`, refuses an inbox that didn't load, an unknown or closed thread, a thread linked to another issue and a `through` that is not one of the thread's notes, keeps a `fixing` thread's `Fix`, and rolls back when the save fails; `FixThread` refuses a published thread (the watcher fixes it), and `CloseThread`'s reason is one line of at most `feedback.MaxCloseReason` bytes, checked by the model. `Posted` covers notes by position in `Thread.Notes`, not by ID, since a retried note can join after a newer one. *Silent:* a relinked thread closes when the wrong issue closes; a `Posted` that moves back makes the skill post a comment twice. Enforced by `TestPublishThread_Refusals`, `TestPublishThread_AFailedSaveKeepsNothing`, `TestPublishThread_AFixingThreadKeepsItsFix`, `TestFixThread_RefusesAPublishedThread`, `TestCloseThread_ABadReasonIsRefusedAndChangesNothing` and `TestInbox_PublishNeverMovesPostedBack`.
7. **The issue poll reads and never writes, and a thread closes only on a `gh` answer that its issue is `CLOSED`.** `maybeCheckFeedbackIssues` runs from the health tick through `gateFeedbackIssues` (every `feedbackIssuesInterval`, one call in flight), checks the issues of at most `feedbackIssueChecks` published threads, the least recently checked first (the times live in memory), each with `github.IssueStateOf` under `ghTimeout` inside `feedbackIssueBudget`, in the feedback directory. A closed issue closes every thread linked to it with `issue #<N> closed (<reason>)`; a failed check changes no status and records the error in `FeedbackView.IssueErrs`, bumping `rev` only when something a client shows changed. The poll runs with no client connected and needs no workspace. *Silent:* a timeout or auth failure read as closed closes a thread whose fix hasn't landed, and the grouper opens a new one for its notes. Enforced by `TestFeedbackIssues_ClosedIssueClosesItsThreads`, `TestFeedbackIssues_FailedCheckChangesNothing`, `TestFeedbackIssues_ChecksTenLeastRecentlyCheckedFirst` and `TestFeedbackIssues_ARepeatedFailureBumpsNoRevision`, and for the one result and the disarm by `TestProductionGatedJobsYieldOneResult` and `TestGatedDeliveryDisarmsFirst`.

## How it fits

- **Publishing:** `FeedbackChanged` is a state event, published by `publishFeedback` when `feedbackState.rev` or `grouperOff()` moved, after the queue's and before the views, coalesced by the server (`coalesceKey` `feedback`) and kept by the replica, which answers `Core.Feedback`. Bump `rev` on every change to the inbox or the grouper's settings.
- **Settings:** `refreshFeedbackSettings` rereads the global `config.json`'s `feedback` block (`diskConfigBlock`) when forced (boot, a note, a fix) and at most once a minute from the grouper's builder, so a hand edit applies.
- **The skill:** `/feedback-triage` is the only writer to GitHub for feedback: it drafts, scans (`loom feedback scan --thread T`), asks the owner, posts with `gh`, and then links with `loom feedback publish`; it recovers a created but unlinked issue by the issue body's last line `Feedback thread T` (linking through the last `Feedback note nN` line above it), a folded but unlinked thread by the `Feedback thread T` line that ends its fold comment, and a posted but unlinked comment by the `Feedback note nN` lines in the issue body and the comments the owner's account wrote (never a stranger's). The daemon never creates, comments on or labels an issue.
- **Tests:** `fbModel` (`core/feedback_test.go`) boots an inbox under a fresh global dir with a session on launch L1; `fbGrouper` points the grouper at a fake `claude` through `SetFeedbackGrouperForTest` (`core/seams.go`), and `fbRunAll` runs the queued calls to the end.
