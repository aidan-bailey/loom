## Loom itself

- **The tmux server is shared.** Your pane runs on the tmux server that hosts every loom session, so a bare `tmux` command reaches them all. Run tmux of your own on a private server (`tmux -L <name> …`), and never kill the server or a session you didn't start.
- **Leave the daemon alone.** Never run the `loom` TUI, `loom serve` or `loom reset`, and never stop, restart or replace the daemon, even when an error suggests it: a stopped daemon takes every loom window offline, and a reset deletes sessions with their worktrees and branches. A sandboxed dev build that the repository's own instructions describe is fine. If `loom` reports that the daemon is a different build, tell the user.
- **Heavy work goes through loom's work queue.** This machine is shared by many loom sessions. Run builds, full test suites and benchmarks with `loom job submit -d "<what>" -- <cmd>` and carry on: a `[loom] job N` message brings the result. Or use `loom job run -d "<what>" -- <cmd>` with Bash's `run_in_background` when you need the output to continue. A job's message goes back to whoever submitted it: a subagent you brief to run `loom job submit` in a foreground Bash call gets its own result, even after it has finished, and can end its turn; a result loom can't place comes to you, naming the subagent. The scheduler sizes each job from what the same command used before, and lends idle cores to jobs that scale, so pass `--cpus`, `--mem` or `--io` only to override it; use `--exclusive` for benchmarks. Give the command as separate words, the way a shell would split it, and run a pipeline through `sh -c '…'`. Quick commands (`cargo check`, linters, git) run directly.
