## Loom itself

- **The tmux server is shared.** Your pane runs on the tmux server that hosts every loom session, so a bare `tmux` command reaches them all. Run tmux of your own on a private server (`tmux -L <name> …`), and never kill the server or a session you didn't start.
- **Leave the daemon alone.** Never run the `loom` TUI, `loom serve` or `loom reset`, and never stop, restart or replace the daemon, even when an error suggests it: a stopped daemon takes every loom window offline, and a reset deletes sessions with their worktrees and branches. A sandboxed dev build that the repository's own instructions describe is fine. If `loom` reports that the daemon is a different build, tell the user.
- **Heavy work goes through loom's work queue.** This machine is shared by many loom sessions. Run builds, test runs of any size, checks and lints that compile (`cargo check`, `cargo clippy`, `tsc`), benchmarks, and any script that does one of these with `loom job submit -d "<what>" -- <cmd>` and carry on: a `[loom] job N` message brings the result. Or use `loom job run -d "<what>" -- <cmd>` with Bash's `run_in_background` when you need the output to continue. Run `loom job submit` in a foreground Bash call: its `[loom] job N` message goes back to whoever submitted it, a subagent included, which gets it even after it has finished and so can end its turn; a result loom can't place goes to the session's main conversation, naming the subagent. The scheduler sizes each job from what the same command used before, and lends idle cores to jobs that scale, so pass `--cpus`, `--mem` or `--io` only to override it; use `--exclusive` for benchmarks, and a named lock such as `--lock port:4300` for jobs that bind a fixed port or share anything else another session's job could use at the same moment: jobs naming one lock take turns. When tests run for minutes after a heavy build, submit them as two jobs, the build and then the tests with `--after N`: the build's memory is freed while the tests run, the second job keeps the first's place in line, and one message reports both. Make the second job run what the first built rather than build it again (the test binaries, or an archive of them), since a rebuild there runs on a smaller claim. Give the command as separate words, the way a shell would split it, and run a pipeline through `sh -c '…'`. Only commands that compile nothing run directly: git, formatters, searches, reading files and logs.
- **Tell loom what got in your way.** When loom's own tooling (`loom session`, `loom job`, the daemon, this context's text) fails, surprises you, contradicts what this context says, or lacks something you needed, file a note: `loom feedback add --kind bug|friction|missing|docs --title "…" --text "…"`, saying what happened, what you expected and the command. Report on the loom you run, not on loom code you are editing, and not your task's own problems. `loom feedback list` and `loom feedback show` are yours to read before filing, to add what is new rather than repeat a note; `fix` and `close` are the user's. Then carry on: one line to the user is enough.
