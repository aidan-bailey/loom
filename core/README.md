# core

The session model (`core/`): everything that acts on sessions without a terminal. `core.Model` serves every registered workspace to any number of clients. In production it runs in the daemon (`loom serve`, [`internal/daemon/`](../internal/daemon/README.md)) on a `core.Loop`, served over a unix socket by [`core/rpc/`](rpc/README.md); the TUI holds an `rpc.Client` as its `core.Core`. `core` imports nothing of the TUI.

## Workspaces and boot

`Model.workspaces` holds every served workspace, each loaded once and never dropped. Tests reach a workspace's instances through `AddForTest`/`RemoveForTest`/`InstancesForTest`.

`Model.Boot` runs once, in the daemon (`daemon.Serve`), after it takes the lock and before the loop starts; it is not in `Core`. It runs `InitAccounts`, detects the default account's remote-control auth when the global config enables remote control or an extra account exists (following the global config's setting, not the startup workspace's), and runs `boot`: it loads the global workspace (`globalWS`) and every registered one (`ensureLoaded`), one per config dir. `wsByConfigDir` compares canonical paths (`canonicalDir`, through `session.CanonicalPath`), so a renamed registry entry, the startup context, or a second entry reaching the same directory through a symlink is the same workspace, served once under the name it was first served by: serving one directory twice would let a stale copy's save overwrite the other's. Then one orphan sweep runs over them all (`sweepOrphans`). Boot returns its notices, which the server keeps for the first client. A workspace registered later is served from its `Register`, or from the `ReloadRegistry` that finds it (every TUI's `startHome` runs one); one unregistered stays served until the daemon restarts.

`loadWS` is the one load path: `applySessionConfig`, `LoadAndReconcile`, the crash-restart of every session the reconcile found dead with its worktree intact (`crashRestart`), except the workspace terminal's, which waits for the workspace's first open, then `reconcileOrphans`. Loading every workspace leans on the ownership checks in [`../session/README.md`](../session/README.md) (`SessionHome`, `startedElsewhere`, `HeldElsewhere`): tmux names are per server, not per workspace. `Instance.Kill` (and so a discard, which kills a `Recoverable` entry) and `Instance.Resume` ask `HeldElsewhere` of the session under the record's name (`Instance.sessionHeldElsewhere`, `session/reconcile.go`; `core/held_name_test.go`).

**Session flags per config dir.** The loom-context and subagent-tracking launch toggles live in `session` keyed by config dir (`dirFlags`); `syncSessionFlags` sets a workspace's at its load and on `SaveSettings`, and a launch reads its own instance's.

## Opening a workspace

A client showing a workspace, as a tab or as the workspace it shows while none is open, calls `Open(id)` (`open`). The first open since the model started sets `opened`, which gates the workspace's terminal and its GitHub polling, and expedites the GitHub poll. Which workspaces a client shows is the client's own state: an open publishes nothing tab-like, and nothing in the model closes a tab.

`ensureTerminal` creates the workspace terminal, killing a leftover session under its title only when the sweep's ownership test proves it this workspace's (`session.KillOwnedTmuxSession`). For one that died while nobody had the workspace open (`CrashRecovered`) or is Paused (its restart breaker stopped it, or reconcile found its name held), it asks `session.HeldElsewhere` and hands the answer to `settleTerminal`:
- held: the other session is left running and the terminal stays, or is marked, Paused;
- free: it relaunches the terminal (`crashRestart`, or `ResetRestartFailures` then `Restart`);
- unanswered: nothing changes or is saved, the workspace is marked `terminalUnsettled`, and the health tick asks again off the model's goroutine (`maybeSettleTerminals`: one background job per workspace, one check in flight, asked again after every unanswered one, delivered as `terminalChecked`; an answer about a terminal killed meanwhile settles nothing, `TestSettleTerminals_…`) until tmux answers.

`ensureTerminal` saves the workspace after it creates, relaunches or pauses the terminal (`saveTerminal`), so a crash before the next save can't leave a live terminal with no record, which the next first open would kill and recreate, losing its conversation. Until the first open the terminal is dormant: `activeInstances` leaves it out, so the tick neither probes, relaunches nor pauses it.

## Failed loads

`loadWS` leaves a workspace whose load failed served, empty, with its storage's write latch engaged, and records `loadErr` (published as `WorkspaceView.LoadErr`; the boot only logs it, `workspace.load_failed`). The TUI goes by its own failed opens (`failedOpen`), not `LoadErr`, so a failed workspace not in the open list shows nowhere until something opens it. `sweepOrphans` leaves its roots out of the owned set, its titles being unknown, and still sweeps every other workspace. Every `Open` retries it (`retryLoad`, which rebuilds its state, config and storage from disk, since a storage keeps the payload it was built over) and returns the error while it still fails.

The TUI's side (`Workspace.loadErr` reaches it only as `LoadErr`): a classic startup on a failed workspace exits with the error. A saved tab that fails to open at startup (`restoreSavedWorkspaces`) stays in the open list the TUI persists (`home.failedOpen`, appended by `openList`) and shows checked in the picker, labelled "(failed to load)", so later launches retry it, until it opens (`openTab`) or the user deselects it (`applyWorkspaceToggle`); global mode (`enterGlobalMode`, or `stayInGlobalMode` for a Global commit made from global mode) closes them all. When every restored tab fails, the classic slot opens the startup workspace instead; if that fails too, the error is shown rather than exiting, the latch refuses every save (the daemon's stop skips it: `core.Model.SaveForQuit`, `quitSkipsSave`), and `handleQuit` keeps the failed tabs in the open list. Those skips are lossless because new sessions are refused while the focused storage `WritesRefused()` (`latchedStorageErr`), so a latched list stays empty.

## Requests, replies and causes

Every lifecycle action is a request, by ID where it names an instance, with an optional `ReqID` (`core/requests.go`): `Kill`, `Pause`, `Resume`, `ResumeWith` (the `R` flow: the new launch options applied, then a resume), `Recover`, `Merge`, `Push`, `SendPrompt`, `Create(ws, NewInstance, req)` (builds and adds an instance and, with `Start`, configures and starts it) and `FetchIssue`. A non-zero `ReqID` is answered by a `Reply` (`Req`, `ID`, `Err`, `Notice`, `Issue`): at once for a refusal or a `Create`, otherwise when the request's job lands (`track`, `deliverTracked`).

Each request that names an instance first runs `admit` (`Create`, which names a workspace, refuses one no longer served instead): a served workspace must hold the ID (else `ErrNoSession`), and the instance must pass `precondition`, which mirrors the keys' gates in `app/intents.go` (a gate that needs a pane, such as the send's liveness check, stays in the TUI) (no kill, pause or push of a workspace terminal or a busy session, no resume of one not Paused, …). A refusal's error matches `core.ErrRefused` (`ErrNoSession` does too); with `ReqID` 0 it is only logged (`request.refused`). A failed job is not a refusal: the model has already shown it as a `Notice`, and the Reply's `Err` carries it too.

The pane triggers name instances by ID as well (`SetSelected`, `PaneOutput`, `PaneQuiet`, `VerifyDead`); `MarkOutput` takes the session name.

**The request is ambient** (`Model.cause`). While the model applies a request's job result (a `caused` result, which `Deliver` unwraps through `causedBy`, or a tracked one), the `Started`, `Recovered` and `Notice` events it emits carry the request in `Req` (`emit` stamps them), and the jobs it spawns meanwhile serve the request too (`spawn` wraps their results as `caused`). So a chain's last event (`Create`, then the start, then the initial prompt's send, then `Started`) still names it. The model's own jobs (the tick's probe, gated jobs, dead checks) go through `spawnBackground` and never inherit it. The loop takes the two kinds apart (`takeJobsSplit`) and counts the foreground ones until they land: `Loop.Quiesce`, the daemon's stop, fires no more ticks, waits for those (the daemon allows `Options.QuiesceTimeout`) and leaves the background ones to be dropped at `Stop`, so a pause or kill is never cut off mid-step.

**The selection is a set** (`Model.selected`): `SetSelection` names every client's selected row at once (`SetSelected` names one), and the tick's probe refreshes the full diff of each (`selectedInstances`).

## Completions

Completions (`core/completions.go`) act on the `*session.Instance` they carry: a failed start (a `StartResult` with an error) removes its instance from its owner's workspace and kills that instance (`killUnstarted`), a `KillResult` removes its instance from every served workspace (`removeEverywhere`), and an `OpFailed` reverts the instance it carries (and emits `Reactivated`). Results that need a workspace carry the owner stamped at dispatch on the model's goroutine: `core.StartResult.Owner` and `ResumeResult.Owner` (from `startOwner`, the served workspace holding the instance; the workspace the caller passes is only the fallback) and `RecoverResult.Owner` (the workspace holding the placeholder, found by the `Recover` request's lookup). `deliverStart`, `deliverResume` and `deliverRecover` resolve the owner (`owningWorkspace`), act on its instances and storage (`saveWS`; the owner is always served, since the model never drops a workspace), and report through events (`Started`, `Recovered`, `SessionLaunched`, …) stamped with their cause. A pause saves inside its job, so `PauseResult` only asks for a prune. A job that needs the owner's storage captures it when the model builds it (`killInst`, `pauseInst`, `saveSnapshot` in `core/ops.go`). An N flow's initial prompt is sent by a job after the start lands (`sendInitialPrompt`), and `Started` is emitted only once that send returns (`deliverPromptSent`), so a client's inline attach, which forwards keys to the agent, begins only after the prompt is in.

The model has no focus. Where an operation needs a workspace the user chose (`Create`'s, also the start's fallback owner) the caller passes it, an ID request finds its workspace by lookup, and whatever depends on focus or `m.state` (the selection, inline attach, the "started in X" wording, the `stateDefault` guard) stays in the TUI's event appliers.

## Instances and workspaces as values

Clients see an instance only as a `core.InstanceView` (`view.go`): everything the TUI renders or gates a key on (`Active()` is the active-instance rule; `WorktreeRepoPath` is what Lua's worktree handle is built on) and nothing that acts. It names its instance by a `core.InstanceID`, which `idOf` derives from the record (its workspace's canonical config dir, its title and `created_at`), so every daemon over one disk agrees; 0 is never assigned (the TUI's draft row uses it). `Views(id)`/`View(id)` (`views.go`) build views of served workspaces only.

A workspace crosses as a `core.WorkspaceID` (`wsIDOf`, a hash of its canonical config dir, so every daemon over one disk agrees and a tab closed and reopened shows the same one) and a `core.WorkspaceView` (`workspace_view.go`; `LoadErr` is the text of a failed load, "" once it loaded), answered by `Workspaces()` (every served workspace, in serve order) and `Workspace(id)`. The workspace requests take and return IDs and views (`workspace_requests.go`: `Workspaces`, `Open`, `Views`, `Create`, `IsLoaded`, `Registry`, `ReloadRegistry`). `Started`/`Recovered` name their owner by ID with its label.

`SaveSettings` (`settings.go`) replaces a workspace's settings, writes its `config.json` and applies the change at once: that workspace's launch toggles in `session`, and, for the global workspace only, the program the accounts' Claude commands run with (`Options.Program`, the global config's in the daemon, then the global workspace's last saved default program). The program a client's drafts default to is the client's own (`home.program` in the TUI). `SetUIPrefs` and `SetHelpScreensSeen` write its `state.json`.

`Registry()` is a `RegistryView` copy (the registered workspaces, the open list, `LastUsed`). `ReloadRegistry` rereads the registry and serves any workspace registered since. The registry's writes are `Register` (which returns the new workspace's view, for the client to `Open`), `SetLastUsed` and `PersistOpenList` (the open list a client hands it, its tabs then the ones it failed to open: the model only writes it, and never acts on it). `AccountNames()` is all the TUI sees of the account registry. Every query hands out copies (`GitHubSnapshot`, `AccountUsage`, `AccountSync`, the views; `core/copies_test.go`).

## Publishing state

`Sync` (`syncEvents`) publishes by diffing, in a fixed order and ahead of every other event: one `WorkspacesChanged` carrying every served workspace's view whenever any changed (`publishWorkspaces`, `workspace_views.go`), then `publishState`'s events (`state_publish.go`), then a `ViewsChanged` for each served workspace whose views changed since the last publish, carrying deep copies (`cloneViews`). It also forgets the IDs of instances no served workspace holds.

`publishState` emits three events, each carrying a state view of `state_views.go` (the fourth, `WorkspacesView`, is the workspace views):
- `ModelChanged` (`ModelView`: the default account's remote-control auth and the registry);
- `AccountsChanged` (`AccountsView`: the names, the loaded and extra flags, the Claude program, the accounts, their auth, link reports and usage, the probes' errors, `CredentialOverride` and `RunningAsAccount`);
- `GitHubChanged` (`GitHubView`: the snapshots, the poll errors, the aliases and gh's availability).

The model and account views are diffed whole (`reflect.DeepEqual`). The views' `Clone` methods deep-copy their slices and keep every other field (a `ModelView.Clone` that rebuilt the `RegistryView` once lost `LastUsed`, so every replica's restore focused the first tab). The account view is also republished after every usage probe round (`usageGen`, bumped in `deliverUsage`), since the TUI renders a sample's age; the GitHub view, whose snapshots can be large, is republished whenever a poll lands (`ghGen`, bumped in `deliverGH`, the one place its state changes). Nothing emits `AccountsChanged` or `GitHubChanged` by hand.

`Model.Snapshot` is the whole published state as events, in `Sync`'s order, and leaves the diff baseline alone. `Loop.SyncAndSnapshot` (not in `Core`) runs a `Sync` and a `Snapshot` in one loop call, so a client that connects starts from exactly the state the next `Sync` diffs against.

The state views' methods replicate the logic of the model's own queries, which stay as they are because several run on every tick. Parity is tested twice: `TestStateViews_AnswerAsTheModel` and `TestWorkspacesView_AnswersAsTheModel` (`core/state_views_test.go`) compare view and model directly, and `TestReplica_AnswersAsTheModel` (`core/rpc`) compares the client with the loop over the wire, misses included.

## Core, the loop and jobs

`core.Core` (`iface.go`) lists every method the TUI calls, and `home.core` has that type. `*Loop` implements it in process (`loop.go`, with every forwarder in `loop_core.go`, each checked by `TestLoopForwardsEachMethodToItsNamesake`); `*rpc.Client` implements it over a connection. `iface.go` is also the wire's source: the wire code is generated from it, and its parameter names are the wire's field names (`auth`, `settings`, `prefs`, `program`, `number`, `workspace`). A method's line comment says how a client serves it: `// rpc:local` is answered from the client's replica; `// rpc:cast` is sent one way, with no reply, and the server publishes nothing after one; `// rpc:client` (`Sync`) never leaves the client; every other method is a request, whose reply follows the events it produced. `CredentialOverride` and `RunningAsAccount` are local; `WatchGitHub` is a cast. Not in `Core`: `Boot`, `InitAccounts`, `SetRCAuth`, `Begin`, `SyncAndSnapshot`, `SetSelection`. `SaveForQuit` is still in `Core`, though only the daemon calls it.

`Core` is value-typed: `TestCoreIsValueTyped` (`core/value_boundary_test.go`) walks every method and every `Event` (`EventTypes()`, the production list the wire names and decodes events by, kept complete by `TestAllEventsListsEveryEvent`) by reflection and fails on anything but plain data (no func or chan, no interface but `error` and `Event`, no `sync` type, none of the model's own objects).

`Model` is single-goroutine, and its `Loop` runs it: the loop serves each call as a round trip, starts the jobs the model queued (`takeJobs`, after every step) on goroutines of their own, delivers their results on the loop (`core.Model.Deliver`), fires the health tick from its own timer (`tickInterval`, armed by `Loop.Begin`, which whatever serves the loop calls once: `daemon.Serve`, or `rpc.InProcess` in tests; re-armed only when the probe's `HealthResult` lands, so probes never overlap), and signals `Loop.Wakes` after anything it did unprompted. A panic on the loop's goroutine or in a job is a `core.LoopPanic`; the loop keeps the `LoopPanic`, and every later call re-raises it (the model's state is unknown after one). `Quiesce` readies a stop, and `Stop` ends the loop: later results are dropped and later calls run nothing.

Blocking work is a `core.Job` (`func() any`) that reads no model state; `Deliver` routes its result by type. Every job goes to the outbox, which the loop empties after every step; the `Event`s wait there until the server's `Sync` publishes them, after every request and on every wake.

## The health tick and gated jobs

`core.Model.Tick` (`tick.go`) fires from the loop's timer, favouring every client's selected row, and queues one probe job over every active instance of every served workspace, an unopened workspace's dormant terminal excepted (tmux liveness, parity, diff stats: `probeJob`). `deliverHealth` applies its `HealthResult`: `applyLiveness` pauses the dead (`pauseGone`, saved through `saveUnprompted`) and relaunches a dead workspace terminal under its circuit breaker (`maxWorkspaceTerminalRestartFailures`); Claude's reported status is adopted; an instance a kill, pause or resume moved to Deleting or Loading while the probe ran fails `statusEligible` and is skipped entirely. `MarkOutput` fills the dirty set the next probe takes (`takeDirty`) to gate diff refreshes, and `core.HealthChecked` is emitted when the probe's result lands.

The tick also dispatches the gated jobs that are due (roster, hook scan, GitHub poll, usage probe, the Claude temp-dir sweeps workspace loads queued) and stats `accounts.json` for a change (`maybeReloadAccounts`). Every throttled background job goes through a `pollGate` (`gate.go`; intervals in `gateIntervals`, keyed by kind, so even a zero-value `core.Model` is throttled): `dispatchGated` arms the gate only when its builder returns a `core.Job`, and wraps the result in a `gatedResult` that `Deliver` disarms (`deliverGated`) before routing the inner result to its handler. A `request()` made while a dispatch is in flight dispatches the job once more after that flight lands (`redispatch`). Adding one: [`../docs/claude/adding-a-gated-job.md`](../docs/claude/adding-a-gated-job.md).

## Claude status and the roster

`session/claude_roster.go` shells out to `claude agents --json`. `rosterQueryJob` (`claude_status.go`) runs it off the model's goroutine on its own cadence: `maybeRosterQuery` throttles by `rosterInterval` and guards against overlap through `gateRoster` (`core/claude_status.go`), because the snapshot path's faster tick would otherwise keep a `claude` process alive much of the time, and stack concurrent ones if the CLI hung. The roster covers ordinary interactive sessions, not just `claude --bg` ones, keyed by cwd. The model's `roster` field holds the result; `rosterStatusFor` joins on `Instance.GetWorktreePath()` and maps `busy`→`Running`, `waiting`→`Prompting`, `idle`→`Ready`. The roster is per config dir (`claude agents --json` under an empty dir returns `[]`), so `rosterQueryJob` runs one query per account in use (`session.QueryClaudeRosterEnv`) and `rosterStatusFor` joins `rosterByAccount[inst.Account()]` (the default account's stays in `roster`); one account's failed query clears only its own entries.

A roster answer is offered to each active Claude instance as it lands (`observeRoster`), stamped with the query's start time (`rosterResult.at`), and merges with hook observations, the newest observation winning (`session/claude_state.go`). Only the model writes a reported status: `deliverHealth` and `applyClaudeStatus` (hook scans, roster answers) both go through `adoptClaudeStatus`, which applies the status and records `Instance.WaitReason`. The TUI's status paths (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path) write no status: they read the row's `StatusReported` before their content ladder and leave a reported row to the model; an authoritative answer also suppresses `maybeRedetect`.

`rosterStatusFor` fails closed, like `DetectClaudeRemoteControlAuth`: non-Claude agents, an empty or failed query, no entry for the worktree, an ambiguous cwd (dropped in `QueryClaudeRoster`, logged as `session.roster.ambiguous_cwd`), a cwd holding only background sessions, and unrecognized status strings all return `false` from `rosterStatusFor` (no opinion), and the scraper ladder decides. A failed query clears the roster and turns every roster-sourced observation into no opinion (`claudeState.rosterSilent`); a hook-sourced one stands. `RosterEntry.WaitingFor` (Claude's own reason for blocking: `"sandbox request"`, `"dialog open"`, `"input needed"`, `"goal proposal"`, …) rides through `adoptClaudeStatus` onto the transient `Instance.waitReason` and replaces the generic phrase in `CardData.statusLabel`, verbatim and truncated; any non-Prompting or non-authoritative outcome clears it. It is never serialized. Tests: `session/claude_roster_test.go`, `core/claude_status_test.go`, `core/gate_test.go`, `app/roster_status_test.go`, `ui/card_test.go`.

**Hook scans.** `maybeHookScan` (`core/hook_scan.go`, `gateHookScan`) runs on the health tick, on pane output (`core.Model.PaneOutput`) and, through `pollGate.request()`, on pane quiet (`PaneQuiet`) when `Stop` and `PermissionRequest` arrive. A scan that changes a status applies it at once (`applyClaudeStatus`) and requests a roster query to confirm it. Answering a prompt fires no hook, so output on a Prompting session queries the roster (`maybeRosterQuerySoon`, at most every `promptingRosterSpacing`). A scan naming the conversation a relaunch resumes is saved (`deliverHookScan`, through `saveUnprompted`).

## The GitHub poller

`maybeGHQuery` (`core/github.go`) rides the health tick on its own `ghInterval` cadence through `gateGH`; the `ghAvailable` backoff is a pre-check ahead of `dispatchGated`, and no opened repo means no dispatch. It polls only the repositories of opened workspaces (`openedRepos`: every workspace a client has opened since the model started), each with its own workspace's base branch. An opened workspace with no repository (the global one) stands for the repositories its sessions run in (`Instance.Path`), against its own base branch, and with no session it polls nothing. Last come the repositories a client asked for (`Core.WatchGitHub`, a cast: the issue picker asks on every open and on every `GitHubChanged` while it stays open, and an `N` prompt's `#n` expansion asks for its draft's repository), against the global workspace's base branch, each polled for `ghWatchTTL` after the last ask (`ghWatched`; an expired one is dropped at the next ask). An ask the poll has answered already renews the watch without polling at once. Workspaces with a repository of their own come first, deduplicated canonically (`canonicalDir`), so a global session in a registered repository is polled against that workspace's base branch.

`ghPollJob` groups the paths by their checkout's top level (`git.RepoRoot`, `git rev-parse --show-toplevel`, canonical; a path git can't place stands for itself), so a repository reached through a symlink or a subdirectory is polled once, against the first path's base branch, for the issues every path links. Its results (`ghState`, `ghErrs`, `ghBases`) are keyed by that top level, and each path inside another's is recorded as an alias (`ghAliases`, published as `GitHubView.Aliases`); every lookup goes through `ghRepoKey` (the instance join, parity's base, `GitHubSnapshot`/`GitHubErr` on the model and the replica). Each poll resolves and fetches the base ref per repo (`git.FetchRef`, even without `gh`) and, when `gh` is available, runs `github.Query`. `ghState` is replaced wholesale, so an errored repo is dropped: its cards render `Known=false` (nothing), and `Known=true, HasPR=false` is a real "no PR". Results join onto `Instance.SetGitHubState` (transient; `viewOf` copies it into `InstanceView.GitHub` through `GitHubState()`, and `ui.BuildCardData` reads the view's). Ahead/behind (`Instance.UpdateParity`, one local `rev-list`) rides `probeJob`, keyed on `ghBases`.

`core.Model.ExpediteGitHub()` makes the next tick poll at once (an in-flight poll still lands first). A successful push (`core.Model.Push`, applied by `deliverPush`), an issue-born session (`handleIssuePicked`; `handleIssueExpanded` asks `WatchGitHub`, which expedites too), the issue picker opening on a repo with no snapshot or error yet, and a workspace's first open (`Core.Open`) all expedite. The TUI reads the poll through `GitHubSnapshot`/`GitHubErr`/`GitHubUnavailable`, answered from its replica, and `core.GitHubChanged` refreshes an open issue picker. GitHub state never sets `NeedsAttention`.

`ghAvailable.ok` latches true: `req.check` is `!checked || !ok`, so once `CheckCLI` succeeds it never re-runs, and gh breaking mid-session surfaces only as per-repo errors. An unavailable result is re-probed every `ghRecheckInterval`, so `gh auth login` after the daemon started recovers without a restart. `ghPollRequest.configured` is a `map[string]string` keyed by repo path, built by `baseBranchByRepo()` from each opened workspace's own `config.json`, since each workspace has its own `BaseBranch` (the TUI's `m.settings()` is only the focused slot's). `ghPollBudget` bounds the whole poll, under `ghInterval`: `github.Query` budgets each `gh` subprocess separately (two list calls plus one `issue view` per linked closed issue), and one repo with many linked closed issues would otherwise stall every other workspace's refresh. `UpdateParity` runs in `probeJob` before the `wantFull`/`ShouldRefreshDiff` early return, which skips git for an idle session (`tmuxUpdated` false), because the base branch moves with no session activity at all.

Both issue fetches are `core.Model.FetchIssue` requests (a `github.View` job) whose `Reply` carries the issue. On the TUI's side (`app/state_issue_picker.go`) the picker's pick and the `N` prompt's `#n` expansion record a `pendingIssue` holding an `issuePickedMsg` or `issueExpandedMsg`, which `handleReply` fills and hands to `handleIssuePicked`/`handleIssueExpanded`. They can land long after the user acted; both drop the result, with an explanation, when `msg.repo != m.repoPath()` or `m.state != stateDefault`, because `openLaunchOptionsForNew` would otherwise replace another flow's pending launch options. `handleIssueExpanded` also drops a result whose draft is no longer `m.draft`, and discards the draft whenever a guard fires (`issueExpandDropped`); it degrades on a fetch error, so its guards run before its `err != nil` branch.

## Accounts and usage

The account registry, auth, sync, usage and reload logic live in `core/accounts.go` and `core/usage.go`; the views are the TUI's, refreshed on `core.AccountsChanged`. `maybeReloadAccounts` rides the health tick and only stats `accounts.json`, reloading (`core.Model.ReloadAccounts`) when its size or mtime moved; every user-paced action that reads the registry (opening Launch Options, opening Settings, an Accounts-screen request) calls `ReloadAccounts` first. `accountsChanged` compares a signature (the default, every `name=dir`, and the load error) against what was last seen (`noteAccountsState`, also called after the model's own writes), so a no-op reload touches no view and a load error is reported once. Auth is re-read (`RequestAccountsRefresh`, `gateAccountsRefresh`, `accountsRefreshJob`) when a reload finds an account with no auth entry, while the default account's identity is unknown and an extra account exists, or when a usage probe finds an account that had plan access losing it (`lostAccess`; an expired login probes like API-key auth, `Usage.Available=false`, until `claude auth status` re-runs). The refresh re-syncs an existing account only through `syncMainDir`'s guard. `publishAccounts` hands the registry's dirs to `session.SetAccountDirs`, which every launch resolves an account name through. The default account's remote-control auth (`RCAuth`) is detected by `Boot` and refreshed by the accounts refresh; it is per account (`core.Model.RCAuthFor`; an extra account not read yet is Unknown). Usage probes (`account.ProbeUsage`, a headless `claude -p` answering the SDK's experimental usage request; `TestRealClaude_UsageProbe`, opt-in, pins its shape) run on `gateUsage`, expedited when a picker opens; usage is display-only, so a failed probe keeps the last sample. `accountUsers` counts each loaded workspace's live instances and reads `state.json` only for config dirs no loaded workspace covers. The model's own environment decides `CredentialOverride` and `RunningAsAccount` (`noteRunningAsAccount`).

## Orphans and Claude temp dirs

`reconcileOrphans` (`core/load.go`, called from `loadWS`) auto-cleans stale worktrees and surfaces unsaved or live ones as `Recoverable` entries. `Recoverable` is ephemeral: filtered out of `core.Persistable`, re-derived from disk each load, and inert (`EnsureRunning` no-ops on it). `r` recovers (`core.Model.Recover`: adopt via `ReconcileAndRestore`); `D` discards (worktree removed, branch kept, `IsExistingBranch`). `reconcileOrphans` also queues a Claude temp-dir sweep (`requestClaudeTmpSweep`, snapshotting the claim set then; a workspace whose storage failed to load queues none), which the tick (`Model.Tick`) dispatches on `gateClaudeTmp`, one in flight (`core/claude_tmp.go`). A Pause and a Resume of the same worktree refuse each other (`core.Model.Resume` takes only a Paused instance; a Lua `inst:pause()`/`inst:resume()` is the same request), as do two of the same, keyed by the canonical worktree path in `opsInFlight`.

## Wire errors

On the wire an error is a `core.WireError{Code, Message}` (`wire_error.go`), which keeps the sentinels clients test with `errors.Is`. Codes: `not_found` (`ErrNoSession`, whose `Is` also matches `ErrRefused`), `unavailable` (`ErrUnavailable`: the daemon is stopping, or the client has lost it; also a refusal, and never the model's own answer: the stopping server and the client produce it, and the TUI fails its stranded requests with it; an older peer sees only the message), `refused` (`ErrRefused`), `storage` (`session.ErrStorageLoadFailed`), `error` (anything else: only its message survives), `panic`, `protocol`, `mismatch` and `unsupported` (`CodeUnsupported`: a method the server does not know, an ordinary error so a newer client can probe an older server). `ToWire` encodes: a `WireError` passes unchanged, an error wrapping one keeps the inner code with the whole wrapped message, and any other takes the code of the first sentinel it matches. `FromWire(nil)` is a nil interface, never a typed nil. `Notice`, `Reply` (`events_json.go`) and `git.DiffStats` (`session/git/diff.go`) encode their error fields this way; `DiffStatsData`, the persisted form, does not.

## Saving

The daemon saves on requests, after the changes the model makes on its own (`saveUnprompted`: the tick pausing an agent whose session is gone, `pauseGone` from `applyLiveness`; a hook scan naming a conversation, `deliverHookScan`), and at its stop (`SaveForQuit`, which saves every served workspace: a failed save of a workspace opened in this run is returned for the daemon to log, the write latch excepted, `quitSkipsSave`; an unopened one's failure is only logged, `quit.save_failed_unopened`; one whose config dir is gone is skipped rather than recreated).

## Boundaries

`TestCoreImportsNoUI` (`core/boundary_test.go`) walks the import graph and fails on `app`, `ui/...`, `script`, `keys` or a `charm.land` package reached from `core`, directly or through another loom package. `seams.go` and `model.go` hold the test-only exports, and `TestNoProductionCallsOfTestSeams` (`internal/testenv/seams_enforce_test.go`) fails on any production use of one, a call or a reference taken as a value. `core/doc.go` holds the package comment.

## Tests

Core's own tests drive a `Model` directly, on their goroutine, with `Sync` (events and jobs), `Drain` (which publishes no views) and `Deliver`.
- `NewForTest` builds a model with no workspace and no side effects; `SetWorkspacesForTest(wss...)` installs workspaces, each served and opened, in serve order (the model has not booted, and a `Boot` loads the global and registered workspaces beside them).
- `core/boot_test.go`'s `workspaceDef` and `bootModel` build a model over registered workspaces laid out on disk (its own global dir, a tmux executor on which every session is dead), which the test then boots; `openDef` opens one. `startForeignSession` starts a session holding a title from another directory, standing in for another workspace's or another loom's.
- `CausedForTest` delivers a result as a request's job would. Other result types come from `seams.go`'s `…ForTest` constructors.
- `core/testhelpers_test.go` holds the fixtures: `storedWorkspace` (a workspace over a fresh config dir and storage), `newInst`, `newTerminal`, `pausedInst`, `startedInst`, `gitRepo`, `pausedWorktreeInst`, and `isolateTmux(t)` (a fresh private tmux server per test, killed when it ends).
- `core/testmain_test.go` isolates tmux and `~/.loom` for the binary.
- The loop's seams: `StartForTest` (a loop that holds every job for `JobsForTest` and never ticks on its own, `TickForTest`; idle between calls, so a test may reach its model through `ModelForTest`), `DeliverForTest`, `SelectedForTest`, `SetRCAuthForTest`.
