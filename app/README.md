# app

The Bubble Tea application layer: the view and key routing. Lifecycle goes through `core`, by request. `app` keeps everything that renders or reads a pane client, `m.state`, overlays, key dispatch, the Lua engine and script host, the workbench and review, the overview cursor, tab bar, menu and error bar, the split-ratio throttle, full-screen attach, the issue picker (its fetches are `core.Model.FetchIssue` requests), and the views of accounts and GitHub state. It holds none of the model's objects: no `*session.Instance`, workspace, registry, storage or state.

## How it runs

- `app.go` owns the `home` model and its `Update`/`View` (Model-View-Update). `home.Update` is a thin wrapper: it runs the message switch (`update`), then `drainCore` (`app/core_glue.go`), which empties the client with `core.Core.Sync`, then `publishSelection`, which tells the model the selected row (`SetSelected`) when it moved.
- Keys route in two stages: `handleKeyPress` dispatches by `m.state` to a per-state handler in `app/state_*.go`; in the default state, keys flow through the Lua engine via `app_scripts.go`'s `dispatchScript`, which consults `script.Engine.HasAction` and returns a Cmd that drains the resulting `scriptDoneMsg`. The keymap is `script/defaults.lua`; user scripts in `~/.loom/scripts/*.lua` rebind or add keys.
- The TUI holds the daemon's client as `home.core` (a `core.Core`, in production an `rpc.Client`), with its wakes (`home.wakes`) and its closer (`home.stopCore`, deferred in `Run`; the daemon serves on). `Run`'s `forwardWakes` goroutine turns each coalesced wake into a `coreWakeMsg`; it never blocks the client's reader or the model's loop, since `p.Send` waits for Update.
- `Sync` never leaves the client. It returns the state events for what changed since the last `Sync` (`WorkspacesChanged`, `ModelChanged`, `AccountsChanged`, `GitHubChanged`, then each changed workspace's `ViewsChanged`, coalesced to the newest), then the other events in arrival order; `applyCoreEvent` applies each.
- `app/core_glue.go` is the seam: `coreWakeMsg`/`forwardWakes` carry the wakes, `drainCore`/`applyCoreEvent` apply events, `publishSelection` tells the model the selection, `newSlotView` builds a slot over a workspace's view, and `slotFor` finds the slot showing a `WorkspaceID`.
- When the client loses the model (the daemon stopped, crashed or was replaced), `Update` quits at once (`home.coreLost`, `home.exitErr`) and `Run` returns `ErrDaemonGone`, which `main.go` reports once the terminal is restored. Saves are the daemon's: `handleQuit` flushes the split ratios and persists the open list, and saves no session.
- The model keeps ticking and applying results while the TUI's event loop is blocked (a full-screen attach, `$EDITOR`, `claude auth login`); its events wait, coalesced into one wake.
- The TUI reaches tmux by session name, never through an instance, on the daemon's tmux server (pinned by `main.go` before `Run`): the full-screen attach builds `tmux.NewSessionNamed(name, program)`, and the liveness guards call `m.sessionAlive(name)` (a has-session probe; tests set its `aliveProbe` seam). Its own environment still decides what it starts itself: the terminal pane's shells (their `update-environment` variables), a relative or `~` `ctx:new_instance{path=…}`, which it makes absolute (`scriptPath`) before the `Create`, and a login from the Accounts screen.

## The model boundary

- The TUI talks to the model through `core/rpc/`'s client. Every `rpc:local` query in `core/iface.go` reads the client's replica; requests cross the wire and their events arrive before their reply, which is why the read-back sites (`syncViews`, `syncWorkspaces`, the drains right after a transition, the nested drain in `newLaunchOptionsOverlay`) see a request's effect with no extra round trip. A cast gives no such guarantee. `m.core` locks its own replica, so calling it from a Cmd body would not race, but it would read state no drain has applied.
- `TestTUIHoldsNoModelObject` (`internal/testenv/instance_enforce_test.go`) fails on any production use in `app/`, `ui/` or `script/` of `session.Instance`, its constructors or options, `session.Storage`, the launch toggles' setters, `core.Workspace`, `core.Model`, `core.New`, `core.Loop`, `core.Start` or `core.Job`, `config.WorkspaceRegistry`/`LoadWorkspaceRegistry`, `config.AppState`/`State`/`LoadStateFrom` or `config.SaveConfigTo`, or `account.Registry`, under whatever name the file imports the package, and on the deleted bridges (`InstanceOf`, `IDFor`, `AdoptForScript`, `instOf`) anywhere.
- Registry writes go through the model on Update: the startup registration prompt's Cmd returns `registerWorkspaceMsg`, and Update calls `Register`.

## Workspaces and slots

- A workspace the TUI shows (a tab, or its classic workspace while no tab is open) is a slot (`workspaceSlot`, `app/workspaces.go`): `{id, info, views, list, splitPane, workbench}`, a view of a workspace the model serves, named by `core.WorkspaceID`. `home` embeds `*workspaceSlot`, the focused slot, so `m.id`, `m.info`, `m.list`, `m.splitPane`, `m.workbench` and the accessors (`name()`, `label()`, `settings()`, `uiPrefs()`, `recovery()`, `m.repoPath()`, `m.configDir()`) resolve to that slot's own. `m.slots` (a `[]*workspaceSlot`) holds the tabs in order, so every open slot's state is always current, with no save step and no `i == m.focusedSlot` branch to pick the live copy; `openSlots()` yields them, or the classic slot alone, for fleet-wide walks.
- Which workspaces the TUI shows is its own state, not the model's: `m.slots`, the classic slot, `home.startupName` (the workspace the classic slot shows at startup: "" for the global one, a registered name for `loom <dir>` or `--workspace`), `home.failedOpen` (saved tabs that failed to open, kept in the open list) and `home.program` (the agent program drafts default to, from `-p`, else the startup workspace's config).
- Invariant (`checkSlotInvariant`, asserted in tests): every slot shows a workspace the model serves (`IsLoaded(slot.id)`); no slot appears twice and no two tabs show one workspace; with tabs open, `m.workspaceSlot == m.slots[m.focusedSlot]`; with none it is the classic slot (not in `m.slots`), showing the startup workspace or, once `enterGlobalMode` ran, the global one; never nil, and every slot has a `splitPane` and `workbench`. Only a bare test home shows no workspace (`m.id == 0`).
- Transitions (`app/workspaces.go`, `app/app_init.go`), each showing a workspace through `Core.Open` and draining right after: startup and the saved-tab restore (`startHome`, `restoreSavedWorkspaces`); opening a tab (`openTab`, `activateWorkspace`); closing one (`deactivateWorkspace`, which refuses the last tab); global mode (`enterGlobalMode`, which opens the global workspace before dropping anything; `stayInGlobalMode` for a Global commit made from global mode, which rebuilds nothing); the picker's commit (`applyWorkspaceToggle`, which keeps the open tabs when every desired workspace fails); registration (`registerWorkspaceMsg`: `Register`, then `openTab`, or global mode when the directory is the global workspace's). `openList` is the tabs in order, then `failedOpen`; `persistOpenList` writes it through `Core.PersistOpenList`.
- `servedID` finds a served workspace by name in `Core.Workspaces`, after a `ReloadRegistry` for one registered since. It refuses a name whose directory the model serves under another (`servedFor`, comparing directories as the model does, `sameDir`): a twin, the other name still registered ("X is the same directory as Y, which loom serves: open Y"), or a rename made while the daemon runs ("stop the daemon (`loom serve stop`), then start loom, to open it as X"). Startup and the restore open the served twin in its place instead, with a one-time note shown with the recovery summary (`twinOf`, `twinNote`, `addNote`, `showStartupInfo`).
- A workspace registered at `$HOME` shares the global config dir, so the model serves it as the global workspace: startup on it shows global ("home shares its config dir with the global workspace; showing global"), a saved tab of it opens nothing, with a note, the picker refuses it ("… which loom serves: pick Global"), and registering it (`loom ~`) shows global with the same note.
- A saved tab that fails to open at startup stays in `failedOpen` and shows checked in the picker, labelled "(failed to load)", so later launches retry it, until it opens or the user deselects it; global mode closes them all. When every restored tab fails, the classic slot opens the startup workspace; if that fails too, the error is shown instead of exiting, and new sessions are refused while the focused storage refuses writes (`latchedStorageErr`).
- Dropping a slot (closing a tab, the classic slot giving way to the first tab, `enterGlobalMode` dropping the tabs or a classic workspace slot) returns `prunePanes` and `releaseSlotCmd`, which detaches the attach clients its terminal pane holds on `loom_term_*` shells (`TerminalPane.DetachAll`; the pane `enterGlobalMode` carries into the global slot keeps only the clients of sessions the global list holds, `DetachExcept`), and the caller runs `instanceChanged`.
- Each slot caches its workspace's `core.WorkspaceView` (`slot.info`: name and paths, a `config.Settings` copy, UI prefs, help screens, storage flags, load error, recovery summary), replaced by each `WorkspacesChanged` and reread by `syncWorkspaces` after the TUI's own write. UI prefs (`mutateUIPrefs`) and help screens are `SetUIPrefs`/`SetHelpScreensSeen` requests; the view mode persists per workspace in `state.json`'s `ui` block.
- The settings overlay edits a `config.Config` of the TUI's own (`m.settingsEdit`, built by `config.FromSettings`), each change sent back whole as `SaveSettings`; a saved default program becomes `home.program`. A theme or default program another TUI saved for the focused workspace applies when its `WorkspacesChanged` arrives (`applySettingsChange`, `app/state_settings.go`: the theme painted, `home.program` replaced), and only when it changed.

## Views, rows and drafts

- Each slot keeps its workspace's `core.InstanceView`s as its view store (`workspaceSlot.views`, `app/views.go`): seeded from `core.Core.Views` (the client's replica) when the slot is built (`seedViews`), replaced wholesale by each `ViewsChanged`, and reread by `syncViews` where an Update reads back a change its own request just made.
- Every reader sees the store through `rowsOf` (the rail's `ui.InstanceSource` is `slotRows`), which copies each row, lays the TUI's own overlays over it (`overlay()`: the bells of `home.bells`, set by a pane's bell and cleared by focus, and the ladder's scraped status in `home.ladder`) and appends the creation flow's draft row.
- `findRow`/`viewByID`/`viewBySession` look a row up across every open slot, `activeViews` lists the active ones, `refreshSelection` repoints the split pane's and menu's copies (`SetInstance`) at the selected row on every store or overlay change (the focused slot's `ViewsChanged`, `setLadder`, `newDraft`/`discardDraft`, `createReplied`), and the `ViewsChanged` applier runs `pruneBells`/`pruneLadder`.
- Creation flows edit a `draft` (`app/drafts.go`, `m.draft`): it shows as a row with ID 0 at the end of its own slot's rail until `confirmDraft` sends `core.Model.Create`, and every cancel path calls `discardDraft` (`discardPendingLaunchOptionsCancel` included).

## Requests and completions

- `app/requests.go` is the request book: `newReq` records what a request with a `core.ReqID` waits on (`pendingCreate`, `pendingSend`, `pendingOp`, `pendingScript`, `pendingIssue`) and `handleReply` routes its `Reply`. Every lifecycle request the user starts carries one (`opReq`, a `pendingOp`), so that `refusal()` can show a refusal through `handleError`.
- A prompt send holds input to its instance until its Reply (`sendPrompt`, `holdInput`, `m.sending`); meanwhile `sendingTo` refuses inline attach and another send to it with an info line.
- `app/completions.go` keeps the view's half of the completions (`applyStarted`, `applyRecovered`). Every client attaches the session's pane; only the one whose request it was (`Started.Req`/`Recovered.Req` non-zero) selects the row, attaches inline or shows a notice. For its own start, an owner that is the focused slot gets the row selected and inline attach (or, with another flow on screen, "X started"); a background owner gets the row selected in its own rail and "X started in Y". `applyRecovered` selects the same way, unless another flow is on screen, attaches nothing inline, and always confirms the recovery. An N flow's initial prompt is sent by a job after the start lands (`sendInitialPrompt`), and the model emits `Started` only once that send returns (`deliverPromptSent`), so no typed key can join the prompt.

## Panes and the health tick

- The TUI holds one attach client per live agent session in `ui.PaneClients` (`home.panes`), keyed by tmux session name; every pane render, scroll, cursor, mouse event, paste, inline-attach key and status scrape goes through `m.panes.For(v)` (`ui.Pane`, for a view `v`). A client is keyed by the view's `TmuxSession`, and its adapter (trust-prompt and pending-prompt patterns) comes from the view's `SessionProgram` (`inst.Pane().SessionProgram()` on the model side), never `Program`. Only an active row (`InstanceView.Active()`: started, not paused, not Loading, Deleting or Recoverable) gets a client, and the terminal pane starts a shell only for an active row (`ensureSessionLocked`, `ui/terminal.go`).
- The attach points (`app/panes.go`) all run on Update: `ensureSlotPanes` at every workspace load; `replacePane` when a start, resume or recover lands in a loaded slot (`core.Started`, `core.SessionLaunched`, `core.Recovered`, a Lua `inst:resume()` included) and after a workspace terminal's auto-restart (`core.SessionLaunched`), since the old client watched the replaced session; `ensurePane` for the repair after the health tick's probe and after `VerifyDead`, both on `core.Alive` (live session, client not attached, no full-screen attach running: `attachingID`), after a returning full-screen attach, and after a reverted kill or pause (`core.Reactivated`).
- Releases go through `prunePanes`, which `Retain`s the active rows' session names and hands every other client to `releaseClientsCmd`, and per open slot detaches the terminal pane's clients of titles the slot has no live row for (`keepsTerminal`: started, not Paused, not Recoverable; `TerminalPane.DetachExcept`). The prune runs on the health tick, on `core.ClientsStale` (a kill or pause completing, `KillResult`/`PauseResult`, or an `OpFailed`) and at every slot drop. `Instance.Kill` and `Pause` end the agent's session and the terminal pane's shell in their jobs (`CloseRelatedSession`, by name), which gives each pump EOF; the prune releases both clients. A resumed, recovered or reverted row gets its shell with the refresh its completion triggers (`InstancesChanged`, `Recovered`).
- A release runs `PausePreview` (detach, session left running) in a Cmd. The attach fd is blocking, so closing a client of a still-live session waits the full `pumpWaitTimeout` (`signalPumpStop`'s deadline can't cut the read short), while a dead session's closes at once; `releaseClientsCmd` closes its clients in parallel. Full-screen attach (`startFullScreenAttachMsg`) still runs `PausePreview` on Update and pays that wait there; making the PTY pollable is a follow-up.
- With the emulator there is no preview tick: panes re-render on `paneDirtyMsg` from the output pump, status transitions ride `paneQuietMsg`, and `ptyDeadMsg` runs `VerifyDead`'s probe. The events (`events.go`, handled in `update`) report to the model by the ID of the row their session name resolves to (`viewBySession`): `paneDirtyMsg` calls `MarkOutput` (by session name: the dirty set the next probe takes, `takeDirty`) and `PaneOutput`, and `paneQuietMsg` calls `PaneQuiet`; both feed hook scans and the Prompting roster query.
- The health tick splits along the pane boundary. The model's half (`core.Model.Tick`, `core/tick.go`) fires from the loop's own timer and favours every client's selected row (the server merges each client's `SetSelected` into the model's selection set, `SetSelection`, and the probe refreshes each one's full diff): one probe job (`probeJob`: liveness, parity, diff stats) over every active instance, whose `HealthResult` `deliverHealth` applies (`applyLiveness` pauses the dead and relaunches a dead workspace terminal under its circuit breaker, `maxWorkspaceTerminalRestartFailures`; an instance a kill, pause or resume moved to Deleting or `Loading` while the probe ran fails `statusEligible` and is skipped, liveness included); it dispatches the gated jobs that are due and stats `accounts.json` (`maybeReloadAccounts`). The loop re-arms it when the probe lands, so ticks never overlap a probe. The TUI's half (the `tickUpdateMetadataMessage` case in `app.go`, on its own `tickUpdateMetadataCmd`) expires toasts, prunes pane clients, runs the inline-attach backstop, the snapshot path's status scan (`snapshotScan` → `snapshotStatusMsg`) and the workbench scan; `core.HealthChecked` re-arms nothing here (it refreshes the workbench's diff tab). Under `LOOM_PANE_RENDERER=snapshot` (and on Windows) a 100ms preview tick and a 500ms health tick with a capture-pane status scan remain.
- The status ladder (`statusDetectedMsg` on the event path, `snapshotStatusMsg` on the snapshot path, `paneDirtyMsg`'s Ready→Running promotion) writes only `m.ladder[id]` (`setLadder`: a status and since when), which `overlay()` shows for an active row whose view has no reported status (`!StatusReported`); its gates read the row as shown. So the model's status of a non-Claude session is its lifecycle status (Running once started), which `state.json` saves; Ready and Prompting from the ladder live only in the TUI. For Claude sessions the hooks and roster report the status, and the ladder is the fallback.
- Inline attach checks the focused pane's own session (`focusedPaneAlive`, `state_inline_attach.go`): the terminal pane's shell is a separate tmux session (`loom_term_<title>`), and tmux's last write to a dying client is the literal "[exited]".

## View modes

- The view modes are `viewMode`s: `m.viewMode` (focus, overview, workbench) is orthogonal to `m.state`: overlays and per-state handlers work unchanged on top of it. `tab` toggles focus and overview; `enter`/`esc` return to focus; `n`/`N` drop to focus first.
- Overview spans the open workspaces only, one card group each, with a global cursor (`home.overviewCursor`, translated to `ui.OverviewCursor` in `overviewData`). `state_default.go` gates script dispatch through `overviewKeyAllowed`, mouse events are dropped, and bell and attention badges clear only on entering focus. Cursor-committing keys go through `focusCursorSlot()` (`loadSlot`, then select), so `enter`, `D`, `r` and `n` reuse focus mode's intents on the right workspace.
- Workbench mode (`app/workbench.go`) reuses the focus split for its left half: `viewWorkbench` force-hides the split's terminal (restored from `wbPrevTerminalHidden` by `cleanupWorkbench`, the single teardown, which `leaveFocusedSlot` calls) and shares its `TerminalPane` with the right panel through `SplitPane.Terminal()`. The markdown follow scan rides the health tick as a Cmd; scan, load and save results apply only in Update handlers, gated on the session title. Workbench mode is never persisted: a restart lands in focus.
- The review tab (`5`/`c`) freezes markdown follow mode on entry and resumes it on exit (`q`) or teardown, and `q` returns to the tab the review was opened from (`home.wbReviewPrevTab`). Persistence runs as Cmds delivering `reviewui.SavedMsg` (non-fatal, shown in the footer). The pane claims only the keys it acts on (`reviewui.claimsIdleKey`), so idle `esc`, session ops, workspace navigation and, in doc mode, the panel-tab digits fall through to the workbench. `home.wbReview` (the concrete `*reviewui.Pane`) and the `Workbench.SetReview` interface field stay in lockstep; `Workbench.SetSession` drops its half on a title change, so every retarget goes through `home.dropReviewPane` (`instanceChanged`'s workbench retarget does). The wheel feeds the pane synthetic cursor keys (`reviewScrollKey`).

## Keys, modal states and mouse

- `handleMenuHighlighting` defers a keypress matching a built-in binding (`keys.KeyForString`, a reverse lookup of the built-in table used only for highlighting) to a later Update through an async replay Cmd, tracked by one flag (`m.keySent`) that assumes the next `KeyPressMsg` is that replay. Full-screen modal states sit on its exclusion list. `View()` places the active overlay only for the states its switch names (`statePrompt`, `stateHelp`, `stateConfirm`, `stateWorkspace`, `stateSettings`, `stateMergePicker`, `stateLaunchOptions`, `stateIssuePicker`).
- `keys/` defines the enumerated `KeyName` values and `keys.GlobalkeyBindings`, which drive the help panel and menu highlighting only; dispatch is the engine's, and `TestKeymapParity` (`app/keymap_parity_test.go`) keeps the table in step with `script/defaults.lua`.
- `ctrl+c` is hard-reserved in the default state, checked before the engine, so no script can trap the user in the TUI.
- Mouse selection works over the rendered text: `SplitPane.HitTest(mouse.X - m.listWidth, mouse.Y - m.topChromeHeight())`. Mouse messages reach Update in every state; selection runs in `stateDefault` and `stateInlineAttach`, and the wheel has no state gate. In interact mode (`app/interact.go`) the left button is deferred: a drag becomes a loom selection copied to the clipboard, a plain click is forwarded into the agent (`forwardClickToFocused`). The clipboard is written by `tea.SetClipboard` (OSC 52, which tunnels over SSH) with a local fallback (`app/clipboard.go`). Interact mode exits on `ctrl+q` or a double `esc` (`home.lastEscAt`); a single `esc` reaches the agent.

## Scripts

`scriptHost` (`app/app_scripts.go`) holds no `*home`. Script nav, scroll, diff and workspace primitives record a `func(*home)` through `deferModelMutation`, drained into `scriptDoneMsg` and applied on the main goroutine in `handleScriptDone`; those that move the selection or the focused slot go through `deferFocusMutation` and apply only in `stateDefault`, since the message can land after an awaited intent opened a flow. Reads (`ctx:selected()`, `ctx:instances()`, `ctx:config_dir()`, …) come from a snapshot `newScriptHost` takes on the Update goroutine when the dispatch or resume begins (views, minus the draft row). A script's lifecycle calls and `ctx:new_instance` are intents the host queues; `handleScriptIntent` turns them into model requests (`scriptInstanceOp`, `scriptCreate`), and each call's coroutine resumes when its `Reply` lands (`scriptReplied`, a `scriptResumeMsg`). The snapshot pins the focused slot and `scriptDoneMsg.slot` carries it back: `handleScriptDone` sends a `ctx:new_instance` as a `Create` in that slot's workspace only if it is still focused, decided before the script's deferred actions run; otherwise the call raises "new_instance: workspace changed while a script ran; not creating <title> here".

## Issue picker and late results

Both issue fetches are `FetchIssue` requests whose `Reply` carries the issue: the picker's pick and the `N` prompt's `#n` expansion record a `pendingIssue` holding an `issuePickedMsg` or `issueExpandedMsg`, which `handleReply` fills and hands to `handleIssuePicked`/`handleIssueExpanded` (`app/state_issue_picker.go`). They can land long after the user acted. Both drop the result, with an explanation, when `msg.repo != m.repoPath()` or `m.state != stateDefault`; `handleIssueExpanded` also drops a result whose draft is no longer `m.draft`, and discards the draft whenever a guard fires (`issueExpandDropped`). `handleIssuePicked` returns on a fetch error before either guard; `handleIssueExpanded` falls back to the literal, unlinked prompt on error, so its guards run before its error branch. The picker asks the poll to cover its repository (`WatchGitHub`) on open and on every `GitHubChanged` while it stays open, and `GitHubChanged` refreshes it.

## Accounts

The account views (the strip, the Accounts screen, the Launch Options row) live in `app/accounts.go`; the registry, auth, sync, usage and reload logic live in the model. `core.AccountsChanged` refreshes the views (`refreshAccountViews`), and the account queries answer from the client's replica of `AccountsView`, which the model republishes after every usage probe round so a sample's age re-renders. Opening Launch Options, opening Settings and every Accounts-screen request call `ReloadAccounts` first. All account UI stays off until an extra account exists, and the strip's row goes through `topChromeHeight`.

- While a credential env var in the daemon's environment overrides every account (`Core.CredentialOverride`), the strip leads with "⚠ $VAR set: all accounts use it" (`credentialOverrideWarning`, through `AccountStrip.SetWarning`) and the Accounts screen shows the same text as a screen-wide notice above its rows while an extra account exists (`accountsScreenNotice`). The model's warning that loom runs as an extra account (`Core.RunningAsAccount`) shows once per client (`showRunningAsAccount`).
- Usage is display-only: a failed probe keeps the last sample, dimmed with its age.
- Launch Options shows a notice under its Account row (`SetAccountNotice`) before the user confirms whenever the account it preselected no longer exists (a resumed session whose account was removed) or a live refresh removes the selected account, naming the account the session will run on.
- The Accounts screen's remove refusal for unshared content points at `loom account remove --force <name>` (the screen has no force of its own). Its in-use count comes from the model (`accountUsers`). Its login (`accountLoginCmd`) stats the account's dir first and refuses a missing one, saying to remove the account and add it again.

## Test harness

- **Isolation.** `TestMain` (`app/app_test.go`) points `LOOM_TMUX_SOCKET` at a private tmux server and kills it afterwards, so tests never touch the developer's default server; `isolateTmux` gives a test a fresh server of its own, and `core.Model.SetExecForTest` swaps the workspace load paths' executor for a recorder.
- **Panes.** Tests attach agent-pane clients through the registry, as production does: `app/testpanes_test.go`'s `attachTestClient` registers one per fixture instance and `wirePanes` points a test `home` at it. Fake attach PTYs are `internal/testpty` pairs, open until the test ends or closes the peer.
- **Fixtures.** The harness lives in `app/testcore_test.go` and `app/testpanes_test.go`. `testWS` builds a `core.Workspace` from its handles plus instances (added through `AddForTest`); `slotOver` builds a slot view over one, and `slotWith` records the workspace of a slot built by hand (`fixtureWS`). `wireCore` (`app/testcore_test.go`) installs the model, served over the pipe by `testLoop`: it serves every slot's workspace in a model that has not booted (`SetWorkspacesForTest`: the tabs in order, then the focused slot's, each opened), gives the home a liveness probe (`aliveProbe` = `fixtureAlive`, the has-session answer of the fixture instance's mock session) unless the test set one, names each slot after its workspace (`id`, `info`) and fills every slot's view store (`syncViews`). A test needing the global and registered workspaces boots the wired model in place (`bootFixture`, safe while the loop is idle; a later `wireCore` drops what it booted) after `registerWorkspaces` has registered them under the test's own `LOOM_GLOBAL_DIR`.
- **Startup.** `startupHome` (or `tryStartupHome`, which returns `startHome`'s error) builds the TUI as `Run` does: a `core.NewForTest` model with the test's executor and registry, booted as the daemon boots it (`Model.Boot`), served by `startTestCore`, then `startHome` with the boot's notices, a startup workspace name ("" for the global one) and an optional pending directory.
- **Reaching the model.** Tests build instances in core and read them through the TUI. A slot holds only an ID and a view, so tests reach the model's workspace through test-only slot accessors (`ws()`, `wsCtx()`, `storage()`, `appConfig()`, `appState()`); a test that changes a handle and then reads through the TUI calls `m.syncWorkspaces()` first, and a settings test opens its overlay over a TUI-owned config (`settingsOverlayForTest`). A test that changes the model's instances outside an Update (`ws.AddForTest`, a status set on the instance) calls `m.syncViews()` before reading. `ws.InstancesForTest()` returns the instances, `testModel(m).IDOfForTest(inst)` an ID and `InstanceForTest` an ID's instance; `testModel` is the loop's `*core.Model`, safe to reach because the loop is idle between calls, and `loopOf(m)` is the loop, found through `testStacks`. `ui` and `script` tests build `core.InstanceView` literals (`core.ViewForTest` copies a fixture instance into one). `reworkspace` rebuilds a slot's workspace with edited handles, and `editRCAuth` edits the default account's remote-control auth (`SetRCAuthForTest`).
- **Jobs and results.** The loop holds every job (`JobsForTest`), so no job's result rides a Cmd. `deliver(t, m, result)` delivers one as the runtime would (`DeliverForTest`, then a `coreWakeMsg` through `Update`, whose drain pings first); `pumpCore` runs a Cmd's tree and every held job until both settle, so a job that follows another (a start's initial-prompt send) lands too. `requestJob` returns the one job a request made outside an Update queued, `requestResults` runs them all, and `tickModel` runs the model's tick (`TickForTest`). Results whose types core keeps unexported come from `core/seams.go`'s `…ForTest` constructors (`FetchedIssueForTest`, …; `UntrackedForTest` strips a request's tracking). `core.CausedForTest(req, result)` wraps a result as this client's own request's, so the `Started`, `Recovered` and `Notice` it produces name `req`; an unwrapped one is another client's, and `applyStarted`/`applyRecovered` only attach its pane.
- **Over the wire.** `startTestCore` serves a test's model in process, over a pipe, with no daemon: `rpc.InProcessForTest` runs it on a `core.StartForTest` loop (which holds every job and never ticks on its own) behind a server, with a synchronous client that pings before every local read (`Sync` included) and after every cast, so a read sees what the model published and a cast has reached the model when it returns. `startTestCore` records each client's stack in `testStacks`; `stackOf(m).stop` stops it. `TestRealLoop_…` (`app/core_wake_test.go`) swaps in the production loop and a raising client (`rpc.InProcess`) to show a job's result reaches the TUI by wakes alone; run it under `-race`. `TestDaemonGone_GoesOffline` (`app/daemon_client_test.go`) dials a server with `rpc.Dial` and closes it under a running TUI; `app/link_test.go` and `app/reconnect_test.go` do the same for the link states and the rejoin onto a second daemon booted from the same disk. `core/rpc`'s own tests use production (non-synchronous) clients. A `time.Time` loses its monotonic reading on the wire, and `reflect.DeepEqual` and `assert.Equal` compare it, so a fixture time compared after the wire is `time.Now().Round(0)` (`app/usage_test.go`).
- `app/views_freshness_test.go` pins every reread site (`syncViews` after a confirmation's task in `runTask`, after the unconfirmed kill, pause, resume and recover paths, and in `attachDoneMsg`); each removal fails a test.
